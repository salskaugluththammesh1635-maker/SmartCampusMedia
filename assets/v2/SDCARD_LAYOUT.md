## 1. 这张卡给谁用

安路 EG4S20BG256「智播校园」多媒体终端。FPGA 通过 SPI 读 SD 卡，日常模式循环播放 6 张校园图 + 背景音乐，科普模式播放 RLE 压缩视频 + 解说音频 + 字幕，应急模式播放双音警报。

### 5.2 视频（`COMMON/VIDEO/`）

| 项 | 值 |
|---|---|
| 源 | `work/fpga_intro_video/fpga_intro_640x480_60fps.mp4`（5,535,871 B，H.264） |
| 编码 | 自定义 `.RLE`，magic `"SCMR"`，RGB565（16 bpp）+ 8 bit 游程 |
| 分辨率 | 640×480 |
| 源帧率 → 目标帧率 | 60 fps → **5 fps**（每 12 帧取 1 帧） |
| 帧数 / 时长 | 631 帧 / 126.200 s |
| 文件大小 | **82,362,927 B**（78.55 MiB） |
| 单帧字节 | 均值 130,527 B / 最小 3,612 B / 最大 203,484 B / p95 194,244 B |
| 压缩比 | 0.2124（相对未压缩 RGB565） |
| 所需带宽 | 均值 **0.653 MB/s**（占 SD 1.25 MB/s 的 52.2%），最坏 1.017 MB/s（81.4%） |

**帧文件命名规范**：

- 默认（本卡采用）：单文件多帧。所有帧顺序写进一个 `SCI.RLE`，**每帧自带 12 字节头**（`magic(4) + width(2) + height(2) + run_count(4)`，全部小端），第 N 帧的偏移 = 前 N-1 帧 `run_count` 累加。依据 `PLAN.md` §7.6 / `ARCH.md` §6.7。
- 备选（未采用）：每帧独立文件，命名 `F00000.RLE` ~ `F00629.RLE`（`F` + 5 位十进制帧号 + `.RLE`，主名 6 字符，满足 8.3）。好处是单帧损坏不影响后续；坏处是 FAT 目录项膨胀、随机定位仍要查 FAT 链。
- `SCI.IDX` 是**工具用**索引表（ASCII 定长：帧号 5 位、偏移 11 位、字节数 10 位、游程数 6 位）。RTL **不读**索引文件——`rle_decoder` 自己用 `run_count` 累加定位。

限帧率的原因（必须原样进答辩材料）：SD 卡走 SPI 12.5 MHz，实用带宽约 **1.25 MB/s**；而 640×480 未压缩 RGB565 单帧 614,400 B，30 fps 需 18.43 MB/s —— **差 14.7 倍**。素材是 PPT 风格动画、大片纯色，游程极长，RLE 压缩比 0.206 把帧率从 1 fps 抬到 5 fps。**帧率固定 5 fps**（`dmz_eg4s20_hdmi_top.v:521` 把 `.play_fps` 硬接常量 `8'd5`）。持续欠载时的真实行为是**停在上一个已显示帧、不插黑、不撕裂**，**不自动降帧** —— 初版文档曾写「自动降帧 / 2 fps 是承诺下限」，那是**设计目标未落地**（RTL 从未实现），已作废；2 fps 只是带宽核算的假设工况。终口径见 `docs/plan_v2/KEY9_RULING.md` 同级的帧率说明与 `DELIVERY_GUIDE.md` §3.6。

### 5.3 字幕与滚动标语（`COMMON/SRT/` 与 `COMMON/TICKER.TXT`）

| 文件 | 内容 | 格式 | 字节 |
|---|---|---|---|
| `NARR.SRT` | 科普解说字幕 18 条，时间轴 00:00:00,800 → 00:02:04,906 | UTF-8 + LF | 2,177 B |
| `NARR.IDX` | 同上的 ASCII 时间轴索引 | 定长 ASCII | 498 B |
| `TICKER.TXT` | 日常模式滚动标语，正好 64 字符 | 纯 ASCII | 64 B |

滚动标语原文（48 字符 + 右补空格到 64）：

```
SMART CAMPUS MEDIA - WELCOME - DAILY MODE ONLINE
```

**为什么必须正好 64 字符**：`osd_caption.v` 用 `ticker_col = (像素列 + 滚动偏移) & 6'b111111` 取模，64 = 2⁶ 是位掩码，取模零逻辑成本。字符集受 `osd_font8x16` 字模 ROM 限制：只有 `空格 - . / 0-9 : A-Z`。

> ⚠️ **中文字幕当前无法直接上屏**：`osd_font8x16.v` 是纯 ASCII 8×16 字模，而 `NARR.SRT` 含 **253 个不同字符**（含汉字）。t3 产出的 `cjk16_font.v` 只有 95 个字形，**不足以覆盖字幕全集**。按 `PLAN.md` §13 R-09，字幕是**编译期转 ROM 表**、不运行时解析；因此本卡提供 UTF-8 原文作为 ROM 生成源，实际是否上屏取决于后续字库扩容。这是**已知降级项**，不是遗漏。

## 6. 为什么没有 `scaled/NN/` 预生成目录

任务书原文提供了两个分支：「预生成缩放图」或「依赖 `img_scaler.v` 实时缩放」。**两个分支都不成立**，已在 `PLAN.md` §5.2 定稿：

| 方案 | 判定 | 理由 |
|---|---|---|
| A. 实时窗口裁剪 | ✅ **采用** | `image_window_mask.v`（已存在，41 LUT）+ `ratio_map`（+30 LUT）。窗口内原始像素 1:1 显示、无插值损失、切换延迟 1 帧、**素材工作量零** |
| B. 预生成五套素材 | ❌ 否决 | 6 图 × 5 档 = 30 个文件，`t4` 素材工作量 ×5；且窗口内是缩放后的图，有插值损失 |

五档屏占比（`ratio_sel` 0→4）的窗口参数全部是 640×480 的整数分数，由 RTL 组合译码得出，**不需要任何素材**：

| `ratio_sel` | 占比 | `win_w`×`win_h` | 偏移 | 面积 |
|---|---|---|---|---|
| `3'd0` | 1/2 | 320×240 | (160,120) | 25.0% |
| `3'd1` | 5/8 | 400×300 | (120,90) | 39.1% |
| `3'd2` | 3/4 | 480×360 | (80,60) | 56.3% |
| `3'd3` | 7/8 | 560×420 | (40,30) | 76.6% |
| `3'd4` | 1 | 640×480 | (0,0) | 100% |

## 8. 烧录步骤

1. 把 SD 卡格式化为 **FAT32**（Windows 资源管理器：右键 → 格式化 → 文件系统选 FAT32；32 GB 以上卡 Windows 会隐藏 FAT32 选项，可用 `diskpart` 或 Rufus）。
2. 把 `assets/v2/sdcard/BURN640/` **里面的内容**（不是这个目录本身）拷到卡根。
3. 确认卡根直接能看到 `IMG001.BMP`、`BGM.WAV`、`SCI.RLE` 等 **17 个文件**，且**没有任何子目录**（若看到 `AUDIO/` `VIDEO/` `SRT/`，说明拷的是旧版子目录布局，`fat32_reader` 读不到里面的文件）。
4. 用 `python scripts/gen_assets_v2_sdcard.py --verify` 核对：自检项 13~18 会检查顶层 17 个文件 / 零子目录 / 8.3 名合法性 / FAT 目录项形态 / SUBDIR 列全为 `.`。
5. 上板：先上电 SD 初始化，再看日常模式是否循环出图。

> **不要**把 `assets/campus_media/preview/smart_campus_showcase.mp4` 拷进卡里当视频源：它是 H.264，FPGA 无解码能力，只能作答辩演示素材（`PLAN.md` §7.7 素材红线）。

## 11. 跨任务阻塞点（需 RTL 侧配合，不属于素材范围）

以下三条是素材包**已经按架构准备好、但当前 RTL 还读不到**的地方，如实上报。

> **读法说明（重要）**：§11.1 已**由素材侧定案**（卡根扁平，不再等 RTL 决策），§11.2 是纯 RTL 侧的前置条件，两者是**先后关系而非二选一**。
> 早期版本把「扁平化放卡根」写成「零 RTL 改动」备选，这是错的：扁平化绕得过「不递归子目录」，绕不过「文件名逐字节硬编码」——`SCI.RLE` 的首字节 `'S'=0x53` 撞上 `exp_byte=8'h49('I')` 立刻不符，照样读不到。
> 所以正确表述是：**§11.1 已按扁平落盘（素材侧完成），§11.2 是 RTL 侧必须做的前置条件**；两者都解决之前，三个模式的媒体功能无法上板。

### 11.1 【已定：扁平】`fat32_reader.v` 只遍历根目录

`fat32_reader.v` L142-144 的目录游标只有 `dir_cluster` / `dir_sec_idx` / `dir_fat_cnt` 三个寄存器，**没有子目录栈、没有递归**；`ST_DIR` 状态只沿 `dir_cluster <= root_cluster` 的根目录簇链推进。L551-552 的注释逐字为「属性字节: 排除 LFN(0x0F) / 卷标(0x08) / 目录(0x10)」，判据 `(attr & 0x18) == 0` **显式排除目录项**。

**结论：卡根必须扁平。** 这条已经定下来，不再是备选：

- **已采用方案**：媒体全部放卡根，用 8.3 可容纳的扁平名（`SCI.RLE` `BGM.WAV` `BGM2.WAV` `BGM3.WAV` `ALARM.WAV` `NARR.WAV` `NARR.SRT` `NARR.IDX` `SCI.IDX` `TICKER.TXT`，全部已在 §3 验证合法）。卡根 17 个文件、零子目录，**当前 `BURN640/` 就是按这个装配的**（`stage_card()` 默认 `layout=flat`，自检项 13~18 从磁盘实测保证）。FAT32 根目录无项数上限（与 FAT16 的 512 项固定根区不同），17 项完全无压力。
- **未采用方案（仅留档对照）**：给 `fat32_reader` 加一级子目录进入（解析目录项 attr `0x10` 位 → 取 `first_cluster` → 从该簇继续遍历），即 `ARCH.md` §6.7 的原始 `VIDEO/` `AUDIO/` `SRT/` 布局。**不采用的理由**：要动 FSM 的 DIR 阶段、加一组子目录游标寄存器，而扁平布局的代价是 0 —— 同样能解决问题时不应引入额外 RTL 复杂度与回归风险。脚本仍保留 `--subdir` 开关可装配这种布局，**仅供对照，不要烧进卡**。

> **注意 §11.2 仍然是前置条件**：即便卡根已经扁平，`IMGnnn.BMP` 以外的 10 个文件名在读完 §11.2 之前依然匹配不上。扁平只解决了「能不能看到这些目录项」，没有解决「看到之后认不认得」。

### 11.2 短名匹配是硬编码 `IMGnnn.BMP`（**前置条件，不可绕过**）

`fat32_reader.v` L590-614（always 块④）把期望短名逐字节写死：

```verilog
5'd0 : exp_byte = 8'h49;  // 'I'
5'd1 : exp_byte = 8'h4D;  // 'M'
5'd2 : exp_byte = 8'h47;  // 'G'
5'd3 : exp_byte = 8'h30 + {4'd0, idx_h};  // 百位
5'd4 : exp_byte = 8'h30 + {4'd0, idx_t};  // 十位
5'd5 : exp_byte = 8'h30 + {4'd0, idx_o};  // 个位
5'd6, 5'd7 : exp_byte = 8'h20;            // 空格
5'd8 : exp_byte = 8'h42;  // 'B'
5'd9 : exp_byte = 8'h4D;  // 'M'
5'd10: exp_byte = 8'h50;  // 'P'
```

**除 `IMGnnn.BMP` 外任何文件名都匹配不上。** 这不是「布局问题」而是「匹配逻辑缺失」：`SCI.RLE` / `BGM.WAV` / `NARR.WAV` / `NARR.SRT` / `TICKER.TXT` 一个都读不到。

修法建议（属 rtl-engineer 范围）：把 `exp_byte` 的译码参数化——目标名从端口输入（或 11 字节小 ROM），逐字节比较，`IMGnnn.BMP` 退化为其中一种特例。改完后 `img_loader` 的 `img_index` 逻辑可保持不动（仍用特例参数）。

**这是 `ARCH.md` §6.5/§6.6/§6.7 新增的 RLE / WAV / SRT 三路读取的共同前置条件。**

### 11.3 非 640×480 的 BMP 现有管线会缩小显示，不会放大

`img_scaler.v` L24-38 明确「**只做缩小，不做放大**；源图小于 640×480 时按 1:1 原尺寸居中」。所以 **`RES320`~`RES576` 这四档 BMP 对当前 RTL 不可用**：放进去只会显示成屏幕中央一小块，不是放大的画面。

正确用法（`PLAN.md` §4.1 的 N1 口径）：**SD 卡只放一套 640×480 源图**，五档分辨率由 `video_geom_map.v` 在**输出侧**用最近邻 DDA 放大实现，即「内部渲染分辨率」而非「素材分辨率」。所以：

- **实际烧录用 `RES640/`（= `BURN640/`）**。
- `RES320`~`RES576` 四档是**素材完整性与架构备选**（万一将来改成「直接喂小图」的方案），当前 N1 架构不消费它们。
