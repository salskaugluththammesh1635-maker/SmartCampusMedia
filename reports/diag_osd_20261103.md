# OSD 字幕下方黑条：定位与移除方案（诊断报告）

- 日期：2026-11-03
- 范围：只诊断，**不改任何 .v、不上板**
- 对应现象：用户报 ⑥「OSD 字幕下方的黑条碍事，要求移除」
- 工程：`D:\FPGA_Compelate\SmartCampusMedia`，HEAD = `7163c66`
- 结论一句话：黑条是 **候选 B（`video_overlay.v` 底部信息条的深色底，y=464..479，全宽 640，`24'h10_18_20`）**，不是候选 A（`osd_caption.v` 的衬底压暗带）。推荐**方案 1：把信息条从「全宽 16 行」收窄为「12 格区域 96×8，仅方块行，格内保留局部暗底」**，信息零丢失、黑面积缩减 13.3 倍、只改 1 个 RTL 文件 + 1 个 TB。

## 0. 屏幕坐标系（先固定标尺）

`rtl/video/video_timing_gen.v:88-127`：`H_ACTIVE=11'd640`、`V_ACTIVE=10'd480`，VESA 640×480@60 负极性。
→ `active_x ∈ [0,639]`、`active_y ∈ [0,479]`，左上为原点，**y 增大 = 向下**。

这条标尺很重要：`video_overlay.v:213` 的 `active_y >= 10'd464` **没有写上界**，它的物理上界就是 `479`，即**屏幕最底部 16 行**。

### 1.3 亮度对比：为什么用户把它读成「黑」

- B 的 `0x10_18_20` 相对白 0xFF 只有 **16/255 ≈ 6.3%**，相对常见照片暗部（0x20~0x40）几乎同亮度 → 肉眼即「黑」。
- 字幕白字 `0xF0F0F0` 的字形底边正好落在 y=463，**下一行 464 就是 `0x101820`**。对比度 240:16 ≈ 15:1，视觉边界极硬。
- 若画面偏暗，A 的「×1/4」几乎看不出来（0x10→0x04），此时 **A 与 B 连成一片，形成 32 行连续黑带**，用户会把它整体归到「字幕下方」。
- 应急模式下更明显：`emerg_page.v` 页背景 `C_BG = 24'h0B_10_20`，与 `0x10_18_20` 几乎同色 → 信息条在应急页上完全「隐形」，只剩一条比背景略亮的带。

## 2. 候选判定：是 B，不是 A

### 2.1 判定结论

| 判据 | 候选 A | 候选 B |
|---|---|---|
| 是否在「字幕**下方**」 | ✗ 它就是字幕**所在**的带（文字画在 448..463 内） | ✓ 文字底边 463 之下紧接 464..479 |
| 视觉上是否「一条黑」 | ✗ 是半透明压暗，暗画面上不可见 | ✓ 固定近黑、全宽、16 行，边界锐利 |
| 是否常驻、用户无法消除 | ticker 带可按 Key5 关 | ✓ **硬接 1'b1，永远在** |
| 是否符合「碍事」的主观描述 | 压暗是设计者刻意保留画面层次的手法（`progress.md:2268`） | ✓ 一条纯色带，无信息价值（信息只占其中 96×8 的小方块） |
| 面积占比 | 640×16 = 10240 px（3.3%） | 640×16 = 10240 px（3.3%），**其中只有 96×8=768 px（7.5%）承载信息** |

**判定：用户指的是候选 B。** 决定性理由是「**下方**」+「**常驻不可关**」两条同时只对 B 成立。A 是字幕自身的衬底，去掉它等于去掉白字的可读性保障（见 §4）。

### 2.2 一个容易误判的点（必须写清）

`px_info` 的 `active_y >= 464` **没有上界**，看起来像「会一直延伸到屏幕外」。实际上 `active_y` 由 `video_timing_gen.v` 限定在 `[0,479]`，所以物理范围就是 **464..479**，正好 16 行，不多不少。这一点在改代码时不要误加 `<= 479` 之外的边界（加了也无害，但属冗余）。

### 2.3 另一条旁证：信息条在缩放档位下「本来就是黑」

`ratio_map.v` 五档窗口：

| 档 | 窗口 | 窗口 y 范围 | 窗口底边 | 字幕带 448..463 | 信息条 464..479 |
|---|---|---|---|---|---|
| 0 | 320×240 @(160,120) | 120..359 | 359 | 窗外=纯黑 | 窗外=纯黑 |
| 1 | 400×300 @(120,90) | 90..389 | 389 | 窗外=纯黑 | 窗外=纯黑 |
| 2 | 480×360 @(80,60) | 60..419 | 419 | 窗外=纯黑 | 窗外=纯黑 |
| 3 | 560×420 @(40,30) | 30..449 | 449 | 仅 448/449 两行在窗内，450..463 共 14 行纯黑 | 窗外=纯黑 |
| 4 | 640×480 @(0,0) | 0..479 | 479 | **窗内** | **窗内** |

→ 档 0..3 时 y≥450 整块本来就是纯黑（`image_window_mask` 屏蔽 + `video_content_mux` 补 0），信息条的 `0x101820` 只让那 16 行从「纯黑」变成「近黑」，**视觉差异几乎为零**（`0x101820` 亮度 6.3%，在黑色旁边几乎看不出边界）。只有档 4（全屏）时，信息条才在画面上切出一条可见的带。这也解释了为什么用户觉得「黑条碍事」——他多半在 100% 全屏档看日常/科普画面。

## 3. 移除方案对比（三个方案 + 一个改进版）

### 方案 1（推荐）：只保留 12 格区域，去掉全宽深色底

**做法**：把 `px_info` 从「整条 16 行全宽」收窄为「方块行 × 12 格区域」。**只改 `px_info` 一行，`rgb_mixed` 合成链完全不动。**

```verilog
// 现状（video_overlay.v:213）
wire px_info = info_en && (active_y >= 10'd464);

// 方案 1（示意，未实施）—— 单行替换
wire px_info = info_en && (active_y >= 10'd468) && (active_y <= 10'd475) &&
               (active_x >= 11'd8)    && (active_x <= 11'd103);
```

**为什么一行就够：现有合成链天然给出正确结果。**

| 像素位置 | 命中条件 | 输出 | 是否正确 |
|---|---|---|---|
| 格内实心、位=1 | `px_box_on`（`:241`，优先级高于 `px_info`） | `0x40E0D0` 青 | ✅ 1 位 |
| 格内实心、位=0 | 落到 `px_info` | `0x10_18_20` 暗底 | ✅ 0 位 |
| 格内间隔（`bd_x[2:0]`=6/7） | 落到 `px_info` | `0x10_18_20` | ✅ 与现状一致（V08 已断言 x=14/15 为此色） |
| 12 格之外（x<8、x>103、y 464..467、y 476..479） | 不命中任何 OSD 层 | 图像色 | ✅ 黑带消失 |

`px_box_win`（`:215-216`）会变成 `px_info` 的冗余子集（`x>=8`、`y 468..475` 已含在 `px_info` 里），**可原样保留**——多几个与门无功能影响，只在综合时被优化掉；若追求代码干净，可简化为 `wire px_box_win = px_info;`，但那属可选清理，不影响行为。

**⚠️ 必须理解的陷阱：12 格是双态编码，0 位靠底条颜色区分。**
`box_lit`（`:224-239`）只输出「亮/不亮」两种状态；不亮的格**不是画黑色，而是露出 `px_info` 的底条色**。如果简单地把 `px_info` 整个删掉（`info_en=1'b0` 或删 wire），不亮的格就变成「图像本身」——图像可能比青色亮格 `0x40E0D0` 更亮（例如白墙照片），于是「0 位」和「1 位」无法区分，**信息条彻底失效**。这正是「只去掉深色背景」必须理解为「去掉 12 格之外的背景、格内保留局部暗底」的原因，也是方案 1 与方案 2（整体关闭）的本质区别。

**效果**：
- 黑/近黑面积：`640×16 = 10240 px` → `96×8 = 768 px`，**缩减 13.3 倍**（占屏 3.3% → 0.25%）。
- 视觉上从「一条通栏黑带」变成「屏幕最左下角一小排青色方块」，且这排方块正是信息本身。
- 信息零丢失：图号 5 位 / 模式 2 位 / 亮度 3 位 / 倍率 2 位全部保留。
- 与字幕的相对关系：方块行 468..475 距字幕底边 463 有 4 行间隙（464..467），视觉上不再「贴着字幕」。

**代价 / 风险**：
- 未点亮格的暗底 `0x101820` 在纯黑画面上（档 0..3）与背景同色 → 0 位仍不可见。但这是**既有问题**，方案 1 不加重（现状同样如此）。
- 若未来想彻底解决「0 位在纯黑画面上不可见」，需给未点亮格换一个非黑底（如 `0x30_30_30`）——不在本次范围。

### 方案 2：整体关闭（`info_en = 1'b0`）

**做法**：`dmz_eg4s20_hdmi_top.v:165` 改一行。

**效果**：黑条完全消失，屏幕底部 32 行干净（只剩字幕带的压暗）。

**信息去哪了？——不会丢，转由参数面板承载。**
`osd_panel.v` + `osd_param_text.v` 已经显示：
- 行 2：`MODE:xxxxxxx  IMG:nn/nn`（模式名 col 5..11、图号 col 17/18、图库张数 col 20/21）
- 行 1：`B:n V:n R:n P:n`（亮度/音量/分辨率/倍率）+ 条件列组 `I:n`（反色）、`Xn`（倍率）

`osd_autopop.v:99-105` 监视 7 个参数（`bright_lvl`/`vol_lvl`/`res_sel`/`ratio_sel`/`invert_en`/`auto_sw_sel`/`info_mode`），**任一变化即弹面板 2.5 秒**（`HOLD_MS=2500`）。所以按 Key6/7/8/9 调参时，参数面板会立刻给出可读文字，信息条不是唯一载体。

**E4 加分项角度**：赛规 E4 原文是「利用板载开关或按键调节显示参数（如亮度、对比度等），并**尝试在画面上呈现参数变化信息**」（`reports/plan_v2/SPEC_CONSTRAINTS.md:108`）。「参数**变化**时呈现」比「常驻一条位图」更贴题；且面板是文字、可读性远高于方块位图。**方案 2 不削弱 E4，反而更贴题。**

**代价**：
- 科普模式与日常模式的「唯一区别」不再是信息条第 5~6 格。但**科普标记 `px_sci` 是独立图层**（`video_overlay.v:171-173`，`info_mode==2'b01` 时画左上角青色块，**不依赖 `info_en`**），所以科普模式仍有明确视觉标识。✓
- 常驻的「当前图号」消失。用户只能按键才看到 `IMG:nn/nn`。若产品定位需要「随时知道第几张」，这是退步。
- 失去「位图信息条」这一实现亮点（答辩/文档里已写进 `docs/keymap_2026-10-26.md:40`、`docs/board_verification_2026-10-27.md:172`）。

### 方案 2b（改进版）：信息条改为「参数变化时临时显示」

**做法**：`info_en` 不再硬接 `1'b1`，改接 `osd_autopop` 的面板使能（需从 `osd_panel` 引出 `panel_on`，或由 `osd_pop_req` 展宽 2.5 s）。

**效果**：平时无黑条；按 Key6/7/9 时，信息条与参数面板**同时出现 2.5 秒**，一起消失。信息零丢失、视觉零常驻。

**代价**：改动面比方案 1/2 大——要动 `osd_panel.v` 端口（+1 输出 `panel_on`）或新增一个展宽计数器（约 30 位，`HOLD_MS` 同款），并改顶层 1 行。且面板弹出时**已经盖住右上角**，信息条在左下角，两者同时出现会让画面「到处是 OSD」，未必比方案 1 好看。

### 方案 3：把信息条移到别处

**结论：屏幕没有空位，不可行。** 逐区排查：

| 区域 | 占用者 | 能否放信息条 |
|---|---|---|
| 左上 y≤7 通栏 + x≤23 & y≤31 | 科普标记 `px_sci` | ✗ |
| 右上 x446..631 / y8..65 | 参数面板（弹 2.5 s） | ✗ 会被面板盖住 |
| 右中 x616..631 / y380-h..380 | 电平条 `px_level`（`level_en=1'b0`，当前关闭但端口保留） | ✗ 太窄（16 px） |
| 中下 x64..575 / y376..439 | 音频波形 `px_wave`（Key10 开） | ✗ |
| 左下 x8..103 / y468..475 | **信息条自己** | — |
| 底部 y448..463 | 滚动字幕（全宽） | ✗ |
| 中央画面 | 图像主体 | ✗ 遮挡内容 |

`osd_panel.v:25-30` 的设计注释已经写明这个结论：「左上被科普标记占……右下角有 12 格方块信息条（y>=464），右中有电平条……**右上角是唯一干净的区域**」——而右上角给了参数面板。

→ 方案 3 只能退化为「把信息条并入参数面板的某一行」（用字库而非方块位图），这等于方案 2 的信息承载方式，但要多改 `osd_param_text.v` 的排版（面板只有 3 行 22 列，已排满），成本高于收益。

## 4. 候选 A（衬底压暗带）是否也该去掉？

### 4.1 结论：**不该去掉，建议保留原样。**

理由链：

1. **它不是用户指的黑条**（§2）。用户说「字幕**下方**」，A 是字幕**所在**的带。
2. **它是白字可读性的唯一保障**。`osd_caption.v:274` 注释：「衬底带：字幕所在区域整体压暗，保证白字在任何画面内容上都可读」。去掉后，`0xF0F0F0` 白字落在亮画面（白墙、雪景、白底 PPT 截图）上对比度接近 1:1，**完全不可读**。
3. **设计者已经权衡过「压暗 vs 填黑」**：`docs/progress.md:2268`「填黑会在画面上糊出一条硬边黑条，观感很脏；压到 1/4 亮度则保留画面明暗层次，像半透明底纹，白字同样可读」。这条记录说明「压暗」是刻意选的折中，不是疏忽。
4. **科普模式最依赖它**（见 §5）：科普字幕是 16×16 中文点阵，笔画比英文细，在亮画面上最先糊掉。

### 4.2 若要「更轻」，三个替代方案的评估

| 替代方案 | 做法 | 可读性 | 成本 / 风险 | 评价 |
|---|---|---|---|---|
| **只压暗字后区域** | 按字符单元（16 px 宽，`ticker_col = ticker_src[9:4]`）压暗，空格不压 | 有字的格仍可读 | 需 `osd_caption` 多输出一个「本像素在字符格内」信号，且空格处会露出亮图像 → 视觉变成**马赛克状碎片底纹**，比整条更脏 | ❌ 不推荐 |
| **加描边（stroke）** | 白字外加 1 px 黑边 | 亮/暗画面都可读，且不需底色 | 16×16 字形在 640×480 上，1 px 描边会让笔画变粗、中文小字糊成一团；实现需 3×3 邻域 9 次 BRAM 读或额外描边 ROM，LUT/BRAM 成本高（`brightness_apply.v:73-74` 已提示 DSP 余量仅 10/29，虽不占 DSP 但 BRAM 也不宽裕） | ⚠️ 成本高、效果差 |
| **降低压暗比例**（1/4 → 1/2） | `{1'b0, r_inv[7:1], ...}` | 画面更亮更自然，但白字对比度下降：亮画面 0xFF → 0x7F，白字 0xF0 对比仅 ≈2:1，**边缘可读** | 改 1 行，零成本 | ⚠️ 可选微调，但不解决「用户觉得有带」的问题，只是让带更淡 |

**建议**：A 保持 `>>2`（1/4）不动。若后续上板觉得字幕带仍显眼，再单独评估「1/4 → 1/2」，那是一个 1 行改动、可独立回归的微调，**不要和本次黑条移除捆绑**（否则两个视觉变化叠在一起，上板无法归因）。

### 4.3 一个必须写进实施说明的边界

`band_on` 里 title/state 两带带 `&& !narr_en` 门控（`:283-285`），**ticker 带没有**。也就是说：
- 日常/应急模式：三条带都可能出现（title 32..127 ∪ 576..623、state 32..103、ticker 全宽）。
- 科普模式（`narr_en=1`）：只剩 ticker 全宽带。

这个不对称是**有意设计**（`tb_video_overlay.v:619-623` 的注释明确记录了这个「t13 语义变更」），不是 bug。

## 5. 科普模式（`narr_en=1`）是否会被破坏？

**结论：不会。方案 1 / 2 / 2b 都只碰 `video_overlay.v` 的 `px_info` 或其顶层接法，完全不触及 `osd_caption.v` 的 `band_on`。**

逐条确认：

| 检查项 | 现状 | 改动后 | 结论 |
|---|---|---|---|
| `band_on` 表达式 | `(ticker_band && caption_en) \|\| (title_band && band_title_x && !narr_en) \|\| (state_band && band_state_x && !narr_en)`（`:283-285`） | **不变** | ✅ |
| 科普时 `band_on` | `narr_en=1` → 只剩 `ticker_band && caption_en` | 不变 | ✅ |
| 科普字幕的衬底 | ticker 带全宽压暗（`px_cap_band`，`:297`） | 不变 | ✅ 中文 16×16 笔画仍可读 |
| 科普字幕的字形通路 | `narr_active` → 2 拍（`narr_subline` → `cjk16_font`） | 不变 | ✅ |
| 科普字幕的 x 取样 | `t_bit = narr_active ? active_x[3:0] : ticker_src[3:0]`（`:249`） | 不变 | ✅ |
| 科普标记 `px_sci` | `(info_mode==2'b01) && (y<=7 \|\| (x<=23 && y<=31))`（`:171-173`），**不依赖 `info_en`** | 不变 | ✅ 科普仍有左上角青色标识 |
| 字幕带与信息条是否重叠 | 448..463 vs 464..479，**0 行重叠** | 方案 1 后信息条缩到 468..475，**间隙扩大到 4 行**（464..467） | ✅ 更不会互相干扰 |
| 合成优先级 | `px_info`（`:313`）**高于** `px_caption`（`:314`） | 不变 | ✅ 两者 y 范围不重叠（448..463 vs 468..475），优先级不产生实际作用 |

**⚠️ 唯一必须守住的边界（比「理论风险」更严重）**：因为 `px_info` 的优先级**高于**字幕层，如果把 `px_info` 的 y 下界误改成 `< 464`（例如写成 `active_y >= 460`），信息条的 `0x10_18_20` 会**直接覆盖掉字幕笔画**，字幕整条变成暗底——不是「多一圈暗底」，而是**字幕消失**。`video_overlay.v:305-306` 的注释也点明了这一点：「字幕排在底条之后……这条顺序只在未来改动坐标时才起作用」。所以方案 1 的 `active_y >= 10'd468` **不是随手取的值，而是必须 ≥ 464 的安全边界**（取 468 是为了留 4 行视觉间隙）。实施时必须连同这条注释一起复核。

**另一个必须注意的点**：`caption_en` 在顶层接的是 `ticker_en_eff = emerg ? 1'b1 : ticker_en`（`key_router.v:308`），而 `ticker_en` 复位为 1（`:93`）。所以科普模式下字幕默认是开的，用户按 Key5 可关（关了 `band_on` 只剩 0，字幕和衬底一起消失）。这与本次改动无关，但说明「科普字幕可读性」在默认状态下是有保障的。

## 6. 建议方案与改动面

### 6.1 建议

**采用方案 1（收窄 + 格内局部暗底）**，理由：

1. **视觉目标达成**：黑面积从 10240 px 降到 768 px（-92.5%），从「通栏黑带」变成「一小排信息方块」。
2. **信息零丢失**：图号/模式/亮度/倍率 4 类信息全部原位保留，E4 的「信息叠加」加分项不受影响，答辩时「12 格位图」这个实现亮点还在。
3. **科普模式零影响**：不碰 `osd_caption.v`，字幕可读性链路完全不动。
4. **改动面最小可控**：1 个 RTL 文件 + 1 个 TB，逻辑纯组合，无新增寄存器。
5. **可回退**：与方案 2（`info_en=1'b0`）不冲突——若上板后仍嫌那排方块碍事，再把顶层改 1 行即可完全关掉，两者是叠加关系而非互斥。

**备选**：若产品更看重「底部绝对干净」，选方案 2（1 行改动、TB 零影响、E4 更贴题），代价是图号不再常驻。

### 6.3 是否需重跑综合？

**需要。** 流程（`scripts/sync_src.ps1` 是唯一真源同步入口）：

1. 改 `rtl/video/video_overlay.v`
2. `powershell -ExecutionPolicy Bypass -File scripts\sync_src.ps1`
   （把 `rtl\video\video_overlay.v` → `project\hdmi\video_overlay.v`，见脚本 `:66`；同步后自动跑 `lint_verilog.py`）
3. 仿真回归：`tb_video_overlay`（V07/V08/V09/V10/V13）+ `tb_osd_caption` + `tb_osd_caption_cjk`（后两个应**零改动**通过，因为它们只测 `osd_caption`）
4. TD 重综合 → 布局布线 → bitgen
5. 独立审查（不看实现者自评）

**资源与时序影响评估**：
- 逻辑：`px_info` 从 1 个比较器（`>=464`）变成 4 个比较器 + 3 个与门，**净增约 8~12 LE**（`active_x` 的 2 个比较器是 11 位、`active_y` 的 2 个是 10 位；EG4S20 单个 LUT4 可吞掉部分比较位）。`rgb_mixed` 合成链**零改动**，无新增三目级。EG4S20 余量充足（`brightness_apply.v:73-74` 提到 DSP 余量 10/29，LE 未告急）。
- 时序：全部为**纯组合、无新增寄存器**，且位于 `video_overlay` 的既有组合路径上（`active_x/active_y → rgb_out`），路径长度几乎不变。参考 `brightness_apply.v:33-44` 的同类判断（纯组合不打拍，hold WNS +0.003 ns 的既有裕量不会被这条改动吃掉）。
- 结论：**需重跑综合出位流，但预期时序/资源影响可忽略**；仍须以 TD 报告为准，不得凭本报告结论跳过综合验证。
