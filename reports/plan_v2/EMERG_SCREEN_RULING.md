## §3 Q2 结论：`emerg_page.v` 触及「不得带额外处理器」边界吗？

### 3.1 不触及，四条理由

**理由一（条文文义）**：1.3 那条禁令的主语是「**外围电路或成品模块**」——「允许根据作品需要搭配外围电路或成品模块，但不得带有额外处理器」。`emerg_page.v` 不是外围电路，不是成品模块，它是**FPGA 内部的一个 .v 源文件**。该条款对「FPGA 内部源码」没有、也不可能有约束力——否则整个工程的所有 .v 都违规。

**理由二（条文目的）**：这条禁令要禁的是「把本该 FPGA 做的事挪到外部芯片去算」。`emerg_page.v` 恰恰是**不挪出去**的正面实现。它与 1.3 前置句「所有算法、控制逻辑及数据处理流程应在 FPGA 中自主编程实现」是**同向**的，不是需要豁免的对象。

**理由三（同构先例，已实测）**：本项目已有三个同构模块，全部纯组合、全部零时钟：

| 模块 | 实测 | 时序检查结果 |
|---|---|---|
| `rtl/video/science_page.v`（13,601 B / **274 行**） | `always @*` 仅 `L97`、`L246` 两处；`L246-267` 全是范围比较出颜色 | 全文 `clk` / `rst_n` 命中 **0 处**；无 `posedge`/`negedge` |
| `rtl/video/image_window_mask.v`（2,460 B / 43 行） | 纯 `pixel_valid` 门控 | 无 `always @(posedge)`；`clk`/`rst_n` 命中 **0 处** |
| `rtl/storage/fade_mixer.v`（1,781 B，`L14` module） | 纯 `wire` + `assign`（`L21-29`），无任何 `always` | 无时钟端口 |

`science_page.v` 的写法是「每个图形元素 = 一组 `active_x`/`active_y` 范围比较，全部命中后按优先级覆盖 `rgb_out`」（`L246-267` 的 `if (header) rgb_out=...; if (box_border||arrow) rgb_out=...;` 级联）。**`emerg_page.v` 照此写，与上述三者完全同构。**

**理由四（归谬）**：若「FPGA 内实时算像素颜色」也算处理器，则本项目 `science_page`（1052 le）、`video_overlay`（630 le）、`osd_panel`（247 le）、`image_window_mask`（43 行）、`fade_mixer` 全是处理器，整个工程只剩 SDRAM 控制器可用。这个解释会直接摧毁赛题一的可实现性，与 1.3 允许「多个算法的有机结合」自相矛盾。

### 3.2 需要准备类 AHT20 的论证材料吗？

**不需要单独辩护材料，但建议做一页 PPT 归属图——性质是「加分展示」而非「合规辩护」。** 两者的区别是本质性的：

| | AHT20 | `emerg_page.v` |
|---|---|---|
| 待证问题 | 「这个**外部模块**内部有没有 MCU？」 | 「这段**源码**在哪里？」 |
| 为何要证 | 它是成品模块，处于「可能违规」的灰区，必须用数据手册自证 | 它就在 FPGA 里，不存在「在哪里」的疑问 |
| 需要什么 | 数据手册 + 功能框图红框标注 + 对比页（t12 已列 M1~M8） | **不需要** |

**建议做的那一页不是辩护，是「自主实现证据链」的一部分**（可与主干证据放在一起）：

- `emerg_page.v` 源码行数 / 资源实测（`science_page` 同构基准：**1052 le / 672 lut / 0 bram / 0 dsp**，来源 `reports/watchdog_20261030/area.txt:221`；其字形 ROM `science_font16` 为 `L22` 行 `292 le / 292 lut / 0 bram`）
- **零外部依赖**：不读 SD 卡、不读任何 ROM 文件、无时钟域
- 一句话：「这一页没有一个像素来自 SD 卡或任何外部芯片，全部由 FPGA 用坐标算出」

## §5 「程序化生成 = 自主编程实现的最强证据」这个叙事站得住吗？

**方向站得住，但「最强证据」的提法建议降级为「最直接的证据」或「零依赖的自主实现范例」。** 三段论证如下。

### 5.1 站得住的部分（三条，都有可验证的事实支撑）

1. **对比是硬的**：官方样例 lab_ex_4 / lab_ex_5 的做法是「TF 卡存 640×480 非压缩 BMP → SDRAM → HDMI」，读预制图**只证明你会写存储→显示通路**，不证明「算法」。而 `emerg_page.v` 是**用像素坐标算颜色**，每一像素都是当拍算出来的——这正是 1.3（`L544`）「算法、控制逻辑及数据处理流程应在 FPGA 中自主编程实现」的字面实现。
2. **可验证性**：预制图方案 LUT 成本≈通路成本（画面逻辑为零）；`emerg_page` 同构基准 672 lut（`science_page` 实测）。改一个字：预制图要重新生成 BMP 再上卡，`emerg_page` 改一个 `localparam` 重综合。这个对比在评委面前当场可验。
3. **最强的一点其实是「不依赖 SD 卡」**：应急场景最需要「卡坏了也要显示」。本项目已有同类工程先例——`rtl/control/err_prompt.v`（20,666 B）文件头 `L4-21` 记载的正是「硬件故障时仍要给出可读提示」的设计动机（把 5 个模块的 1~9 内部码归并成 5 类用户动作 `C/F/0/b/d`）。**应急画面同样是「SD 卡坏了也必须显示」的模块**，与 `err_prompt` 属同一设计哲学。这条比「我会画图」强得多。

### 5.2 三个反效果风险（不规避会反噬）

**风险 1：「画个平面图算什么算法」——评委确实会这么想。**

> **规避：不要把它当「算法」讲，要当「系统鲁棒性」讲。**
> 定位应为：它是 **P15 §1.5 基础要求（2）「显示稳定性与鲁棒性」**（`guide.txt:571`）的证据，而不是「算法炫技」。正确话术是「应急信息不能依赖 SD 卡——卡坏、卡拔、格式化错都必须能显示疏散路线，所以这一页由 FPGA 用坐标实时算出，零外部依赖」。
> 这样它同时命中**两项基础要求**（①核心功能完整性 ②显示稳定性与鲁棒性），比当「算法」讲更稳，也不会招来「算法含量」的质疑。

**风险 2：说成「最强证据」会贬低自己的主干。**

> 本项目真正吃资源的是 `image_player`（area.txt 实测 **7483 le / 6094 lut**）、`hdmi_core`（1706 le / 1234 lut）、`img_scaler`（1381 le / 989 lut）、`gallery_probe`（1052 le / 767 lut）。这些才是「算法」主战场：BMP 解析、SDRAM 双缓冲、任意比例缩放、HDMI 编码。
> `emerg_page` 预计 ~1000 le，是**辅助模块**。把它讲成「最强」，评委下一句就是「那你 SDRAM 双缓冲与缩放呢」，反而暴露你没分清主次。
> **建议表述**：「最直接的证据」「零依赖的自主实现范例」「不开 SD 卡也能画的模块」。

**风险 3：「程序化生成」这个词本身有歧义。**

> 它容易被误听成「用**程序**生成（脚本/软件离线生成位图再烧进去）」，恰好招来「是不是外部工具生成」的联想——正中 1.3 禁令的靶心。
> **建议换词**：「**FPGA 内实时栅格化**」（real-time rasterization in fabric）或「**坐标域实时着色**」。这两个词听起来就是硬件行为，没有歧义。

### 5.3 结论

叙事可用，但请按以下三条修正后使用：
① 「最强证据」→「最直接的证据 / 零依赖范例」（§5.2 风险 2）
② 「算法」→「系统鲁棒性」（§5.2 风险 1）
③ 「程序化生成」→「FPGA 内实时栅格化」（§5.2 风险 3）

## §6 一句话答辩口径

**评委问「为什么应急是个平面图」：**

> 「应急信息发布的核心不是『出事了』，是『往哪走』。纯红色只告诉人出事了，不告诉人往哪走；平面示意图能标出当前位置、两个出口和最近的路线——赛规 P14 §1.2 把应急信息发布列为认可的应用场景，这一页就是那个场景该有的信息量。而且它不读 SD 卡，是 FPGA 用像素坐标实时栅格化出来的，卡坏了照样显示，这正是 1.3『算法与控制逻辑在 FPGA 内自主实现』和 1.5『显示稳定性与鲁棒性』的直接体现。」

**评委问「这不就是画个图吗，算什么技术含量」：**

> 「这一页的可比对象不是『画图』，是官方样例 lab_ex_4 那种『SD 里存 BMP 再读出来显示』的做法。区别在于：读 BMP 只需要通路，画面本身零逻辑；这一页每个像素都是当拍算的，改一个字要改 RTL 重综合，而不是重做一张图。另外它没有 SD 依赖，这是我们整个系统里唯一一个『卡全坏也能正常工作』的功能模块。」

## §6.5 措辞纪律补充：AHT20 手册 p.15 免责条款对本页叙事的约束（2026-11-01 补记）

> 触发来源：用户提供的 AHT20 官方手册（`D:\date sheet\AHT20.pdf`，15 页，2024-07 版，ASAIR，SHA256 `999B49DC0FA6987D3C83B4B7003D2A340A4D5F03184B0B09985901270BF06822`）第 15 页「警告，人身伤害」载明：「**勿将本产品应用于安全保护装置或急停设备上**，以及由于该产品故障可能导致人身伤害的任何其它应用中……如不遵从此建议，可能导致死亡和严重的人身伤害。」

### 为什么这条会影响应急画面的答辩口径

本页（平面示意图）本身与 AHT20 无因果关系——它不读传感器、不依赖 SD 卡、纯 RTL 栅格化，**即使把 AHT20 拔掉，按 Key3 依然能显示这一页**。但**叙事上二者会被评委连成一条链**：「温度超阈值 → 自动进应急 → 显示疏散平面图」。一旦这条链被讲成「本系统是一个**火灾/安全报警装置**」，就会同时踩两件事：

1. **AHT20 手册 p.15 免责条款**：厂商明确声明不得用于安全保护装置，而消防疏散正是典型安全保护场景；
2. **赛规层面过度宣称**：赛规（`guide.txt` 全文 1,248 行）**没有任何安全/消防功能条款**，本项目的应急模式是「明确应用场景」的一部分，不是安全认证产品。宣称越重，被追问「你做了哪些安全等级验证」时越难答。

### 强制措辞纪律（与本报告 §1、§6 的口径一致，此处单列以便现场执行）

| ❌ 禁用措辞 | ✅ 统一措辞 | 理由 |
|---|---|---|
| 消防报警系统 / 火灾报警器 | **应急疏散引导演示** | 手册 p.15；且赛规无安全认证要求 |
| 安全功能 / 安全保护装置 | **多源驱动的模式切换演示（温度阈值触发 / Key3 手动触发）** | 定性在叙述层，零成本改口 |
| 消防通道指示系统 | **应急信息发布画面（平面示意图）** | 与赛规 P14 §1.2 的「应急信息发布」原文一致 |
| 本系统保障人员安全 | **本系统演示如何在应急场景下快速切换并给出可读信息** | 不承诺安全后果，只陈述演示行为 |

### 与 §6 答辩话术的衔接（一句补充，接在「为什么应急是个平面图」之后）

> 「需要说明的是，这一页是**演示性**的应急疏散引导画面，不是消防安全设备——传感器厂商的手册明确写着该器件不得用于安全保护装置，我们照此执行：本系统对温度的响应只是**多源驱动模式切换的一个演示入口**，真正的应急入口是 Key3 手动直达，不依赖任何传感器。这一页本身也不依赖 SD 卡，是 FPGA 内部实时栅格化的。」

## §9 保守做法：最低要求 → 有余力再加强

用户已裁「画平面示意图」，所以平面图本身是最低要求。建议分三层，**P0 必须做，P1/P2 视 LUT 余量**（余量参考：`RESOURCE_BUDGET.md:161-163` P0+P1 累计 17,777 / 19,600 = 90.70%，余量 1,823）。

### P0 —— 最低必须（约 400~600 le，零 BRAM 零字形 ROM）

- 矩形外墙框（1 条粗边框）
- 一条横向主走廊（纯色带）
- 房间分格（若干竖线）
- **当前位置**：一个实心方块（不同色，如青 `24'h00_C8_E0`）
- **2 个出口**：不同色高对比（如亮绿）+ 边框加粗
- **最近路线**：从当前位置到最近出口的**直角折线**（先横后竖），**不用斜线**——斜线会引入斜率乘法，本工程 DSP 只剩 10/29
- **文字统一走 OSD 字幕层（已有 `osd_caption`）**，`emerg_page` 内不画字

> **P0 的关键设计选择：`emerg_page` 内不画中文**。这样它是**真正的零 BRAM、零字形 ROM**，且中文文字与滚动字幕共用一套字库不重复造，t14 字库扩容延误也不影响应急页上线。这是最保守也最省的做法。

### P1 —— 加强（约 +300 le）

- 路线改成**连续箭头链**（每 16 像素一个箭头，用两组三角形范围比较实现，仍无乘法）
- 出口**闪烁**：由外部提供 `blink` 输入信号（`emerg_page` 自身仍纯组合，`blink` 是输入不是内部状态）。**t8 需提供 blink 源**——`mode_ctrl` 已有计时器可用

### P2 —— 加分（约 +300~400 le）

- `emerg_page` 内嵌字形 ROM 画中文（「应急疏散」「出口」「您在此」），需 t14 扩字库
- 此时资源与 `science_page` 同量级（1052 le / 672 lut / 0 bram）

### 明确不建议

- **多套平面图可切换（楼层/楼栋选择）**：用户没要求，会引入 ROM/RAM 与选择逻辑，纯属给自己加风险与工作量。

## §10 措辞与赛规的边界：哪些安全类比可以用、哪些必须避开

> 本节应 captain m01297 要求补写。逐行替换文本见 `reports/plan_v2/SAFETY_WORDING_RULING.md`（下称「措辞裁定」）；本节只回答**原则**：边界在哪，为什么在那。

### 10.1 先确定一件事：赛规里根本没有"安全"这个得分项

`_guide/guide.txt` 全文 1,248 行，`应急|消防|疏散|安全` **仅命中 1 处**（`L529 [P14]`，§1.2 应用场景举例，非功能条款）。评分落点是 `L570 [P15]` 「（1）核心功能完整性」。

**推论：安全类比在答辩中只能充当"设计严谨性"的论据，不能充当"功能价值"的论据。**

- 说「我们像告警设备一样考虑交互」→ 评委会觉得你想得周到 → **加分**
- 说「我们保障安全」→ 评委翻赛规找不到对应条款，只会去问「你做了哪些安全验证」→ **不加分，只加负担**

这条推论是本节所有规则的根。**任何安全类比，只要它带来的是"价值宣称"而不是"严谨性说明"，就该改。**

### 10.2 三档判定：可用 / 慎用 / 禁用

| 档位 | 判据 | 例子 |
|---|---|---|
| **✅ 可用** | 主语是「设计/做法」，说的是「这套交互为什么这样定」 | 「进入零延迟、退出需双确认」是**告警类人机交互的通用惯例：拉响是瞬时动作，复位必须是有意识的操作**」<br>「一次性误触不应解除告警」<br>「温度回落不等于事件已处理」 |
| **⚠️ 慎用** | 提到具体设备类别，但**只作为参照系、且当场标明是类比** | 「参照**报警类面板**的交互惯例」——必须紧跟一句「这是类比，本系统是演示装置」；<br>若省略这句限定，慎用档立刻降级为禁用档 |
| **❌ 禁用** | 主语是「本系统」，或宣称设备用途/能力 | 「这是按**消防报警器**逻辑设计的」<br>「应急信息发布是**安全功能**」<br>「**安全功能**静默失效」<br>「本系统**保障人员安全**」<br>「**消防通道**提示」 |

### 10.3 两个反直觉的边界（容易判错的地方）

**边界一：删掉"安全"二字不等于改对了。**

「应急字幕**承载安全信息**，不可关」与「应急字幕**承载疏散引导文字**，不可关」——后者才是对的。区别不在「安全」这个词，而在**「安全信息」暗示了系统在传递安全级别内容**（意味着它承担安全职责）；「疏散引导文字」只描述内容属性。

**判据：看这句话有没有在暗示"本系统的输出具有安全权威性"。**

**边界二：不要矫枉过正，把工程术语一并删掉。**

`RESOURCE_BUDGET.md:166` 的「**1,823 的余量是安全边际**」、RTL 里 21 处「安全」（`跨时钟域安全`、`失败安全`、`安全值`、`对功放最安全`）**全部保留**。它们修饰的是电路/代码/数值，与产品定性零关系。删掉反而让工程文档读起来不通顺，且显得在掩饰什么。

**判据：看"安全"修饰的对象——修饰电路/代码/数值 → 留；修饰本系统能力或输出内容 → 改。**

### 10.4 与 AHT20 手册 p.15 的精确关系（避免过度反应）

p.15 原文约束的是「**勿将本产品应用于**安全保护装置或急停设备上」——**约束的是产品用途（application），不是设计灵感来源**。

所以：
- 我们**参照**了一套交互惯例 → 不受 p.15 约束（不是"应用于"）
- 我们**宣称**本系统是安全保护装置 → **正是 p.15 禁止的**

这也解释了为什么 §6.5 的处理方案是「定性教学演示装置 + Key3 冗余通道 + 措辞纪律」三件事，而不是「不用 AHT20」——**只要用途定性正确，器件本身完全可用**。

### 10.5 一句话执行口径

> 「参照**告警类人机交互的通用惯例**：拉响是瞬时动作，复位必须是有意识的操作。」——这句话同时做到了三件事：解释了设计的严谨性（加分）、没有宣称产品身份（不碰 p.15）、与赛规「核心功能完整性」的落点对齐（`L570 [P15]`）。
