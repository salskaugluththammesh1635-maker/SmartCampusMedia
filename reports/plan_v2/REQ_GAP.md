## 1. 判定 (a)：AHT20 是否构成「额外处理器」

### 1.1 赛规原文与本条的冲突点

- **[P14] H7**：「允许根据作品需要搭配外围电路或成品模块，但**不得带有额外处理器（无论用于辅助控制还是算法预处理）**。」
- **[P14] H6**：「允许根据作品需要搭配外围电路或成品模块。」

两条叠加的净效果：**可以用模块，但模块内不能有会算东西的东西**。冲突点在于 —— AHT20 内部**确实**执行了「用 OTP 校准系数对原始 ADC 值做补偿运算」这一步。这一步算不算「算法预处理」？

### 1.2 判定结论

> **AHT20 不构成「额外处理器」，判定合规。风险等级：中（合规本身低风险，但需备材料应对现场追问）。**

### 1.3 判定依据（四条，按证据强度排序）

**依据 1（技术定义）：AHT20 不具备「处理器」的三个必要特征。**
处理器的技术定义是「可执行指令序列的可编程器件」，须同时具备 ①指令集 ②程序存储器 ③取指-译码-执行通路。AHT20 三者皆无：
- 命令表只有 **3 条硬连线命令**（0xAC 触发测量 / 0x71 读状态 / 0xBE 软复位），不是指令集，无跳转、无循环、无分支；
- 无程序存储器，校准系数存于**出厂固化的 OTP**，用户不可写、不可改；
- 内部数据通路是**固定硬连线**的专用 ASIC（电容式敏感元件 → 24bit ADC → 固定系数补偿 → I2C 从机移位寄存器），不可编程。

**依据 2（赛规自身类比，最强论据）：赛规自己允许比 AHT20 复杂得多的模块。**
- **[P5]** 官方把「**摄像头模块**」「语音处理」列入 40Pin 外扩的**官方预期用途**。
- 工程内已登记的 `OV5640` 摄像头模组，内部含 **ISP（图像信号处理器）+ SCCB 寄存器组 + 自动对焦控制**，复杂度、可配置度、内部运算量**全面超过 AHT20**（见 `HX4S20_Contest_202606/3_原理图/OV5640_*` 共 6 份手册）。
- **逻辑**：若 OV5640 合规，则 AHT20 必然合规。若 AHT20 被判违规，则官方列举的「摄像头模块」也违规 —— 该推论荒谬，故 AHT20 不违规。

**依据 3（边界一致性）：按「含数字逻辑即违规」的极端解释，赛规将自相矛盾。**
工程实际使用的 SD 卡（内部含 Flash 转换层 FTL 控制器）、SPI Flash（内部状态机）、HDMI 显示器（内部 scaler）、ES8388 声卡（含 I2C 寄存器组）**全部**含数字逻辑与内部运算。若这些算「额外处理器」，则赛题一根本无法实现。故「额外处理器」的正确解释只能是**可编程的通用/专用处理器核**，不含固定功能 ASIC。

**依据 4（本项目的自证设计）：所有算法与控制流仍 100% 在 FPGA 内。**
AHT20 只输出 **20bit 原始数字量**（温度），以下全部在 RTL 内完成：
| 处理环节 | 实现位置 | 是否 FPGA 内 |
|---|---|---|
| I2C 时序生成（100kHz，起始/停止/应答/时钟拉伸） | 新增 `rtl/input/i2c_master.v` | ✅ 是 |
| 上电等待 40ms、触发测量、读 6 字节、状态轮询 | 新增 `rtl/input/aht20_ctrl.v` 状态机 | ✅ 是 |
| **CRC8 校验**（多项式 0x31） | 新增 `rtl/input/crc8.v` | ✅ 是 |
| 20bit 原始值 → 温度换算（×200/2^20 − 50） | 新增定点运算 | ✅ 是 |
| 阈值迟滞判断（≥45℃ 触发 / ≤40℃ 解除） | 新增比较+迟滞寄存器 | ✅ 是 |
| 联动决策（切应急模式、OSD 提示、蜂鸣器告警） | 扩展 `player_ctrl.v` | ✅ 是 |
| AHT20 自身 | 只做「敏感元件 + ADC + 固定补偿」 | 无任何算法/控制决策 |

→ **符合 H5「所有算法、控制逻辑及数据处理流程应在 FPGA 中自主编程实现」**。

### 1.5 替代方案（若评委仍质疑，或 M1 拿不到）

**方案 A（推荐保底 · 零合规争议）：片内 SAR ADC + NTC 热敏电阻**

工程内已有官方依据：`HX4S20_Contest_202606/6_EG4S20数据手册/EG4S内部ADC使用指南.pdf`（TN304_1.3，5 页）明确：
> 「EAGLE 系列芯片中内嵌有 **1 个 8 通道 SAR 型 ADC 模块**。8 个通道输入和用户 IO 复用……当用户不需要 ADC 时可以当作普通用户 IO 使用，复用 IO 设置相互独立」
> 「最高采样速率 1MHz」「最高时钟频率 16MHz」「ADC 输出数字位宽 12bit」「ADC 有效精度 8bit」「采样范围 0.1*VREF ~ 0.9*VREF」

实现：**NTC 10k 热敏电阻 + 1 个分压电阻**（属 H6 明确允许的「外围电路」）→ EG4S20 ADC 通道 → FPGA 内查表线性化 + 迟滞判断。
- **合规强度**：★★★★★（外部只有两个无源电阻，**零外部芯片**，无法被质疑）
- **技术强度**：★★★★（12bit 输出 / 8bit 有效精度，测温分辨力足够做 45℃/40℃ 阈值；ADC 最高 1MHz 采样远超 1Hz 需求）
- **成本**：需占用 1 个 ADC 复用球 + 1 个精密电阻；需查 ADC 通道球位表（`EG4S内部ADC使用指南.pdf` 表 3 仅给通道使能参数，**球位需查 EG4S20 数据手册引脚表**）
- **代价**：失去「AHT20」这一具体型号的演示亮点，但保留「温度联动」全部功能语义

**方案 B（并行保底 · 必做）：Key3 手动直达应急模式**
无论 AHT20 是否落地，**应急模式必须可由 Key3 手动直达**。这是赛规 [P14] 1.2「应急信息发布」场景的**保底演示路径** —— 传感器失效/未焊/未接时，作品核心场景仍可完整演示。
→ **强制要求**：`player_ctrl.v` 的应急模式入口不得只挂在温度阈值上。

**方案 C（不推荐）：仅作可选扩展，主演示不依赖**
把 AHT20 降级为「B 级可选扩展」，A 级基线不含温度联动。**代价**：失去一个差异化亮点，且用户 m00001 明确要求此项 → 仅在方案 A 也无法落地时启用。

**最终建议（给 architect 的输入）**：
> **AHT20 作为主方案（B 级），方案 A（片内 ADC + 热敏电阻）作为并行开发的 Plan B（同为 B 级），Key3 手动直达作为 A 级必做保底。** 三者共用同一套「温度阈值 → 迟滞 → 联动」上层逻辑，仅底层数据源不同（I2C 读寄存器 vs ADC 读通道），切换成本约 1 个 mux + 1 个模块替换。

### 1.6 引脚可行性核实（修正一处既有认知）

任务描述称「D1/E1 未被占用」，实测需修正为：**D1/E1 在 `.adc` 中未被本项目占用，但它们在底板引脚定义中属「屏接口复用球」**。

依据 `docs/pending_confirmations.md:46` 原文：
> 「并口屏：DATA[15:0]=K1,J1,H1,H2,G1,F1,F2,**E1**,E2,**D1**,M5,M3,M2,L4,L3,P2 + CS=N3,RS=M4,WR=L5,RD=L1,RST=K2,BL_CTR=R2；SPI 屏：**SCL=D1,SDA=E1**,RES=F1,DC=H2,CS=J1,BLK=K2（**本项目不用，仅登记**）」

**结论**：
- D1/E1 **确实可用** —— 本项目不使用并口屏/SPI 屏，两个球空闲。
- 但需注意：这两个球在底板上**物理连到屏接口排针**，AHT20 模块须从该排针引出 SCL/SDA（而非另有独立 I2C 排针）。
- **风险等级：低**。处置：接线图须标明「AHT20 从屏接口排针取 D1/E1」，并在文档中说明「该排针本项目不用作显示」。
- **额外好处**：SPI 屏的 SCL/SDA 语义本身就是 I2C 双线 → 底板**已为该排针预留 I2C 用途**，接线无争议。

## 2. 判定 (b)：SD 卡 640×480@60Hz 视频播放的可行边界

### 2.1 判定结论

> **按用户原义「SD 卡存 640×480@60Hz 视频」：③不现实，风险等级 = 阻塞。必须降级，且降级维度不可省略。**
> **降级后可达成「SD 卡序列帧/短视频循环播放」，用户体验等价于视频播放，且完全合规。**

### 2.2 依据：三处带宽实测/推导（逐层排除）

**第一层：SD 卡读取带宽是唯一真瓶颈**

| 项 | 实测值 | 依据 |
|---|---|---|
| SD 控制器主时钟 | 25 MHz | `rtl/storage/sd_spi_ctrl.v:35` `parameter CLK_FREQ_HZ = 25_000_000` |
| 数据阶段 SCK | **12.5 MHz** | `sd_spi_ctrl.v:37` `parameter SCK_FAST_DIV = 1, // 读数据 SCK 半周期拍数：25M/(2*1)=12.5MHz` |
| 理论峰值 | **1.5625 MB/s** | 12.5 MHz ÷ 8 bit |
| 实用取值（含 CMD17/CMD18 命令开销、块间间隙、FAT 簇链跳转、卡内部延迟） | **≈ 1.25 MB/s** | 保守工程值（理论值 × 0.8） |
| 初始化阶段 SCK | 390.6 kHz | `sd_spi_ctrl.v:36` `SCK_INIT_DIV = 32`（卡要求 100~400kHz） |

**第二层：需求侧带宽**

| 格式 | 单帧字节 | @60Hz 需带宽 | 相对 SD 供给的缺口 |
|---|---|---|---|
| 640×480 RGB888（24bit，官方样例格式） | 921,600 B | **55.3 MB/s** | **44×** |
| 640×480 RGB565（16bit） | 614,400 B | **36.9 MB/s** | **29.5×** |
| 640×480 RGB332（8bit） | 307,200 B | 18.4 MB/s | 14.7× |
| 320×240 RGB565 | 153,600 B | 9.2 MB/s | 7.4× |
| 320×240 RGB332 | 76,800 B | 4.6 MB/s | 3.7× |

→ **即使把分辨率砍到 320×240、色深砍到 8bit，仍差 3.7 倍。**

**带宽缺口的两种口径（避免答辩时被追问「你到底用哪个数」）**：

| 口径 | SD 供给 | 640×480@60 RGB565 缺口 | 640×480@60 RGB888 缺口 | 使用场合 |
|---|---|---|---|---|
| **理论峰值**（12.5MHz ÷ 8，无任何开销） | 1.5625 MB/s | **23.6×** | **35.4×** | 最有利于「勉强可行」的乐观假设 —— 即便如此仍不可行，故结论更硬 |
| **实用值**（×0.8，含命令/块间隙/FAT 跳转） | 1.25 MB/s | **29.5×** | **44.2×** | 工程排期与演示指标采用此值 |

→ **两种口径都指向同一结论：不可行。** 本文档后续指标计算统一采用**实用值 1.25 MB/s**（保守、可用于排期）；引用「不可能」时用**理论峰值**（最不利于自己的假设下依然不成立，论据更硬）。

**第三层：排除「是不是 SDRAM 不够」的误判（重要 —— 会被评委问到）**

| 项 | 数值 | 依据 |
|---|---|---|
| SDRAM 时钟 | 40 MHz | `rtl/storage/sdram_pll.v:2`「40MHz 0° + 40MHz 180°」 |
| SDRAM 理论带宽 | **160 MB/s** | `sdram_pll.v:52` 原文「带宽校核：40MHz × 4 字节 = 160 MB/s」 |
| 视频播放时 SDRAM 负载 | 写 1.25 MB/s（SD→SDRAM）+ 读 36.9 MB/s（SDRAM→HDMI）= **38.2 MB/s** | 占 160 MB/s 的 **23.9%** |

→ **SDRAM 余量充足，不是瓶颈。瓶颈 100% 在 SD SPI 接口。**
→ 顺带修正一个可能的误判：`sdram_pll.v` 曾两次降频（150→100→40MHz），40MHz 是**时序收敛**决定的（读路径需 T/2 ≥ 10.565ns → f ≤ 47.33MHz），**不是带宽决定**的。40MHz 的 160 MB/s 对视频播放绰绰有余。

**第四层：SDIO 升级也救不了（排除「优化接口」的幻想）**

| 方案 | 理论带宽 | 对 640×480@60 RGB565（36.9MB/s） | 工作量 |
|---|---|---|---|
| 当前 SPI @12.5MHz | 1.56 MB/s | ✗ 差 23.6× | — |
| SPI @25MHz（SCK_FAST_DIV=0，已到 25MHz 主时钟上限） | 3.125 MB/s | ✗ 差 11.8× | 低（改 1 个参数），但 25MHz SCK 多数卡不稳 |
| SDIO 4-bit @12.5MHz | 6.25 MB/s | ✗ 差 5.9× | **高**（需新写 SDIO 控制器，数百行 RTL + 新时序） |
| SDIO 4-bit @25MHz | 12.5 MB/s | ✗ 差 3× | 极高 |

→ **无论怎么升级接口，640×480@60 全屏未压缩视频都不可达。这是硬结论，不是实现质量问题。**

### 2.3 必须降级的维度（四维，可组合）

| 维度 | 可选档位 | 带宽收益 | 代价 |
|---|---|---|---|
| **① 分辨率** | 640×480 → 320×240 / 256×192 | **4× / 6.25×** | 画面细节下降（但 320×240 上采样到 640×480 显示可接受） |
| **② 色深** | RGB888 → RGB565 → RGB332 → 索引色 256 | **1.5× / 3× / 3×** | 色彩层次下降；索引色需 256 项调色板 LUT（约 1 个 BRAM） |
| **③ 帧率** | 60 → 30 / 15 / 10 / 8 fps | **2× / 4× / 6× / 7.5×** | 流畅度下降；8fps 已明显卡顿，10fps 为可接受下限 |
| **④ 编码** | 非压缩 → **RLE 游程压缩** | **2~4×**（UI/卡通类内容；实拍内容 1.2~1.5×） | 需 RLE 解码器（约 300~500 LUT）；实拍素材收益小 |

**注意：JPEG/MJPEG 不可行。** 依据：
- 工程内**无任何 JPEG/MPEG/H.264 解码 RTL**。核验方法与结果：
  - 全 RTL 搜索 `jpeg|jpg|mpeg|h264|IDCT|huffman` → **命中 0 处**；
  - 搜索 `decode` → 命中全部为无关命名：`seg_decoder.v`（七段数码管译码，含 `seg_led_decoder`/`seg_sel_decoder` 引用）、`pix_reader.v:129` 的 `g_gray_decode`（格雷码译码）、`image_path_probe.v` 的 `decode_valid`/`decode_pixel`（**BMP 解码探针信号名**，非视频解码器）。**无一处为视频编解码实现**；
- LUT 余量仅 **4512**（15088/19600 已用 76.98%），而一个基线 JPEG 解码器需 ≥ 20,000 LUT → **资源上不可能**；
- 无视频解码硬核（EG4S20 无 H.264/JPEG 硬核）。

### 2.4 三条可行路径（按推荐度排序，供 architect 决策）

**路径 P1（首推）：序列帧播放 = 「视频」的用户体验，零解码器**
- 实现：SD 卡内存 `SEQ001.BMP … SEQnnn.BMP`（640×480 RGB565 或 320×240 上采样），`player_ctrl.v` 增加「序列模式」状态，按帧率定时切换文件；底层复用现有 `image_player` 全链路（BMP 解析 → 缩放 → SDRAM 双缓冲 → HDMI）。
- **新增 RTL 极少**：主要是一个帧序列索引器 + 定时器，估 **300~600 LUT**。
- 可达指标：640×480 RGB565 @ **2 fps**；320×240 RGB565 @ **8 fps**；320×240 RGB332 @ **16 fps**。
- 合规：**完美**（全部 FPGA 内，无解码器，与官方 lab_ex_4「按键切图+自动轮播」同源，只是把「按键触发」换成「定时触发」）。
- **这条路径把 R8 从「阻塞」降为「低风险」** —— 因为它根本不需要 60fps，它需要的是「连续变化的画面」。

**路径 P2（亮点方案）：SDRAM 预载短循环动画**
- 实现：8MB 片内 SDRAM，双缓冲帧缓存占 1.2MB（`FRAME_WORDS=153600` 字 × 2 × 4B），**剩约 6.8MB** → 可预存 **11 帧 640×480 RGB565**（6.8MB ÷ 614.4KB）。
- 播放：SD 一次性加载 11 帧（11 × 614400 ÷ 1.25MB/s ≈ **5.4 秒加载**）→ 加载完成后 SDRAM 本地循环播放，**帧率不再受 SD 限制**，可跑满 60fps（SDRAM 带宽 160MB/s 够）。
- 可达指标：**640×480 RGB565 @ 60fps，11 帧循环（约 0.18 秒素材）**。
- 演示价值：**「60fps 流畅动画」这个卖点可以拿回来**，且完全合规。
- 代价：素材极短（0.18s），需设计成「循环动效」（如扫描线、呼吸灯、循环滚动）而非叙事视频。LUT 增量小（复用双缓冲 + 加一个帧基址轮转）。

**路径 P3（不推荐）：降级为「静态图 + 动效」**
- 放弃连续帧，改为「单张图 + OSD 动画/转场」（即 E1+E2 扩展项）。
- 优点：零风险；缺点：不满足用户「视频播放」的字面要求。

**给 architect 的决策建议**：
> **P1 作为 A 级基线**（保证「SD 卡视频播放」需求在功能语义上被满足）；**P2 作为 B 级亮点**（拿回 60fps 卖点）；**P3 仅作降级兜底**。
> **明确写入 t2 计划文档**：不得承诺「SD 卡直接流式播放 640×480@60fps 未压缩视频」，该承诺在 EG4S20 + SPI 接口上物理不可达。

**t2 实际裁决结果（t10 复核）**：
> **选 P1 并叠加 RLE 压缩**，指标 **640×480 RGB565，5fps 目标 / 2fps 保底**（`ARCH.md` §11:1032-1102）。**P2 被明确否决**（`ARCH.md`:1093-1102 记为后续可选增强、本版不实现），否决理由三条：① 占满 SDRAM 使任何后续扩展不可能；② 11 帧 @60fps = 0.18 s 循环，视觉上是「抖动的 0.18 秒」，体验反而更差；③ 预载 6.76 MB 需 5.4 s（按 1.25 MB/s），启动延迟不可接受。**P3 未采用**（不满足用户「视频播放」字面要求）。
> → 因此本文件 §2.4 的 P2「拿回 60fps 卖点」**不再成立**，答辩叙事以「满分辨率 640×480 + RLE 压缩把帧率从 1fps 提到 5fps」为主线（`ARCH.md`:1042 已备逐字口径）。

### 2.5 素材格式的连带风险（必须同步处置）

工程内现有素材 `assets/campus_media/preview/smart_campus_showcase.mp4`（**7,274,931 B**）。
- 若为 30 秒 → 平均码率 242 KB/s → 折合 640×480 RGB565 约 **0.39 帧/s** 等效 → 说明这是**高度压缩的 H.264/H.265 视频**。
- **H.264 解码在 EG4S20 上不可能**（LUT 余量 4512，基线 H.264 解码器需数十万 LUT）。
- **处置**：该 mp4 **只能作为「宣传/答辩视频素材」**，**绝不能作为 SD 卡播放源**。SD 卡播放源必须是**预转换的非压缩/索引色 BMP 序列**。
- **强制要求（写入 t3 asset-curator 任务）**：所有上板素材必须经 `assets/campus_media/sd_card/*.BMP` 同款管线转换（现已有 IMG001~IMG006.BMP 各 921,654 B = 640×480×3 + 54B 头，格式已验证正确）。

## 3. 判定 (c)：4×4 矩阵 16 键与 GPIO 直连 AHT20 的平台合规性

### 3.1 判定结论

> **不违规，且不影响评分。风险等级：低。**

### 3.2 依据（四条）

**依据 1：1.1 的用词是「推荐选用」，不是「必须」。**
**[P14]** 1.1 原文：「推荐选用平台 1：HX4S20C」。全文未见「仅限」「必须使用官方板卡」等排他表述。

**依据 2：「4 组输入按键」是**板载资源清单**，不是**功能上限规定**。**
**[P4]** 原文位于「平台一 HX4S20C 硬件参数」表格的「人机互换信号」行：「**4 组输入按键** / 4 组拨码开关 / 1 组控制蜂鸣器开关 / 1 组切换数码管和双色 LED 开关」。
→ 这是**描述 HX4S20C 这块板有什么**，不是**规定作品能用几个键**。赛规通篇没有任何「按键数量上限」条款。

**依据 3：赛规 P5 明确把「键盘」列为 40Pin 外扩的官方预期用途。**
**[P5]** 原文：「用户外扩 2 组 40Pin DC3（多达 72 组扩展 IO）供外扩 LCD、ADC、DAC、摄像头模块、电机、HDMI 输入模块、交通灯、点阵、**键盘**、语音处理等」
→ **外扩键盘是官方鼓励的用法**。本项目所用 DMZ-EG4S20 底板**板载** 4×4 矩阵键盘，比「外扩」更省事。

**依据 4：本项目使用的是自购 DMZ-EG4S20 底板，其板载资源就是 4×4 矩阵。**
依据 `docs/pending_confirmations.md:26`：
> 「自购 DMZ-EG4S20 为**核心板+底板结构**：核心板载 LED×8/数码管×4/**4×4矩阵键**/拨码×8/蜂鸣器/UART/扩展排孔，底板另带 HDMI 排母（P3）、SD 卡槽（支持SDIO）、VGA、RGB565/并口屏/SPI 屏接口、音频输入/输出/喇叭、DAP Link 调试器。核心板与底板分离，两者组合后**功能面与官方板相当**」

→ 硬件本身合规（核心器件 EG4S20BG256，见 SPEC_CONSTRAINTS §2）。键盘数量差异是**板卡差异**，不是**违规**。

### 3.3 答辩口径（逐字可用）

> **问：官方平台只有 4 组按键，你们用 16 键，是不是超出平台规格？**
>
> 答：三点。
> 第一，赛规 1.1 的原文是「**推荐**选用平台 1」，不是强制；1.3 的强制表述落在「基于**安路 EG4S 系列芯片**」和 1.2 的「以安路科技 **EG4S20BG256 器件**作为核心平台」——约束的是**芯片型号**，本项目核心器件正是 EG4S20BG256，与官方平台同款同型号。
> 第二，「4 组输入按键」出现在 [P4] 的**平台一硬件参数表**里，描述的是 HX4S20C 这块板**有什么**，赛规通篇没有任何按键数量上限条款。相反，[P5] 把「**键盘**」明确列入 40Pin 外扩的**官方预期用途**——外扩键盘是赛规鼓励的做法，我们只是把外扩做在了板载。
> 第三，也是最重要的一点：**键位数量不影响赛规的核心硬约束**。[P14] 要求「所有算法、控制逻辑及数据处理流程应在 FPGA 中自主编程实现」——我们的 4×4 矩阵扫描、20ms 消抖、键值译码、动作分发**全部由 RTL 实现**，没有一颗 MCU 参与。键多键少只影响交互丰富度，不影响合规性。

> **问：AHT20 用 GPIO 直连，算不算「额外处理器」？**
>
> 答：不算，且这恰恰是最保守的接法。
> AHT20 是**纯数字传感器 ASIC**：只有 VDD/GND/SDA/SCL 四根线，I2C 从机地址 0x38，命令表只有 3 条（触发测量/读状态/软复位），**无指令集、无程序存储器、不可编程**。它不是处理器。
> 更强的论据是赛规自身：[P5] 官方把「**摄像头模块**」列为 40Pin 外扩的预期用途，而 OV5640 内部含 ISP 图像处理器 + SCCB 寄存器组，复杂度**远高于** AHT20。若 AHT20 违规，官方列举的摄像头模块也违规——这显然不是赛规本意。
> 而 AHT20 输出的**只是 20bit 原始数字量**：I2C 时序生成、CRC8 校验、温度换算、阈值迟滞、联动决策**全部在我们的 RTL 里**。这完全符合 [P14]「所有算法、控制逻辑及数据处理流程应在 FPGA 中自主编程实现」。
> 补充：如果评委仍希望看到「零外部芯片」的方案，我们已备好 Plan B —— 用 EG4S20 **片内 8 通道 SAR ADC**（官方 TN304 手册）接 NTC 热敏电阻，外部只有两个无源电阻。两套方案共用同一套上层联动逻辑。

### R1 Key0~Key9 十键功能重排 —— ①可直接做 / 低

### R2 五档分辨率 —— ②需论证（部分不现实）/ **高**

**核心问题：PLL 与 TMDS 串化时钟的物理上限。**

依据 `rtl/video/hdmi/hdmi_pll.v` 头部注释原文：
> 「VCO = 1000MHz，两个输出均由同一 VCO 整数分频 → 天然同源、相位固定」
> 「25.175MHz（VESA 标准值）无法由 50MHz 整数分频得到（**所需 VCO 超出芯片上限 ~1200MHz**），故取 25MHz：偏差 0.7%，场频 59.58Hz」
> PLL 参数：`REFCLK_DIV = 2` → 内部参考 25MHz；`VCO = 25 × CLKC0_DIV(40) = 1000 MHz`（**芯片 VCO 范围约 400~1200**）；`C0 = 1000/40 = 25MHz`；`C2 = 1000/8 = 125MHz`（5× 串化）

**逐档核算**（约束：TMDS 串化时钟 = 5 × 像素时钟，且必须由同一 VCO 整数分频；VCO ∈ [400, 1200] MHz）：

| 档 | 目标分辨率@刷新 | 需像素时钟 | 需串化时钟 | 可行 VCO | 判定 |
|---|---|---|---|---|---|
| 1 | 640×480@59.5 | 25.0 MHz | 125 MHz | 1000（DIV 40 / DIV 8） | ✅ **已验证上板** |
| 2 | 720×480@59.94 | 27.0 MHz | 135 MHz | 810（DIV 30 / DIV 6） | ✅ 理论可行，需重验 PLL |
| 3 | 800×600@60 | 40.0 MHz | 200 MHz | 1200（DIV 30 / DIV 6） | ⚠ **VCO 恰在上限 1200**，临界，需重验 |
| 4 | 1024×768@60 | 65.0 MHz | **325 MHz** | 650（DIV 10 / DIV 2） | ✗ **325MHz 串化超 EG4S20 LVDS 可达范围**（125MHz 已验证，5× 已达 325MHz 未见任何官方例程支持） |
| 5 | 1280×720@60 | 74.25 MHz | **371.25 MHz** | 742.5（非整数）或 1485（超限） | ✗ **VCO 无法整数生成 + 串化超限，双重不可行** |

**结论**：
- 5 档中**只有 2 档（640×480、720×480）确定可行**，800×600 临界，**1024×768 与 1280×720 不可行**。
- 额外约束：PLL 仅 **4 颗，已用 2 颗**（`hdmi_pll` + `sdram_pll`，见 `area.txt` `#pll 2/4`）。若为多档分辨率例化多个 PLL，**最多再加 2 颗** → 无法为 5 档各配一颗 PLL。**必须走「单 PLL 可重构」路线**（TD 支持 PLL 参数化重建，但**运行时不可动态改分频** → 只能在综合期选定一档）。
- **这是硬约束：运行时「按键切换分辨率档位」若跨像素时钟，必须重新配置 PLL —— TD 的 EG_PHY_PLL 不支持运行时动态重配置。**

**给 architect 的三条可选方案（必须择一写入 t2）**：

| 方案 | 做法 | 优点 | 缺点 | 风险 |
|---|---|---|---|---|

| N3 | 五档全真实时序 | 字面完全满足 | **1024×768/1280×720 物理不可行** | **阻塞** |

**N1 的关键技术障碍（必须告知 architect）**：
现有 `rtl/storage/img_scaler.v`（419 行）**明确只做缩小，不做放大**。原文（`img_scaler.v` 第 24-40 行）：
> 「【二、只做缩小，不做放大（关键设计决策）】缩小: 任意比例，逐行逐列抽稀……放大: **不支持**。源图小于 640×480 时按 1:1 原尺寸居中显示。」
> 「为什么不做放大——在本架构下物理上做不到实时……放大要求「一个源像素/源行重放到多个目标像素/目标行」……源侧每字节间隔约 16 个 25MHz 拍……若源图仅 32×24 = 768 像素，平均每源像素要产 400 个目标像素，需要 25 倍于输入速率的输出能力。硬件上只能靠「先整图缓存再重扫」，而帧缓存正被显示通路占用，没有第二块空间放源图。」

> **【t10 复核更正 · 实现路径已由 t2 定稿改变】** 上面「放大在写入路径（SD→SDRAM）」是 t1 当时构想的 N1 实现方式，**t2 未采纳**。t2 定稿改为 **`video_geom_map.v` 在读取路径做坐标映射**（见 `ARCH.md` §3.4、§4.2）：以**目标坐标** `active_x/active_y` 为自变量，用 **Bresenham 双累加器**（`x_acc += step_num; if (x_acc >= step_den) {x_acc -= step_den; src_x++}`）反算出源坐标 `src_x/src_y`，交给 `pix_reader` 去 SDRAM 取像素。物理连线仍是 `geom_map（出坐标）→ 各源模块 → image_mask → content_mux → overlay`。

→ **两条实现的差别与结论**：
- t1 方案（写入路径整数倍重放）需要「写侧放大模块」，且只支持整数倍（2×/4×），无法覆盖 t2 定稿的 400×300（1.6×）、576×432（1.111×）两档**非整数倍**。
- t2 方案（读取路径坐标映射）**克服了 `img_scaler.v` 的「不做放大」限制**——因为它不做「源图重放到多个目标像素」的实时重放，而是**反向查表**：每个输出像素只查一次源坐标，读 1 个源像素，带宽与 1:1 显示完全相同。这正是 `img_scaler.v` 文件头所说「物理上做不到实时」的反例解法：问题不在「重放次数」，而在「方向」。
- **仍然必须新写模块**（`video_geom_map.v`，估 **+220 LUT / +60 REG / 0 DSP**，见 `RESOURCE_BUDGET.md:124`），**不可复用 `img_scaler.v`**（后者是缩小方向 + 21 位除法流水，958 LUT）。
- 副作用：非整数倍（1.6×、1.111×）会有**非均匀像素宽度**（某些源像素被重复 2 次、某些 1 次），视觉上表现为轻微不均匀，但**无累积误差**（DDA 保证每行结束时相位归零）。400×300 选 4:3 精确比 426×320 更优，理由见 `ARCH.md` §3.3。
