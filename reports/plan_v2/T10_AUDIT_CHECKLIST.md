# t10 合规终审检查清单（预置）

> **文件性质**：本文件是 spec-auditor 为 **t10「合规终审与需求偏差纠正（第 2 轮）」** 预置的执行清单，**不是 t10 的产出**。t10 解锁（deps: t4 + t9 完成）后按本表逐项执行，执行结果另写 t10 正式报告。
>
> **写于**：t1 / t12 均已完成、t10 尚未解锁的空档期。
> **依据来源**：`reports/plan_v2/SPEC_CONSTRAINTS.md`（赛规硬约束）、`reports/plan_v2/REQ_GAP.md`（需求裁决）、`reports/plan_v2/AHT20_COMPLIANCE_PACK.md` + `PLAN_B_NTC_ADC.md` + `SENSOR_DECISION.md`（AHT20 论证与 Plan B）、`docs/plan_v2/PLAN.md` / `ARCH.md` / `KEYMAP.md` / `RESOURCE_BUDGET.md`（t2 定稿）、captain 裁决（m00549 / m00562 / m00796）。

---

## 0. 使用方式

- 每条含 **检查点 / 查哪里 / 通过判据 / 失败后果** 四要素。
- **判定只有两档**：`pass`（实测符合）/ `fail`（实测不符，须给 severity + requiredFix）。不接受「看起来没问题」——凡断言必附实测行号或命令输出。
- **A 类为红线**：任一 fail 即整个 t10 判 `needs_revision`，不得通过。
- **B 类为高优先**：captain 指定或我判定为「最难查、后果最重」的陷阱。
- **C 类为口径一致性**：文档定稿 vs RTL 实现的偏差，影响答辩与验收。
- **D 类为风险落地复核**：t1 标为 ②需论证 / ③阻塞 的项，实际降级到什么程度。

## B 类 · 四条最高优先级抽查（captain 指定 3 条 + 我判定 1 条）

### B1 ⚠ `vol_apply` 与 `brightness_apply` 档位方向必须相反

| 项 | 内容 |
|---|---|
| 检查点 | 亮度档 **0 = 最亮（100%）→ 9 = 最暗（3/32 = 9.4%）**；音量档 **0 = 最轻 → 9 = 最响** |
| 查哪里 | `rtl/**/brightness_apply.v`、`rtl/**/vol_apply.v` 的 `case` 分支；`docs/plan_v2/KEYMAP.md:302-337`、`ARCH.md:671-680`、`PLAN.md:347-361` |
| 通过判据 | 两个模块的 `case` 顺序**不得相同**。最硬的判据：直接跑 `PLAN.md:351-361` 预置的 `tb_volume_direction.v` 两行相邻断言——`brt_out(0) > brt_out(9)` 且 `vol_out(0) < vol_out(9)` |
| 失败后果 | **答辩现场灾难级**：按「音量减」输出满功率。按 Key7 到档 0 会输出 1.000 而非 0.094 = **放大 10.67 倍**，整个音量跨度 20.56 dB 反向。且故障现象误导——用户先怀疑喇叭/音频通路，最后才想到 case 顺序 |
| 备注 | 这是 captain 在 m00796 中特别点名新增的抽查项：「答辩现场最难查的陷阱」 |

### B2 ⚠ `video_geom_map` 必须做成读取路径反向查表，不得写成写入路径整数倍重放

| 项 | 内容 |
|---|---|
| 检查点 | 以目标坐标 `active_x/active_y` 为自变量反算源坐标（Bresenham 双累加器），每输出像素只读 **1** 个源像素 |
| 查哪里 | `rtl/**/video_geom_map.v`；`ARCH.md:380-390`、`RESOURCE_BUDGET.md:124` |
| 通过判据 | ①无像素缓存（模块内无 frame buffer / line buffer 阵列）；②DDA 形式为 `acc += step_num; if (acc >= step_den) {acc -= step_den; src_x++}`；③五档 DDA 增量 **0.5 / 0.625 / 0.8 / 0.9 / 1.0** 全部落在 `src_x <= 639` 且无累积误差；④资源落在 **+220 LUT / +60 REG / 0 DSP** 量级 |
| 失败后果 | **400×300（1.6×）与 576×432（1.111×）两档做不出来**——非整数倍在写入路径重放方案下无法实现。若 t7 才发现，改就是伤筋动骨 |
| 备注 | 这正是 t1 原文写错、经 t2 定稿纠正的一条；`img_scaler.v` 文件头「物理上做不到实时」的结论在此被绕过，**但仍不可复用 `img_scaler.v`**（缩小方向 + 21 位除法流水 958 LUT） |

### B3 ⚠ `brightness_apply` 实例位置必须在 overlay 之后、osd_panel 之前

| 项 | 内容 |
|---|---|
| 检查点 | 链路顺序 `image_mask → content_mux → overlay → brightness → osd_panel → video_rgb_to_axis` |
| 查哪里 | `rtl/top/*.v` 顶层例化顺序；`ARCH.md:889-909`（八级链路表）、`:1008-1012`（例化编号：21 u_image_mask / 22 u_content_mux / 23 u_overlay / **24 u_brt** / 25 u_osd_pop / 26 u_osd_panel / 27 u_axis） |
| 通过判据 | `u_brt` 在 `u_overlay` 之后、`u_osd_panel` 之前；`brightness_apply` 为**纯组合零寄存器**（`assign de_out = de`、`assign rgb_out = de ? {...} : 24'd0`，无 always 打拍） |
| 失败后果 | 若串在 OSD 之后：最暗档 9.4% 下参数面板不可读 → **E4「实时参数调节与 OSD 信息叠加」得分点直接失效**，而 E4 是五项扩展里逐字命中用户需求的项 |
| 备注 | t1 原文写反（写「亮度在 OSD 之后」），已两次修正（REQ_GAP.md:364 / :431）。captain 在 m00796 中确认此为 t10 重点抽查项 |

### B4 ⚠ `image_window_mask` 与 `bright_sel` 两个易错接法

| 项 | 内容 |
|---|---|
| 检查点 | ①`image_window_mask` 必须在 `content_mux` **之前**、`overlay` **之前**，且只门控图片路 `pixel_valid`；②`bright_sel` 端口**必须保留**且接 `bright_lvl[2:0]`，**不得恒接 3'd0** |

| 编号 | 检查点 | 定稿口径（来源） | 失败后果 |
|---|---|---|---|

| C8 | 故障处理 | `sensor_fault` **只置标志，不得触发应急模式**；应急模式靠 Key3 手动直达兜底 | 传感器坏了就把屏幕锁死在应急画面 → 日常功能全不可用 |
