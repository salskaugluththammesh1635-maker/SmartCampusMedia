## §0 一句话结论

**Key9 的纵向跳行在 EG4S20 上物理不可行**：顺序 FIFO 无法在流中「回头」取已丢弃的偶数行
⇒ 必须整帧缓存 240 条偶数行 = 76,800 字 = 2,457,600 bit = **267 块 BRAM9K**，
而全片只有 **64 块**（当前位流已用 37 块，只剩 27 块）。**267 是下界，不是估值。**

给审计看的三句：

1. **这不是欠账。** t22 的实质产出已由 t28 承接并落地：清掉 `pix_reader.v` 的 1 行死代码、
   落 `docs/plan_v2/KEY9_RULING.md` 终口径裁定、`TODO(` 门禁 2 → 0（§6）。
2. **这不是「差一点」。** 从最省的算法算起（RGB565、只缓存 120 条源行）仍需 67 块，
   超全片 64 块；按正确口径（32 位一字）是 4.17 倍。三条替代路线已逐条否决（§4）。
3. **失败处置干净。** t22 失败时两个被改文件已还原为原始字节、工作区无半成品残留，
   指纹与 `KEY9_RULING.md §5.1` 的「改前（t22 复原版）」逐字一致（§3.1 / §8.1）。

## §1 需求原样（Key9 第 2 步当初要做什么）

用户需求是「Key9 切换屏幕大小（1/2 到 1，5 档）」。Key9 拆成两步：

| 步骤 | 内容 | 状态 |
|---|---|---|
| 第 1 步 | **横向**：`pix_reader` 消费侧降采样（每字 2 像素，取偶列），窗口外填黑 | 已交付 |
| 第 2 步 | **纵向**：行级 DDA 配额跳行，让非满屏档在纵向也等比 | **本文件结案：物理不可行，定案不做** |

第 2 步立项时的估算（**已作废，仅存作历史**，原文见 `docs/plan_v2/T7_INTEGRATION_PLAN.md:2017-2037`）：

> `pix_reader` 加一个垂直配额累加器，**零 BRAM、零 DSP、约 +40~70 LUT**；
> 关键认识：窗口外那 `640 − win_w` 拍正好用来把下一条源行读出来丢掉，不需要额外带宽。

这个估算的前提是「**窗口外的空拍可以把多余的源行读出来丢掉**」。§3.1 的实测日志证明：
在顺序 FIFO 上这个前提**根本没被用上**（四档 `out_reads=0`），而一旦真要留住数据，
缓存需求就是 §2 的 267 块。

## §2 物理上限算术（第三方可独立复算）

### §2.1 输入常量（全部可从 RTL 与几何直接读出）

| 常量 | 值 | 出处 |
|---|---|---|
| 显示几何 | 640 × 480 | `rtl/top/dmz_eg4s20_hdmi_top.v` 端口与 `ratio_map.v` 档 4 行 |
| 每字像素数 | 2（一字两像素） | `pix_reader.v:259` `WORDS_LINE16 = PIX_PER_LINE / 2`（本体 450 行版） |
| 一条源行字数 | 640 / 2 = **320 字** | 同上 |
| 一帧字数 | 320 × 480 = **153,600 字** | 同上 |
| 每面板行可用拍数 | 640 | 像素时钟与 SDR 时钟比 1:1 下的行有效拍数 |
| 一片 BRAM9K 容量 | 9,216 bit | 1,024 × 9 |
| 全片 BRAM9K | **64 块** | `SmartCampusMedia/reports/t7b_seed_seed7_area.txt:17` `#bram 37 out of 64` |

### §2.2 推导（档 0：窗口 320×240，边长比 1/2）

```
需显示的源行 = 偶数行 0,2,...,478  共 240 条
需丢弃的源行 = 奇数行             共 240 条

顺序 FIFO 的约束：
  帧流是单向的。读到第 k 条源行时，第 k-1 条已经流过去了，不会再来。
  要让「窗口行」拿到它后面那些偶数行，就必须在非窗口行期间
  把整帧读进来并**留住**后面还要用的偶数行。
  ⇒ 240 条偶数行必须同时驻留

需缓存字数 = 240 × 320 = 76,800 字
需缓存位数 = 76,800 × 32 bit = 2,457,600 bit      （32 位一字：RGB888 双像素）
所需 BRAM9K = ceil(2,457,600 / 9,216) = ceil(266.6667) = 267 块
全片可用    = 64 块
倍数        = 267 / 64 = 4.17×
```

### §2.3 三种位宽口径的对照表（堵住「差一点就够」的侥幸）

| 算法 | 位/字 | 需缓存 | BRAM9K | 超 64 的倍数 | 结论 |
|---|---|---|---|---|---|
| **32 位一字（RGB888 双像素，正确口径）** | 32 | 2,457,600 bit | **267 块** | 4.17× | 远超 |
| 16 位一字（RGB565 双像素，常见错算） | 16 | 1,228,800 bit | **134 块** | 2.09× | 仍远超 |
| RGB565 且只存需跳过的行（最乐观假设） | 16 | 614,400 bit | **67 块** | 1.05× | 仍超 64 |

第三行的含义：这是**把假设一路放宽到极限**的结果 —— 位宽砍一半（16 位），
缓存对象再从 240 条砍到 120 条（120 × 320 × 16 = 614,400 bit）。
即便如此仍需 **67 块 > 64 块**。也就是说：**把所有能省的都省掉，还是不够。**

计算式（可复跑）：

```
267 = ceil(2,457,600 / 9,216) = ceil(266.6667) = 267
134 = ceil(1,228,800 / 9,216) = ceil(133.3333) = 134
 67 = ceil(  614,400 / 9,216) = ceil( 66.6667) =  67
```

### §2.4 向上取整说明（不是四舍五入）

三处都**必须向上取整**，因为半块 BRAM 装不下剩余数据。三个商分别是 266.6667 / 133.3333 / 66.6667，
取整后是 267 / 134 / 67。若误用截断取整，会得到 266 / 133 / 66 —— 那正好落在 64 块附近，
**看起来像「差一点」**，这是本条最容易被误算成「可行」的地方。

> 一处已知笔误，本文件不重复其错：`docs/plan_v2/T7_INTEGRATION_PLAN.md:2020` 写「16 位一字也要
> **133 块**」。正确值是 `ceil(133.33) = 134`（`docs/plan_v2/KEY9_RULING.md:65` 与本文件 §2.3 一致）。
> 该文件属本卡 outOfScope，**未改**，此处如实标注。
>
> 该行同处的 267 与 67 两个数**是对的**，只有 134 写成了 133 —— 所以这不是「整句不可用」，
> 而是**一个数字的笔误**。引用那一行时必须改这一个数，不能整段照抄。

### §2.5 267 是下界，不是估值

「只缓存需要的 240 条偶数行」这个前提**本身已经是最优假设** —— 它默认了
「知道哪些行要、且能精确只留这些行」。而顺序 FIFO 实际做不到：

- 它不知道下一帧什么时候来；
- 它不知道用户会不会中途改档（Key9 按键随时可能按下，`ratio_sel` 是运行时可变的寄存器）。

所以真实需求只会 **≥ 267**，不会更少。答辩时若被问「这是不是估保守了」，
答案不是「我再算算」，而是「**这是最省算法的下界，实际只会更多**」。

### §2.6 全片 BRAM 实况（比「全片 64 块」更有力的口径）

| 项目 | 值 | 出处 |
|---|---|---|
| 全片 BRAM9K | 64 | `t7b_seed_seed7_area.txt:17` |
| 最终位流已用 | **37 块（57.81%）** | 同上 |
| 实际剩余 | **27 块** | 64 − 37 |
| 本功能需求 | **267 块** | §2.2 |
| 64 块能装下需求的 | **24.00%** | 64 × 9,216 bit ÷ 32 bit = 18,432 字；18,432 / 76,800 = 24.00% |

（37 块由 cjk16 字库 15 + 波形 2 + narr 字幕 1 + 其余 19 构成；本表只取总数，不展开。）

### §2.7 根因定性（这句是核心，比「带宽」准确）

> **根因是顺序 FIFO 无法在流中「回头」取已被丢弃的偶数行 ⇒ 必须整帧缓存。**
> **不是带宽。** 帧平均只需要 `153,600 / 307,200 = 0.50 字/拍`，现有通路完全够用。

「带宽」这条错误归因必须显式否掉，理由有二：

1. **算术上不成立**：帧平均 0.50 字/拍，而通路按 1.0 字/拍设计，余量一倍；
2. **工程上有害**：把根因归到带宽会引出一个错误结论 ——「那就降分辨率 / 降帧率」。
   而这两个手段对「必须在流中回头」这个结构性障碍**完全无效**：降到什么分辨率，
   缓存需求都随窗口行数同比例变小、随源帧同比例变小，**比值不变**（这正是 §4 方案②被否决的理由）。

## §4 三条被否决的方案（逐条给理由，不只列结论）

### ① 放开 `image_player.v` 的 `.FIFO_AW` / `.LEVEL_HI` —— 否决

- **量级不对**：需求 76,800 字，实测最好只能到 8,000 字，**差 9.6 倍**（76,800 / 8,000）。
- **要动已冻结文件**：`rtl/storage/image_player.v` 在 t20 已冻结（本文件 §8.1 给出当前指纹）。
- **要重跑位流**：当前交付位流 MD5 `59A6BACC75613F5E953B7ED5A33E05E8`，
  且 `Fmax` 余量只有 0.28%（`25.071 MHz` / 需求 25 MHz），重跑风险极高。
- **就算加深也不够**：深 FIFO 下 tier2 仍 `row_bad=30`、tier0 仍有 1 次源行非严格递增
  （三个真问题 F1/F2/F3 未解），说明这条路不是「调个参数」能收尾的。

### ② 降级只做较宽档 —— 否决（安慰剂）

**可行性跟「是否等比」无关：窗口行少，分母（窗口外的空拍数）也同比例变小，比例没变。**

具体说：档 3（560×420）需要跳过的行是 60 条，看着只有档 0（240 条）的四分之一；
但它的面板行总数里可用于补水的空拍也同比例缩到四分之一。
**比值 60/420 = 240/480×... = 恒定**，所以档 3 的可行性和档 0 完全一样 —— 都不行。
这条方案唯一的实际效果是「把问题挪到更小的窗口上，看起来不那么刺眼」，属于安慰剂。

### ③ 改行缓存 —— 否决

与 `pix_reader` 的「零 BRAM 行缓存」模块定位直接冲突（该模块的卖点就是不占 BRAM），
且 267 块 BRAM 物理不存在（全片只有 64 块，见 §2.6）。

## §7 答辩一问一答

**Q1：为什么不干脆让纵向也跟着缩放？**
A：纵向也跟着缩放的话，必须「跳行」，而跳行在顺序 FIFO 上要求整帧缓存 240 条偶数行
= 76,800 字 = 267 块 BRAM9K，而全片只有 64 块（§2）。这是**物理上限**，不是实现难度。
现在的方案是横向等比压缩 + 纵向 1:1 裁剪，画面完整、不丢内容、不拉伸。

**Q2：267 块这个数是怎么来的？会不会估保守了？**
A：`240 × 320 × 32 ÷ 9,216 = 266.67 → 267`。**这是下界，不是估值**：
「只缓存需要的 240 条偶数行」这个前提本身已经是最优假设，而顺序 FIFO 连这个都做不到
（不知道下一帧何时来、不知道用户会不会中途改档），所以真实需求只会更多（§2.5）。

**Q3：那能不能用 RGB565 把缓存砍一半？**
A：能省一半，267 → **134 块**，**还是超 64 一倍多**。把假设一路放宽到极限
（16 位 + 只缓存 120 条）仍需 **67 块 > 64 块**（§2.3）。不是「差一点」，
是从最省的算法算起也差。

**Q4：这是不是一笔待办？以后会不会补上？**
A：**这是定案，不是排期。** 性质是「物理上限约束下的主动取舍」——
判据是 §2 的算术（267 > 64），任何人都能独立复算。
纵向 1:1 裁剪**已经实现且逐像素钉住**（§5.2，五档 `align_bad=0`、`empty=0/307200`），
所以「纵向」这件事并不是空着的，只是采用了裁剪而不是缩放。

**Q5：如果将来换更大的 FPGA 呢？**
A：那就不是「补上」，而是**换平台后重新评估**。在 EG4S20 上这条路的边界是
267 块 BRAM9K，任何「再优化一下」的提法都要先跨过这个数。本文件 §2 的算术
可以直接套到别的器件上（改的只有「全片 64 块」这一项）。

**Q6：我怎么确认这些数字不是编的？**
A：§8 给出六个可复核锚点（路径 + 字节数 + MD5 + 关键行号，行号声明版本），
§2 的算术只需一个计算器，§3.1 的日志是原始 vsim 输出、`FAILED` 行明写 `errors=16`。
重跑路径：`powershell -File sim\scripts\run_storage_regression.ps1 -Suite Pixels -FullVga`
（约 245 s），然后 `Select-String -Path reports\s6_validation\tb_pix_reader_vga.log -Pattern "^# K9Y"`。

> 表述纪律：❌ 四类错误说法（含中性措辞）见 `docs/plan_v2/KEY9_RULING.md §4`（`:120-131`），
> 本文件不复述其原文，以免本文件自身成为措辞污染源。正确表述只有一句：
> **「横向等比压缩 + 纵向 1:1 裁剪，非等比缩小；这是资源约束下的主动选择。」**

                    (16, "16 位 + 只缓存 120 条（最乐观）")):

| `§2.7` 第 2 条末 | 「随窗口行数…、随源帧…」两个「同比例」被写成「等比例」 | 「同比例变小」 | 描述的是**缩放关系**，不是终口径结论；用禁词面会被当成在主张终口径 |
| `§5.3` 表第 3 行 | 误读示例直接用了 W5 词面 | 「所以纵向也缩了，画面会糊」 | 示例词落在禁词表内 = 本文件自身成为污染源 |
| `§7` Q1 设问 | 设问直接用了 W5 词面 | 「为什么不干脆让纵向也跟着缩放？」 | 同上：设问会把禁词当正常说法引入 |
| `§7` Q4 设问 | 设问用了 W1 词面 | 「这是不是一笔待办？」 | W1 无豁免，必须清零 |

> 这条留痕本身就是本卡的判据之一：**禁词表的意义不是让文档里搜不到那几个字，
> 而是让「这个功能是什么性质」在文档里只有一种说法。** 逐字引文与任务卡指定的
> 正确表述必须保留原文（否则引文失真、正确表述不成立），其余位置一律换成同义表述。
