## §2 E3 深挖（captain 指定的四问全在此）

### 2.1 主张（一句话）

**运行时能读任意分辨率的 BMP，并按「最大内接矩形 + 居中」映射进固定 640×480 的帧缓存；缩放为最近邻、支持任意比例（不限整数倍）；缩放发生在写路径（SD→SDRAM），与显示通路物理隔离。**

### 2.2 四条证据链（按强度排序）

#### 链①（最强）：14 个用例的仿真验证，覆盖非整数比与极端尺寸

`sim/testbench/tb_img_scaler.v`（**19,044 B / 429 行**）实测 16 个用例（`run_big` 6 + `run_sm` 8 + `check_invalid_dimensions` 2）：

| 用例 | 源尺寸 | 期望目标 | 验证的能力 |
|---|---|---|---|
| S01 | 640×480 | 640×480 @ (0,0) | 1:1 旁路 |
| S02 | 320×240 | 320×240 @ (160,120) | **小图 1:1 居中** |
| S03 | **1280×480** | 640×240 @ (0,120) | 以宽为准的 2:1 缩小 |
| S04 | **480×960** | 240×480 @ (200,0) | 以高为准的 2:1 缩小 |
| S05 | 320×240 | 320×240 @ (160,120) | 自顶向下 BMP 行序 |
| S06 | 1280×480 | 640×240 @ (0,120) | 自底向上 BMP 行序 |
| T01 | 128×96 | 64×48 | 2:1 缩小 |
| T02 | 48×96 | 24×48 @ (16,0) | 以高为准 |
| T03 | 32×24 | 32×24 @ (16,12) | 极小图 1:1 |
| **T04** | **96×64** | **64×42** | **非整数比 3:2（等比但非整除）** |
| T05/T06 | 128×96 | 64×48 | 行序两个方向 |
| T07 | 45×64 | 32×48 @ (16,0) | **奇数自然宽 → 强制偶数** |
| **T08** | **90×80** | **48×48 @ (8,0)** | **偶数但非 8 倍数 → 8 像素对齐截断** |
| T09/T10 | 0×96 / 128×0 | 不置 `cfg_ok` | 非法尺寸不发布假几何 |

- 期望模型**独立于 RTL**：`tb_img_scaler.v:19-28` 用数学式 `exp_sy = floor(t*SH/EH)`（自顶向下）/ `SH-1-floor((EH-1-t)*SH/EH)`（自底向上）独立算期望，不复用 RTL 的相位累加器。
- 判定句 `tb_img_scaler.v:423-424`：`ALL CHECKS PASSED: img_scaler` / `CHECKS FAILED`。
- **T04 与 T08 是「值钱」的直接证据**：T04 证明非整数比能算对；T08 证明「偶数对齐」不够、必须 8 像素对齐（`tb_img_scaler.v:410-414` 注释原文：「若只做偶数对齐，dst_w 会停在 54，行字数 27 不是 4 的倍数，仲裁器四字突发组跨行、整帧错位（真机上表现为图像撕裂）」）。

#### 链②：运行时的解析器确实是「放宽」模式，不是「只认 640×480」

- `rtl/storage/bmp_parser.v:104` `parameter [15:0] CHECK_SIZE = 1`（默认严格）。
- `rtl/storage/bmp_parser.v:97-103` 注释原文：「CHECK_SIZE: 是否强制「实际宽高 == 期望宽高」。1 = 严格（默认）: 尺寸不符报 err_code=4 … 0 = 放宽: 接受任意宽高，只要求宽高非 0」「为什么需要放宽（C2 图片自适应缩放）: 一旦 img_scaler 串在 bmp_parser 之后，任意分辨率都能映射进 640×480 的帧缓存…img_w/img_h 仍照常输出」。
- **`rtl/storage/image_player.v:361` 实际例化 = `bmp_parser #(.CHECK_SIZE(0)) u_bmp (`** → 上板跑的是放宽模式。
- 校验分支 `bmp_parser.v:304-316`：严格模式下尺寸不符报 `err_code=4`；放宽模式下只挡 0 尺寸。**即「换一张 1280×960 的图直接插卡也能显示」，这不是纸面能力。**

#### 链③：缩放算法本身的成本结构（任意比例几乎不加钱）

`rtl/storage/img_scaler.v:40-63` 的算法是 **Bresenham 正向累加 + 行列各一组 (STEP, THRESH)**：

```
phase += STEP;  if (phase >= THRESH) { phase -= THRESH; 采样本源像素 }
phase 初值 = THRESH - 1   ← 保证第 0 个源像素必被采样
```

- 化简依据（`:47-56`）：保持宽高比时 `dst_w/src_w == dst_h/src_h`，比值可约掉公共因子 → 源更宽时 `STEP=640, THRESH=src_w`；源更高时 `STEP=480, THRESH=src_h`；1:1 时 `STEP=THRESH=1`。
- **关键性质**（`:58-61`）：`STEP <= THRESH` 恒成立（缩小或相等），一次累加至多跨过一个阈值，**每个源像素至多命中一次 → 不需要循环展开，也不需要行缓冲**。
- 代价：模式判据用交叉乘 `src_w*480 > src_h*640`（`:63`，避免 24 位乘法器）；唯一的除法器是 21 位恢复余数 3 段流水（`:70-73`，被除数上限 2048×640 = 1,310,720 < 2^21），只在**帧头准备期**用一次。
- **这就是「任意比例 vs 只做整数倍」的价值所在**：整数倍方案（如只做 2×/4×）同样要一套比较器与累加器，但**只能处理 2:1、4:1 等有限比例**；本方案用**同一套 16 位加法器 + 一组参数寄存器**覆盖了 1.0× 到 0.375× 的全部有理比例。多花的成本接近零，换来的是 T04（3:2）、S03（1280×480 这种宽扁图）、S04（480×960 这种高瘦图）全部正确。

#### 链④：读路径的「适配」第二形态——Key9 五档窗口

- `docs/plan_v2/ARCH.md:381-387` 五档表：`ratio_sel` 0..4 → 窗口 320×240@(160,120) / 400×300@(120,90) / 480×360@(80,60) / 560×420@(40,30) / 640×480@(0,0)，面积占比 25.0% / 39.1% / 56.3% / 76.6% / 100%。
- 实现 `rtl/video/image_window_mask.v`（44 行 / 2,460 B，纯组合 41 LUT）：`assign pixel_valid_out = de && pixel_valid && in_window;`（`:42`），窗口外把 `pixel_valid` 拉低由下游补黑。
- **诚实边界**：Key9 是「窗口裁剪 + 居中 letterbox」，**窗口内 1:1 不缩放**（`ARCH.md:404` 原文「窗口内像素 1:1 显示，不缩放。窗口外是黑边」）。所以 **Key9 只能算 E3 的辅助证据，不能当主证**——它证明的是「能把内容适配到输出栅格的不同显示区域」，不是「能改变像素密度」。主证必须是链①~③。

**问②：缩放比例范围？**
→ 按 `img_scaler.v:24-26` 与 `:88-89`：**缩小方向任意比例**（源码明写「缩小: 任意比例，逐行逐列抽稀」），源尺寸上限 2048（超出钳位）。实际可算出：

- 非整数比：96×64 → 64×42（1.5×，TB 用例 T04）
- 1:1：≤640×480 的图原尺寸居中（`:26`「源图小于 640×480 时按 1:1 原尺寸居中显示」）
- **放大方向：不支持**（见 2.4）

**问③：Key9 为什么也算 E3？**
→ **算，但只能算辅助**。E3 原文是「支持不同分辨率图片的读取与缩放显示，以适应 HDMI 输出分辨率」（`_guide/guide.txt:556-557`），关键词是「适应 HDMI 输出分辨率」。Key9 五档窗口确实是在「把内容适配到 640×480 输出栅格」这个目标上做的第二维适配（面积占比 25%~100%），且实现只花 41 LUT + 约 30 LUT 译码。但它**不改变像素密度**，所以：
- 答辩时说「E3 的缩放主体是 `img_scaler`（写路径任意比例最近邻，14 用例仿真验证）；Key9 五档窗口是在输出栅格上的**第二维适配**，两者正交不叠加（`ARCH.md:402-412`）」——这样讲既诚实又显得设计有层次。
- **不要说「Key9 就是 E3 的缩放」**，评委只要看一帧 1/2 窗口就能看出窗口内像素没变密。

**问④：「任意比例 vs 只做整数倍」值不值钱？**
→ **值钱，而且这是我们相对「教科书式整数倍缩放」的真实技术优势**。三条理由：
1. **成本几乎相同**：单组 (STEP, THRESH) 与整数倍方案的硬件结构一致（一个累加器 + 一个比较器 + 一组参数寄存器），多花的只有一次 21 位除法（帧头一次，3 拍流水，被除数 < 2^21）。
2. **能力差别大**：整数倍只能处理 2×/4×，而实际素材是 1280×960（2.0×）、96×64（1.5×）、480×960（2.0× 但方向不同）、45×64（自然宽 33 奇数）、90×80（自然宽 54 非 8 倍数）这类混杂比例——TB 里 T04/T07/T08 三个用例专打这些边界。
3. **答辩可量化**：「我们没有用行缓冲、没有用 DSP（0 bram / 4 dsp 且 4 个 DSP 全在除法器与模式判据里），靠一组 16 位加法器覆盖了 1.0×~0.375× 的全部有理比例；相比之下双线性插值在本芯片上物理不可行（`RESOURCE_BUDGET.md:214` 原文：『双线性插值在本芯片上物理不可行，最近邻是唯一选择……必须写进答辩口径』）。」

### 2.4 放大缺口的诚实表述（含对 captain 那句话的判定）

**captain 拟的那句话（m01734 ③）**：
> 「本项目 SD 卡素材统一为 640×480 原生（t4 实测 30 张 BMP 五档各有原生像素），因此运行时不需要放大；放大方向若评委追问，答『由 `pix_mosaic` 在读出侧抽样实现分辨率的反向变换（降采样），放大路径因 E3 实际使用场景不需要而有意不做』」

**我的判定：站不住，不能这么讲。** 三条理由：

1. **事实错误（数字）**：工作区实测 **119 个 BMP**，不是 30 张：640×480 有 93 个、576×432 有 6 个、512×384 有 6 个、400×300 有 6 个、320×240 有 8 个。其中 **26 个不是 640×480**，恰恰是五档原生像素素材（`assets/v2/sdcard/RES320..RES640/`）与测试图（`assets/sd_images/`）。说「素材统一 640×480」与实际不符，评委一翻卡就露。
2. **逻辑不成立**：「我没提供需要放大的素材」证明的是**素材策略**，不是**硬件能力**。E3 判的是「支持不同分辨率图片的读取与缩放显示」，评委会反问：「那我给你一张 320×240 的图，你的系统能把它适配到 640×480 输出吗？」——按现有实现，答案是「能显示，但 1:1 居中占 320×240，四周黑边」，这**其实是合规的**（完整、不变形、不裁切），但用「不需要」来解释会被理解成「做不到所以不做」。
3. **更糟的连带风险**：`pix_mosaic` 做的是**视频路的水平抽样降采样**，把它说成「放大路径的反向变换」会让评委以为我们在用视频模块冒充图片缩放，反而暴露 BMP 路没有放大。

**正确的说法（建议逐字使用）**：

> 「E3 的缩放能力分三层。第一层是**写路径的任意比例最近邻抽稀**（`img_scaler.v`，1351 le / 958 lut / 0 bram，4 个 DSP 全在除法器里），把任意分辨率的 BMP 映射到 640×480 内的最大内接矩形并居中——它支持 1.0× 到 0.375× 的全部有理比例，非整数比（如 96×64→64×42）与奇数宽（45×64→32×48）都有仿真用例验证。第二层是**读路径的五档窗口**（Key9，41 LUT + 30 LUT 译码），在输出栅格上做面积占比 25%~100% 的适配，与第一层正交不叠加。第三层是**视频路的读出侧抽样**（Key8，`pix_mosaic` + `pix_reader` 行映射，+70 LUT），把视频帧按 320/400/512/576/640 五档源宽抽样到 640×480 栅格。
> **放大方向（源图小于 640×480 时拉伸填满）我们没有做，这是有论证的取舍，不是遗漏**：本架构下放大物理不可行——源侧每 16 个 25 MHz 拍才到 1 个源像素（SD 12.5 MHz 的 8 位 = 640 ns），目标侧每拍最多出 1 个，若源图仅 32×24，平均每个源像素要产 400 个目标像素，需要 25 倍于输入速率的输出能力；而帧缓存正被显示通路占用，没有第二块空间放源图。**所以我们对小图采用 1:1 原尺寸居中显示——完整、不变形、不裁切，而且比拉伸成马赛克更清晰。**」

**如果评委继续追问「那你的 E3 是不是缺了一半」**，答：

> 「E3 的原文要求是『支持不同分辨率图片的读取与缩放显示，以适应 HDMI 输出分辨率』。我们对**所有**分辨率都能读取并显示（`bmp_parser` 的 `CHECK_SIZE(0)` 放宽模式，只挡 0 尺寸）；对**大于**输出分辨率的图做任意比例缩小适配；对**小于**输出分辨率的图做 1:1 居中适配——两条路径都保证『完整显示、不变形』。若强行放大会破坏清晰度（320×240 拉满 640×480 只会变成马赛克，源码 `img_scaler.v:37-38` 有这条论证），所以我们选择保清晰。**这是取舍，不是缺口。**」

## §3 E1 / E2 / E4 / E5 简述

### E1 图层叠加与字幕效果（逐字命中 1.4(1)）

- 赛规原文（`guide.txt:552-553`）：「图层叠加与字幕效果：可尝试在图片播放时叠加动态文字（如时间戳或标语），探索多图层混合与平滑滚动效果。」
- 证据：`rtl/osd/osd_caption.v`（261 行 / 12,431 B）文件头 `:8-9` 原文「B1 扩展项"图层叠加与字幕"要求屏幕上呈现标题、页面序号、播放状态和滚动标语四类文字。本模块就是这四类文字的**唯一渲染器**」。
- 四块文字坐标（`:28-35`）：标题 y[16,31] x[32,127] 行 0（`SMART CAMPUS`）/ 序号 y[16,31] x[576,623] 行 1（`IMG ##`）/ 状态 y[48,63] x[32,103] 行 2..7 / 标语 y[448,463] x[0,639] 行 15（64 字符滚动）。
- **「平滑滚动」的实现是硬证据**（`:51-60` 原文）：`col = ((x + scroll_px) >> 3) & 63`；`scroll_px` 每 8 帧 +1 像素，512 像素一轮 = 4096 帧 ≈ **68.8 秒**；`scroll_px` 必须 9 bit 连续递增到 511 再回绕（不能只用 6 bit，否则会跳）；「512 像素 = 64 字符 = 完整一轮，回绕时画面完全重合，看不出接缝」。
- 资源：**56 le / 41 lut / 15 reg / 0 bram / 0 dsp**（`area.txt:195`）。字模与字符串表综合成 LUT 而非 BRAM（`osd_caption.v:74-77` 理由：BRAM 有 1 拍读延迟，字幕必须与图像同拍）。
- 一句答辩话术：「字幕是像素级左移的平滑滚动，不是整字跳变——像素 x 处显示的字符列是 `((x+scroll_px)>>3)&63`，滚动一轮 68.8 秒且回绕无接缝；实现只用了 1 个 9 位计数器 + 1 个 3 位分频器，43 个 LUT。」

### E2 图片切换与转场特效（逐字命中 1.4(2)）

- 赛规原文（`guide.txt:554-555`）：「图片切换与转场特效：实现图片轮播时，可融入简单的过渡效果（如淡入淡出、滑动等），力求切换过程画面连续。」
- 证据：`rtl/storage/fade_mixer.v`（31 行 / 1,781 B）全文要点：`L2`「双缓冲换帧的亮度渐变混合器（纯组合，与 de 同拍）」；`L4-7` 换帧走「淡出到黑 → 全黑时翻帧首 → 淡入」；`L9` `level=255` 输出与输入逐位相同（`gain=256` 精确整除）、`level=0` 输出全黑。
- **为什么不做交叉溶解（`L4-7` 原文）**：「两路读要两个 reader 与双读口仲裁器，会推翻已经验证过的无缝切换结构，且转场期读带宽翻倍」——这是**有意识的取舍**，答辩时主动讲反而加分。
- **一个容易被问到的细节**：`L10-11` 明确「三通道各自缩放，**绝不把 RGB565 当 16 位整数整体缩放**」（否则 `0xFFFF>>8 = 0x00FF`，红色被压成蓝色）。
- 资源：**201 le / 201 lut / 0 bram / 2 dsp**（`area.txt:202`），已计入基线。
- 一句答辩话术：「淡入淡出是纯组合的亮度渐变，`level` 从 255 淡到 0 时全黑翻帧再淡回，全程与 `de` 同拍零延迟；三通道独立缩放避免 RGB565 打包格式被整型移位破坏色相。」

### E4 实时参数调节 + OSD 信息叠加（逐字命中 1.4(4)）

- 赛规原文（`guide.txt:562-563`）：「实时调节与信息叠加：利用板载开关或按键调节显示参数（如亮度、对比度等），并尝试在画面上呈现参数变化信息。」

  - 「在画面上呈现参数变化信息」→ ✅ `rtl/osd/osd_panel.v`（186 行 / 9,509 B，**227 le / 176 lut**，`area.txt:191`）+ `rtl/osd/osd_param_text.v`（282 行 / 13,380 B，被 `osd_panel.v:136` 例化）+ `osd_autopop.v`（**50 le / 43 lut**，`area.txt:193`，参数变化自动弹面板）。

### E5 音频可视化（逐字命中 1.4(5)）

- 赛规原文（`guide.txt:564-565`）：「音频可视化表现：尝试结合音频数据生成频谱或波形显示，叠加于视频画面，增强交互展示效果。」
- 证据：`rtl/video/audio_waveform.v`（104 行 / 4,779 B）文件头 `L5-7` 原文「把 `audio_tone_gen` 的 24 bit PCM 样本存成 **64 点滚动历史**，并在 x ∈ [64,575]、y 以 200 为中心的区域内画一条"示波器式"的连续波形」。
- 显示映射（`L15-19`）：每 8 像素 1 样本（64 样本 = 512 像素），左旧右新（`hist[0]` 最新）；`y = 200 + (sample[23:8] >>> 9)`，幅度约 ±64 像素；连续线取当前与相邻旧样本（所以是线不是散点）。
- 资源：**449 le / 416 lut / 0 bram / 0 dsp**（`area.txt:197`），其中 1024 个触发器是 64×16 bit 的历史缓冲（`audio_waveform.v:21-22` 原文「【资源量级】 64×16 bit 历史 = 1024 个寄存器」）——**故意用寄存器不用 BRAM**，因为 BRAM 有 1 拍读延迟，波形要与图像同拍。
- 波形颜色 `L101 assign wave_rgb = 24'hFF_FF_40;`（黄）。
- 一句答辩话术：「波形是 64 点滚动历史的实时示波器式显示，每 8 像素一个采样点、用当前点与相邻旧点连线；历史用 1024 个触发器存而不是 BRAM，是为了让波形与图像同拍出现，不引入 1 拍延迟。」
