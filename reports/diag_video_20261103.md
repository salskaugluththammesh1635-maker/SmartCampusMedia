## 2. 现象①：日常模式图片像素位置偏移

### 2.1 先确认"用户看到的是哪一档"

复位值（`rtl/control/key_router.v`）：

```
:157   res_sel   <= SEL5_MAX;   // 复位 640×480 原生档（无放大，路径最短）
:158   ratio_sel <= SEL5_MAX;   // 复位满屏
:131   localparam [2:0] SEL5_MAX = 3'd4;
```

两条通路在默认档的行为：

**Key8 = 4 → `res_src_w = 640`**（`rtl/top/dmz_eg4s20_hdmi_top.v:686-695`）
→ `pix_mosaic` 的 `src_w = 640` → `take = (active_x==0) || (x_acc >= 640)`，`x_acc` 每拍 +640 后必然 ≥640 → **`take` 恒真 → `rgb565_out = rgb565_in`，恒等旁路**（`rtl/video/pix_mosaic.v:115-122`）。不引入偏移。

**Key9 = 4 → `ratio_map` 输出 640×480@(0,0)**（`rtl/video/ratio_map.v:88-93`）
→ `pix_reader`：`h_ident = (win_w>=640) && (win_off_x==0)` = 1 → `use_key9 = !h_ident && !win_bad` = 0
→ `out_valid = use_key9 ? h_pop : pix_valid_raw` 走**老通路**（`rtl/storage/pix_reader.v:265-268/185-186`）。逐拍等价于改造前，不引入偏移。
→ `image_window_mask`：`in_window` 对 x∈[0,640)、y∈[0,480) **恒真**，`pixel_valid_out = de && pixel_valid`（`rtl/video/image_window_mask.v:40-42`）。等于放行全部。

**⇒ 判据（上板可读）**：OSD 面板第 1 行显示 `B:x V:x R:4 P:4`。
`R` 是 Key8 档、`P` 是 Key9 档，来自 `rtl/osd/osd_param_text.v:290-291`（`5'd10: dec_char(res_sel)`、`5'd14: dec_char(ratio_sel)`），面板列位置见 `:54`（COLS=22，PANEL_X1=631）。**默认态字符串应为 `"B:0 V:6 R:4 P:4"`（`osd_param_text.v:66`）**。
若 R 或 P 不是 4，说明用户按过键，先按回 4 再判。

### 2.2 排除候选 (b) pix_mosaic 与 (c) ratio_map

两者都在默认档被上一条排除：
- (b) `src_w=640` 时 `take` 恒真，是**组合旁路**（`assign rgb565_out = take ? rgb565_in : hold;`，`pix_mosaic.v:117`）。文件头 `:21-33` 已记录：若误写成时序 `rgb565_out <= take ? ...` 会整体左移 1 像素。当前代码是组合，且 `valid_out = valid_in` 零延迟（`:122`）。
- (c) 默认档 `win=640×480@(0,0)`，`h_ident=1`、`in_window` 恒真。ratio_map 四输出同拍更新（`ratio_map.v:58-60` 注释），不存在"窗口画在哪"与"从哪儿取像素"两处不同源的问题（两处都接 `k9_win_*`，见 `top:649-650` 与 `top:743-744`）。

### 2.3 候选 (a) 8 像素对齐：算术完整推导

代码（`rtl/storage/img_scaler.v`）：

```verilog
:183  sq_w8 = (src_w_r[15:3]==13'd0) ? {src_w_r[15:1],1'b0}   // 宽 <8 时取偶
                                       : {src_w_r[15:3],3'b000}; // 否则向下取 8 的倍数
:185  sq_off = ((DSTW - sq_w8) >> 1) & 16'hFFF8;   // DSTW=640
```

1:1 落地（`:370-390`）：`out_w<=sq_w8; out_off_x<=sq_off; out_off_y<=(DSTH-src_h_r)>>1;`
像素输出（`:515-520`）：`dst_x <= out_off_x + col_eff;`

1:1 档 `c_step=c_thr=1` ⇒ `col_hit` 恒真 ⇒ `col_eff` 逐源像素 +1
⇒ **`dst_x = out_off_x + 源列号`，误差与列号无关，恒为 `out_off_x − 真实居中值`**。

真实居中值（理想）= `(640 − src_w)/2`。

**已发运 5 档逐个算**：

| 素材档 | src_w × src_h | sq_w8 | `(640−sq_w8)>>1` | `&0xFFF8` 后 = out_off_x | 真实居中 | **dX** | 丢列 |
|---|---|---|---|---|---|---|---|
| RES640 / BURN640 | 640×480 | 640 | 0 | **0** | 0 | **0** | 0 |
| RES576 | 576×432 | 576 | 32 | **32** | 32 | **0** | 0 |
| RES512 | 512×384 | 512 | 64 | **64** | 64 | **0** | 0 |
| RES400 | 400×300 | 400 | 120 | **120** | 120 | **0** | 0 |
| RES320 | 320×240 | 320 | 160 | **160** | 160 | **0** | 0 |

**⇒ 5 档素材的宽全部是 8 的倍数，`sq_w8 == src_w`，`out_off_x` 恰好等于真实居中值，对齐损失为 0。候选 (a) 在现有素材上不产生任何偏移。**

**反例（证明该路径确实会错，但不是当前现象）**：

| 情形 | src_w | sq_w8 | out_off_x | 真实居中 | **dX** | 丢列 |
|---|---|---|---|---|---|---|
| W%16==8 | 616 | 616 | `12&0xFFF8`=**8** | 12 | **−4**（整幅左移 4） | 0 |
| 非 8 倍数 | 500 | 496 | `72&0xFFF8`=72 | 70 | **+2**（右移 2） | **4** |
| 非 8 倍数 | 502 | 496 | 72 | 69 | +3 | 6 |
| 非 8 倍数 | 639 | 632 | 0 | 0.5 | −0.5 | **7** |

**垂直方向不对称**：`out_off_y = (480 − src_h) >> 1`，**没有 `&0xFFF8`**，所以纵向恒精确（RES320 → 120、RES400 → 90、RES512 → 48、RES576 → 24）。
这个不对称是 `c2_scaler_2026-10-30.md` §4 那个"四字突发组"陷阱的直接后果：`out_off_x/2` 是行首**字**地址，必须落 4 字边界；`out_off_y` 不参与寻址，所以不用对齐。理由原文在 `img_scaler.v:259-268`。

### 2.5 真正的根因：letterbox 区无人屏蔽 ⇒ 旧帧残影被读成"偏移"

`img_scaler` 的设计契约（文件头 `:88-96 §六-3`）：

> letterbox 区域本模块**不写**——它留在帧缓存里是上一张图的旧数据，**必须由顶层按 `out_w/out_h/out_off_x/out_off_y` 屏蔽成黑**，否则会看到残影。

`ARCHITECTURE.md:151` 写的是同一件事：

> 黑边（letterbox）区域 `img_scaler` **不写**——它留在帧缓存里是上一张图的旧数据，必须由 `image_window_mask` 在送显前按 `out_w/out_h/out_off_x/out_off_y` 屏蔽成黑，否则会看到残影。

**但出货代码已经不是这样了**：

```verilog
// rtl/top/dmz_eg4s20_hdmi_top.v
:641    .out_w(), .out_h(), .out_off_x(), .out_off_y(),     // ← 四个端口空连接
:743    image_window_mask u_image_mask (
:743-744    .win_w(k9_win_w), .win_h(k9_win_h), .win_off_x(k9_win_off_x), .win_off_y(k9_win_off_y),
```

顶层自己的注释（`:636-640`、`:738-742`）承认这是 t7-B 的**有意语义变更**："原来是每张 BMP 按自身尺寸居中 letterbox，现在是 Key9 五档固定窗口"。

**后果链**：

1. `img_scaler` 对非 640×480 的源图只写居中窗口内的像素（`dst_x ∈ [out_off_x, out_off_x+out_w)`）；
2. 窗口外**不写**，帧缓存那里是**上一帧的旧内容**（全设计没有任何清屏逻辑：`rtl/storage/*.v` 搜 `clear|zero_fill|memset|fill_` 只命中两处注释，见 `fat32_reader.v:344`、`rle_decoder.v:510`）；
3. `image_window_mask` 现在只看 `k9_win_*`；默认 Key9=4 时窗口=全屏 ⇒ `in_window` **恒真** ⇒ 窗口外像素**原样放行**；
4. 屏幕上于是看到：中间是新图，四周是**上一张图的边缘/上一张图的残留**。

用户描述的"像素位置有偏移"，与"四周露出上一张图的错位内容"在视觉上是同一件事——尤其当上一张是 640×480、下一张是 512×384 时，四周露出的正是上一张图被"裁掉"的那圈内容。

**这条链同时解释了为什么仿真全绿**：`sim/testbench/tb_image_player.v:97-104` 把 `image_window_mask` 例化成 `.win_w(out_w), .win_h(out_h), .win_off_x(out_off_x), .win_off_y(out_off_y)`——**TB 验证的是旧接线**。TB 的两条关键断言 `chk(shown_valid===1'b0,"letterbox area is masked black")`（`:290`）与 `chk(shown_valid===1'b1,"window pixel survives the letterbox mask")`（`:279`）在出货配置下**前提不成立**，属于"验证了一个已不存在的电路"。

**检查器也没兜住**：`scripts/check_port_names.py:261` 确实把 `'out_w','out_h','out_off_x','out_off_y'` 列进了 `EXPECTED_EMPTY` 白名单（`:229 EXPECTED_EMPTY = {`、`:248 'u_player': {`）。所以四根空连接是**被批准**的，检查器不会报——但它只检查"名字对不对、是不是空括号"，**检查不了"语义被换掉"**。

### 2.6 现象①的完整归因树

```
日常模式，图片位置不对
├─ Key8≠4 或 Key9≠4？
│   └─ 是 → pix_mosaic 列抽样 / ratio_map 窗口，见 §3；先按回 4 再判
└─ Key8=4 且 Key9=4（默认）
    ├─ 源图 = 640×480 → 理论上零偏移零黑边（§2.3 第一行）
    │   └─ 若此时仍偏移 → 只剩"帧缓存写入错位"一类，见 ONBOARD_RISK_MAP §2.4/§2.6
    └─ 源图 < 640×480 → 1:1 居中
        ├─ 水平误差 = out_off_x − 真居中 = 0（现有 5 档，§2.3）
        ├─ 垂直误差 = 0（无对齐掩码）
        └─ 但窗口外无人屏蔽 → 旧帧残影 → 视觉上"位置不对"（§2.5）★ 最可能
```

## 3. 现象②：自适应缩放时出现一堆黑边

### 3.1 黑边不是素材里的

用 `System.IO` 逐档读 BMP，扫描中心行/列向内的连续 `0x000000` 像素数：

| 素材档 | 尺寸 | 文件大小 | 上 / 下 / 左 / 右 纯黑像素 |
|---|---|---|---|
| BURN640 | 640×480 | 921654 B | **0 / 0 / 0 / 0** |
| RES640 | 640×480 | 921654 B | **0 / 0 / 0 / 0** |
| RES576 | 576×432 | 746550 B | **0 / 0 / 0 / 0** |
| RES512 | 512×384 | 589878 B | **0 / 0 / 0 / 0** |
| RES400 | 400×300 | 360054 B | **0 / 0 / 0 / 0** |
| RES320 | 320×240 | 230454 B | **0 / 0 / 0 / 0** |

全部 `bpp=24`、`comp=0 (BI_RGB)`、`dataoff=54`、高为正（bottom-up）。
**⇒ 素材本身没有黑边。屏幕上的黑边 100% 来自 RTL 的窗口/letterbox 逻辑。**

### 3.2 黑边也不是 `img_scaler` 画上去的

`img_scaler` 的输出只有一条：`dst_valid` 拍上的 `dst_rgb565`（`:515-520`）。它**没有"输出黑色"的分支**——窗口外根本不产生有效拍。所以"黑"不是它画的，而是"没人写"。

### 3.3 黑边的三个来源，以及如何区分

| 来源 | 触发条件 | 黑边形态 | 面积（分母 640×480=307200） |
|---|---|---|---|
| **A. img_scaler 1:1 letterbox** | 源图 < 640×480 且 Key8=4/Key9=4 | 四周固定、宽度随源图尺寸变化 | RES576 **19.00%**（左右各 32、上下各 24）；RES512 **36.00%**（64/48）；RES400 **60.94%**（120/90）；RES320 **75.00%**（160/120） |
| **B. ratio_map 窗口（Key9）** | 用户按过 Key9 | 四周固定、只跟档位有关 | P0 320×240 → **75.00%**；P1 400×300 → **60.94%**；P2 480×360 → **43.75%**；P3 560×420 → **23.44%**；P4 640×480 → **0.00%** |
| **C. 跨分辨率切换暂态** | 切图瞬间（新 BMP 头已到、前台还没翻帧） | 只闪一下，稳态消失 | 取决于前后两张的尺寸差 |

`ratio_map` 五档全部满足 `2*off_x + win_w == 640`、`2*off_y + win_h == 480`（`rtl/video/ratio_map.v:63-100`），所以 B 类黑边是**严格对称**的。

**关键区分**：A 与 B 的黑边面积可能相同（RES320 与 Key9-P0 都是 75%），但**内容不同**：
- A 类：黑边区内是**旧帧残影**（§2.5），不是纯黑；
- B 类：黑边区内同样是旧帧残影——因为 `image_window_mask` 只屏蔽窗口外，而窗口外从不被写。

**⇒ 无论 A 还是 B，"黑边"区域在稳态下都不是干净的黑，而是上一帧的残留。** 这正是用户说"黑边碍事"的实质。

### 3.4 为什么"自适应缩放"这个说法值得注意

`img_scaler` **只缩不放**（`shrink = (sw_cl>640)||(sh_cl>480)`，`img_scaler.v:159`）。当前 6 档素材最大 640×480，**没有任何一张会触发 `shrink`**——所以"自适应缩放"实际上从未真正缩小过任何东西，用户看到的全部是 1:1 居中。

真正的"缩放"只发生在两个地方：
- `pix_mosaic` 的列抽样（Key8 < 4）：横向隔点抽取，`src_w=320` 时输出 `in[0],in[0],in[2],in[2],...`（`pix_mosaic.v:59-62`）——**不产生黑边，只产生水平分辨率减半 + 每列重复**；
- `ratio_map` 的窗口（Key9 < 4）：**纵向是裁剪不是缩放**（`pix_reader.v:65/67` 端口注释："只参与满屏判据；纵向 1:1 裁剪，不缩放"；`ONBOARD_RISK_MAP.md` 步骤 6 同样口径）。

**⇒ 用户说"自适应缩放时出现黑边"，实际发生的更可能是：按了 Key9（窗口变小 → 四周黑），或放了小图（1:1 居中 → 四周黑）。两者都会露出旧帧残影。**

### 5.3 P2 · 不建议（附理由，供决策留痕）

#### P2-1　RTL 真放大（让中等图铺满）

**结论：纵向不可行，横向可行但无实用价值。**

**(a) 纵向放大为什么不可行**

`img_scaler` 的输出是"1 拍 1 像素"的流，直接进 `img_loader` 拼字、进 FIFO、进帧缓存。要纵向放大 N 倍，同一源行必须被输出 N 次——但源像素是**从 SD 卡按顺序流进来的**（`sd_spi_ctrl.v:37 SCK_FAST_DIV=1` ⇒ SCK=12.5 MHz ⇒ 一字节 640 ns = **16 个 25 MHz 拍**）。要重发同一行，必须先把那一行缓存起来。

- 行缓冲：640 像素 × 16 bit = 1280 B ≈ 1.25 个 M9K。**BRAM 有余量**（37/64 已用，剩 27 个）。
- 但放大 N 倍需要**输出速率 ≥ N × 输入速率**。输入速率 = 1 像素/16 拍，输出上限 = 1 像素/拍 ⇒ 理论上可放大 16 倍。**所以速率不是瓶颈，缓冲也不是。**

真正的瓶颈是**架构契约**：`img_scaler.v:28-38` 与 `ARCHITECTURE.md:135` 的论证针对的是"边读 SD 边放大"这一条路径，其结论（"400 倍"/"25 倍"）**只在这个前提下成立**。若改成"先整图缓存再重扫"，速率论证失效，但要新增：
- 一整块源图缓存（SDRAM 空闲约 7.3 MB，`MEM_WORDS=262144` 字 × 双缓冲 153600 字，2M 字总容量用了 14.6% —— **容量够**）；
- 一次"写源图 → 读回重扫 → 写前台帧"的完整状态机；
- 仲裁器的**第三个端口**（现在只有写侧 + 读侧）；
- 反压通路（`img_scaler` 现在**没有反压端口**，`img_scaler.v:88-96 §六-4`："无反压端口，输出恒 1 拍 1 像素"）。

- **资源**：LUT 剩 3186（16.26%）、DSP 剩 5、BRAM 剩 27。新增状态机 + 第三端口 + 行缓冲，**LUT 余量非常紧**。
- **是否需重跑综合**：**必须**，且**不保证收敛**（当前最差路径 slack 仅 0.113 ns）。
- **风险**：高。这是"重做一个子系统"，不是"改一行"。

**(b) 横向放大为什么"可行但没用"**

`pix_mosaic` 已经在做横向重采样（`p_i = ceil(i*640/src_w)`，`pix_mosaic.v:47-52`），改个方向就能放大。但现有 6 档素材全是 **4:3**（640×480、576×432、512×384、400×300、320×240），横向放大 2 倍而纵向不动 ⇒ **画面被拉扁成 8:3**，比黑边更糟。除非纵向也能放大，而纵向不行（见上）。

**⇒ 结论：在"单次顺序读 + 无行缓冲"的现状下，让中等尺寸图铺满只有两条路——换素材（P1-1），或重做装载通路（P2-1，高风险）。**

#### P2-2　改 `bmp_parser` 的 `CHECK_SIZE`

**已经是 0**：`image_player.v:436-441` 例化为 `bmp_parser #(.CHECK_SIZE(0))`。`bmp_parser.v:309-310` 在 `CHECK_SIZE==0` 时只挡 0 尺寸，任意分辨率都通过。**没有可改的东西**——这条线索可以关闭。

## 8. 不确定性与待确认项

1. **用户卡上实际是哪一档素材——未知。** 这是 §6 判据 1 要解决的第一个问题，也是整份报告最重要的分叉点。MANIFEST 说烧 BURN640，但实际是否照做无法从代码判断。
