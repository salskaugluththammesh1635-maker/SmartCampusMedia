# C2 图片自适应缩放（2026-10-30）

> 结论：图片自适应缩放已实现，通过模块级 161 条检查 + 变异测试 11/11 全捕获、
> letterbox 屏蔽器 20 条、整链路四档回归（8,270 / 8,263 / 1,228,817 / 缩放 1,811 条）、
> `bmp_parser` 37 条回归，lint 与 TD 综合布线全通过
> （setup +1.935 ns / hold +0.003 ns，bitgen 成功）。
> **验证档位：仿真 + 综合布线；未上板。**

## 1. 问题

在此之前，整条链路只接受 **640×480、24 bit、无压缩** 的 BMP：`bmp_parser`
在 `ST_VALIDATE` 里用 `img_w != cap_w || hdr_abs_h != cap_h` 直接报 `err_code=4`，
上层转成错误码 `b2`。任何其他分辨率的图片都进不了帧缓存。

帧缓存本身不能改：一帧固定 640×480 = 307,200 像素 = 153,600 个 32 bit 字
（`ARCHITECTURE.md:162-166`），双缓冲占 2×153,600 字，而 `video_timing_gen`
的 `H_ACTIVE/V_ACTIVE` 也是 640/480。所以缩放必须在**写入帧缓存之前**完成。

## 2. 为什么只做缩小

放大做不到，原因有两个，都是硬约束：

1. **速率**。SD 卡以 12.5 MHz 出字节（`sd_spi_ctrl.v:36-37`，`SCK_FAST_DIV=1`），
   一个字节 640 ns = 16 个 25 MHz 拍，即**每 16 拍才到 1 个源像素**。把 32×24 的图
   放大到 640×480 需要每 16 拍输出 400 个像素，输入带宽根本不够。
2. **缓冲**。放大需要行缓冲（同一源行要重复输出多次），而帧缓存被显示通路独占，
   没有第二块空间放源图副本。

因此策略是：**源图大于 640×480 时按比例缩小并居中；小于时 1:1 居中**（小图不放大，
不失真，也不引入插值模糊）。

## 3. 结构

```
bmp_parser ──hdr_ok──▶ img_scaler ──dst_valid/dst_rgb565/dst_x/dst_y──▶ img_loader
     │  img_w/img_h ──────┘                    │                        │
     │  pix_valid/pix_rgb565/pix_y             │ out_w/out_h/           │
     └──────────────────────────────────────────┘ off_x/off_y/pixels    ▼
                                                                   image_player
                                                                  （写帧缓存）
                                                                        │
                                                                        ▼
                                                          image_window_mask
                                                          （送显前屏蔽黑边）
```

### 3.1 `img_scaler`（新增，`rtl/storage/img_scaler.v`）

Bresenham 抽稀，**行列各用一组 (STEP, THRESH)**：

- 行：`(r_step, r_thr) = (dst_h, src_h)`
- 列：`(c_step, c_thr) = (dst_w, src_w)`

第 m 次命中恰在源索引 `floor(m * thr / step)`，与最近邻采样模型精确一致。
因为 `STEP <= THRESH` 恒成立，一个源像素至多命中一次，主通路**无循环、无除法器**。

相位初值取 `THRESH-1`，保证每行/每帧第 0 个源像素必被采样。

目标尺寸只在帧头算一次，用 21 位恢复余数除法器、3 段×7 级流水
（被除数上限 2048×640 = 1,310,720 < 2^21）。

> **踩过的坑：行列不能共用一组参数。** 最初版本行列共用 `(STEP, THRESH)`，
> 理由是保持宽高比时 `dst_w/src_w == dst_h/src_h`，比值可约掉。但 `dst_h` 是取整
> 结果，比例一旦不能整除就会失配：96×64 → 64×42 时行采样率被迫等于列采样率 2/3，
> 64 个源行只覆盖到第 61 行，最后 2 行被整行丢弃。此前 116 条检查全过，是因为
> 所有用例恰好精确等比（2:1），掩盖了该缺陷。

### 3.2 `bmp_parser` 的 `CHECK_SIZE` 开关

新增 `parameter CHECK_SIZE = 1`：

- `1`（默认）：尺寸必须等于 `cap_w/cap_h`，不符报 `err_code=4`。独立使用本模块时的原语义，`tb_bmp_parser` 的 T10/T10b 依赖它。
- `0`（缩放模式）：接受任意宽高，但仍挡住 0 尺寸（否则 `img_scaler` 算出无效目标尺寸、永不置 `cfg_ok`，上层只能等超时，不如在这里直接失败）。

`image_player` 例化时传 `.CHECK_SIZE(0)`。

同时新增组合值 `hdr_abs_h`：`ST_VALIDATE` 要拿它和 `cap_h` 比，而 `img_h`
在同一拍才被赋值，直接读 `img_h` 会拿到上一帧的旧值。

### 3.3 `image_player` 的三处改造

1. **像素数校验**。原来 `pixel_count == FRAME_PIXELS` 才算完成，缩放后有效像素数是
   `out_w*out_h`。改为 `pixel_count == scale_pixels`，且 `loader_done` 后先等 7 拍
   （缩放器输出比源像素晚一拍，最后一个目标像素可能还没落进 `pix_count`）。
2. **完成判据**。原来 `written == FRAME_WORDS`（整帧 153,600 字），缩放只写局部区域，
   永远到不了。改为 `written == scale_pixels/2`（`out_w` 恒为偶数，字数恰为像素数一半），
   并加 `expect_words != 0` 保护（否则首个字落盘前就误报完成）。
3. **寻址**。`word_addr` 从 `pixel_y * WORDS_LINE + (pixel_x >> 1)` 改为
   `scale_y * WORDS_LINE + (scale_x >> 1)`。

### 3.4 `image_window_mask`（新增，`rtl/video/image_window_mask.v`）

`img_scaler` 只写窗口内像素，窗口外是**上一帧的残影**（不是黑）。必须在送显前屏蔽。

纯组合，不增加像素延迟：

```verilog
wire [16:0] x_end = {1'b0, win_off_x} + {1'b0, win_w};
wire in_window = (x_now >= win_off_x) && ({1'b0, x_now} < x_end) && ...
assign pixel_valid_out = de && pixel_valid && in_window;
```

上界用加法而非减法：`win_w` 为 0（未配置）时减法会得到 `off_x-1` 这种回绕值，
反而把整片区域判成窗口内。

## 4. 关键陷阱：目标宽必须 8 像素对齐

这是本次唯一在**模块级测试全过之后**才暴露的缺陷，值得单独记录。

`image_player.v:331` 把字地址截成 `{word_addr[20:2], 2'b00}` 交给仲裁器 ——
低 2 位被丢弃。而 `framebuf_arbiter.v:112-113` 与 `sdram_ctrl_wrap.v:327`：

```verilog
assign app_wr_addr = WR_ADDR_FROM_FIFO ? (wr_grp_active ? wr_base_hold : wr_word_addr) : wr_addr;
wire [20:0] wr_eff_addr = (wr_phase == 0) ? app_wr_addr : wr_group_base + {19'd0, wr_phase};
```

**一个四字突发组内，第 1~3 拍地址由「组基址 + 相位」推出，组内必须连续。**
所以：

- 每行字数 `out_w/2` 必须是 4 的倍数 → `out_w` 必须是 8 的倍数
- 行首字地址 `out_off_x/2` 必须落在 4 字边界 → `out_off_x` 必须是 8 的倍数

原 640 宽全屏写入时，行字数 320（4 的倍数）、行首字地址天然 4 字对齐，
这个前提被完全掩盖。缩放后行字数 12 字、行首字偏移 2，组边界与 4 字对齐彻底错开。

**症状**：`96×64 → 32×16` 容器，目标 24×16、偏移 4,0。仿真里
`DBG arb[0..3] addr=496` 四个字全写同一地址，整帧左移 4 像素，
letterbox 区出现窗口内容。

**修法**：`dw_c = {dw_c[15:3], 3'b000}`（8 像素对齐），
`out_off_x <= ((DSTW - dw_c) >> 1) & 16'hFFF8`。
1:1 分支同理，用 `sq_w8`/`sq_off` 两个组合值。
代价是目标宽最多少 7 像素，对缩略图显示无可见影响。

> 教训：lint 通过 + 模块级 TB 全过，仍可能因**下游模块的隐含对齐前提**出错。
> 本例的隐含前提写在 FIFO 打包语句里（`{word_addr[20:2], 2'b00, ...}`），
> 不读下游代码根本发现不了。

## 5. 另一个教训：`-g` 是 vsim 的选项

```powershell
# 错：vlog 不认 -g，整条编译命令失败，之后 vsim 跑的是旧库
vlog -gSCALE=1 ... tb_image_player.v
# 对：先编译（不带 -g），再在 vsim 上传参数
vlog ... tb_image_player.v
vsim -c -quiet -gSCALE=1 tb_image_player -do "run -all; quit -f"
```

这个错误造成过一次严重误判：`vlog` 报错后 `vsim` 仍能跑（用旧库），
输出 `off=4,0`（旧黄金模型的值），看起来像"8 像素对齐没生效"，
实际是**根本没编译进新代码**。后来发现 `EXP_OX` 应为 0 才定位到真相。

### 资源开销

| 模块 | LUT 合计 | LUT as logic | 寄存器 | BRAM | DSP |
|---|---|---|---|---|---|
| `img_scaler` | 1,384 | 990 | 419 | 0 | 4 |
| `image_window_mask` | 82 | 41 | 0 | 0 | 0 |

全设计对比 B2 基线：LUT 13,502 → **15,050**（68.89% → 76.79%），
DSP 15 → **19**（51.72% → 65.52%），BRAM 17 → 17（不变）。
时序未退化，仍是 setup +1.935 ns / hold +0.003 ns。

4 个 DSP 来自三处乘法：交叉乘 `src_w*DSTH` / `src_h*DSTW`（模式判据）、
除法器被除数 `src*DST*`（帧头算一次）、`out_pixels = dw_c * dh_c`。
除法器本身是纯组合 + 7 级流水，只占 LUT。

## 8. 未完成

1. **未上板**。仿真验证的是数据通路正确性，真实显示器上缩放后的观感
   （尤其小图 1:1 居中时黑边比例）只能上板判断。
2. **缩放算法是最近邻**。没有双线性插值，缩小大图时会有锯齿。这是有意的取舍：
   双线性需要行缓冲与乘法器，而本设计连行缓冲的空间都没有。
3. **不支持放大**。小于 640×480 的图按 1:1 居中，不放大。
4. **源尺寸上限 2048**（`SRC_MAX` 参数）。超过会被钳位，比例可能失真。
