# 上板一次性验证方案（2026-10-27）

> **这份文档解决什么问题**
> 正式顶层 `dmz_eg4s20_hdmi_top` 至今**从未上板**——工程里所有上板证据都来自独立的诊断工程
> `image_dm_fix`。静态时序已于 2026-10-27 全部收敛（SWNS +1.935 ns / STNS 0 / 7 组 0 违例），
> 位流也已是时序通过后的正式流，但"时序过"不等于"硬件对"。
>
> 本文档把 `docs/progress.md` 里所有标记 🔶（部分完成）与 ⬜（未开始）的条目，
> 转成**一份可以一次跑完的分阶段检查单**。每一条都给出：**怎么操作 → 应该看到什么 → 看到别的说明什么**。
>
> **判据只落在板子真实可观测的五个通道上**：HDMI 屏幕、8 个 LED、4 位数码管、蜂鸣器、3.5mm 音频。
> 顶层 17 个端口里没有 UART、没有 JTAG 观测口，看不到内部信号——所以每条判据都必须能从这五个通道读出来。

## 零、准备（10 分钟）

### 0.1 硬件

| 项 | 要求 |
|---|---|
| 板卡 | 大拇指 DMZ-EG4S20（苏州硬木智能），器件 EG4S20BG256 |
| 下载器 | 与板卡配套的 JTAG 下载器 |
| HDMI | 一根 HDMI 线 + 一台**支持 640×480@60Hz** 的显示器（老旧显示器可能不认这个模式，先拿电视试） |
| SD 卡 | 一张 **≤32 GB 的 SDHC 卡**（SDXC 大卡本工程未验证），格式化成 **FAT32**，主分区 |
| 音频 | 一副 3.5mm 耳机或有源音箱（板载功放直推） |
| 示波器 | **可选但强烈建议**：验证阶段 5 需要测 SDRAM_CLK 与 DQ 的相对关系。没有的话第 5 阶段只能做功能验证，不能做物理余量确认 |
| 跳线 | 无（键盘、LED、数码管都在板上） |

### 0.2 生成 SD 素材（一次性）

工程不把 8 MB 的 BMP 入库，需要现场生成：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\prepare_board_verify_assets.ps1
```

生成四套目录到 `assets/sd_verify/`：

| 目录 | 内容 | 用来验证什么 |
|---|---|---|
| `good\` | IMG001~IMG006.BMP，每张 640×480 24bit，921,654 B | 正常播放全链路 |
| `bad_size\` | IMG001 正常 + IMG002 是 320×240 | BMP 尺寸校验（错误码 b1） |
| `bad_bmp\` | IMG001 正常 + IMG002 签名是 `XX` | BMP 头校验（错误码 b1） |
| `empty\` | 只有 README.txt，无任何 IMGnnn.BMP | "卡好但零张图"（错误码 00） |

**每张 `good\` 图长什么样**（用于判读）：
- 四角有 **40 像素白色边框**（一整圈，不缺口）
- 中央白框内是**黑色 7 段大数字**，就是这张图的编号（IMG003 → 显示 `3`）
- 右下角有 **N 个白色小方块**，N = 图号（IMG003 → 3 个）
- 背景色每张不同：1 深蓝 / 2 深绿 / 3 深红 / 4 深黄 / 5 深青 / 6 深紫

**为什么这样设计**：白框白块用来查 KEY7 亮度（降亮度时白变灰、深底几乎不变，一眼可辨）；
深色底用来查 KEY8 反色（反色后变亮色，对比强烈）；数字与方块双重标号，防止只看一位数误判。

## 一、上电与时钟（阶段 0，必须先过）

**操作**：插上 SD 卡（`good\` 内容在根目录），接好 HDMI，上电。

| # | 观察点 | 期望 | 不符时的含义 |
|---|---|---|---|
| 0.1 | LED[5]（SDRAM PLL 锁定） | **常亮** | 不亮 = SDRAM PLL 没锁，40 MHz 参数有问题，后面的都不用测 |
| 0.2 | LED[4]（PLL 锁定 + HDMI 核视频锁定） | **常亮** | 不亮但 LED[5] 亮 = HDMI 侧 PLL 或发射核没对齐，先查 HDMI 线/显示器是否支持 640×480 |
| 0.3 | HDMI 屏幕 | 出现画面（黑底或测试图案），**不闪、不抖、不花屏** | 花屏/雪花 = TMDS 通道映射或时序参数问题，切到阶段 2 用彩条定位 |
| 0.4 | 数码管 | **从左到右 `3 0 1 0`**：dig3=状态（3=就绪）、dig2=错误码（0=无错）、dig1=图号低 4 位（1=IMG001）、dig0=图案号（0=彩条） | 完全乱码 = 段选/位选极性错（本工程段选高有效、位选独热低）；某一位不亮 = 该位 COM 线虚焊；**显示 `d 8 1 0` = 装载超时（见下方醒目提示）**；显示 `0 0 1 0` = 卡好但一张图都没扫到 |
| 0.5 | 蜂鸣器 | 上电瞬间可能"嘀"一声，之后**静音** | 持续响 = 进了应急模式或故障态，看数码管 |

> **⚠️ 2026-10-28 修复后的期望值变了**
> 修复前（2026-10-27 首次上板）实测稳定读数 **`d810`**：dig3=`d`(CH_DATA) + dig2=`8`(→`image_err=9` 装载超时)、
> dig1=1、dig0=0，LED 只有 **D4/D5/D7** 亮（`err_active=1`、`sdram_locked=1`、`hdmi_locked=1`）、
> **D6(装载中) 灭**、D0(image_ready) 灭。
>
> 根因是顶层 `image_player` 的 `.sd_ready` 接成了 `sd_ok`（而非 `sd_owner_player`），导致
> 图库扫描期间播放器发出的单拍 `blk_start` 被 SD 仲裁器丢弃 → `img_loader` 无超时永久挂死 →
> 4 秒后 `image_player` 报 `error_code=9`。已修复并重新出 bit（`S6_TIMING_PASSED` / EXIT 0）。
>
> **修复后的正确期望**：`3 0 1 0`（就绪）或按过 KEY2 后 `4 0 1 0`（轮播），
> LED 应变为 **D4/D5/D0 亮、D7 灭**（`err_active=0`、`image_ready=1`）。
>
> 若仍显示 `d 8 1 0` → 说明修复未生效，先确认烧的是 17:41 之后的新位流；
> 若显示 **`d A 1 0`** → 命中新加的超时保护（`E_BLKTMO=4'd10`），即"请求已发出但控制器毫无回应"，
> 说明 SD 总线交接仍有问题，但至少已与"读块失败(d4)""簇链异常(d5)"区分开。

> **阶段 0 是硬门槛**：0.1~0.3 任一不过，后面的阶段都没有意义，先解决时钟与显示。

## 二、HDMI 显示链路（阶段 1）

### 1.1 八种测试图案（KEY4 / KEY5 切换）

**操作**：不插 SD 卡也能测这一段。反复按 KEY5（下一图案）、KEY4（上一图案），数码管**最右位（dig0）**应跟着变 0→1→…→7→0。

> **`pattern_sel` 是 3 位无符号寄存器**（`dmz_eg4s20_hdmi_top.v:81-85`）：
> KEY5 加一、KEY4 减一，自然回绕（7 之后回 0，0 之后回 7）。没有边界钳位。

| dig0 | 图案 | 期望看到 | 不符时的含义 |
|---|---|---|---|
| 0 | 八色彩条 | 白 黄 青 绿 品红 红 蓝 黑，**从左到右八条**（每带 80px） | **颜色顺序错乱** = TMDS 三通道映射反了；**某色偏色** = 该通道位序错 |
| 1 | 64px 网格 | **10 条竖线 + 8 条横线**，黑底白线，等间距 64px | 线条歪斜 = 行列计数器错位；缺线 = 比较边界写错 |
| 2 | R 渐变 | 只有红色从左到右渐亮（0→79，约 31% 亮度封顶），绿蓝全 0 | 绿蓝也有亮 = 通道串扰 |
| 3 | G 渐变 | 只有绿色渐变（同上封顶） | 同上 |
| 4 | B 渐变 | 只有蓝色渐变（同上封顶） | 同上 |
| 5 | 纯色 | 纯黑（本工程 `user_color` 接 `24'd0`） | 非黑 = 该参数被改过 |
| 6 | 移动方块 | 极深蓝底（RGB 0,0,32）上一个 **64×64 绿方块**，约每 1 秒移动 64px，往复运动 | 撕裂 = 帧同步问题；方块不动 = 帧计数器停 |
| 7 | 棋盘格 | **16×16 像素**一格，共 **40 列 × 30 行**格子，白黑相间，边缘锐利无灰边 | 边缘有灰边/抖动 = 像素时钟采样点偏移 |

> **⚠️ 关于图案 1 的横线数量**：`test_pattern_gen.v:194` 的注释写「480/64 = 7 条横线」，
> 但按代码 `active_y[5:0] == 0` 实际成立的是 y = 0, 64, 128, 192, 256, 320, 384, **448** —— **8 条**。
> 480/64 = 7.5，第 8 条（y=448）仍在有效区内。**数到 8 条是对的**，注释里的"7 条"是估算笔误。
> 竖线同理：x = 0…576，共 10 条，与注释一致。

> **关于图案 2/3/4 的渐变**：代码是 `{active_x[10:3]}`，即取横坐标的 bit[10:3]，
> 范围 0~79（不是 0~255）。所以渐变**只到约 31% 亮度就封顶**，右边缘不会是全亮。
> 这是刻意的（省掉乘法器），不是 bug——**别把它当成"亮度不够"来报缺陷**。

### 1.2 亮度五档（KEY7）

**操作**：先切到图案 0（彩条）或 7（棋盘格），然后连按 KEY7 五次，应看到 5 档循环后回到最亮。

| 按几次 KEY7 | bright_sel | 期望亮度（相对最亮） | 判读方法 |
|---|---|---|---|
| 0 | 0 | 100% | 基准 |
| 1 | 1 | 87.5%（减 1/8） | 白色略暗 |
| 2 | 2 | 75%（减 1/4） | 白色明显变灰 |
| 3 | 3 | 62.5%（减 1/4 + 1/8） | 更暗 |
| 4 | 4 | 50%（减 1/2） | 白变中灰 |
| 5 | 0 | 回到 100% | 确认循环 |

> **关键判据**：**黑色部分必须始终是纯黑**。亮度是"减掉自身的一部分"，0 减任何数还是 0。
> 若暗部也变亮，说明实现成了"加偏移"而不是"缩放"，是 bug。

### 1.3 反色（KEY8）

**操作**：按 KEY8 一次开反色，再按一次关。

| 状态 | 彩条图案的期望 | 棋盘格的期望 |
|---|---|---|
| 关 | 白黄青绿品红红蓝黑 | 白黑相间 |
| 开 | 黑蓝黄品红绿红青白（每个通道取反） | 黑白相间（正好互换） |

> 反色是 `~rgb`，即 `255 - value`。白色的反色是黑色，红色（255,0,0）的反色是青色（0,255,255）。
> 若反色后整体偏色，说明只反了部分通道。

### 1.4 三个叠加层（KEY11 / KEY12 / KEY13）

| 键 | 功能 | 期望 | 注意 |
|---|---|---|---|
| KEY11 | 九宫格参考线 | 画面叠加 3×3 分割线 | 与图案 1 的网格不同：这个是叠加层，图案本身还在 |
| KEY12 | 底部信息条 | 屏幕底部出现一排方块（每格 8px，6 实心 + 2 间隔） | 显示图号 / 模式 / 轮播档位，编码是二进制方块位图，不是文字 |
| KEY13 | 音频电平条 | 屏幕某侧出现随音频跳动的条 | 没声音时应该是空的或最低位 |

> **重点验证顺序**：`亮度 → 反色 → OSD`。先按 KEY8 开反色，**再**按 KEY12 开信息条——
> 信息条应该**仍然是正常颜色**（不被反色影响），因为 OSD 在反色之后叠加。
> 若信息条跟着反色了，说明处理顺序写反了，现场会看不清读数。

## 三、SD 卡与图库扫描（阶段 2）

### 2.1 正常卡（`good\` 内容在根目录）

**操作**：上电或按复位，观察前 3 秒。

| 时间点 | 数码管 dig3 | LED | 含义 |
|---|---|---|---|
| 上电 0~5 ms | 0 | 只有 LED[5] 亮 | `POWERUP_CYCLES = 131_071` ≈ 5.2 ms @25 MHz |
| 5 ms ~ 8 ms | 0 | 只有 LED[5] 亮 | `PROBE_DELAY_CYCLES = 200_000` ≈ 8 ms 后开始探针 |
| 8 ms ~ 0.5 s | 1（扫描） | LED[0] 灭 | CMD0/ACMD41 初始化 + 枚举 IMG001~IMG00N（只读目录项，很快） |
| 0.5 ~ 1.2 s | 2（装载） | LED[6] 亮（loading） | 读第一张图 1,801 个扇区，SPI 12.5 MHz 纯传输约 0.59 s |
| 1.2 s 后 | **3（就绪）** | **LED[0] 亮**（image_ready） | 首图装载完成 |

> **为什么是 12.5 MHz SPI**：`sd_spi_ctrl.v:36-37` 的 `SCK_INIT_DIV = 32`
> （初始化阶段 25M/(2×32) = 390.6 kHz，符合卡要求的 100~400 kHz），
> 初始化成功后切到 `SCK_FAST_DIV = 1`（25M/(2×1) = **12.5 MHz**）。
> 单张图 921,654 字节 → 1,801 个扇区 → 纯传输约 0.59 秒，加上 FAT 表读取与命令开销，实测应在 1 秒上下。
> **若明显慢于 2 秒**，先怀疑卡本身（低速卡会拖慢），而不是 RTL。

**屏幕**：应显示 IMG001 的画面——**深蓝底 + 40px 白框 + 中央黑色数字 1 + 右下 1 个白方块**。

> **常见偏差**：
> - 数码管显示 `C1` = CMD0 重试用尽，卡没插好或不是 SDHC
> - 显示 `F1` = 扇区 0 签名不是 0x55AA，卡没分区或分区表损坏（**先重新格式化**）
> - 显示 `d1` = 数据令牌/CRC 错，接触不良（**拔插卡**，或换卡）
> - 显示 `C0` = 卡座 `sd_cd` 报"无卡"（`sd_cd` 引脚 E15，无卡=1 插卡=0）

### 2.2 图库切换（KEY0 / KEY1）

**操作**：按 KEY1 六次，观察数码管 dig1（图号低 4 位）与屏幕。

| 按 KEY1 次数 | dig1 | 屏幕应显示 |
|---|---|---|
| 0 | 1 | 深蓝底 + 数字 1 + 1 个方块 |
| 1 | 2 | 深绿底 + 数字 2 + 2 个方块 |
| 2 | 3 | 深红底 + 数字 3 + 3 个方块 |
| 3 | 4 | 深黄底 + 数字 4 + 4 个方块 |
| 4 | 5 | 深青底 + 数字 5 + 5 个方块 |
| 5 | 6 | 深紫底 + 数字 6 + 6 个方块 |
| 6 | **1**（回绕） | 回到深蓝底数字 1 |

**按 KEY0（上一张）**：从第 1 张按一次应**回绕到最后一张**（第 6 张），这是设计行为。

> **判据**：图号、背景色、中央数字、方块数量**四者必须一致**。
> 若数字对了但背景色不对，说明像素数据错位；若背景对但数字错，说明位图区域算错。

### 2.3 自动轮播（KEY2 / KEY9）

**操作**：
1. 按 KEY2 → LED[1] 应**亮起**（auto_play）
2. 等 5 秒 → 应自动跳到下一张，dig1 加 1
3. 按 KEY9 一次（×2）→ 再等，间隔应变成 10 秒
4. 再按 KEY9（×3 = 15 秒）、（×4 = 20 秒）
5. 再按 KEY2 → LED[1] **熄灭**，停止轮播

| 观察 | 期望 | 不符时的含义 |
|---|---|---|
| KEY2 后 LED[1] | 亮 | 不亮 = auto_play_en 没翻转 |
| ×1 档间隔 | 5 秒 ±0.5 秒 | 明显更快/更慢 = AUTO_SW_S 参数或时钟频率错 |
| KEY9 改档后 | **立刻重新计时**，不是接着算 | 改档就跳 = `auto_sw_sel_d` 比较逻辑失效（`player_ctrl.v:433-435` 专治这个） |
| 应急模式下按 KEY2 | 无效（`player_ctrl.v:414-416` 强制关闭） | 应急时还能轮播 = 优先级错 |

### 2.4 图库重扫（KEY10）

**操作**：
1. 保持上电，**拔下 SD 卡**，换一张卡（或把卡拿到电脑上加一张 IMG007.BMP）
2. 插回，按 KEY10
3. 观察：数码管 dig3 应短暂回到 1（扫描），然后回 3（就绪）

> **注意**：`sd_probe` 是**上电单次执行**，成功/失败都锁定，不复位不重试。
> 所以换卡后如果卡本身有问题，KEY10 也救不回来——它只重扫**图库**，不重新初始化 SD 卡。
> 这是设计取舍（见 `rtl/storage/sd_probe.v:14-42`），不是 bug。

### 2.5 三张异常卡（决定性测试）

依次换上 `bad_size\`、`bad_bmp\`、`empty\` 三套素材，每次**断电重上电**（因为 `sd_probe` 单次执行）。

> **⚠️ 关键操作细节：坏图必须被"装载"才会报错。**
> `bad_size\` 与 `bad_bmp\` 的第 1 张（IMG001）是正常的，`gallery_probe` 会数出 **2 张**，
> 首图装载 IMG001 成功——**此时屏幕正常、数码管正常、不报警**。
> 必须**按一次 KEY1 切到第 2 张**，才会触发 BMP 解析失败，才能看到 `b1`。
> 不按 KEY1 就判定"测试失败"是误判。

| 素材 | 操作 | 数码管完整 4 位（左→右） | LED[7] | 蜂鸣器 | 屏幕 |
|---|---|---|---|---|---|
| `bad_size\` | 上电 → **按 KEY1 一次** | **`b 1 2 0`**（dig3=b 类型, dig2=1 子码, dig1=2 图号, dig0=0 图案号） | **亮** | 静默 1.5 s 后响 3 s | 按 KEY1 后**仍显示 IMG001**（装载失败，前台保持旧帧） |
| `bad_bmp\` | 上电 → **按 KEY1 一次** | **`b 1 2 0`** | **亮** | 静默 1.5 s 后响 3 s | 同上 |
| `empty\` | 直接上电（无需按键） | **`0 0 1 0`**（dig3=0, dig2=0, dig1=1, dig0=0） | **亮** | 静默 1.5 s 后响 3 s | 只显示测试图案（无图可放） |

> **为什么 `bad_*` 卡上电时不报警**：IMG001 正常，首图装载成功，`image_failed=0`。
> 只有按 KEY1 切到坏的第 2 张，`img_loader` 才会在 `bmp_parser` 报 `hdr_fail` 时置
> `E_BMPHDR`（`img_loader.v:395-397`）→ `image_player` 进 `C_FAIL` 并置 `error_code=2`
> → `err_prompt` 的优先级 3 命中 → 数码管切到字母模式。

> **为什么装载失败后屏幕还是 IMG001 而不是黑屏**：`image_player` 在 `SEAMLESS` 模式下
> 切换失败时**先退掉旧帧再清 `image_ready`**（`image_player.v:193-199`）——
> 但这里的失败发生在 `C_LOAD` 阶段，还没走到 `C_COMMIT`，所以前台帧**没被替换**，
> 继续显示上一张。这是双缓冲的正常行为，不是卡死。
> 验证方法：再按 KEY1，仍停在 IMG001 且 `b1` 保持——说明坏图被反复拒绝，旧图稳定。

> **为什么 `bad_size` 与 `bad_bmp` 都是 `b1`**——这是**两层合并**的结果，链条必须看懂：
>
> **第一层合并（在 `img_loader` 里）**：`bmp_parser` 自己会报细分错误码
> （1=签名非 BM、2=非 24bit、3=有压缩、4=宽高不符、6=数据偏移越界），
> 但 `img_loader` 只接了一根 `bmp_hdr_fail` 单拍信号（`img_loader.v:76`），
> 收到就一律置 `err_code <= E_BMPHDR = 4'd2`（`img_loader.v:395-397`）。
> **所以 bmp_parser 的细分码在这一层就丢了**——这是接口设计的结果，不是 bug。
>
> **第二层合并（在 `err_prompt` 里）**：`image_err == 2` 映射到 `CH_BMP` + 子码 1。
>
> 于是 `bad_size`（宽高不符）和 `bad_bmp`（签名错）走到用户面前**都是 `b1`**。
> 若将来需要区分，得把 `bmp_parser` 的 `err_code` 单独引到顶层——那是增强，不是当前缺陷。
> 详见 `rtl/control/err_prompt.v:182-333` 与 `rtl/storage/img_loader.v:34-37,90-94`。
>
> **`empty\` 的 `00` 是最容易被漏测的盲区**：改造前这种情况灯全灭、屏幕放测试图，
> 看起来和正常启动一模一样。现在 LED[7] 亮 + 数码管 `00` + 蜂鸣器报警，
> 现场换卡后一眼就能看出"卡是好的，但里面没图"。

### 2.6 故障告警音时序

**操作**：用 `bad_size\` 卡上电，秒表计时。

| 时间 | 蜂鸣器 |
|---|---|
| 0 ~ 1.5 s | **静默**（`ALARM_DELAY = CLK_FREQ_HZ*3/2`） |
| 1.5 s ~ 4.5 s | **鸣响**（`ALARM_HOLD = CLK_FREQ_HZ*3`） |
| 4.5 s 之后 | **静默，且不再响**（计数饱和，不回绕） |

> 若 4.5 s 后又开始响，说明 `ALARM_TOTAL` 饱和逻辑失效——每个故障只该提醒一次。

## 四、应急模式与模式切换（阶段 3）

### 4.1 模式循环（KEY3）

**操作**：连按 KEY3，观察数码管 dig3（正常态下显示 playback_state）与 LED[3]。

| 按 KEY3 次数 | mode | 屏幕 | LED[3] | 蜂鸣器 |
|---|---|---|---|---|
| 0 | 0 日常 | 正常图片 | 灭 | 按键音 |
| 1 | 1 科普 | 正常图片（当前版本与日常无视觉差异） | 灭 | 按键音 |
| 2 | 2 应急 | **全屏纯红 `24'hFF0000`** | **亮** | **应急音 E6≈1319 Hz，250 ms 响 250 ms 停** |
| 3 | 0 日常（循环） | 回到图片 | 灭 | 按键音 |

> **应急模式强制红屏，优先级高于图片**（`dmz_eg4s20_hdmi_top.v:211-212`）。
> 即使图片正常就绪，只要 `mode==2` 就显示红色。这是安全功能，不是 bug。

### 4.2 应急直达（KEY15）

**操作**：在任意状态下按 KEY15。

| 期望 | 说明 |
|---|---|
| 立即进入应急模式（红屏 + LED[3] 亮 + 应急音） | 最高优先级，任意状态可用 |
| **自动轮播被强制关闭**（LED[1] 熄灭） | `player_ctrl.v:414-415` |
| 再按 KEY3 退出应急 | 退出后 `auto_play_en` **保持关闭**，需再按 KEY2 恢复 |

> **为什么退出应急后不自动恢复轮播**：这是刻意的。应急广播结束后，
> 设备不该自己突然开始放图片——需要人确认。见 `player_ctrl.v:406-419` 的注释。

### 4.3 两路静音的独立性（关键交叉验证）

这是最容易混的一对键，必须分开验：

| 键 | 管什么 | 不管什么 |
|---|---|---|
| **KEY6** audio_muted | HDMI 内嵌音频 + 3.5mm 输出 | **不碰蜂鸣器** |
| **KEY14** beep_muted | **只掐蜂鸣器** | 不影响 HDMI / 3.5mm |

**验证步骤**：
1. 进入应急模式（有应急音 + HDMI 有声）→ 按 **KEY14** → **蜂鸣器停，但 HDMI 里的声音还在**
2. 再按 KEY6 → HDMI 也静音了
3. 再按 KEY14 → 蜂鸣器恢复，HDMI 仍静音

> 若按 KEY14 连 HDMI 声音也停了，说明两条支路被接错了。

## 五、SDRAM 与画面稳定性（阶段 4）

这一段是**最关键的**——40 MHz 降频后读 DQ 余量只有 **+1.935 ns**，是全设计最小余量。

### 5.1 长时间播放稳定性

**操作**：用 `good\` 卡，开自动轮播（KEY2），**连续跑 30 分钟以上**。

| 观察 | 期望 | 不符时的含义 |
|---|---|---|
| 屏幕 | 始终正常，无花屏、无错位、无闪烁 | 偶发花屏 = SDRAM 读数据偶发错误，正是余量不足的表现 |
| LED[2]（FIFO 溢出/下溢） | **始终熄灭** | 亮起 = 像素读出跟不上/太快，`pix_reader` 的 credit 流控失效 |
| LED[0]（image_ready） | 始终亮 | 熄灭 = 图片被卸载了 |
| 数码管 dig2（image_error） | 始终 `0` | 非 0 = 装载出错，看错误码 |
| 画面切换 | 无撕裂、无黑帧 | 有黑帧 = 双缓冲切换时序问题（`SEAMLESS` 模式） |

### 5.2 快速切换压力测试

**操作**：连续快速按 KEY1（每秒 2~3 次）30 秒。

| 观察 | 期望 |
|---|---|
| 每次按键都能切到下一张 | 不丢键、不连跳 |
| LED[2] 不亮 | FIFO 不溢出 |
| 数码管 dig2 保持 0 | 无装载错误 |

> 快速连按时，`player_ctrl` 每次都会发 `img_switch_req`，
> `img_loader` 需要能中断上一次未完成的装载。若出现 dig2 非 0，说明重入处理有问题。

### 5.3 SDRAM 物理余量（需示波器，可选）

**这是唯一无法靠屏幕判断的项**。README 已把它列为"上板前确认项"。

**测法**：
1. 示波器两个通道：CH1 接 **SDRAM_CLK**（FPGA 内部信号，需要引出测试点或用 TD 的 debug 探针），
   CH2 接任意一根 **DQ**
2. 触发在 SDRAM_CLK 下降沿，观察 DQ 的建立/保持窗口
3. 对比读数与 TD 报告的 `input (hard ip) +5.000 ns`

**参考点**：安路社区有位做过 EG4S20 SDRAM 控制器的开发者实测——
「当 SDRAM 时钟**提前 2.666 ns** 时，读时序 bug 基本消失」，并推算
「输出 buffer 延迟 2~2.5 ns，输入 buffer 延迟 0.5~1 ns，总延迟 2.5~3.5 ns 左右」。
如果实测发现读数据在采样点附近抖动，**优先怀疑这个相位关系**，而不是怀疑 RTL。

> **没有示波器怎么办**：跳过 5.3，但要在报告里明确写"物理余量未实测"。
> 5.1 和 5.2 跑满 30 分钟无异常，可以作为"功能层面稳定"的弱证据，但不能替代物理测量。

## 六、音频链路（阶段 5）

### 6.1 3.5mm 输出

**操作**：插耳机，进入正常播放态。

| 观察 | 期望 | 不符时的含义 |
|---|---|---|
| 底噪 | 安静时几乎无杂音 | 明显"沙沙"声 = PWM 载波泄漏，检查 `pcm_to_pwm` 的滤波参数 |
| 音高 | 随播放状态变化（不同状态不同音） | 完全无音 = `audio_pwm` 引脚（F3）没接对，或 `pcm_to_pwm` 没使能 |
| KEY6 静音 | 立刻静音 | 无效 = `audio_muted` 没接到 `pcm_to_pwm.mute` |

### 6.2 HDMI 内嵌音频

**操作**：HDMI 接到带音箱的显示器/电视，调高音量。

| 观察 | 期望 |
|---|---|
| 有声音 | 与 3.5mm **同一份样本**（不是两路独立发音） |
| KEY6 静音 | HDMI 也静音 |
| 音画同步 | 无明显延迟 |

> HDMI 音频走 `audio_arc`（Audio Rate Control），`f_audio = f_pixel * N / (128 * CTS)`，
> 本工程 `AUDIO_DIV = ACR_N >> 7 = 48`。若完全没声音但 3.5mm 有，
> 优先怀疑 ARC 包的 N/CTS 参数，而不是 PCM 通路。

### 6.3 蜂鸣器三档音调

| tone_sel | 触发条件 | 期望声音 |
|---|---|---|
| 0 | KEY14 静音 | 完全无声 |
| 1 | 按键音（任意键按下） | 短促"嘀"一声，C5≈523 Hz，约 100 ms |
| 2 | 应急模式（mode==2） | 急促"嘀嘀"，E6≈1319 Hz，250 ms 响 250 ms 停 |
| 3 | 故障告警（alarm_req） | 连续鸣响 3 秒（见 2.6） |

**优先级**：`静音 > 故障告警 > 应急 > 按键音`（`dmz_eg4s20_hdmi_top.v:459`）。
验证：进入故障态后按任意键，**应该听到告警音而不是按键音**。

## 七、键盘矩阵行序核定（阶段 6，必须先做）

**这是整个验证里唯一"可能全盘错位"的地方**，所以单独列出。

`rtl/input/key_matrix_4x4.v:71-72` 明确记录：

> ⚠️ 行序存在来源冲突（底板例程写法为反序），本工程采用走近FPGA 顺序，待上板实测核定；
> 若不符，只需调整约束文件中 key_row 的四行即可

约束文件 `constraints/dmz_eg4s20_hdmi.adc:25-28` 当前是：

| 信号 | 引脚 |
|---|---|
| key_row[0] | E10 |
| key_row[1] | C10 |
| key_row[2] | F9 |
| key_row[3] | D9 |

键号公式 `KEY(行 r, 列 c) = 4*r + c`，即：

```
        col0    col1    col2    col3
        E11     D11     C11     F10
row0 E10  KEY0   KEY1   KEY2   KEY3
row1 C10  KEY4   KEY5   KEY6   KEY7
row2 F9   KEY8   KEY9   KEY10  KEY11
row3 D9   KEY12  KEY13  KEY14  KEY15
```

### 核定方法（5 分钟）

1. 上电，进入正常播放态
2. **从上到下、从左到右**依次按每一个键，记录"实际发生了什么"
3. 对照下表判断：

| 现象 | 结论 |
|---|---|
| 按物理第 1 行第 1 列（左上角）→ 切到上一张 | **行序正确**，收工 |
| 按左上角 → 亮度变化（KEY7） | 行序**反了**，实际 r=0 对应 D9（key_row[3]） |
| 按左上角 → 什么都没发生 | 该键是 KEY6（音频静音）或列序也反了 |
| 整行整列错位 | 行/列其中一维反序 |

### 若行序反了怎么改

**只改约束文件，不改 RTL**——这是设计时刻意留的调整点：

```tcl
# constraints/dmz_eg4s20_hdmi.adc 第 25-28 行
set_pin_assignment { key_row[0] } { LOCATION = D9;  ... }   # 原 E10
set_pin_assignment { key_row[1] } { LOCATION = F9;  ... }   # 原 C10
set_pin_assignment { key_row[2] } { LOCATION = C10; ... }   # 原 F9
set_pin_assignment { key_row[3] } { LOCATION = E10; ... }   # 原 D9
```

改完重跑 `scripts/sync_src.ps1` 与 `flow_s6_bit.tcl`，重新烧录。

> **列序**若也不对，同样方法调 `key_col[0..3]`（E11/D11/C11/F10）。

## 八、SD MOSI/MISO 引脚极性核定（阶段 7）

`docs/pending_confirmations.md` 记录了第二个来源冲突：

| 来源 | SCK | CS | MOSI | MISO |
|---|---|---|---|---|
| 引脚说明 | F15 | F13 | **F14** | **D14** |
| 底板例程 | F15 | F13 | D14 | F14 |

本工程采用**引脚说明**（`constraints/dmz_eg4s20_hdmi.adc` 中 `sd_mosi = F14`、`sd_miso = D14`）。

### 核定方法

如果阶段 2 的 SD 卡**完全读不出来**（数码管显示 `C1` 或 `d1`），且换卡、重新格式化都无效，
那么嫌疑最大的就是这一对引脚反了。

**改法**：在 `.adc` 里互换 F14 与 D14 的 `set_pin_assignment`，重新出 bit。

> **不要一上来就改**——先用 `good\` 卡正常验一遍。能读出来就说明引脚是对的，
> 读不出来才怀疑。贸然改会引入新的变量。

## 十、失败时的排查顺序

按"越底层越先查"的原则，不要跳步：

```
1. LED[5] 不亮（SDRAM PLL 没锁）
   → 查 sdram_pll.v 的 PLL 参数（40 MHz 配置见 docs/progress.md S12）
   → 查 .adc 里 clk 是否 R7

2. LED[5] 亮但 LED[4] 不亮（HDMI 侧没对齐）
   → 查 hdmi_pll.v 参数（25 MHz / 125 MHz）
   → 查显示器是否支持 640×480@60
   → 查 HDMI 引脚 P1/N1/P4/J3 与 LVDS33 电平

3. 有画面但花屏
   → 先切图案 0（彩条）看颜色顺序 → 判断是通道映射还是时序
   → 切图案 7（棋盘格）看边缘 → 判断是采样点还是布线

4. 屏幕正常但 SD 读不出
   → 看数码管错误码（C1/C2/F1/d1 分别对应不同环节）
   → 换卡、重新格式化 FAT32
   → 最后才怀疑 F14/D14 引脚（阶段 7）

5. SD 能读但图不显示
   → 看 dig2（image_error 原始码）
   → b1 = BMP 头或尺寸问题（用 prepare_board_verify_assets.ps1 重新生成素材）
   → d8 = SDRAM 仲裁错误（回到阶段 4）

6. 偶发花屏 / LED[2] 偶亮
   → 这是 SDRAM 读余量不足的典型表现（+1.935 ns 是全设计最小）
   → 短期：确认没有其他负载干扰
   → 长期：考虑再降频到 30 MHz，或向安路索要官方 SiP 时序模型
```

## 附录 B：素材生成脚本的行为

`scripts/prepare_board_verify_assets.ps1` 生成的 BMP 严格满足 `bmp_parser.v` 的全部硬性要求：

- 640×480、24 bit、BI_RGB 无压缩、`biHeight > 0`（底上行序）
- 每行 4 字节对齐（640×3 = 1920，恰好整除，pad = 0）
- 数据偏移 54 字节，标准 40 字节 `BITMAPINFOHEADER`
- 文件大小 = 54 + 921,600 = 921,654 字节

若想改图（比如加更多张测试图），改脚本里的 `$Palette` 数组即可，它会自动按索引生成
背景色、中央数字、右下角方块数。
