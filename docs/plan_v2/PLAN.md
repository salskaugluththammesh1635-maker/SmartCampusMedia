**关于 R8 的降级说明（必须原样告知用户）**：

> 用户要求「SD 卡视频播放」。实测 SD SPI 实用带宽 1.25 MB/s，而 640×480@60 Hz 未压缩 RGB565 需 36.86 MB/s —— **差 29.5 倍**。经 RLE 游程压缩（素材压缩比 0.206）后可达 **固定 5 fps**，画质保留满分辨率，但**画面像幻灯片**。这是 SD 卡 SPI 接口的物理带宽上限，不是实现取舍。

**关于 R11 的确认**：用户原表述「680×480」经确认（队长裁决 B 决策 2）为 **640×480** 笔误。既有素材 `IMG001~006.BMP` 均为 640×480，零额外风险。

### 1.3 赛规合规基线

依据 `reports/plan_v2/SPEC_CONSTRAINTS.md`：

| 硬约束 | 编号 | 本方案合规性 |
|---|---|---|
| 必须用 EG4S 系列芯片 + EG4S20BG256 器件 | H1 | ✅ 不变 |
| 算法/控制/数据流须 FPGA 内自主实现 | H5 | ✅ 全部 RTL 实现，无软核 |
| 不得带额外处理器 | H7 | ✅ AHT20 论证合规（见 §8.1） |
| 五项扩展加分点 | 1.4(1)~(5) | ✅ **五项全勾** |

**AHT20 合规论证要点**（详见 `reports/plan_v2/REQ_GAP.md` §3）：
1. AHT20 **无指令集 / 无程序存储 / 不可编程**，仅 `0xAC`/`0x71`/`0xBE` 三条硬连线命令；
2. 赛规 P5 明确允许复杂度更高的 OV5640 摄像头模块（OV5640 含内部 MCU + ISP + JPEG 引擎）；
3. 极端解释会导致 SD 卡、HDMI 显示器也违规，使赛题无法实现；
4. 20 bit 原始量的**全部处理（换算、迟滞、联动）在 RTL 内完成**。

**判据（一句话答辩）**：「可以用模块，但模块内不能有会算东西的东西。AHT20 里没有 CPU、没有程序、不可编程，它就是一个把物理量变成 20 bit 数字的传感器。」

## 3. 三模式状态机

> **详细状态转移表、迟滞设计、退出确认窗口、端口契约见 `ARCH.md` §2。** 本节只给计划层面的定义与验收口径。

### 3.1 三模式定义

| 模式 | 编码 | 画面 | 音频 | 字幕 |
|---|---|---|---|---|
| **日常** | `2'd0` | SD 图库循环（6 张 640×480 BMP） | BGM 循环（`bgm_serene.wav`） | 校园介绍滚动字幕 |
| **科普** | `2'd1` | SD RLE 视频（640×480@5fps） | 解说音频（`narration.wav`） | **视频字幕（`narr_subline.v`，18 段，`rle_decoder.frame_idx` 驱动，对齐 `narration.srt`；见 `ARCH.md` §9.4）** |
| **应急** | `2'd2` | 应急平面示意图（`emerg_page`，FPGA 内实时栅格化，零 SD 依赖）+ 大字提示 | 警报音（`alarm_siren.wav` 循环），**强制开** | 应急提示字幕（**锁定不可关**，措辞按 `SAFETY_WORDING_RULING.md` A 类） |

### 3.2 切换规则（计划口径）

| 动作 | 触发 | 行为 |
|---|---|---|
| 循环切换 | Key2 | 日常 → 科普 → 日常（**应急态下 Key2 无效**） |
| 直达应急 | Key3 | 任意态 → 应急，**零延迟** |
| 高温自动 | AHT20 ≥ 45 ℃（3 次确认） | 任意态 → 应急，`emerg_src = 2` |
| 退出应急 | Key3 双按（2 s 窗口内） | 应急 → **日常**（强制，不回科普） |
| 温度回落 | < 40 ℃（5 次确认） | **不自动退出**，仅解除「再次触发」条件 |

**三条设计决策（必须写进答辩）**：
1. **应急优先并锁存**：进入零延迟（不设确认），退出需双重确认（防误触）。温度回落不自动解除 —— 「警报响过后自己停了」在现场是极危险信号。
2. **退出强制回日常**：应急前若在科普模式，视频流已被打断，回科普需重新装载会有数秒黑屏；回日常可立即出图。
3. **应急下按键作用域收窄**：Key4（音频）无效、Key5（字幕）锁定、Key0/Key1/Key2 无效；Key6/Key7/Key8/Key9/Key10 仍有效（视觉参数不影响必需输出）。

## 4. 五档分辨率（Key8）

> **技术论证、DDA 实现、几何稳定策略见 `ARCH.md` §3。**

### 4.1 核心口径（必须先说清）

**Key8 切的是「内部渲染分辨率」，HDMI 输出时序恒定 640×480@59.52 Hz（像素时钟 25 MHz）。**

**为什么**：TD 的 `EG_PHY_PLL` 原语在当前配置（`DYNCFG="DISABLE"`）下**不支持运行时动态重配置分频**。切像素时钟必须重配置 PLL → 重锁定（数百 μs 至数 ms）→ HDMI 失锁 → 显示器黑屏重同步。用户会看到闪黑，不可接受。

**答辩口径**：「我们把分辨率做成渲染档位，用整数倍最近邻放大回 640×480。用户看到的是画质变化，不是黑屏。」

### 4.2 五档取值表（可直接翻成 Verilog parameter）

```verilog
// 落点：水平抽样在 rtl/video/pix_mosaic.v（读出侧），垂直行映射在 rtl/storage/pix_reader.v
// 两者共用同一张 res_sel → src_w/src_h 译码表（下表数值即该表的取值，全部保留不变）
localparam [2:0] RES_SEL_MAX = 3'd4;
localparam [15:0] SRC_W_0 = 16'd320, SRC_H_0 = 16'd240;   // 2.00×  1/4 数据量
localparam [15:0] SRC_W_1 = 16'd400, SRC_H_1 = 16'd300;   // 1.60×  0.391 数据量
localparam [15:0] SRC_W_2 = 16'd512, SRC_H_2 = 16'd384;   // 1.25×  0.64 数据量
localparam [15:0] SRC_W_3 = 16'd576, SRC_H_3 = 16'd432;   // 1.111× 0.81 数据量
localparam [15:0] SRC_W_4 = 16'd640, SRC_H_4 = 16'd480;   // 1.00×  旁路
```

| `res_sel` | 内部渲染分辨率 | 宽高比 | 放大比 | 放大比分数 | 插值方式 | 水平 DDA 增量 | 垂直 DDA 增量 |
|---|---|---|---|---|---|---|---|
| `3'd0` | 320×240 | 4:3 | 2.00× | 2/1 | 最近邻（2×2 像素块） | +1/2 | +1/2 |
| `3'd1` | 400×300 | 4:3 | 1.60× | 8/5 | 最近邻 | +5/8 | +5/8 |
| `3'd2` | 512×384 | 4:3 | 1.25× | 5/4 | 最近邻 | +4/5 | +4/5 |
| `3'd3` | 576×432 | 4:3 | 1.111× | 10/9 | 最近邻 | +9/10 | +9/10 |
| `3'd4`（**默认**） | **640×480** | 4:3 | **1.00×** | 1/1 | **旁路** | +1 | +1 |

**五档全部 4:3**，全部由 640×480 的简单分数缩放得到，分母均为小整数，Bresenham DDA 可实现，**零乘法器、零除法器、零 DSP**。

### 4.3 关于候选档位的取舍说明

| 候选 | 判定 | 理由 |
|---|---|---|
| **320×240 / 400×300 / 512×384 / 576×432 / 640×480** | ✅ **采用** | 全部 4:3 精确，放大比为小整数分数 |
| 426×320 | ❌ 否决 | **非 4:3**（426/320 = 1.3313 vs 1.3333，偏差 0.15%），放大到 640×480 会产生可见的列宽不均 |
| 800×600@60 | ❌ 否决 | 需 40 MHz 像素时钟 → VCO 需 1200 MHz，**恰在芯片上限临界**，且串化需 200 MHz |
| 1024×768@60 | ❌ **禁止出现** | 需 65 MHz，VCO 与串化**双重超限** |
| 1280×720@60 | ❌ **禁止出现** | 需 74.25 MHz，**双重超限** |
| 720×480 / 800×480 | ❌ 否决 | 非 4:3（3:2 / 5:3），放大到 640×480 需非等比缩放，几何失真 |

> **注**：队长裁决 A 曾建议 426×320，本文档改为 **400×300**。理由已写明（4:3 精确、8/5 放大无累积误差、数据量差异 < 2%），属**有据微调**，非擅自改动。

### 4.4 多像素时钟方案的三个候选与最终选择

| 方案 | 描述 | 判定 |
|---|---|---|
| **A. 单 PLL 多 C 输出 + 使能切换** | `hdmi_pll` 同时输出多个像素时钟（C0=25M、C1=40M…），用 BUFG 使能切换 | ❌ **不可行**。`EG_PHY_PLL` 的 `CLKC*_DIV` 是编译期参数，且 `FEEDBK_PATH="CLKC0_EXT"` 下 C0 兼反馈，改 C0 会改 VCO；多 BUFG 切换会有毛刺 |
| **B. 新增第 3 颗 PLL** | 用余下 2 颗 PLL 中的 1 颗产生 40/65 MHz | ❌ **解决不了问题**。问题不是 PLL 数量，是「切换时必然重锁定」。且高分辨率所需的 VCO/串化时钟超芯片上限 |
| **C. 降档到共用 25 MHz 整数倍** | 所有档位都用 25 MHz 像素时钟，改内部渲染分辨率 | ✅ **采用（= N1）** |

**最终选择：方案 C（N1）**。零新增 PLL（`#pll` 保持 2/4），零时钟域风险，切换零延迟（下一帧生效）。

### 4.5 切换时的几何稳定策略

| 风险 | 处置 |
|---|---|
| 切档瞬间画面撕裂 | `cfg_changed` 触发后，`image_player` 从**下一帧起始**（`frame_start`）才应用新 `src_w/src_h`；本帧继续用旧值 |
| DDA 累加器跨帧残留 | 每帧 `active_x == 0 && active_y == 0` 时强制 `x_acc <= 0, src_x <= 0` |
| 切档时 SDRAM 读地址跳变 | `pix_reader` 的 `rd_base` 不变（帧基址与分辨率无关），仅行内步进变化 |
| 显示器时序抖动 | **不可能** —— `video_timing_gen` 参数不变，输出恒定 640×480@59.52 Hz |

### 4.6 验收标准

- [ ] 仿真：五档 `res_sel` 逐一验证 `src_x/src_y` 的 DDA 序列与期望完全一致（`res_sel=0` 时 `src_x` 序列为 0,0,1,1,2,2,…,159,159）
- [ ] 仿真：`res_sel=4` 时 `src_x == active_x` 且 `src_y == active_y`（旁路）
- [ ] 仿真：切档瞬间不出现 `src_x >= src_w`（越界）

## 5. 五档屏占比（Key9）

> **实现方式、方案取舍、顺序论证见 `ARCH.md` §4。**

### 5.1 取值表

```verilog
// ratio_sel → win_w, win_h, win_off_x, win_off_y
localparam [15:0] WIN_W_0 = 16'd320, WIN_H_0 = 16'd240, OFF_X_0 = 16'd160, OFF_Y_0 = 16'd120; // 1/2
localparam [15:0] WIN_W_1 = 16'd400, WIN_H_1 = 16'd300, OFF_X_1 = 16'd120, OFF_Y_1 = 16'd 90; // 5/8
localparam [15:0] WIN_W_2 = 16'd480, WIN_H_2 = 16'd360, OFF_X_2 = 16'd 80, OFF_Y_2 = 16'd 60; // 3/4
localparam [15:0] WIN_W_3 = 16'd560, WIN_H_3 = 16'd420, OFF_X_3 = 16'd 40, OFF_Y_3 = 16'd 30; // 7/8
```

### 5.2 实现方案：实时窗口裁剪（不是预生成图）

| 维度 | 方案 A：实时窗口裁剪（**采用**） | 方案 B：预生成五套素材 |

| 结论 | ✅ **采用** | ❌ 否决 |

### 5.3 与分辨率的关系（正交，不叠加缩放）

**Key8 与 Key9 是两条正交链路**：
- **Key8（分辨率）** 控制**读出侧抽样**（`pix_mosaic` 水平 + `pix_reader` 垂直行映射），全屏生效，图片与视频同源同参数。
- **Key9（屏占比）** 控制 `image_window_mask` 的**窗口大小**，窗口内像素 **1:1 显示不缩放**，窗口外为黑边。

**串联顺序：先放大（读出侧抽样）后裁剪（image_mask）**。理由：窗口尺寸永远是 640×480 的整数分数（320=640/2、400=640×5/8、480=640×3/4、560=640×7/8、640=640/1），全部整除，无边界误差；反序则窗口尺寸必须同时整除 `src_w`（320/400/512/576/640）与 640，`400/512`、`480/512`、`560/576` 三处除不尽，会产生边界像素重复或缺失。

**与物理连线顺序不矛盾**：`pix_mosaic` 与 `pix_reader` 行映射都是**流式抽样**（不是像素缓存），自变量是输出域 `active_x`/`active_y`；`image_window_mask` 用同一对 `active_x`/`active_y` 判断目标像素是否落在窗口内。二者自变量相同，数学上等价于「全屏放大后取子窗口」。物理连线仍是 `源（图片或视频）→ pix_mosaic（水平抽样）→ image_mask（窗口门控）→ content_mux → overlay`，`image_mask` **只在 overlay 之前、只门控内容层（图片与视频共用的图片路输出端口），应急平面图除外**，绝不裁 OSD。

**档位表**（`k/32` 移位加，**零 DSP**）。**方向：档 0 = 100% 最亮，档 9 = 9.4% 最暗**，与既有 `video_overlay.v:108` 的 `bright_sel == 3'd0 ? r_in` 语义一致，迁移不翻转：

```verilog
// rtl/video/brightness_apply.v（纯组合零寄存器）
// lvl: 0（最亮 100%）~ 9（最暗 9.4%），k/32 增益
case (lvl)
    4'd0:    brt = x;                                // 32/32 = 100%（复位值）
    4'd1:    brt = x - (x >> 4) - (x >> 5);          // 29/32 = 90.6%
    4'd2:    brt = x - (x >> 3) - (x >> 4);          // 26/32 = 81.3%
    4'd3:    brt = x - (x >> 2) - (x >> 5);          // 23/32 = 71.9%
    4'd4:    brt = x - (x >> 2) - (x >> 3);          // 20/32 = 62.5%
    4'd5:    brt = (x >> 1);                         // 16/32 = 50.0%
    4'd6:    brt = (x >> 1) - (x >> 4) - (x >> 5);    // 13/32 = 40.6%
    4'd7:    brt = (x >> 2) + (x >> 4);              // 10/32 = 31.3%
    4'd8:    brt = (x >> 3) + (x >> 4);              //  6/32 = 18.8%
    default: brt = (x >> 4) + (x >> 5);              //  3/32 =  9.4%
endcase
```

| **0（复位）** | 32/32 | **100%** | 5 | 16/32 | 50.0% |
| 1 | 29/32 | 90.6% | 6 | 13/32 | 40.6% |

### 6.2 10 档音量（Key7）

**现状**：无音量控制，只有 `audio_muted`（KEY6 翻转）与 `HDMI_AUDIO_ATTEN_SHIFT=6`（固定衰减 6 bit ≈ -36 dB）。

## 7. 视频播放路线（Key2 科普模式）

> **完整带宽账、缓冲策略、`.RLE` 格式、端口契约见 `ARCH.md` §6.5 与 §11。**

### 7.1 已确认口径

**640×480 RGB565，RLE 游程压缩，固定 5 fps。**

**帧率口径**：初版文档曾设定「5 fps 目标 / 持续欠载时自动降到 2 fps」，**该自动降级逻辑从未在 RTL 实现**（`dmz_eg4s20_hdmi_top.v:521` 把 `.play_fps` 硬接常量 `8'd5`；`rle_underrun` 接出来但零消费者）。当前实现是**固定 5 fps**，欠载时**停在上一个已显示帧**。「2 fps」只是带宽核算的假设工况，**不是系统能力，也不是承诺下限**。

### 7.2 白话说明（必须原样进答辩材料与用户沟通）

> 「科普模式的视频是**满分辨率 640×480**，但帧率只有 **5 帧/秒**，看起来像幻灯片切换，不是流畅视频。这是 **SD 卡 SPI 接口的物理带宽上限**决定的 —— 不是实现偷懒。我们做了游程压缩（因为素材是大片纯色的 PPT 风格动画，压缩比 0.206），把帧率从 1 fps 提到 5 fps，但这已经是这条 SPI 线的极限。」

| **2 fps（假设工况，非 RTL 行为）** | **0.260 MB/s** | **0.405 MB/s** | **20.8%** | **32.4%** | ✅ 稳（该档位未实现；见下方结论） |

### 7.4 三层缓冲与欠载策略

| 层 | 措施 | 参数 |
|---|---|---|
| ① SDRAM 抖动窗口 | **就是 A/B 双缓冲本身**：`rle_decoder` 解压后直写帧缓冲（走 `image_player` 的 `ext_wr_*` 外部写口），不另设分区、不缓存压缩码流。一帧在 SDRAM 里恒为 `FRAME_WORDS = 153,600` words，与压缩比无关 | **2 帧**（A/B 各一）= **400 ms @5fps**；最坏单帧取数 162.2 ms（396 块 × 409.6 μs，实用口径）→ **2.47 倍裕度**（理论口径 129.8 ms → 3.08 倍，对外一律引实用口径） |
| ② 欠载保持上一帧 | **不需要任何额外逻辑**：`ext_wr_done` 不来 → `commit_pending` 不置位 → `front_sel` 不翻 → 读侧继续读旧帧。**不插黑、不清屏** | 插黑会让「帧率不足」变成肉眼可见的闪烁；保持上一帧只是略卡。与「BMP 慢卡停在上一张」同构 |
| ②′ 读的必是完整帧（三重机制） | 一＝全帧 153,600 words 写完成判据（`rle_decoder` 的 `ext_wr_done` 语义是整帧原子）；二＝换帧只发生在垂直消隐（`image_player` 的 `front_sel` 三处翻转点全被 `vblank_rise` 门控）；三＝消隐期五状态清场（`pix_reader` 的 `P_RUN→P_QUIET→P_DRAIN→P_RESTART→P_READY→P_RUN`，进 `P_RUN` 前 FIFO 已真空、`rd_frame_base` 已锁新值） | 三重都在既有 RTL 里现成，视频复用**零改动** |
| ③ ~~自动降帧率~~ **（设计目标未落地，已作废）** | ~~连续 3 帧 `underrun` → `play_fps` 从 5 降到 2~~ —— **该逻辑从未在 RTL 实现**（`play_fps` 顶层硬接 `8'd5`，`rle_underrun` 零消费者）；欠载时的真实行为见 ② | 不需要这一层：② 已经保证「不插黑、不撕裂」，且**不降分辨率**（降分辨率会连锁影响 Key8 五档与读出侧抽样的倍率） |

**风险声明（必须写进交付说明）**：
> **固定 5 fps。** 若上板实测发现持续欠载（SD 卡质量差、块读取延迟超预期），系统的行为是**停在上一个已显示帧、不插黑、不撕裂**，**不会自动降帧**。初版文档曾写过「自动降到 2 fps / 2 fps 是承诺下限」，那是**设计目标未落地** —— 该逻辑从未在 RTL 实现，已作废。带宽核算里的 @2 fps 一行只是**假设工况**，不是系统能力。

### 7.5 为什么不用 JPEG / MJPEG

| 理由 | 数据 |
|---|---|
| 工程内无任何 JPEG 相关模块 | 全盘检索无 Huffman/IDCT 实现 |
| 自研 LUT 需求 | 基线 JPEG 解码器 ≈ **20,000+ LUT** |
| 可用 LUT 余量 | **247（1.26%）** —— t7-B 集成综合实测 19,353/19,600 = 98.74%，**已越过 92% 软红线 6.74 个百分点**；预算口径的 1,708 已作废。裁剪预案见 `LUT_CUT_PLAN.md` |
| 缺口 | **至少 11 倍** |
| DSP 需求 | IDCT 需 8~16 个乘法器，**余量仅 10 个** |

**结论：JPEG 物理不可行。RLE 是唯一能用 < 400 LUT 换到 5 倍压缩的方案。**

### 7.6 `.RLE` 文件格式

| 偏移 | 长度 | 字段 | 值 |
|---|---|---|---|
| 0 | 4 | `magic` | `"SCMR"`（0x53 0x43 0x4D 0x52） |
| 4 | 2 | `width` | 640（小端） |
| 6 | 2 | `height` | 480（小端） |
| 8 | 4 | `run_count` | 本帧条目数（小端） |
| 12 | 3 × run_count | `payload` | 每条 `{rgb565[15:0], run_len[7:0]}`，**run_len = 0 表示 256** |

**多帧文件**：上述结构**逐帧重复**（每帧自带 12 B 头），便于随机定位与错误恢复。第 N 帧的偏移由前 N-1 帧的 `run_count` 累加得到。

**`run_len = 0 表示 256` 的理由**：8 bit 游程最大 255，而纯色行有 640 像素（需 ≥ 3 条），用 0 表示 256 可省掉转义字节，且实现最简单（`run_len == 0 ? 256 : run_len`，一个 mux）。

**执行纪律**：一次只裁一级 → 立即重跑 TD → 确认指标 → 决定是否继续。裁剪必须记录在本文档 §12 里程碑。不得为凑资源裁红线项（若 C6 后仍超限，应改架构，例如把 `pix_reader` 的 1,672 LUT 异步 FIFO 换成 BRAM 实现，可省约 1,000 LUT）。

### 10.4 DSP 为什么「算法层零新增」却实测 +5（t7-A 更正）

全部新算法用**移位加**实现：
- 亮度 10 档：`x·k/32`（k = 3,6,10,13,16,20,23,26,29,32）
- 音量 10 档：同构（24 bit signed）
- 坐标映射：Bresenham DDA（整数加减，无乘法）
- AHT20 换算：`×200 = (x<<7)+(x<<6)+(x<<3)`、`×100 = (x<<6)+(x>>5)+(x>>2)`
- RLE 解码：游程倒计数（无乘法）

**唯一会超限的方案已否决**：双线性插值需 12 个 DSP，累计 **24 + 12 = 36 > 29**（2026-11-02 按 t7-A 实测 24 更正，原按预算 19 算得 31）硬超限。**最近邻是唯一选择**。

**⚠️ 但「算法层零乘法器」不等于「DSP 零新增」（2026-11-02 t7-A 实测更正）**：t7-A 综合实测 **DSP 24 / 29 = 82.76%（+5）**，来源**不在上表的算法里**，而在 `wav_stream_player.v:305` 内部又例化了一份 `fat32_reader`（每份 6 DSP）。全工程现在有 **3 份** `fat32_reader`：`u_gallery.u_fat` 6 + `u_player.u_loader.u_fat` 6 + `u_wav.u_fat` 6 = 18，另 `u_img_scaler` 4 + `u_fade_mixer` 1 + `image_player` 自身 1 = **24**，与层级表逐项对上。**这是预算表的结构性漏项**：算法层自检只覆盖了「新算法用不用乘法器」，没覆盖「子模块内部复用第三方 IP 带不带乘法器」。

**DSP 现在是比 LUT 更紧的资源**：硬上限 29，**余 5**。任何再引入 DSP 的方案（如顶层加第 4 份 `fat32_reader`）→ 24 + 6 = 30 > 29，**综合直接失败**，不是「余量紧张」。因此 `file_lba` 的 B/C 方案已物理排除。**任何新增 DSP 的方案必须先报 captain 并由 arch-lead 复核**（见 `RESOURCE_BUDGET.md` §9「★ DSP 独立红线」）。答辩时**不要再说「19 个已被占用」——那是预算值，实测是 24**。

### 10.5 Hold WNS 风险应对（本工程最大风险）

**定性**：Hold 违例是「数据来得太早」，与逻辑深度无关。**新增组合逻辑加深的是 setup 路径，不恶化 hold**。真正会恶化 hold 的是：① 新增 CDC 路径；② 新增时钟域；③ 新增 I/O 时序约束。

**四条强制措施**：
1. AHT20 的 D1/E1 输入必须加 **2 级同步触发器**，SDC 新增 `set_false_path`
2. `wav_stream_player` 全程 25 MHz 同域（**同步 FIFO，无需 CDC**，见 `ARCH.md` §6.6 更正）
3. 新增 IO 必须在 ADC 文件里显式约束 IO 标准与位置
4. **每次综合后必须检查 `final_timing.rpt` 的 `HWNS`**
