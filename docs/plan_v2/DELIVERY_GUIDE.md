## 0. 三分钟跑起来（先看这一节）

| 步骤 | 做什么 | 判断成功 |
|---|---|---|
| 1 | 准备一张 **FAT32** SD 卡（推荐 ≥ 512 MB） | Windows 右键属性里「文件系统」显示 FAT32 |
| 2 | 把 `SmartCampusMedia/assets/v2/sdcard/BURN640/` **里面的内容**拷到卡根（不是拷这个目录本身） | 卡根直接看到 `IMG001.BMP`、`BGM.WAV`、`SCI.RLE` 等 **17 个文件，零子目录** |
| 3 | 用 TD 下载器烧录位流（路径与 MD5 见 **§2.1**），**MD5 应为 `59A6BACC75613F5E953B7ED5A33E05E8`** | 下载工具报成功；板子 HDMI 出画面 |

### 1.3 三条硬约束（**不符合就上不了板**）

#### ① FAT32，且**只接受 FAT32**

`rtl/storage/fat32_reader.v:243-248` 用下面这组判据区分「直接 FAT32 的 VBR」与「MBR 引导扇区」：

```
bytes_per_sec == 512 && root_entries == 0 && fat16_size == 0 &&
reserved_s != 0 && fat_size != 0 && root_cluster >= 2 && root_cluster <= 0x0FFF_FFEF
```

**`root_entries == 0 && fat16_size == 0` 就是「必须是 FAT32」** —— FAT16 的两个字段非 0，会被判为 VBR/BPB 非法（错误码 **2**）。
> ⚠️ **`assets/v2/SDCARD_LAYOUT.md` §2 写的「也接受 FAT16 小卡」是错的**，与 RTL 判据直接冲突。以 RTL 为准：**只能 FAT32**。32 GB 以上的卡 Windows 资源管理器会隐藏 FAT32 选项，用 `diskpart` 或 Rufus 强制格式化为 FAT32。

#### ② 卡根扁平，**零子目录**

`fat32_reader.v:592-593` 的目录项过滤是 `(attr & 0x18) == 0` —— **同时排除 LFN(0x0F)、卷标(0x08) 与目录(0x10)**。模块内部只有 `dir_cluster / dir_sec_idx / dir_fat_cnt` 三个游标，**没有子目录栈、不会递归**。

⇒ 把文件放进 `AUDIO/`、`VIDEO/` 之类的子目录，等价于**文件不存在**。这是本工程踩过的最贵的一个坑：早期 `BURN640/` 落盘成「3 个子目录 + 根目录 8 个文件」，结果 9 个媒体文件全部定位失败（日常没音乐、科普没视频没解说、应急没警报），而**屏幕上一切看起来正常**。

#### ③ 文件名逐字节匹配 8.3 短名，全大写

`fat32_reader.v` 的 `target_name[87:0]` 是**定宽 88 位（11 字节）常量**，由各消费者硬编码：

| 消费者 | 位置 | 硬编码短名 | 注意 |
|---|---|---|---|
| 图库 | `img_loader.v:557-560` | 自动模式 `.target_name(88'd0)` → 回退按 `img_index` 拼 `IMGnnn` + 空格 + `BMP` | 三张图号必须补零：`IMG001` 不是 `IMG1` |
| 音频 | `audio_src_mux.v:34-36` | `"BGM"` + **5** 空格 + `"WAV"` / `"NARR"` + **4** 空格 / `"ALARM"` + **3** 空格 | 空格**个数不同**，因为主名长度不同；改文件名时分隔空格数必须跟着改 |
| 视频 | `gallery_probe.v:152`, `:284` | `"SCI"` + **5** 空格 + `"RLE"` | |

⇒ **改名就找不到**。`IMG1.BMP`（少两个零）、`bgm.wav`（小写）、`IMG001 .BMP`（多一个空格）全部匹配失败。文件名严格用上表 11 字节形态。

### 1.4 `TICKER.TXT` 是**死文件** —— 改它不会改变屏幕上一个字

全仓 `rtl/` 目录下搜 `TICKER.TXT` / `ticker.txt` **零命中**。滚动字幕的文案**编译在比特流里**：

| 内容 | 实际来源 | 改文案要做什么 |
|---|---|---|
| 静态 ASCII 三带（`SMART CAMPUS` / `IMG #n` / `PLAY`·`PAUSE`·`AUTO`·`WAITING`·`EMERGENCY`·`FAIL`） | `rtl/osd/osd_strings.v` line 0~7 | 改 `osd_strings.v` → 重新综合 |
| 日常六段中文校园介绍 | `rtl/osd/osd_strings.v` line 8~13（465 字形，来自 `cjk16_bitmap.hex`） | 改文案 → 跑 `scripts/gen_osd_strings.py` → 重新综合 |
| 科普视频 18 段字幕 | `rtl/osd/narr_subline.v`（由 `narration.srt` 生成，1 块 BRAM，563 深） | 改 `narration.srt` → 重新生成 → 重新综合 |
| 应急疏散两段文案 | `rtl/osd/osd_strings.v` line 14~15（104 字，整轮翻转） | 同上 |

⇒ **答辩演示时若被问「这块屏上的字是卡里的还是芯片里的」**，答案是**芯片里**，卡上的 `TICKER.TXT` 只是协议占位。同理 `NARR.IDX` / `NARR.SRT` / `SCI.IDX` 也都不在运行时被读。

### 1.5 素材格式硬门槛（不满足就报错，不会「尽力而为」）

| 素材 | 必须满足 | 不满足时的表现 | 代码位置 |
|---|---|---|---|
| BMP | **640×480 / 24 bit / BI_RGB 无压缩 / 54 字节头** | 数码管 `b` + 子码（`1` 非 BM、`2` 非 24bit、`3` 有压缩、`4` 宽高不符） | `bmp_parser.v:28`, `:41` |
| WAV | **PCM(Format==1) / 单声道 / 48 kHz / 16 bit** | 数码管 `d` + 子码（`1` 非 RIFF/WAVE、`2` 非 PCM、`3` bits≠16、`4` 采样率≠48k、`9` 声道≠1）**立即停** | `wav_stream_player.v:38-63`, `:55-63` |
| RLE | magic `SCMR` / 631 帧 / 640×480 RGB565 | 科普模式无画面 | `rle_decoder.v` |

> 位图**只做缩小、不做放大**（`img_scaler.v:24-38`）：把 320×240 的图放进去只会显示成屏幕中央一小块。**卡里只放一套 640×480 源图**，五档分辨率是「内部渲染分辨率」—— 由输出侧抽样放大实现，与素材分辨率无关。

### 1.6 图片必须从 `IMG001` 起**连续编号，中间不能缺号**

`gallery_probe.v:18-35` 的枚举规则：按 `IMG001.BMP`、`IMG002.BMP` … 顺序**逐个探测，遇到第一个缺失即停**，输出「连续素材数」。

⇒ 卡里放 `IMG001` `IMG002` `IMG004`（缺 `IMG003`），**只有 2 张可用**；零散放一张 `IMG005` 不会被当成「第 5 张」。这是有意的设计：`player_ctrl` 的索引是 0 基连续量，中间有缺口时「下一张」会落到空文件上，不如从一开始就截断。
枚举上限 `MAX_COUNT` 默认 **31**（5 位索引的物理上限）。

### 1.7 烧录步骤（照做即可）

1. 格式化 SD 卡为 **FAT32**（≥ 32 GB 卡需 `diskpart` / Rufus 强制）。
2. 把 `SmartCampusMedia/assets/v2/sdcard/BURN640/` **里面的内容**（不是目录本身）拷到卡根。
3. **肉眼核对**：卡根直接能看到 `IMG001.BMP`、`BGM.WAV`、`SCI.RLE`，且**没有任何文件夹**。若看到 `AUDIO/` `VIDEO/` `SRT/`，说明拷的是旧版子目录布局，`fat32_reader` 读不到里面的文件。
4. 可选自检：`cd SmartCampusMedia` → `python scripts/gen_assets_v2_sdcard.py --verify`（脚本自检项 13~18 会核对顶层 17 个文件 / 零子目录 / 8.3 名合法性 / FAT 目录项形态 / `SUBDIR` 列全为 `.`）。
5. 插卡 → 烧录位流 → 复位 → 等 5 秒。

**不要**把 `assets/campus_media/preview/smart_campus_showcase.mp4` 拷进卡里当视频源 —— 它是 H.264，FPGA 无解码能力，只能作答辩的电脑端演示素材。

### 1.8 常见失败对照表（现象 → 最可能的原因 → 查哪里）

| 屏幕现象 | 数码管 | 最可能的原因 | 查什么 |
|---|---|---|---|
| 一直放测试彩条，不出图 | `C0`~`C*` | 卡没插好 / 卡不响应 / 卡不兼容 | 换卡；确认 `sd_cd`（球 E15）插卡时为低 |

## 3. 使用说明

### 3.1 上电流程与指示灯

上电顺序（**顺序本身有信息量**）：

1. **LED bit4 亮**（HDMI 锁定）—— 它要求「PLL 锁定 **且** 发射核视频锁定」两个条件同时成立。只看 PLL 锁定的老语义分不出「时钟有了但核没对齐」这种最难查的故障（插上线却不亮、PLL 灯却是亮的）。
2. **LED bit5 亮**（SDRAM 锁定）—— 视频通路不依赖 SDRAM PLL（`video_content_mux` 在没图时出测试彩条），但图片/视频播放依赖。
3. **LED bit0 亮**（图片就绪）—— 帧缓存里已有一帧完整图像。
4. 数码管 `dig3` 从 `1`（正在扫描 SD）→ `2`（正在装载）→ `3`（就绪）→ `4`（轮播）。

### 3.2 LED[7:0] 逐位含义（`dmz_eg4s20_hdmi_top.v:1238`）

| bit | 信号 | 含义 |
|---|---|---|
| 7 | `err_active` | **存在任何面向用户的错误**（含「卡好但零张图」这类改造前没有任何指示灯反映的盲区） |
| 6 | `image_loading` | 正在装载图片 |
| 5 | `sdram_lock_pix[1]` | SDRAM PLL 锁定 |
| 4 | `locked && hdmi_video_locked` | HDMI 锁定（PLL 锁 **且** 发射核视频锁） |
| 3 | `mode == 2` | 应急模式 |
| 2 | `\|reader_status[1:0]` | FIFO 异常 |
| 1 | `auto_play` | 自动轮播中 |
| 0 | `image_ready` | 图片就绪 |

> **bit7 的语义在 v2 被特意扩大**：否则现场换一张没有 `IMGnnn.BMP` 的卡，灯全灭、屏幕放测试图，看起来和正常启动一模一样。

### 3.3 数码管四位（`dmz_eg4s20_hdmi_top.v:1242-1255`）

**高两位（`dig3`/`dig2`）在「有错」与「正常」两种口径间整组切换**：

| 状态 | `dig3` | `dig2` |
|---|---|---|
| **有错** | 助记字母类：`C` / `F` / `0` / `b` / `d` | 类内子码 |
| **正常** | 播放状态：`0` 空闲 / `1` 扫描 / `2` 装载 / `3` 就绪 / `4` 轮播 / `5` 应急 | 当前图号 |

低两位固定：`dig1 = loader_index[3:0]`、`dig0 = pattern_sel`。

> 改造前故障码与播放状态码**混用同一个数字空间**（都占 `dig3`），用户看到 `13` 必须查表才知道是什么意思。改用字母后「类型一眼可分」。

### 3.4 故障提示：五类「用户该做什么」（`rtl/control/err_prompt.v`）

把 5 个模块散落的 1~9 内部码，归并成 **5 类用户动作**：

| 助记 | 英文 | 用户该做什么 |
|---|---|---|
| **`C`** | Card | 请**插卡**（无卡 / 卡不响应 / 卡不兼容） |
| **`F`** | Format | 请**格式化**为 FAT32（签名错、BPB 非法、簇链坏） |
| **`0`** | 零张图 | 卡是好的，但**根目录没有图片** —— 请放 `IMG001.BMP` 起的连续文件 |
| **`b`** | bmp | **图片格式/尺寸不符**（非 BM、非 24bit、有压缩、非 640×480） |
| **`d`** | data | **数据通路/存储故障**（读块错、SDRAM、超时、FIFO 无空间） |

**为什么助记字母这么奇怪**：`seg_decoder.v` 只实现 `0~9 / A / b / C / d / E / F` 共 16 个字符，**没有 P、n、r**，所以 `Picture` 这类词用不了，改用数字 `0`（「零张图」，语义自明）代替；`b`/`d` 用小写以便与 `B`/`D` 区分。

**蜂鸣器设计：延迟 1.5 s、只响 3 s、错误消失即清零。** 理由不是省事：本设备是无人值守的校园媒体屏，**若告警音无限循环，没人来处理的后果就是整栋楼一直听滴滴声 —— 那比完全不响更糟，用户会直接把蜂鸣器拆掉，告警通道彻底失效**。设计成「响一段就停」：听到的人过来看数码管，数码管会把问题一直摆在那里。

**应急画面为什么不用图片**：`emerg_page.v` 的每一个像素都由自己的 `(active_x, active_y)` 经组合比较得出，**不依赖 SD 卡是否插入、是否可读、是否格式化**。纯红屏只能表达「出事了」，说不出「往哪跑」，而后者才是应急页的目的。画面构成：外墙框 4 px（x∈[64,575)、y∈[72,408)）、一条水平主走廊 + 一条北支走廊、房间隔断 2 px、当前位置=青色实心块、两个出口=亮绿实心块、到最近出口的路线=**直角折线**（严格轴对齐、不评估斜率 ⇒ 无乘法器 ⇒ 零 DSP）。**文字不由本模块画**，由 OSD 层提供 —— 这让它零 BRAM / 零 DSP / 零状态机。

**实测能力与设计目标的关系（★ 本节已按 RTL 实况更正，勿沿用旧说法）**：

视频通路按 **5 fps 固定帧率**运行（`rtl/top/dmz_eg4s20_hdmi_top.v:521` `.play_fps(8'd5)` 为常量）。SD 卡读带宽按 5 fps 核算过，均值 **0.649 MB/s**、最坏 **1.012 MB/s**，占 SPI 实用带宽 1.25 MB/s 的 **52% / 81%**。**若实测出现持续欠载（例如卡质量差、块读延迟超预期），系统的行为是「停在上一个已显示帧、不插黑、不撕裂」，不是自动降帧。**

「自动降 2 fps」在初版设计中讨论过并写入过 `ARCH.md:1244` / `PLAN.md:477`，但**从未在 RTL 实现** —— 这是文档与实现的偏差，如实记录在此。2 fps 是带宽核算的假设工况，不是系统能力。

**为什么能确定这一点（三条机器可查的证据，答辩被问时逐条摆）**：

- `play_fps` 在顶层是硬接常量 `8'd5`（`dmz_eg4s20_hdmi_top.v:521`）。全仓 `play_fps` 只有 `rle_decoder.v:93`/`:94`（注释）、`:177`（端口声明）、`:282`（取非零保护 `fps_eff`）、顶层这一处例化 —— **没有任何一条路径能把 5 改成 2**。
- `rle_underrun` 全仓只有两处：顶层 `:511` 的 `wire rle_underrun;` 声明与 `:528` 的 `.underrun(rle_underrun)` 连接。**它不驱动显示、不改变帧率、不上报错误码** —— 是一个「接出来但没用」的信号。
- 欠载时的真实行为写在 `rle_decoder.v:29`：`underrun keeps the previous frame: no done -> no commit -> no flip` —— **画面停在上一帧，不撕裂、不闪白、不黑屏**。这是可演示、可解释的行为，**答辩就按这个讲**。

**观感说明**：5 fps 是「幻灯片切换」而非流畅视频，这是 SD 卡 SPI 接口的物理带宽上限（实用 1.25 MB/s）决定的，不是实现偷懒。带宽按 5 fps 核算后最坏占 81%，仍有余量 —— **所以固定 5 fps 是有依据的选择，不是妥协后的残值**。

## 4. 答辩材料骨架：五个加分项 E1~E5

### E1 图层叠加：滚动字幕

- **口径**：在视频/图片画面上**叠加**滚动文字层，而不是切换整屏。
- **实现位置**：`rtl/osd/osd_caption.v`（滚动带 `TICKER_Y0=448` / `TICKER_Y1=463`，全宽）、`rtl/osd/osd_strings.v`（16 行字符表）、`rtl/osd/cjk16_font.v`（中文字库 **15 块** BRAM9K）、`rtl/osd/narr_subline.v`（科普字幕 1 块 BRAM）。
- **关键设计**：图层**四带分布**（标题 y∈[16,31]×x∈[32,127]、图号 y∈[16,31]×x∈[576,623]、状态 y∈[48,63]×x∈[32,103]、滚动带 y∈[448,463] 全宽），与画面主体**几何不重叠**。优先级链：应急滚动 > 科普字幕 > 日常校园介绍。
- **实测数字**：字库 `cjk16_charset.txt` **465 字形**；科普字幕 18 段、最长一段 57 字符 < 滚动带容量 64 列（**所以一行够，不需要第二行**）。
  - 字库 `cjk16_font`：**15 块 BRAM9K**（探针三写法均 15，`project/t2_cjk16_probe/reports/area_a/b/c.txt`；`area_ref.txt` 基线 0）+ 4 LUT。
  - 科普字幕 `narr_subline`：**1 块 BRAM**、最终位流 **121 LUT / 13 REG**（`reports/t7b_seed_seed7_area.txt`）；探针增量实测 **+399 LUT / +8 REG / +1 BRAM**（`project/t13_narr_probe/reports/area_a.txt` 436 − `area_ref.txt` 37）。
  - 字幕层整体 `osd_caption`（含字库与字幕两个子实例）：最终位流 **203 LUT / 27 REG / 16 BRAM**。
- **60 秒演示**：日常模式看图下方滚动中文 → Key5 关掉（字幕与静态三带一起消失、画面与音频不受影响）→ Key5 开回来 → Key2 进科普模式看视频字幕跟着 `frame_idx` 逐句切换 → Key3 进应急看滚动带被强制打开。
- **追问与答**：
  - 「字幕是卡里读的吗？」→ **不是**，全部编译进比特流。改文案要改 `osd_strings.v` / `narration.srt` 后重新综合。
  - 「字库够用吗？」→ 465 个字形，而字幕去重只需 253 个字符（汉字 230 + 非汉字 23），**缺字 0**。
  - 「一层字幕为什么需要 BRAM？」→ 字库是 `reg [15:0] mem [0:8191]`（`cjk16_font.v:84`），地址 = `{glyph[8:0], row[3:0]}` 共 13 位，**物理深度 8,192 字 × 16 bit = 16 KB**（实际用到 465 字 × 16 行 = 7,440 条，其余留空）。16 KB 塞不进 LUT（那要 1.6 万左右的 LUT 槽位），所以做成同步读的 BRAM —— 探针实测占 **15 块 BRAM9K**（每块 9,216 bit，15 × 9,216 = 138,240 bit ≥ 131,072 bit）。

### E2 画面转场：淡入淡出

- **口径**：图片切换有过渡效果，而非硬切。
- **实现位置**：`rtl/storage/fade_mixer.v`（21 行组合逻辑，`level` 0 = 全黑、255 = 原样）；**例化在 `rtl/storage/image_player.v:624`（`u_fade`），不在顶层**。
- **实测数字**：最终位流 `route` 阶段 **33 LUT / 1 DSP**（`reports/t7b_seed_seed7_area.txt` 实例行 `u_fade`）。

### 5.1b 一笔结构性收益：像素 FIFO 从分布式 RAM 换成 BRAM（t25）

最终位流 `route` 后 **16,414**，相对前一趟 `route` 的 **18,473**（`reports/hdmi_area.txt`，11-02 20:11:06）降了 **2,059 LUT**。其中**最大的一笔是结构优化，不是砍功能**。

**下面这张表用的是同一对报告，也是 `route` vs `route`** —— 改前基准就是上面那句里的 `hdmi_area.txt`，一份报告同时充当总量基准与模块基准，读者不必在两份文件之间跳：

| 实例 | 改前（`route`，`reports/hdmi_area.txt` 11-02 20:11:06） | 改后（最终位流 `route`，`reports/t7b_seed_seed7_area.txt` 11-03 00:31:36） | 差异 |
|---|---|---|---|
| `u_pix_fifo`（`pix_reader` 内跨时钟域像素 FIFO） | **1,638 LUT / 0 BRAM** | **48 LUT / 2 BRAM** | **−1,590 LUT / +2 BRAM** |
| `u_write_fifo`（同一模块的另一次例化） | 78 LUT / 3 BRAM | 83 LUT / 3 BRAM | +5 LUT / **0**（BRAM 数不变） |

> **归因纪律（重要，否则会被问倒）**：这 2,059 是**两趟不同综合的总量差**，**不是**某一项的单独贡献。可确证归因于 FIFO 改法的部分是上表那 **−1,590**（同一实例、同一层次位置、**且两侧同为 `route` 阶段**）；余下 **2,059 − 1,590 = 469** 来自 seed 搜索、`merge_tiny_lut`、`min_ripple_len` 等综合设置变化 —— **不要把它们说成 t25 的成果**。（这正是 `RESOURCE_BUDGET.md` §1.1c 那条禁令的实例：跨趟相减看起来像增量，但只在能对上同一实例时才算归因。）

**根因**：`async_fifo.v` 原实现是 `assign rd_data = mem[rd_bin[ADDR_WIDTH-1:0]];` —— **异步组合读，结构上无法映射到 BRAM**，只能铺成分布式 RAM（每个比特一个 LUT 槽位）。改成 **FWFT（First-Word-Fall-Through）同步读 + 预取寄存器** 后，512×32 bit = 16,384 bit 用 2 块 BRAM 就装下了。

> **为什么只省 2 块 BRAM 却省 1,590 LUT**：BRAM 与 LUT 不是同量纲的替代关系 —— 16,384 bit 铺成分布式 RAM 就是一万六千个 LUT 槽位的量级。
>
> 这条也顺带解释了本工程一个长期反常现象：**`#bram` 一直很闲（37/64 = 57.8%）而 LUT 一直紧张**。原因不是 BRAM 用不上，而是有大量本该进 BRAM 的阵列在吃 LUT —— 异步读法让综合器无法推断成 BRAM。
>
> **答辩可以直接用这条**：我们要过资源关靠的是**改实现**，不是删功能。全工程 C1~C6 六级裁剪预案**至今一级都没执行**。

**为什么另一处 `u_write_fifo` 只涨了 5 LUT 而没有跟着受益**：它本来就已经是 3 块 BRAM（写侧 FIFO 的读法不同，旧实现就推断成功了）。改 FWFT 后小涨 5 LUT（78 → 83，同阶段 `route` 对比）是预取寄存器与控制逻辑的代价。**验收时要盯住它的 `#bram` 不得掉到 3 以下**，否则等于「省了像素 FIFO、赔了写 FIFO」。

**怎么解读这两组数（答辩会被问）**：`Setup WNS +0.113 ns` 是**报告口径的余量**；`clk0 实际可达 25.071 MHz` 是把余量折算成频率的说法 —— 二者是同一个事实的两种表达。

> **唯一允许的对外说法（逐字，`BOARD_ACCEPTANCE.md` §0.1 定的）**：
> **「时序通过，余量 0.28%（`Fmax 25.071 MHz` / 需求 25 MHz），属零余量级。」**
>
> **禁止的四种说法**：❌「时序有余量」／❌「时序充裕」／❌「时序 margin 充足」／❌「`Fmax 25.071 MHz` 满足 25 MHz 需求，有余量」。**「通过」与「有余量」是两件事** —— 通过了，但余量只有 0.28%。

**为什么必须说「零余量级」而不是「通过」了事**（三条前提，缺一条这句话就不成立）：

1. **五条件共同达成，任一项回退即跌破零**：`set_param rtl min_ripple_len 45`（+ `commit_param -step rtl`）、`set_param place seed 7`、t24、t25、t26 —— 少任何一项就不是这个位流。**v2 是活证据：只多了 t26 那 1 个 LUT，`SWNS` 就从 `+0.113 ns` 掉到 `−0.194 ns`。**
2. **温度 / 电压 / 器件批次均无余量**：0.113 ns 是室温、额定电压、这一块板的结果，**没有为工艺角与温漂留任何余量**。
3. **只有室温真机跑通才作数**：静态时序签核 ≠ 上板能跑。上板验收见 §5b。

> **`STNS 0.000` 与 `Viol Endpoints 0` 不能互推，两个数都要单独报。** `TNS = 0` 的意思是「所有违例路径的负余量之和为零」，它**在存在正余量路径时同样成立**；`Viol Endpoints 0` 是「一条违例端点都没有」。**反过来，只要出现一条违例，`TNS` 必然不为零；但 `TNS = 0` 推不出零违例** —— 两个数是不同维度，别用一个代替另一个。
> `place` 阶段曾有 14 条 hold 违例（`Hold TNS -154`），**`route` 阶段已全部修复为 0** —— 这说明 hold 修复确实在 route 阶段执行了，不是被忽略。

### 6.2 D-01a：AHT20 厂商免责条款的主动声明（**必读，答辩前必须看这一节**）

**这一节不是「补充说明」，是主动披露。** 依据是 AHT20 数据手册（`D:\date sheet\AHT20.pdf`，2,100,321 B / 15 页 / SHA256 `999B49DC0FA6987D3C83B4B7003D2A340A4D5F03184B0B09985901270BF06822`）**第 15 页「注意事项 / 警告，人身伤害」**的原文：

> **「勿将本产品应用于安全保护装置或急停设备上，以及由于该产品故障可能导致人身伤害的任何其它应用中。不得应用本产品除非有特别的目的或有使用授权。在安装、处理、使用或维护该产品前要参考产品数据表及应用指南。如不遵从此建议，可能导致死亡和严重的人身伤害。」**

**关键在条文文义，不在自我定性**：这句免责条款限制的是两类用途 —— **「安全保护装置」**与**「急停设备」**。本系统**两类都不是**，这不是我们给自己贴的标签，是对条文适用范围的判读：

**第一层：我们不做什么（四条，每一条都能被 RTL 验证）**

| # | 声明 | RTL 依据 |
|---|---|---|
| 1 | **不控制任何执行机构** | 顶层端口表里没有任何执行器输出（`rtl/top/dmz_eg4s20_hdmi_top.v` 全部 38 个端口：时钟 / 复位 / 键盘矩阵 / LED / 数码管 / 蜂鸣器 / SD / 音频 PWM / I²C / HDMI） |
| 2 | **不切断任何电源** | 同上 —— 无继电器、无电源使能引脚 |
| 3 | **不输出任何告警联动信号** | 全仓 `temp_alarm` 与 `sensor_fault` **无一处进 `err_prompt`、无一处进蜂鸣器**（逐文件 grep 核实）。`temp_alarm` 的全部去处只有两处模式切换（`mode_ctrl.v:179` / `:203`，均为 `DAILY→EMERG` / `SCIENCE→EMERG`） |
| 4 | **不承担保护职能** | 应急模式产出的是**屏幕画面**（疏散示意图 + 滚动文字），不产生任何外部动作 |

**第二层：我们做什么 —— 定性为「应急疏散引导演示」**

本系统是**教学演示装置**，应急模式的功能是**在屏幕上演示一套疏散引导画面**（`emerg_page.v` 画楼层示意与到最近出口的直角折线路线，OSD 字幕层给出疏散文字）。它**不是**火灾探测装置，**不是**联动报警装置，**不是**生命安全设备。

**第三层：传感器失效了怎么办 —— 两条独立的兜底**

1. **AHT20 只是触发入口之一，不是唯一入口**。进入应急有两条路径：① `temp_alarm` 上升沿（温度 ≥ 45.00 ℃）② **Key3 单按**（`mode_ctrl.v:172` / `:197`）。**Key3 是独立的手动冗余通道** —— 温度通道完全失效时，演示流程仍可完整走通（进应急、看画面、Key3 双按 2 s 退出，`:216-224`）。
2. **`sensor_fault` 绝不触发应急 —— 这是对免责条款的正确响应，不是「保守」**。`rtl/top/dmz_eg4s20_hdmi_top.v:306-311` 有一条绝对禁令原文：**「`sensor_fault` 绝不能接到 `temp_alarm`。传感器坏 ≠ 着火。接了会让终端进应急并且退不出来」** —— 退出要等温度降到 `TH_LOW`，而传感器坏了根本不再出读数。**「把屏幕锁死在应急画面」比「没有高温联动」严重得多。** 对应地，`aht20_ctrl.v:144-150` 注释也写明「上级 `thermal_guard` **不得因 `sensor_fault` 触发应急模式**」。

> **一句话答辩口径**：**「AHT20 的手册明确说不要用在安全保护装置或急停设备上 —— 我们两条都不是。这套系统不控制执行机构、不切断电源、不输出联动信号，应急模式是屏幕上的疏散引导演示；而且温度只是触发入口之一，Key3 手动入口是独立冗余；传感器坏了我们选择不触发应急，而不是把屏幕锁死在应急画面上。」**
>
> **为什么主动写进正文明而不是藏进附录**：评委是否读过这份手册我们无法预判。**读过而没说，是隐瞒；没读过而没说，是运气 —— 运气不该作为交付的一部分。**

### 9.1 全仓扫描型自验必须带阳性对照

**现象**：`Select-String` 扫全仓，命中 0 处 —— 结论写「已清零」。

**陷阱**：「0 处命中」和「扫错了」在输出上完全一样。目录不存在、编码不匹配、文件名模式写错，都会给出一个**看起来完全正常的 0**。

**做法**：同一条命令再跑一次，pattern 换成一条**你确信存在的**字符串（本仓用 `17,892`，实测 31 行）。**阳性也是 0 ⇒ 本次自验作废，不是「已清零」。**

**本仓实例**：t11 曾报「命令 A / B 均 0 处」，复跑后真实为 **A = 19 行 / B = 1 行** —— 上一轮只扫了 `DELIVERY_GUIDE.md` 一份文件，却报了整目录结论。阳性对照一跑就会露。

### 9.2 混合 BOM 目录里，`Get-Content` 会让一半文件静默失配

**现象**：同一个 pattern，扫同一批文件，有的能命中有的不能，**不报任何错**。

**根因**：`Get-Content`（PowerShell 5.1，不带 `-Encoding`）**靠 BOM 猜编码**。无 BOM 的 UTF-8 文件会被按 GBK 解码，中文全部变成 `瀵勫瓨鍣ㄤ細琚炕鎴` 这类乱码，于是中文 pattern 一个都匹配不上。

**本仓实测：16 份 md 的 BOM 状态是分裂的（9 份有 BOM / 7 份无 BOM）** ——

| BOM = True（9 份） | BOM = False（7 份） |
|---|---|
| `ARCH.md`、`ARCH_ADDENDUM_VIDEO_PATH.md`、`DELIVERY_GUIDE.md`、`FONT_ARCH_RULING.md`、`KEYMAP.md`、`PLAN.md`、`RESOURCE_BUDGET.md`、`T2_EMERG_PAGE.md`、`T3_CJK_TICKER.md` | `FAT32_REENTRY_FIX.md`、`LUT_CUT_PLAN.md`、`T1_GEOM.md`、`T1_TO_T7_WIRING.md`、`T4_VIDEO_PATH.md`、**`T5_CONTROL_SENSOR.md`**、`T7_INTEGRATION_PLAN.md` |

**⇒ 这是最坏的分裂形态：同一命令扫到一半正常、一半失配，结果看起来「大部分对」。** 命令 A 的 19 处全在有 BOM 的文件里，用错写法也「基本正常」；命令 B 唯一那处恰在无 BOM 的 `T5_CONTROL_SENSOR.md`，**恰好被吃掉且不报任何错**。

**同一份文件、同一批字节，换一种读法连行数都不一样**（`docs/plan_v2/KEY9_RULING.md`，无 BOM，实测）：

| 读法 | 行数 |
|---|---|
| `Get-Content $p`（默认，靠 BOM 猜编码） | **173** ✗ |
| `Get-Content $p -Encoding UTF8` | 240 ✓ |
| `[System.IO.File]::ReadAllLines($p, [System.Text.Encoding]::UTF8)` | 240 ✓ |
| python `open(p, encoding='utf-8')` | 240 ✓ |

**差 67 行，不是差几行。** 机制：GBK 是双字节编码，汉字首字节落在 `0x81`–`0xFE` 而**下一个字节恰好是 `0x0A`** 时，那个换行会被吞进「一个 GBK 字符」里 —— **换行凭空消失，行号整体错位**。所以结论要从「pattern 匹配不上」升级为「**行号和内容一起错**」。

**t10 会踩这个坑**：t10 要做「文档与代码不符」的比对，若用 `Get-Content` 数行号或做逐行 diff，会读到错位的行，甚至把两份**不同**的文件判成「行数一致」、把同一份文件的两个版本判成「行数不一致」。**行号一律用 `ReadAllLines(...,UTF8)` 或 `Select-String`（后者自带行号且按文件编码读）。**

**三条硬规矩**：

1. 一律用 `Select-String -Path`（按文件编码读），**不要** `Get-Content` + `-match`
2. 需要读全文时用 `[System.IO.File]::ReadAllLines($p, [System.Text.Encoding]::UTF8)` 或 Python `open(p, encoding='utf-8')`
3. **判据：同一个命令在两种读法下结果不同，就是编码问题，不是文件内容问题**

**单文件三行对照（可复现，PS 5.1.26100.9711 实测）**：

```powershell
$f = 'D:\FPGA_Compelate\docs\plan_v2\T5_CONTROL_SENSOR.md'   # 无 BOM，前 3 字节 23 20 74
Select-String -Path $f -Pattern '静默失效'                    # → 1 命中  ✓
(Get-Content $f) | ? { $_ -match '静默失效' }                 # → 0 命中  ✗
(Get-Content $f -Encoding UTF8) | ? { $_ -match '静默失效' }  # → 1 命中  ✓
```

### 9.3 报数必须带分母

**「0 命中」和「0 个文件」在输出上完全一样。**

写 `A = 19 行 / 16 文件`，不写裸的「0 处」。扫描类结论一律附三个数：**扫了几个文件、命中几行、阳性对照命中几行**。

**为什么值得单列**：本项目已经因为「永远返回通过的判据」付出过代价 —— `tb_fifo_fwft` 146 条假绿、`tb_osd_param_text` 58 条假绿、`check_port_names.py` 自身被反证抓出两个 bug。**验证工具本身也需要被验证。**

### 9.4 报「同一实例前后对比」时，两侧必须同阶段 —— 即使结果凑巧接近

**现象**：本文档 §5.1b 初版那张 `u_pix_fifo` 对照表，左栏引 `optimize_gate` 阶段的 `reports/t7b_gate_area.txt`（1,634 LUT），右栏引 `route` 阶段的 `reports/t7b_seed_seed7_area.txt`（48 LUT），算出 **−1,586 LUT**。

| 实例 | 改前 `route` | 改后 `route` | 同阶段差异 | 初版跨阶段差异 |
|---|---|---|---|---|
| `u_pix_fifo` | 1,638 LUT / 0 BRAM | 48 LUT / 2 BRAM | **−1,590 / +2** | −1,586（差 4） |

### 9.7 改文件必须走同一条通道（硬规则，本工程已因此毁过三次文件）

**规则**：本仓任何文本文件（`.md` / `.v` / `.py` / `.tcl`）的写操作，**必须走同一条通道**：

```python
# 读：utf-8-sig 会自动吃掉 BOM
txt = io.open(p, "r", encoding="utf-8-sig").read()

# 写：显式声明编码与换行；原文件有 BOM 的，写回时补回去
io.open(p, "wb").write(b"\xef\xbb\xbf" + txt.encode("utf-8"))
```

**写完立刻回读断言三件事**（一个都不能省）：

1. **BOM 状态与改前一致**（`raw[:3] == b"\xef\xbb\xbf"`）
2. **CRLF 计数符合预期** —— 本仓 `docs/plan_v2/*.md` 全部是 LF，所以 `body.count("\r") == 0`
3. **总行数增删与预期相符** —— 插入 N 行就应涨 N 行，差出几十行就是结构坏了

**三次事故的完整账**（都不是「写错了内容」，是「写坏了文件结构」）：

| # | 做法 | 后果 | 发现方式 | 修复代价 |
|---|---|---|---|---|
| 1 | `Set-Content -Value` 传 `-join` 之后的**单个字符串** | `T7_INTEGRATION_PLAN.md` 从 **1,897 行变成 1 行、0 个换行符**（内容一个字没丢，但整份文件成了一行） | 回读时 `Get-Content` 只报 1 行 | **几个小时** —— 该仓不是 git 仓库、无备份，只能从会话存档（zstd）里重建 84 个写操作的全局时间线、全量重放，再与损坏文件做去空白 diff 逐字符验证 |
| 2 | `Set-Content -Encoding UTF8` 直写 `.v` | 给 Verilog 源加了 UTF-8 BOM | `vlog` 编译报 **`unexpected non-printable character 0xef`** | 几分钟（去掉 BOM） |
| 3 | Python `io.open(p, "w", encoding="utf-8")` 重写 `.md` | **丢掉了原文件的 BOM**，文件从「有 BOM」变成「无 BOM」 | 回读断言 `BOM=False` 立刻抓到 | 几十秒（`b"\xef\xbb\xbf" + raw`） |

> **为什么事故 1 的代价比 2、3 高两个数量级**：前者的破坏是**结构性的且不可从文件本身恢复**（文件里只剩下「内容正确的一行」），后两者的破坏是**可逆的一个字节**。所以「写完回读断言」这件事的价值不是均匀的 —— 它主要在防第一种。

> **顺带解释一个看似矛盾的现象**：事故 3 丢掉 BOM 本身不会让任何东西报错，但它会让 §9.2 那个坑从「部分文件失配」变成「刚改过的那份失配」—— **同一个目录里 BOM 状态不一致，就是 `Get-Content` 默认编码猜错的直接成因**。三次事故里有两处是「先发现内容对、后发现结构坏」，靠人工回读才抓到。

**结论三条（现在就生效）**：

1. 写 `.md` / `.v` / `.py` 一律用 Python 显式 `encoding="utf-8"` + `newline="\n"`（写二进制时自己补 BOM）。
2. **禁止用 PowerShell 的 `Set-Content` / `Out-File` 直写交付文档** —— 它的 `-Value` 语义（把单串当一行写）与编码默认值（靠 BOM 猜）都会静默改变文件结构。确需用 PowerShell 时，改 `[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))`，并同样回读断言。
3. **批量改表格 / 长文档时，用「锚点断言」而不是「下标搜索」**：先 `assert txt.count(old) == 1` 再替换，替换后立刻回读断言。**不要用 `IndexOf` 找「段首 / 空行」来界定替换块** —— 本工程曾因块内用 `>` 作间隔行而非空行，一次替换误删了一整节正文，靠 8 个关键串全部 0 命中才发现。
