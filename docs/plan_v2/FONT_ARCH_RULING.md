## 2 Q1 之一：LUT 成本不是一个数，而是跨 8.5 倍的区间

### 2.1 三个实测锚点（同一 RTL 家族，`area.txt` 分层报告）

`Report Hierarchy Area` 列顺序 = `le | lut | ripple | seq | bram | dsp`。**只引 `le`/`lut`/`bram`/`dsp` 四列，不引 `reg` 列**——该列对纯组合模块也会非零（`science_page` 纯组合却记 380），不是触发器数。

| 实例 | 模块 | 字形 × 行 × 位宽 | 总 bit | 实测 lut | 折算 |
|---|---|---|---|---|---|
| `u_osd_panel / u_font` | `osd_font8x16` | 41 × 16 × 8 | 5,248 | **36** | 145.8 bit/lut |
| `u_caption / u_font` | `osd_font8x16` | 41 × 16 × 8 | 5,248 | **16** | 328.0 bit/lut |
| `u_science_page / u_font` | `science_font16` | 38 × 16 × 16 | 9,728 | **284** | 34.3 bit/lut |

**前两行是同一份 RTL、同一个模块、同一份字模常量**，只因例化上下文不同（`u_caption` 里 `t_line` 只取 0/1/15 三个值、`t_col` 范围有限，常量传播把大量 case 分支优化掉了）就差了一倍多（36 : 16 = 2.25 倍）。这证明：**模块级 lut 是优化后的数字，不能当常数外推。**

### 2.2 465 字形的三个口径

| 口径 | 依据 | 换算率 | 465 字形折算 | 占 LUT 余量（4,281） |
|---|---|---|---|---|
| **最乐观** | 套 `osd_font8x16@u_osd_panel` 的 145.8 bit/lut（按字形数外推：36 × 465 ÷ 41） | 145.8 | **409 lut** | 9.6% |
| **非零位口径** | `cjk16_bitmap.hex` 7,440 行全有效，非零行 6,080（81.7%），非零 1-bit 总数 32,871；`science_font16` 非零位 4,645 bit ↔ 284 lut = 16.35 bit/lut | 16.35 | **2,010 lut** | 47.0% |
| **最悲观** | 套 `science_font16` 的 34.25 bit/lut | 34.25 | **3,475 lut** | 81.2% |

三口径相差 8.5 倍。**这个区间本身就说明：用 LUT 方案做决策是拿一个跨 8.5 倍的不确定量去赌 4,281 的余量。**

### 2.3 余量还在缩

`reports/diag_key1_fifo_backpressure_20261101/area.txt` 仍是 **t5 开始前**的快照。t5 已落盘但尚未综合的 6 个模块合计 2,014 行：`rtl/sensor/i2c_master.v`(412) / `aht20_ctrl.v`(731) / `thermal_guard.v`(173) / `rtl/control/mode_ctrl.v`(257) / `key_router.v`(310) / `rtl/video/brightness_apply.v`(131)。加上 t6/t7 待写的 `rle_decoder` / `wav_stream_player` / `audio_src_mux` / `pix_mosaic` / `ratio_map` / `emerg_page`，**真实余量必然小于 4,281**。

LUT 方案的悲观口径（3,475）会吃掉真实余量的 81% 以上，中值口径（2,010）也要吃掉近一半。**在「核心功能（视频解码、音频流、温控联动）还没开始综合」的阶段把一半余量押在一个字库上，是资源错配。**

## 3 Q1 之二：「不能有 1 拍延迟」不是硬约束

### 3.1 那句话的出处与被覆盖范围

两处注释说的是同一件事，不是两条独立证据：

- `rtl/osd/osd_caption.v:74-77`：「字模与字符串表是组合查表，**综合成 LUT 而非 BRAM（BRAM 有 1 拍读延迟，字幕必须与图像同拍，加不起这个延迟）**」
- `assets/v2/masters/font/cjk16_font.v:27-30`：「综合成 LUT 查表（不用 BRAM：BRAM 读延迟 1 拍，OSD 需与像素同拍组合）。**注意：接入 RTL 前请与 rtl-engineer 确认字库容量预算（BRAM9K/LUT 余量）**」

注意第二句自己就留了口子：「请与 rtl-engineer 确认预算」。它是在**陈述当时的实现选择**，不是在**证明架构不可能**。

### 3.2 现状取字链路的时序事实（逐行核实 `rtl/osd/osd_caption.v`，260 行）

```
active_x/active_y（来自 video_timing_gen.v:207-208，寄存器输出）
  ↓ 同一拍组合计算（osd_caption.v:161-199 的 always @(*)）
t_line / t_col / t_row / t_bit / t_on
  ↓ 同拍
osd_strings u_strings(.line_sel(t_line), .col(t_col), .char_code(raw_code))    // :216
  ↓ 同拍
占位符替换 rep_code（:227-240，纯组合）
  ↓ 同拍
osd_font8x16 u_font(.char_code(rep_code[5:0]), .row(t_row), .pixels(glyph_px)) // :247
  ↓ 同拍
wire glyph_on = glyph_px[~t_bit];                                              // :255
assign caption_pixel = t_on && glyph_on;                                       // :257
```

**模块内除 `scroll_px`（9 位）/ `scroll_div`（3 位）外零寄存器**，整条链路在同一拍内完成。「必须同拍」描述的是这个事实。

### 3.3 关键结构事实：字形点阵是 16 位并行输出，一个字符窗口内地址不变

这是绕开 1 拍延迟的物理基础，很多人没注意到：

- **`glyph_px` 是一个字符的整行点阵（16 位并行）**，不是一个像素。一个字符的 16 个像素位在**同一个 data word** 里。
- 中文 16 像素宽 → **一个字符占 16 个像素时钟拍**。这 16 拍里，`t_col`（= 字符列）不变、`t_row`（= 带内行号）不变 → **BRAM 地址在 16 拍内恒定**。
- 所以 BRAM 不需要每拍出数据：**同一个字符窗口内 16 拍的地址完全不变**，BRAM 每次读出的都是同一个 16 位 word，只是取位索引 `t_bit` 在变。

对比 ASCII 8 像素宽：一个字符占 8 拍，同样成立，只是窗口短一半。

**这个「一个字符 = 一个 16 位 word = 16 拍」的事实，是后面所有时序方案的地基**——它意味着 BRAM 的读带宽需求只有像素率的 1/16。

### 3.4 「提前一拍给地址」这条预取路走不通——行号无法预取

最直觉的绕法是「在字符窗口末拍把地址切到下一个字符」。**列能够预测，行不能。这是本节的结论，也是最终方案分叉的原因。**

**列可以预测**：`ticker_src = active_x + scroll_px`（`osd_caption.v:142`），当 `ticker_src[3:0] == 4'hF`（窗口末拍）时下一拍列号自然 `+1`（6 位回绕到 0），无需特判。

**行无法预测**：`t_row = active_y[3:0]`（`osd_caption.v:174/177/194`）。要提前一拍知道下一行的行号，就必须知道下一拍 `active_y` 的值。而 `video_timing_gen.v:207-208` 是：

```verilog
active_x <= de_c ? (h_cnt - H_ACT_START) : 11'd0;
active_y <= de_c ? (v_cnt - V_ACT_START) : 10'd0;   // ← 消隐期强制归零
```

**消隐期（`de == 0`）`active_y` 被强行打成 0**，直到新行第一个像素那一拍才变成真实行号。也就是说：

- 行末最后一拍，`active_y` 还是旧行行号
- 紧接的消隐拍，`active_y == 0`
- 新行第 0 拍，`active_y` 才跳到新行行号

**所以在消隐期的那一拍，电路根本不知道下一行是第几行——`v_cnt` 没有引出来，`active_y` 被打成 0。** 任何「提前一拍给行地址」的实现在行切换处必然给出错误行号，表现为「每一行的第一个字符行用错字形行」——**这是静默缺陷，仿真不一定抓得到（只在每行首字符的 16 拍内错）**。

> 同理，「地址 = f(`active_x + 1`)」的简化预测在行首那一拍也会错：上一拍是消隐（`active_x == 0`、`active_y == 0`），预测出的行号是 0。**这条更危险**，因为它在**每一行**都错一次，而 TICKER 带每帧有 16 行。

### 3.5 唯一可靠方案：**中文路径整体打一拍**（延迟跟随数据，不是预测地址）

既然地址不能提前，就让数据晚到——**把中文路径的输出整体打一拍，同时把与它配对的控制信号一起打拍**，使「点阵 + 位索引 + 有效标记」始终自洽。

```verilog
// 中文路径的读延迟补偿：延迟拍数 N 必须等于 cjk16_font BRAM 的实际读延迟
//   若 BRAM 配成无输出寄存器 → N = 1；若配成带输出寄存器 → N = 2
//   实现时先按 N = 1 写，M1 lint 后按综合报告确认，N 是参数
reg [15:0] cjk_px_q;      // 点阵
reg [3:0]  t_bit_q;       // 与点阵配对的位索引（打同样的拍数）
reg        t_on_q;        // 与点阵配对的有效标记
reg        is_cjk_q;      // 与点阵配对的路径选择位

always @(posedge pixel_clk or negedge rst_n) begin
    if (!rst_n) begin
        cjk_px_q <= 16'h0000;
        t_bit_q  <= 4'd0;
        t_on_q   <= 1'b0;
        is_cjk_q <= 1'b0;
    end else begin
        cjk_px_q <= cjk_px;        // BRAM 输出
        t_bit_q  <= t_bit;         // 同一拍的位索引
        t_on_q   <= t_on;
        is_cjk_q <= rep_code[9];   // bit9 = 1 表示中文路径
    end
end
```

**为什么这样是对的**：拍 N 给出地址 → BRAM 在拍 N+1 输出对应拍 N 地址的点阵 → 同时 `t_bit_q` 也是拍 N 的 `t_bit`。所以拍 N+1 用「拍 N 的点阵」配「拍 N 的位索引」，**配对的物理含义完全正确，只是整体晚了一拍**。跨字符窗口、跨行、跨带全部自动正确，**零边界特判**。

这正是与 §3.4 的差别：§3.4 试图「让数据准时到」，§3.5 承认「数据就是晚一拍」，把配对信号一起延后。**后者在数学上无条件成立。**

### 3.6 代价：TICKER 相对屏幕右移 1 像素，而这对滚动字幕是零影响

打拍方案的唯一副作用：中文路径的 `caption_pixel` 比 `de`/`active_x`/`active_y` 晚 1 拍 → **字幕整体右移 1 像素**。

**这个副作用在 TICKER 上是零可见的**，理由是滚动字幕的固有属性：

- TICKER 的横向位置由 `ticker_src = active_x + scroll_px` 决定，`scroll_px` 每 4 帧 +1 像素（见 §7.4）
- 「整体右移 1 像素」在数学上**等价于 `scroll_px` 减 1**——只是滚动相位差了一个像素
- 滚动相位本来每 4 帧就变 1 像素，肉眼看到的是连续左移。**相位差 1 像素不可能被察觉**
- 字符窗口内部：16 个像素位的相对位置不受影响（它们来自同一个 16 位 word），**字形本身不会变形、不会错位、不会串字**

**对比：如果把三条静态 ASCII 带也打拍，就会看到文字偏 1 像素（8 像素网格错位，明显）。所以 ASCII 路径坚决不打拍，保持现状纯组合。**

裁定：

| 路径 | 是否打拍 | 理由 |
|---|---|---|
| 中文（TICKER，line 8..14） | **打 1 拍** | BRAM 延迟必须补；TICKER 滚动，1 像素等价于相位差，零可见 |
| ASCII（title / index / state，line 0..7） | **不打拍，保持现状** | 静态文字，1 像素偏移可见；且 ASCII 走 LUT 组合查表，本无延迟 |

### 3.7 `caption_band`（压暗带）不必跟着打拍

`caption_band` 决定「本像素落在字幕带内 → 把图像层压到 1/4 亮度」（`video_overlay.v:286-287`）。

- 带的范围是整条 `y ∈ [448, 463]` × 全宽，1 像素的横向错开意味着「带的右边界少 1 个像素」
- 这在整条 640 像素宽的暗带上**完全不可见**
- 而如果为了对齐去给 `caption_band` 也打拍，就必须连带修改 `video_overlay.v:287` 的 `img_final` 选通时序，**动一处就要动三处，得不偿失**

**裁定：`caption_band` 保持现状纯组合，不打拍。**

## 4 Q1 裁定：BRAM + 中文路径打 1 拍补偿

### 4.1 裁定

**采用方案 A：BRAM（15 块 BRAM9K，探针实测）+ 中文路径打 1 拍补偿。**

理由三条，按重要性排序：

1. **资源错配是主因，成本估算只是佐证。** LUT 已用 78.16%（余 4,281→实际更少），BRAM 只用了 26.56%（余 47 块）。15 块 BRAM 只吃掉 BRAM 余量的 32%，LUT 几乎零消耗。**在「一种资源快用完、另一种资源剩一大半」的前提下，用富余资源换稀缺资源不需要精确估算作依据。**
2. **LUT 成本本身是跨 8.5 倍的区间（409~3,475），而 BRAM 成本是确定的 15 块。** 一个确定值对一个不确定区间，选确定的。
3. **打拍补偿是纯加法，不修改任何现有行为。** `osd_caption` 端口不变、`video_overlay` 例化不变、`osd_font8x16` 保持不变（继续给 title/index/state 三条 ASCII 带用）。中文只走新的 `cjk16_font` 路径，ASCII 路径一个寄存器都不加。

### 4.2 否决 B（LUT）的具体后果推演

若走 LUT 中值口径 2,010 lut：基线 15,319 → 17,329（88.41%），余量 4,281 → 2,271。而 t5 六模块 + t6/t7 八个模块还没综合。在这之后还要容纳 `rle_decoder`（估 360）、`wav_stream_player`（估 400）、`emerg_page`（估 400）、`i2c_master`（220）、`aht20_ctrl`（380）……**余量 2,271 要在功能模块还没落地的阶段就分出 2,010 给字库，后面必然触发 P0 裁剪。** 而 P0 裁剪砍掉的是「视频解码」或「温控联动」——**用核心功能换一个能显示得更舒服的字库，是错的交换**。

若走 LUT 悲观口径 3,475 lut：15,319 → 18,794（95.89%），余量只剩 806。**直接触发裁剪，且时序收敛风险剧增（3,475 个 LUT 是纯组合大扇入 case，扇出与布线都会恶化 SWNS +1.935 ns）。**

### 4.3 否决 C（SD 按需加载）

滚动字幕是**连续显示**的：每帧都要取字，行内每 16 拍换一个字符，一行 640 像素要取 40 个字符。SD SPI 实用带宽 1.25 MB/s、单次 512 B 块读取约 410 μs（见 `ARCH_ADDENDUM_VIDEO_PATH.md` §18.6 实用口径）。**任何一次取字未命中都会让字幕卡顿**，而缓存命中率取决于文案的字符分布，无法保证。

更关键：应急模式下用户的期望是「零 SD 依赖也能显示提示」。把字库放在 SD 卡上，等于让「应急提示文字」和「SD 卡是否插好」强耦合。**这条与架构叙事冲突，直接否决。**

### 4.4 否决 D（按模式分表）

`cjk16_charset.txt` 明确写「**索引 0..94 共 95 个字形永久冻结**，任何新增字符只能从后面追加，不得重排——RTL 以 index 硬引用字库，重排=屏幕静默显示错字（不报错、不变红，只是字不对）」。按模式分表意味着同一字符在不同模式下索引不同，**要么重排（违反冻结）、要么 RTL 按模式切换索引基址（引入第二套映射，且每个引用点都要跟着切）**。

而且分表不减总量：日常/科普需要 UI 179 字 + 校园 129 字，应急需要 79 字，三套都要常驻才能无延迟切换 → `129 + 79 + 179 ≈ 387`，相比全常驻的 465 只省 17%。**为一个 17% 的节省引入第二套索引映射，不划算。**

## 5 BRAM 组织与块数核算

### 5.1 存储组织

地址 = `{glyph[8:0], row[3:0]}` = **13 位 / 8,192 深**，数据 **16 位**。有效地址 465 × 16 = 7,440 个。

EG4S20 的 BRAM9K 容量 9,216 bit，可配置为 1024×9 / 512×18 / 2K×4 / 4K×2 / 8K×1。深度扩展用 512×18 配置：

- 8,192 深度 ÷ 512 = **16 个深度段**（按容量除出来的理论值）
- 宽度 16 位 ≤ 18 位 ✓（每个 512×18 块只用 16 位，浪费 2 位/地址）
- **综合器实际落地 = 15 块 BRAM9K**（`project/t2_cjk16_probe/reports/area_a.txt`、`area_b.txt`、`area_c.txt` 三种写法探针**实测都是 `#bram 15`**）

> **为什么理论 16、实测 15**：有效地址只有 7,440 个（465 字形 × 16 行），最后一段 512 地址里只用了 7,440 − 15×512 = **1,080** 个，综合器把尾部残余合并压缩后落到 15 块。**资源账一律用实测 15**，理论 16 只作推导说明。

总容量 15 × 9,216 = 138,240 bit，有效 119,040 bit，**位利用率 86.1%**（浪费来自 465 未填满 512、16 位未用满 18 位）。

### 5.2 块选择与数据合成

地址高位 `row[3:0]` 译码出 15 块中哪一块被使能，只有一块输出有效数据；15 块输出按位或起来即得 `glyph_px`。**块使能译码与输出或仍按 16 段结构实现**（综合器把第 16 段的逻辑识别为常量后自动省略），LUT 代价仍按 16 段保守计。

- 块使能译码：4 位 → 16 条使能，约 16 lut
- 输出或（16 位 × 16 段 → 16 位）：每位 16 输入 OR，4 输入 LUT 需 5 级树 → 16 位 × 5 = **80 lut**（15 块落地后第 16 段恒 0，综合器会再省掉，这里按 16 段保守计）

**这是 BRAM 方案唯一的固定 LUT 代价。** 部分综合器会把「块使能 + 输出或」优化成「深度扩展的标准结构」，实测值可能低于 80，这里按 80 保守计。

### 5.3 同域同沿

`cjk16_font` 的读时钟就是 `pixel_clk`（25 MHz），与 `osd_caption` 同域同沿。**没有跨时钟域问题，不需要 CDC，不需要 `set_false_path`。** 这一点与 `ARCH.md:580` 的 `wav_stream_player`（声明同域、同步 FIFO）是同一类处置。

### 5.4 BRAM 初始化怎么落地（`$readmemh` 硬证据，不是推测）

BRAM 方案的唯一落地疑点是「465 字形常量怎么进 BRAM」。答案在 TD 安装目录的**官方可综合 RTL** 里 —— 它自己就用 `$readmemh` 初始化 BRAM：

   > **但 `#bram` 门禁仍要保留**，因为它防的是**另一种**失效：`.hex` 存在、也被读进来了，却被综合器优化成**分布式 RAM**（`#bram` 不涨而 `#lut` 异常涨），这种情况下流程是成功的、V-11 断言（只覆盖仿真）也抓不到。

## 6 Q2 裁定：465 字形全常驻

### 6.1 裁定

**全常驻，不做按模式预筛。**

### 6.2 理由

1. **BRAM 余量足够。** 15 块占余量 47 块的 32%，还剩 32 块。预筛最优情况（只留 TICKER 并集的 191 字）能降到 8 块，省下 8 块——**但 BRAM 本来就不是瓶颈资源，省它没有收益**。
2. **预筛会破坏单一真值来源。** 现在 `cjk16_charset.txt` 的索引就是 RTL 引用字库的唯一凭据。预筛需要维护「字符 → 新索引」的第二张表，而这张表一旦与 `cjk16_charset.txt` 不同步，后果是 `cjk16_font.v:34` 说的「屏幕表现为空白，不会画出乱码」——**静默失败，不报错**。多一张必须手工同步的表，就是多一个静默失败点。
3. **465 字是真实文本并集算出来的，不是猜的。** `cjk16_charset.txt` 记载：科普旁白字幕 267 / UI 179 / 校园文案 129 / OSD_PHRASES 82 / 应急 79 / EXTRA 13，缺字 0。**任何一次文案微调都要重新校验缺字**，全常驻让这件事变成「不用管」。
4. **为未来留余量。** t11 的交付文档、答辩演示可能临时加文案。全常驻让新增文案只需核对「字在不在 465 里」，不需要「改索引 + 重生成 + 重同步」。

## 7 Q3 裁定：中文滚动字幕 RTL 改造

### 7.1 中英混排：不做，纯中文单表 + 英文全角格

**裁定：纯中文单表，所有字符按 16 像素等宽步进；英文/数字按 16×16 全角格显示（字形居中，左右各留空白）。**

理由：

- **中英混排是变长编码。** 英文 8 像素、中文 16 像素 → 字符列到屏幕像素的映射不再是 `x >> 4`，需要「列宽表」或每个字符带一个宽度位，并且要维护累加器 `x_acc += char_width[col]`。
- **`active_x` 是纯组合反查，变长后无法直接反查。** 现状 `osd_caption.v:161-199` 那 40 行 `always @(*)` 就是按 `x >> 3` 直接算列号的。变长编码后只能改成「前缀和查表」或「按行缓存」，**这 40 行要整体重写**。
- **这种改动最容易在「英文那一段字幕偏移几个像素」上出错，仿真还不一定发现。**
- 而用户 m00001 要的是「校园介绍的滚动字幕」——**纯中文**。科普模式的旁白字幕来自 `NARR.SRT`，含少量英文缩写（FPGA / HDMI / SD），在滚动字幕里用全角格显示，字距宽一点完全可接受。

**代价：英文看起来字距宽。收益：`osd_caption.v:161-199` 的反查结构零重写，`x >> 4` 保持单调递增。**

### 7.3 三条 ASCII 带：**零改动，继续 8 像素网格**

这是我上一版文档的自相矛盾之处，现在定死：**只有 TICKER（line 8..14）走 16 像素中文网格；title / index / state 三条带继续走 8 像素 ASCII 网格，坐标常量与 `t_col` 换算一个字都不改。**

**为什么不定三条带也 16 网格化**：

- 三条带的内容全是 ASCII（`SMART CAMPUS` / `IMG #*` / `PLAY` / `EMERGENCY` 等），字模 `osd_font8x16` 是 8×16 的，**16 像素网格化会让每个字符左右各空 8 像素，视觉上字距过宽，反而更难看**
- 三条带的 x 带终点（`TITLE_X1=127`、`INDEX_X1=623`、`STATE_X1=103`）都是按 8 像素设计的，改成 16 需要连带改宽度，**改动面扩大但收益为零**
- 双路查表已经是天然的隔离边界：`rep_code[9] == 0` 走 ASCII 8×16 路径，与现状**完全一致**

**唯一需要保证的一致性是 `t_bit`**：`t_bit` 从 3 位扩到 4 位后，三条带分支仍写 `t_bit = active_x[2:0]`（3 位零扩展成 4 位），**行为与现状完全一致**；只有 ticker 分支写 `t_bit = ticker_src[3:0]`（4 位真实值）。

|---|---|---|---|
| title `:181` | `active_x[2:0]` | **`{1'b0, active_x[2:0]}`** | 4 位零扩展，值不变 |
| index `:186` | `active_x[2:0]` | **`{1'b0, active_x[2:0]}`** | 同上 |
| state `:192` | `active_x[2:0]` | **`{1'b0, active_x[2:0]}`** | 同上 |
| ticker `:175` | `ticker_src[2:0]` | **`ticker_src[3:0]`** | 4 位真实值，中文 16 像素网格 |

**三条带的坐标常量一个都不改**（`TITLE_X0/X1`、`INDEX_X0/X1`、`STATE_X0/X1` 全部保持现状）。

### 7.4 滚动参数

- **一轮滚动 = 64 字符 × 16 像素 = 1,024 像素**（`scroll_px` 10 位，0..1023）
- 需要把每段文案**补齐到 64 字**（用空格填充），这样 `ticker_col = ticker_src[9:4]` 对 64 取模仍是位掩码，**零逻辑成本**
- 若不补齐（实际 33~39 字），一轮长度为非 2 的幂，取模需要比较器 → **不划算，一律补齐到 64**
- **滚动速度裁定：`scroll_div` 阈值 `3'd7` → `3'd3`（每 4 帧 +1 像素）。**
  - 中文一轮 1,024 像素 × 4 帧 = 4,096 帧 @ 59.52 Hz ≈ **68.8 秒一轮**（每像素 4 帧 = 67 ms/像素，视觉上是缓慢平滑左移）
  - 若保持 `3'd7`（每 8 帧 +1 像素）则要 137.6 秒一轮，字宽 16 像素下移动过慢，像卡住
  - 若改成每帧 +1 像素（`3'd0`）则 17.2 秒一轮，太快，看不清
  - **68.8 秒是「一段 38 字的文案在两分钟内完整走完」的节奏，符合「校园介绍」的阅读速度**

### 7.5 六段校园文案的切换（谁供图号）

**`t_line` 由 `img_index` 选段，纯组合译码，放在 `osd_caption` 内部：**

```verilog
// 段选择：日常模式按当前图片索引选 6 段之一；科普/应急由上层给固定段号
reg [3:0] seg_line;
always @(*) begin
    if (img_index >= 5'd6) seg_line = 4'd8;           // 越界回落到第 1 段
    else                   seg_line = 4'd8 + img_index[2:0];  // 段 0..5 → line 8..13
end
```

- 日常模式：`t_line = seg_line`（8..13，对应 6 段校园文案）
- **科普模式：`t_line` 不再指向 `osd_strings` 的任何一行** —— 旁白字幕走独立模块 `narr_subline.v`（1 块 BRAM9K，18 段，`rle_decoder.frame_idx` 驱动），`narr_code[8:0]` 直连 `cjk16_font.glyph`，**不经过 `osd_strings`、也不占 line 14**（line 14/15 是应急文案）。完整设计见 `ARCH.md` §9.4。
- 应急模式：`t_line` 锁定为应急文案段（`LINE_EMG0 = 4'd14` / `4'd15`，由 `emg_half` 每滚完一轮翻转；`ticker_en_eff` 强制为 1）

> **口径纠错（2026-11-02）**：本节早期草稿写「科普模式：`t_line = 4'd14`」，**这是错的** —— line 14 是应急疏散文案的第一行（`gen_osd_strings.py` 的 `EMG_LINE0 = 14`、`EMG_LINES = 2`），科普字幕从未占过 line 14。让 18 段字幕挤进 `osd_strings` 的 LUT case（`TOTAL_LINES` 16→34）会让条目翻倍到 2,176、源文件约 170 KB，LUT 不可接受，故改走 BRAM 独立模块。

### 7.6 `osd_strings.v` 改造

现状：`{line_sel[3:0], col[5:0]}` = 10 位地址，行 0..7 是 ASCII 状态行，行 8..14 空，行 15 = 64 列 ASCII TICKER。

改造后：

| 行 | 内容 | 说明 |
|---|---|---|
| 0..7 | 保持不变 | ASCII 标题/序号/状态 |
| **8..13** | **6 段校园文案（每段 64 列，中文字形索引 9 位）** | 新增 |
| **14..15** | **应急疏散文案（104 字拆两行，`emg_half` 整轮翻转）** | 新增 |
| — | ~~科普旁白字幕段~~ | **不占 `osd_strings` 的行**，改由独立模块 `narr_subline.v` 承载（1 块 BRAM9K，见 `ARCH.md` §9.4） |
| 15 | 保留原 ASCII TICKER | P2 可废弃（现状：line 15 已划给应急第二行，原 ASCII TICKER 概念废弃） |

**关键结构变更：字符码位宽从 7 位（ASCII）扩到 10 位（`{seg_kind[1:0], glyph[7:0]}` 或直接 `glyph[8:0]` + 1 位选择位）。**

裁定：**`char_code` 从 `[6:0]` 扩到 `[9:0]`**，最高位 `code[9]` 作为「中文/ASCII 选择位」：

- `code[9] == 0` → `code[6:0]` 是 ASCII 码，送 `osd_font8x16`（8 位点阵路径，三条带用）
- `code[9] == 1` → `code[8:0]` 是 `cjk16_charset.txt` 的字形索引（0..464），送 `cjk16_font`（16 位点阵路径）

**两条点阵路径的选择是纯组合 mux，`caption_pixel = t_on && (code[9] ? cjk_px[~t_bit[3:0]] : ascii_px[~t_bit[2:0]])`。** 三条 ASCII 带继续走 ASCII 路径（零改动），只有 TICKER 走中文路径。

**注意：ASCII 路径的 `t_bit` 是 3 位、中文路径是 4 位，`~t_bit[2:0]` 与 `~t_bit[3:0]` 取反位数不同，必须分开写，不能共用。**

`osd_strings.v` 由 `scripts/gen_osd_strings.py` 生成，**改脚本 + 重跑即可，不手写 case**。

### 7.8 打拍补偿与双路查表的合并（完整代码，t7 照抄）

打拍只做在中文路径上，ASCII 路径保持现状纯组合。`caption_pixel` 的最终形态：

```verilog
// ---- 第一级：字符串表（码宽 7 → 10 位，bit9 = 中英选择位）----
wire [9:0] raw_code;
osd_strings u_strings (.line_sel(t_line_q), .col(t_col_q), .char_code(raw_code));

// ---- 占位符替换只在 ASCII 路径做（中文路径直通）----
wire [9:0] rep_code = raw_code[9] ? raw_code : replaced_code;  // replaced_code 是原 :227-240 逻辑

// ---- 第二级：双路查表 ----
wire [7:0]  ascii_px;   // 组合，零延迟
wire [15:0] cjk_px;     // BRAM，1 拍读延迟
osd_font8x16 u_ascii (.char_code(rep_code[5:0]), .row(t_row_q), .pixels(ascii_px));
cjk16_font   u_cjk   (.glyph(rep_code[8:0]),     .row(t_row_q), .pixels(cjk_px));

// ---- 中文路径补偿 1 拍（配对信号一起延后，见 §3.5）----
reg [15:0] cjk_px_q;
reg [3:0]  t_bit_q;
reg        t_on_q, is_cjk_q;
always @(posedge pixel_clk or negedge rst_n) begin
    if (!rst_n) begin
        cjk_px_q <= 16'h0000; t_bit_q <= 4'd0; t_on_q <= 1'b0; is_cjk_q <= 1'b0;
    end else begin
        cjk_px_q <= cjk_px;
        t_bit_q  <= t_bit;
        t_on_q   <= t_on;
        is_cjk_q <= rep_code[9];
    end
end

// ---- 选位合成（注意：两路取反位数不同，必须分开写）----
wire glyph_on = is_cjk_q ? cjk_px_q[~t_bit_q[3:0]]   // 中文 16 位行，4 位取反
                         : ascii_px[~t_bit_q[2:0]];  // ASCII 8 位行，3 位取反

assign caption_pixel = t_on_q && glyph_on;
assign caption_band  = band_on;                       // 保持纯组合不打拍，见 §3.7
```

**关键点三条**：

1. `t_bit_q` 同时服务两路——中文取 `[3:0]`（4 位取反逐位反转得 15-i），ASCII 取 `[2:0]`（3 位取反得 7-i）。**`t_bit` 由 3 位扩到 4 位后，ASCII 路径仍只取低 3 位，行为与现状完全一致**（因为 ASCII 窗口内 `t_bit` 的高位恒 0：窗口 8 拍，`ticker_src[3]` 在 ASCII 8 像素网格下不参与……**注意：`t_bit` 改成 `ticker_src[3:0]` 后高 1 位对中文正确、对 ASCII 需保证低 3 位就是 8 像素内的偏移**。ASCII 三条带不走 `ticker_src`，它们的 `t_bit` 在 `:181`/`:186`/`:192` 分支里由 `active_x[2:0]` 给出——**改为 4 位后仍是 `active_x[2:0]` 零扩展，行为不变** ✓）。
2. `t_line_q`/`t_col_q`/`t_row_q` 是 §7.7 第 5 条的输出寄存——它们本来就要寄存（为了让 `osd_strings` 的输入被寄存器夹住，见 §8.3），**不是额外的预取结构**。
3. `band_on` 保持纯组合，因为它只影响「整条暗带」，1 像素错位不可见（§3.7）。

### 8.3 时序影响

- **新增路径全部在 25 MHz 像素域（40 ns 周期），同域同沿，无 CDC。**
- 最长新增组合路径：`active_x/active_y → t_col/t_row 组合译码 → t_col_q/t_row_q 寄存器`（1 级 LUT + 1 级寄存器）**与** `t_col_q/t_row_q → osd_strings 组合查表 → cjk16_font BRAM 地址`（两级 LUT 树）。两条都被寄存器夹住，**各占 40 ns 周期的一小部分**，且比现状（整条链路 `active_x → 坐标译码 → osd_strings → osd_font8x16 → 选位` 全在同一拍组合里）**更宽松**。
- **BRAM 的读路径不进组合路径**（同步读，数据在寄存器后出），因此**不恶化任何现有路径**。
- `osd_strings` 扩到 10 位码 + 240 项 case：这是纯组合大扇入，**但它的输入 `t_line`/`t_col` 已经是寄存器（`t_line_q`/`t_col_q`），输出进 `cjk16_font` 的 BRAM 地址（寄存器输入），所以这条路被两个寄存器夹住，只有 40 ns 可用的一部分**——比现在（夹在 `active_x` 组合链中间）**更宽松**。
- **对 hold（HWNS +0.003 ns 贴边）：新增 40 个触发器全部同域同沿，且都由 `pixel_clk` 驱动，不引入新的保持检查路径类别。但 HWNS 余量只有 3 ps，M3 综合后必须复核 HWNS ≥ 0。** 若转负，处置办法是给新增寄存器加 `set_max_delay` 或用 `place` 约束，**不是放弃 BRAM 方案**。

## 10 对 t7（rtl-engineer）的明确禁令

这三条是本文档最重要的可执行输出，**t7 不要自行取舍**：

1. **不要做中英混排。** 一律 16 像素等宽步进。英文/数字按全角格显示（字形在 16×16 格内居中，左右各留 4 像素空白）。理由是变长编码会推翻 `osd_caption.v:161-199` 整个反查结构（40 行），且这种改动最容易在「英文字幕偏移几像素」上出错而仿真抓不到。
2. **不要做任何「提前一拍给地址」的预测。** 列能预测、**行不能**——`video_timing_gen.v:207-208` 在消隐期把 `active_y` 强制归零，那一拍电路根本不知道下一行是第几行。任何预测实现在行切换处必然给出错误行号，表现为「每行第一个字符的行点阵错乱」，**这是只在每行首字符 16 拍内出现的静默缺陷，仿真不一定抓得到**。必须用 §3.5 的「中文路径整体打一拍 + `t_bit`/`t_on`/`is_cjk` 配对信号一起延后」。
3. **打拍只许打中文路径，不许打 ASCII 路径，也不许打 `caption_band`。** 三条 ASCII 带是静态文字，1 像素偏移肉眼可见（8 像素网格错位明显）；`caption_band` 干脆不打，因为它只影响整条 640 像素宽的暗带，1 像素错位不可见，而为了对齐去打拍会连带改 `video_overlay.v:287` 的 `img_final` 选通时序，动一处要动三处。**`osd_caption` 的对外端口保持不变**，`video_overlay.v:269-280` 的例化一个字符都不用改。

**另加一条（写给 t6/t7 的 `pix_mosaic`）**：`pix_mosaic` 在像素通路第 2 级（`image_player` 之后、`content_mux` 之前），`osd_caption` 在 `video_overlay` 内部（第 4 级之后）。**两者不在同一层，互不影响。** 中文字库的改动不会波及 `pix_mosaic`，`pix_mosaic` 也不需要知道中文字库存在。

## 12 答辩口径

被问「中文点阵字库怎么存的、为什么这样选」，三句话：

> 一、「字库是 465 个 16×16 点阵，一共 119,040 个比特，**在 FPGA 内部按块 RAM 组织，不占逻辑资源**。选块 RAM 不是因为算出来它更省，而是因为我们的逻辑资源已经用掉 78%、块 RAM 只用掉 26%——**拿富余的换紧缺的，这个判断不需要精确的估算作依据**。」

> 二、「块 RAM 有 1 拍读延迟，这一点我们在设计初期就意识到了。这个延迟**不需要绕，只需要补**：中文点阵走一条独立的数据路径，把点阵和它配对的位索引、有效标记一起延后一拍，三者始终自洽。**这个延后只作用在滚动字幕上，而滚动字幕本来每几帧就往左走一个像素——晚一拍在数学上等价于滚动相位差一个像素，肉眼不可能察觉。** 静态的三条状态文字走原来的组合查表路径，一个寄存器都没动，所以不会出现文字偏一像素的问题。」

> 三、「为什么不用逻辑资源直接做查表？因为同样的字库，**在不同例化上下文里综合出来的逻辑量能差 2.25 倍**——我们实测过同一份代码的两个实例，一个占 36 个逻辑单元、一个占 16 个。再往极端外推，最乐观与最悲观的折算口径之间跨度达 8.5 倍。把这个不确定性当成决策依据，等于拿核心功能的余量去赌。」

**若被追问「块 RAM 的内容是怎么装进去的」**（这是唯一会被问到落地细节的地方）：

> 四、「用 `$readmemh` 在综合期装入，**不引入任何厂商原语、也不手写七千多条 case**。这不是我们发明的做法 —— 工具厂商自己的可综合存储模板就是这么写的：`apm_memory.v` 里 `$readmemh(MEMORY_INIT_FILE, memory)` 配 `ram_style = bram`。数据文件是 7,440 行、每行正好 4 个十六进制字符的纯文本，格式天然吻合。**而且我们设了一条断言：仿真里读索引 0「日」的第 0 行必须等于 `16'h3FF8`；如果读到全零，说明路径没解析到，我们按硬失败处理，不会让一个「文字全空白但不报错」的版本上板。**」
