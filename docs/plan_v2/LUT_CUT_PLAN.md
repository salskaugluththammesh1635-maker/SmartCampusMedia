### 1.2 place 维度（mslice，与 LUT 解耦）

`mslice` 是 TD 的物理打包单位，上限 **4,900**（= 19,600 LUT ÷ 4）。它衡量的是「打包得多紧」，不是「逻辑有多少」。

| 判据 | 观测值 | 含义 |
|---|---|---|
| `optimize_gate` 后 `#Total_luts` ÷ mslice | 11,282 ÷ 2,651 = **4.25 LUT/mslice** | 打包良好 |
| `place` 内 `Stage 2.7.1` 之后 | 2,655 → **5,306 mslice**（2.13 LUT/mslice） | **HFN 复制把打包密度打散，密度腰斩** |
| 硬上限 | **4,900 mslice** | 5306 > 4900 → `PHY-9009` 失败 |

> **⚠️ 本表密度的分子是 `#Total_luts`（独立查找表逻辑），不是 `#lut`（槽位总占用）** —— 它衡量「每个 mslice 装了多少独立逻辑」，用来观察 HFN 复制前后的**打包效率变化**（4.25 → 2.13，腰斩）。**不要拿它去除 `#lut`**：`#lut ÷ 2.13` 是分子分母不同类的无意义式子（曾误写为 `19,353 ÷ 2.13 ≈ 9,086`，已删）。要算「需要多少 mslice」，用 §1.3 的**槽位装载率**口径（`#lut ÷ 4` 为理论下限）。

### 1.3 为什么两个维度必须分开（这条是本文档的立论）

**先把三个词分清（这是全文最容易被追问的一处）**：

> 📌 **本小节用首次 `place` 失败时的实测值（`#lut 19,353` / `#Total_luts 11,282` / `ripple 8,071`）解释机制**，因为那是最能说清「两种资源口径」的一组数。
> 参数调优后（`rtl min_ripple_len` 30/45）三项一起变：`#Total_luts` 11,282 → **15,020**、`ripple` 8,071 → **2,625**、`#lut` 19,353 → **17,645**（见下表与 §6 答辩口径）。**机制解释不变，数值按档位取。**

| 术语 | 含义 | 是不是真实逻辑 |
|---|---|---|
| `#Total_luts` = 11,282 | **独立查找表逻辑**（每个 LUT 当一个 4/5/6 输入函数用） | ✅ 是 |
| `ripple` = 8,071 | **进位链占用的 LUT 槽位** —— 加法器 / 比较器 / 加法树把 LUT 内部的专用进位通道也用上了，这些 LUT 不能再被当作独立函数使用，故单列 | ✅ **是（不是开销）** |
| `#lut` = 19,353 | 上面两者相加 = **LUT 槽位总占用**，这才是对着 19,600 硬上限算的那个数 | ✅ 是 |

> ❌ **绝不能说「11,282 才是真实逻辑，8,071 是打包开销」** —— 评委追问一句「那 8,071 是什么逻辑」就会崩。**准确说法：8,071 是进位链占用的槽位，是真实逻辑，只是用 LUT 的另一种内部资源。**
>
> ⚠️ **`mslice` 才是物理打包单位**（4 个 LUT 槽位 / mslice，故 `19,600 ÷ 4 = 4,900`）：`#lut 19,353 ÷ 4 = 4,838` 是理论最少 mslice。**要装进 4,900 个 mslice，槽位装载率必须 ≥ `19,353 ÷ (4,900 × 4) = 98.74%`** —— 与 LUT 百分比是同一个数（因为 `4,900 × 4 = 19,600`）。实测报出 **5,306** 个 mslice，对应装载率只有 `19,353 ÷ (5,306 × 4) = 91.2%`（即 **3.65 槽位/mslice**），**差 7.5 个百分点 → `5,306 > 4,900`**。**逻辑量没超，是布局密度不够。**

`place` 失败的根因是高扇出网络复制（`active_x` / `active_y` / `de` 这类信号被七八个模块同时消费），`Stage 2.7.1 Synthesize High-fanout Net` 把 LUT 复制出去，2,655 个新增 mslice 全部发生在这一步（CELL 23,698→24,239、WL 增加 36,712）。

> **⇒ 而且 place 参数确实是有效的**（见 §1.4 扫描表）：把进位链形式的 LUT 转成 LUT4/LUT5 形式后，`#lut 19,353 → 17,645`、mslice `5,306 → 4,849`、place 通过。**注意这条正是「两种资源口径」的实证**：`#lut` 降了 1,708，而 `#Total_luts` 反而从 11,282 涨到 15,020 —— 同一批逻辑换了 LUT 内部资源实现，槽位占用与打包密度同时改变。**所以「砍功能」从来不是第一选项，C1~C6 至今一级都没执行。**

## 3. 不砍清单（写死，防止「顺手优化」）

以下各项**任何情况下不裁**。这一节的存在理由是：它们看起来「可以省」，实际省不到，或者省下来的是功能、赔进去的是别的东西。

| 项 | 当前占用 | 为什么不能砍 |
|---|---|---|
| **`cjk16` 465 字形** | **15 块 BRAM / 4 LUT**（`u_cjk cjk16_font 4/0/0/15/0`） | **它几乎不占 LUT**，砍它省不到 LUT，反而丢全部中文显示。它吃的是 BRAM（余 29 块，充裕）。**任何「砍了 cjk16 就省 1,200 LUT」的说法都是把 C4b 的「退回 LUT 实现」方向说反了** —— 退回 LUT 是**增加** LUT |
| **字幕带几何 `y ∈ [448, 463]`** | 0（纯常量比较） | 它是**波形显示区 `y ∈ [376, 439]` 成立的唯一前提** —— 两者之间的 8 行硬间隙（440~447）由此而来。改字幕带位置会连带改波形几何，属于牵一发动全身，且省不到 LUT |
| **波形显示区 `y ∈ [376, 439]`** | `u_wave audio_waveform 481 LUT` | Key10 音频可视化是赛规 1.4(5) 逐字命中的加分项。砍它省 481，但**它同时也是 `audio_waveform` 与电平条 D-03 决策的共同依据**（D-03 保留波形、弃电平条，正是因为它信息量更大） |
| **`rle_size` / `rle_lba` 32 位** | 含在 `u_rle` 1,189 内 | **82 MB 的卡会把 32 位撑爆**（若截成 16 位或 24 位，大卡上的文件偏移会算错且不报错）。已经按 32 位接线、按 32 位探针实测（t19）。缩位宽是**静默数据错误**，比省几百 LUT 危险得多 |
| **`rle_spc_bad` 非法 spc 守卫** | ≈ 8 LUT | t19 实测「去掉非法 spc 守卫只省 8 LUT」（`new6` 变体 1252 vs `new` 1260）。**8 个 LUT 买一个「卡上文件损坏时报错而不是花屏」，是整个预算里最划算的 8 个 LUT** |
| **`bright_sel` 4 位全 10 档** | 含在 `u_keyrouter` 24 + `u_bright` 95 内 | t16 刚修完的 E4 显示缺口（`wire [2:0] bright_sel = bright_lvl[2:0]` 截断 10 档）。**再砍回 3 位等于把 t16 的工作撤销** |
| **面板三项 `vol_lvl` / `res_sel` / `ratio_sel` 显示** | 含在 `u_osd_panel` 215 内 | 赛规 1.4(4)「实时调节与信息叠加」的演示场景直接依赖它。§4.2 红线已明写「砍它等于用赛规加分项换百分比」。**C4 / C6 砍的是档位数量与按键响应，不是砍显示** |
| **三模式状态机 / Key3 应急直达 / Key0-2 / Key5 / Key9 / Key10 / E2 淡入淡出 / 参数 OSD 自动弹出** | 见 `RESOURCE_BUDGET.md` §4.2 | 已列为红线，本文档不重复 |

> **新增到本清单的流程**：任何「看起来能省」的项，先进本表讨论，不进 §2 执行。理由要写清「省多少（实测还是外推）」与「丢什么」。

## 5. 结构优化优先于功能裁剪（比 C2~C6 都优的路径）

**在执行任何 C 级之前，必须先评估这一节。** 理由：§2 每一级换来的都是功能损失，而结构优化换来的是同样的 LUT 且**功能一点不少**。

| # | 手段 | 实测依据 | 预估回收 | 代价 | 状态 |
|---|---|---|---|---|---|
| **S1** | **把 `pix_reader` 的 `async_fifo`（分布式 RAM 实现）换成 BRAM** | `u_pix_fifo async_fifo 1634/6/43/0/0`（主工程层级表，**1,634 LUT / 0 BRAM**）。`project/fifo_probe/` 14 变体单变量对照：`a_async32`（现状 32×512 异步读）`#lut 2,317 / #bram 0` → `b_sync32`（同尺寸只改读法）`#lut 80 / #bram 2`；`c→d`（16×1024）同样 −2,265 LUT / +2 BRAM；`b` vs `d` 的 `#lut` 只差 9，**说明省下来的是读法不是深度** | **a→b −2,237 LUT / +2 BRAM**（wrapper 口径）。折算主工程：**`u_pix_fifo` 净省约 1,577 LUT + 2 BRAM** —— 按 `80/2,317 = 3.5%` 折算到主工程 1,634 LUT 上，**不是直接减 2,237** | 读出多 1~2 拍延迟，需核对 `pix_reader` 的流水线（`LEVEL_HI` 水位判据）；且 `async_fifo.v` 与 `u_write_fifo`（73 LUT / **3 BRAM**）共用，改它风险面大于收益 | **备选优化，当前不执行**（place 已由 `min_ripple_len 30/45` 通过，`#lut 17,645 / 90.03%`；S1 保留作为未来加功能时的降本手段） |
| **S2** | 三份 `fat32_reader` 时分复用 | `u_gallery.u_fat` 782 + `u_player.u_loader.u_fat` 782 + `u_wav.u_fat` 762 = **2,326 LUT**（含 18 个 DSP） | 复用一份可省 **≈ −1,500**，且 **DSP 24 → 12** | 需仲裁器 + 状态机改写，改动面大，风险高 | 未评估 |
| **S3** | 顶层广播信号加一级寄存器缓冲 | HFN 复制是 place 失败的根因（§1.3） | **省的是 mslice，不是 LUT** | 1 个时钟延迟，需核对 `active_x` 的消费时序 | 属 §1.4 第二级 |

> **S1 的性价比仍然很高，但它已经不是必需的了**：探针实测 `a→b −2,237 LUT / +2 BRAM`（wrapper 口径），折算主工程**净省约 1,577 LUT**（≈ 回到 17,645 − 1,577 = 16,068 / 81.98%），代价只是 FIFO 读出加几拍延迟，**零功能损失**。它一项就顶得上 C2 + C3（1,561 LUT）的总和。**但 place 已经由 `min_ripple_len 30/45` 通过，所以当前不需要动它** —— 保留作为未来加功能时的降本手段。
> **⚠️ 深度是 9 不是 10（2026-11-02 captain 实测更正，arch-lead 原写错）**：`pix_reader.v:42` 的默认值确实是 `parameter FIFO_AW = 10`，但**顶层实际例化时被覆盖** —— `image_player.v:605` `pix_reader #(.PIX_PER_LINE(WIDTH), .FRAME_LINES(HEIGHT), **.FIFO_AW(9)**, .LEVEL_HI(384)) u_reader (`，再经 `pix_reader.v:440` `.ADDR_WIDTH(FIFO_AW)` 传进 `async_fifo`，而 `async_fifo.v:83` `localparam DEPTH = (1 << ADDR_WIDTH);` → **512 深，16,384 bit**。**教训：读参数的默认值不等于读实例的实际值** —— 只看 `pix_reader.v:42` 会得出 1024 深、4~8 块 BRAM 的错误结论，答辩时被问「512 深 32 位怎么要 8 块 BRAM」一句就露。
>
> **`RESOURCE_BUDGET.md` §4.3 纪律 3 已经写过这条路**（「例如把 `pix_reader` 的 1,672 LUT 异步 FIFO 换成 BRAM 实现，可省约 1,000 LUT，这是比裁剪功能更优的路径」）。本文档把它从「一句话建议」升级为**已实测的备选方案**：`project/fifo_probe/` 14 个单变量变体证明「**省的是读法不是深度**」（`a_async32` 2,317 → `b_sync32` 80，同尺寸只改读法；`b` vs `d` 不同深度只差 9 LUT）。
>
> **执行顺序（2026-11-02 终版）**：
> **① 用官方三参数通道调 `rtl min_ripple_len`（✅ 已完成，30/45 使 place 通过）→ ② 等 route + bitgen 出位流后再定主口径 → ③ 若将来加功能把 `#lut` 推回 19,000 以上，才评估 S1（净省约 1,577 LUT，需动与 `u_write_fifo` 共用的 `async_fifo.v`，风险面大）→ ④ §2 的 C1~C6 至今一级未执行，只在硬上限告急时启用**

## 6. 答辩口径

**被问到「资源这么紧，你们怎么保证能跑」时，按下面这段说（一段话说完，不要展开成辩解）：**

> 「EG4S20 的 19,600 个 LUT 是硬上限。LUT 槽位最终 **17,645 / 19,600 = 90.03%**，余 1,955。这个数由两部分组成：`#Total_luts`（独立查找表逻辑）+ `ripple`（加法 / 比较进位链占用的 LUT 槽位）—— **两者都是真实逻辑**，只是用 LUT 内部不同资源（查找表 vs 进位链）。**首次 `place` 报 `PHY-9009`（`mslice 5,306 > 4,900`），我们没有去砍功能，而是查清了根因**：`#lut` 里 8,071 是进位链占用的槽位，它让打包密度只有 **3.65 槽位/mslice**（理论上限 4.00，`4,900 × 4 = 19,600`）。」

> 用 TD 官方的 `rtl min_ripple_len` 参数（`set_param rtl min_ripple_len 45` + `commit_param -step rtl`）把长进位链转成 LUT4/LUT5 形式后，**`#lut` 降到 17,645（−1,708）、gate `slices%` 从 41.03% 降到 13.24%、mslice 4,801（≤ 4,900），`place` 通过，`Setup WNS +1.357 ns`、`FMAX 42.296 MHz`（需求 25 MHz，裕度 69%）**。整个过程中我们试了 6 组 TD 参数、逐个用日志证据判定，最终只保留有效的那一个 —— **一个功能都没砍**。」

> 「更细一点说：**`#lut` 降了 1,708，而 `#Total_luts` 反而从 11,282 涨到 15,020**（取 45 档是 17,645 / 15,020；取 30 档是 17,744 / 13,885）。这不是矛盾 —— 同一批逻辑换了 LUT 内部资源实现：进位链形式的 LUT 转成独立查找表形式后，`#Total_luts` 变多，但 `ripple` 大幅减少，**槽位总占用与打包密度同时改善**。这就是我们坚持把两个口径分开写的原因。」

> **⚠️ 对外只报 17,645 / 90.03%（`min_ripple_len` 45 档）或 17,744 / 90.53%（30 档）中的一个，并注明档位。19,353 / 98.74% 是未提交该参数前的历史值，只在解释「为什么 ripple 是真实逻辑」时引用。**

**禁止的表述**（会把自己逼到墙角）：
- ❌「11,282 才是真实逻辑，8,071 是打包开销」—— **这个说法会被一句「那 8,071 是什么」问倒；ripple 是进位链占用的槽位，是真实逻辑**
- ❌「98.74% 说明我们功能做得很满」—— 槽位占用高 ≠ 功能多，且这个说法会把进位链槽位误说成「功能」
- ❌「mslice 超限所以我们砍了 XX 功能」—— 两者因果不成立，且承认了不必要的功能损失
- ❌「19,353 − 17,299 = 单模块增量」—— 两次基线不可比（见 `RESOURCE_BUDGET.md` §3.4 未测项框）
- ❌「我们砍了功能才过 place」—— **一个功能都没砍，`#lut` 反而是降的（19,353 → 17,645）**。C1~C6 至今一级未执行
