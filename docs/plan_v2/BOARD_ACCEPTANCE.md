### 0.2 Key9：这是定案，不是"没做完"

**逐字采用**（引 `docs\plan_v2\KEY9_RULING.md` §1；该文件由 t28 交付，若尚未落盘则以本节为准）：

> **横向**：`pix_reader` 消费侧降采样（每字 2 像素取偶列），**等比压缩**。
> **纵向**：**1:1 裁剪**（不跳行）⇒ 非满屏档为「**横向压缩 + 纵向裁剪**」，**不是等比缩小**。
> 这是资源约束下的**主动取舍**，不是缺陷。

**四条禁令（第一句必须排第一）**：

- ❌ 不能写「Key9 **没做完 / 待完成 / 进行中 / 后续会做**」—— 中性措辞同样暗示将来会做完，答辩会被追问排期；正确说法是「**物理上限约束下的主动取舍**」。
- ❌ 不能写「**等比缩小**」（纵向是裁剪，不是缩放）。
- ❌ 不能写「**带宽不成立**」或「**需要行缓存**」—— 根因是顺序 FIFO 无法在流中「回头」取被丢弃的偶数行，必须整帧缓存。
- ❌ 不能写「**后续版本会补上**」（已定案不做）。

**物理上限算术**（被追问时用这三个数）：真实几何 640×480、每字 2 像素、一源行 320 字、一帧 153,600 字。档 0（窗口 320×240）需显示偶数行 240 条、丢弃奇数行 240 条；顺序 FIFO 下非窗口行必须把整帧读进来 ⇒ FIFO 需缓存 240×320 = **76,800 字 = 2,457,600 bit → 267 块 BRAM9K**，全片仅 **64** 块。

三种算法对照（堵住「差一点就够」的追问）：

| 算法 | 位/字 | 需缓存 | BRAM9K | 结论 |
|---|---|---|---|---|
| 32 位一字（正确） | 32 | 2,457,600 bit | **267 块** | 远超 64 |
| 16 位一字（常见错算） | 16 | 1,228,800 bit | **133 块** | 仍远超 |
| RGB565 且只存需跳过的行 | 16 | 614,400 bit | **67 块** | 仍超 64 |

> 267 是**下界不是估值**：它只按"存下需丢弃的 240 条奇数行"算，未计 FIFO 头尾与对齐开销。

**实测佐证**（证明「算法对、结构不行」，不是「算法写错顺手甩锅给资源」）：默认 `FIFO_AW=6 / LEVEL_HI=48` → tier0 `words=6512/12800 row_bad=20` + 粘滞下溢；`FIFO_AW=11 / LEVEL_HI=768` → tier0 7232、tier2 10476 仍红；`FIFO_AW=13 / LEVEL_HI=8000` → tier0 `words=12800` **精确守恒、row_bad=0**。8,000 字 vs 需 76,800 字 = **差 9.6 倍**。

**口径差异（如实记录）**：captain 消息里写的档位比是「1/2、5/8、3/4、7/8、1（边长比）」，而 `rtl\video\ratio_map.v:86-129` 实测是 320×240 / 400×300 / 480×360 / 560×420 / 640×480，对应**面积比** 1/4、5/12、9/16、3/4、1（边长比 1/2、5/8、3/4、7/8、1）。**两者一致**，本节按 RTL 实测写窗口尺寸，档位比按边长比表述。

## 5. 已修 bug 的「用户可见现象」留档

答辩被问「你们修了什么」时用这两条 —— 它们都不是"编译错误"，而是**功能静默错误**。

### 5.1 fat32_reader 终态自锁（t26 修复）

**真实症状不是报错，而是静默重播上一个文件**：

- `err_code` 全程 **0**，没有任何错误码；
- 用户只感知「**切了模式但音乐没变**」；
- 根因：`fat32_reader.v:426-434` 的 `S_DONE` / `S_FAIL` 是自锁终态，`:268-269` 只在 `S_IDLE` 检查 `start`，除复位（`:239`）外**没有回 `S_IDLE` 的路径** ⇒ 第二次 `start` 被忽略，`found` 永不到，wav 等到超时才失败，表现成"继续播上一首"。

**修复**（B4 方案）：`found/fail` 改 `output wire` + `term_reentry` 零延迟屏蔽。双向反证：改前 `tb_fat32_reader` 57 PASS/6 FAIL + `tb_wav_stream_player` 42 PASS/4 FAIL；改后 **64/0 + 46/0**。

### 5.2 `tb_wav_stream_player.v` 的 NARR 用例从未真正测过（假红）

## 7. 本清单无法从定稿确认的事项

以下条目**没有**在 RTL 或回归中找到可判定依据，故只写"现象"不写"精确判据"，上板时以实测为准并回填：

1. **D-03 上一张的边界行为** —— `player_ctrl` 在 `img_index=1` 时再按 Key0 是停住还是回绕到最大，代码里未找到明确语义，需实测。
2. **D-07 音频开关的生效延迟** —— `OSD_HOLD_MS=2500` 是 OSD 提示保持时间，与音频开关无关；实际音频静音延迟取决于 PWM 载波与滤波器，未实测。
3. **S-04 视频音频同步偏差** —— 5 fps 帧率下音视频对齐的实测偏差未测，清单里给了 ≤200 ms 的宽松阈值，属经验值而非规格。
4. **E-09 高温触发延迟** —— AHT20 上报周期 1 s（`PERIOD_CYCLES=25_000_000`）+ `thermal_guard` 迟滞判定，理论 ≤2 s，但加热过程本身耗时远大于此，实测会包含热传导延迟。
5. **P-03 Key8 分辨率 5 档的具体档位值** —— 未在本次核查范围内逐档确认，需对照 `docs\plan_v2\KEYMAP.md` §9 档位值表。
6. **波形幅度与音量的定量关系** —— `audio_waveform.v` 用 `sample[23:8] >>> Y_SHIFT`，Y_SHIFT=10，满幅 64 行；但"档 3 音量的波形幅度应为多少像素"没有规格，只能定性看"有起伏"。
7. **Key11 图库重扫** —— `key_router` 的 `P2_EN=1'b0` 把 `rescan_req` 内部钳位为恒 0，**当前版本 Key11 无效**，这是配置而非缺陷；若将来打开 P2，需重新验收重扫路径。
