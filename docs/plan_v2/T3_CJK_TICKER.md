## §2 为什么走块 RAM（答辩口径）

465 个 16×16 点阵共 **119,040 bit**。当前资源占用呈倒挂：

| 资源 | 基线 | 余量 | 中文子系统的处置 |
|---|---|---|---|
| LUT | 15,319 / 19,600（78.16%） | 仅 4,281 | 几乎不消耗 |
| BRAM9K | 17 / 64（26.56%） | 富余 47 | 吃 **15 块**（探针实测）→ **32 / 64（50.00%）**；科普字幕 `narr_subline` 再 +1 → 33 |

> 「选块 RAM 不是因为算出来它更省，而是因为逻辑资源已用 78%、块 RAM 只用 26%——拿富余的换紧缺的，这个判断不需要精确估算作依据。」

另一个决定性事实：同一份字模代码在不同例化上下文里综合出来的逻辑量差 **2.25 倍**（实测 36 对 16 个逻辑单元），
把这个不确定性当决策依据等于拿核心功能余量去赌；而块 RAM 的成本是**确定的 15 块**（探针实测，见下表）。

**BRAM 推断已实测**（队友 rtl-emerg 的探针 `project/t2_cjk16_probe/`，TD 6.2 同流程）：

| 变体 | #lut | #reg | **#bram** | 结论 |
|---|---|---|---|---|
| `cjk16_wrap_ref`（不例化 ROM） | 26 | 13 | **0** | 基线 |
| `cjk16_wrap_a`（带 `ram_style = bram`） | 66 | 16 | **15** | 推断成功 |
| `cjk16_wrap_b`（另加 `force_ram`） | 66 | 16 | **15** | 与 a 逐字节相同 |
| `cjk16_wrap_c`（零 pragma） | 66 | 16 | **15** | 与 a 逐字节相同 |

**结论：TD 6.2 对这个模式默认就推断块 RAM，pragma 不是风险点。** 落地 **15 块**（早期按容量除算写 16，2026-11-02 按探针实测更正为 15，`FONT_ARCH_RULING.md` §5.1 已同步）；15 而非按容量除出的 16 是因为探针只寻址 465 个字形
（9 位 glyph 未全用），完整集成后仍按 **15 块** 计（《裁定书》§5.1 已同步为实测值）。M3 综合后 `#bram` 应从 17 涨到 **≥33**（17 + 15 字库 + 1 科普字幕）；
**若仍为 17，说明 `.hex` 没进 BRAM（可能被优化成常量全零）**——注意 `.hex` 文件本身找不到时 TD 会在 elaborate 阶段 fail loud（`HDL-8007` + exit 3，2026-11-02 实测），流程根本走不到综合报表；所以这一步实际抓的是「文件在、被读进来了、却被常量折叠或推成分布式 RAM」这类**流程成功但语义错**的情况。

## §3 字库 ROM 实现（`cjk16_font.v`）

```verilog
module cjk16_font (
    input  wire        clk,
    input  wire [8:0]  glyph,     // 字形索引 0..464
    input  wire [3:0]  row,       // 行号 0..15
    output reg  [15:0] pixels     // 该行 16 位点阵
);

reg [15:0] mem [0:8191] /* synthesis ram_style = bram */;

initial begin
    for (init_i = 0; init_i < 8192; init_i = init_i + 1) mem[init_i] = 16'h0000;
    $readmemh("cjk16_bitmap.hex", mem);
end

always @(posedge clk) pixels <= mem[{glyph, row}];
```

**地址映射**：`{glyph[8:0], row[3:0]}` = 13 位 / 8,192 深 / 16 位宽。row 放低位使同一字形的 16 行连续存放，
与 `.hex` 的行序天然对齐。有效项 465×16 = 7,440，其余 752 个地址读回 `16'h0000`。

**为什么用 `$readmemh`**：不引入任何厂商原语、不手写七千多条 case。工具厂商自己的可综合存储模板就是这么写的——
`apm_memory.v` 里 `$readmemh(MEMORY_INIT_FILE, memory)` 配 `ram_style = bram`。

**为什么 `initial` 要先清零**：`$readmemh` 只填 0..7439，其余 752 项在仿真里保持 `x`，而硬件块 RAM 上电为 0。
不清零会导致「未收录字符应显示空白」在仿真里变成 `x`，与上板行为不一致。清零使仿真与硬件等价。

**与 `async_fifo.v` 的差异**：本工程既有的块 RAM 写法（`rtl/common/async_fifo.v:88`、`:130`）是**异步组合读**；
本模块必须**同步读**（寄存器输出），因为中文路径要靠「BRAM 输出寄存器」承担那 1 拍延迟（见 §5）。头注释已写明此差异。

## §4 `osd_strings.v` 与码宽改造

### §4.1 码宽 7 → 10 位

| bit | 含义 |
|---|---|
| `[9]` | 0 = ASCII 码，走 `osd_font8x16`（8 位点阵）<br>1 = 中文字形索引，走 `cjk16_font`（16 位点阵） |
| `[6:0]`（bit9=0 时） | ASCII 码值，0 = 无字 |
| `[8:0]`（bit9=1 时） | `cjk16_charset.txt` 索引 0..464；编码为 `0x200 \| idx` |

### §4.2 16 行分配与实测落位

| 行 | 地址区间 | 条目数 | 内容 |
|---|---|---|---|
| 0 | 0..63 | 11 | `SMART CAMPUS`（标题带） |
| 1 | 64..127 | 5 | `IMG #*`（序号带，`#`/`*` 为占位符） |
| 2~5 | 128..319 | 4 / 5 / 4 / 7 | `PLAY` / `PAUSE` / `AUTO` / `WAITING`（状态带） |
| 6~7 | 384..511 | 9 / 4 | `EMERGENCY` / `FAIL`（状态带） |
| **8~13** | **512..895** | **38 / 39 / 38 / 38 / 34 / 33（合计 220）** | **六段中文校园介绍，IMG n → line 7+n** |
| **14** | **896..959** | **63** | 应急疏散文案上半（第 0..63 字） |
| **15** | **960..1023** | **41** | 应急疏散文案下半（第 64..104 字） |

`case` 总条目 **373**（`osd_strings.v` 里 `char_code = 10'h` 共出现 375 次 = 373 项 + default + 初值）。

**应急文案字数：104 字**（36 + 32 + 36，不含 2 个分隔空格）。
用空格把三段连起来是 106 个字符，多出的 2 个是分隔空格，不计入字数。tb 按 **104** 判，一字不截断。

### §4.3 生成脚本的三个关键设计点

1. **前缀/数字位宽必须逐段对齐**：两个占位符分支都是 `{3 位前缀, 4 位数字}` = 7 位，恰等于 `ascii_rep` 位宽。
2. **必须按「这一行是什么带」禁止中英混编，不能按字符判断**：字库里同时收录了数字与部分大写字母
   （`S`/`A`/`C`/`M`/`P`/`U` 等都在 charset 里），若按「字符在不在 cmap」编码，三条 ASCII 静态带的字母会被
   编成中文索引。故 `encode(..., ascii_mode=True)` 显式指定走 ASCII 路径。
3. **补位 0 必须在白名单检查里跳过**：补位 `0x000` 会被当成字符 `chr(0)` 查白名单。

### §4.4 字库覆盖度的硬约束

`cjk16_charset.txt` 收录 465 字形，但**缺 A-Z 中的 B/I/J/K/M/N/O/Q/R/W/X/Y/Z**，小写只有 e/g/i/l/o/r。
因此科普段（line 14/15 的应急文案之外，`osd_caption` 里并无独立科普行）必须全中文，
**「HDMI」「SD」这类缩写不能出现**（HDMI 缺 M、I）。已实测六段校园文案与三段应急文案**零缺字**；
缺字在生成期硬失败（`raise SystemExit`），不会静默画空白。

## §5 1 拍延迟的补偿方式 —— **与《裁定书》§7.8 示例的差异（重点）**

### §5.1 我的实现

```verilog
// 只打三个配对寄存器，不打点阵本身
always @(posedge pixel_clk or negedge rst_n) begin
    if (!rst_n) begin
        t_bit_q <= 4'd0; t_on_q <= 1'b0; is_cjk_q <= 1'b0;
    end else begin
        t_bit_q <= t_bit;  t_on_q <= t_on;  is_cjk_q <= rep_code[9];
    end
end

wire glyph_on_cjk   = t_on_q && is_cjk_q && cjk_px[~t_bit_q[3:0]];
wire glyph_on_ascii = t_on    && ascii_px[~t_bit[2:0]];
assign caption_pixel = ticker_band ? glyph_on_cjk : glyph_on_ascii;
assign caption_band  = band_on;                       // 纯组合，不打拍
```

### §5.2 为什么与《裁定书》不同

《裁定书》§7.8 的示例写的是「字模**组合**输出 + 外部打 1 拍」，因此有 `cjk_px_q <= cjk_px`。
但本实现用的是**块 RAM 同步读**，`cjk16_font.v` 自己的输出寄存器已经承担了那 1 拍：

```
拍 N  ：addr(N) = f(t_line, t_col, t_row)        地址由组合逻辑给出
拍 N+1：cjk_px  = mem[addr(N)]                   块 RAM 输出寄存器正好一拍
```

**若再寄存成 `cjk_px_q`，点阵就变成 2 拍，而与它配对的 `t_bit_q` 只有 1 拍 → 每个字符的行点阵错开一格
（每行都对、整字错位，比整条错位更难发现）。** 所以正确做法是**只打配对信号、不打点阵**。
两种写法的总延迟都是 1 拍，与《裁定书》§3.6「滚动字幕右移 1 像素」的口径一致，但触发器省 16 个。

> 《裁定书》§8.1 增量表列的是「中文打拍补偿 +8 lut / +22 FF」，本实现落在 +6 FF（`t_bit_q` 4 + `t_on_q` 1 + `is_cjk_q` 1），
> 加上 `emg_half` 1 位 = 7 位，仍在该项预算之内。

### §5.3 用 `ticker_band` 而非 `rep_code[9]` 选路

带的分工是静态的：**滚动字幕永远走中文路径，三条 ASCII 静态带永远走 ASCII 路径**。
`ticker_band` 是纯 y 比较（组合、与本拍无关），而 `t_on_q`/`is_cjk_q` 在进入字幕带的第一拍还停在带外。
若按「本拍字符码」选路，边界那一拍会与 ASCII 分支混用，把中文码低 6 位当 ASCII 码画出乱码字形。
改用 `ticker_band` 后，第一拍由 `t_on_q = 0` 自然熄灭，从第二拍起正常——整体只表现为字幕右移 1 像素。

**`is_cjk_q` 保留为失败安全闸**：字幕带里若出现非中文码（字库未收录退回了 ASCII 路径），
中文分支直接熄灭显示空白，而不是拿 ASCII 码值当地址读字库、画出无关汉字。

### §5.4 预取禁令（未采用，记录理由）

**绝不做「提前一拍给地址」的预取**。《裁定书》§3.4：

```
video_timing_gen.v:207   active_x <= de_c ? (h_cnt - H_ACT_START) : 11'd0;
video_timing_gen.v:208   active_y <= de_c ? (v_cnt - V_ACT_START) : 10'd0;
```

两行都受 `de_c` 门控，消隐期坐标强制归零，**行号无法预测**。行末最后一拍还是旧行、消隐拍 `active_y == 0`、
新行第 0 拍才跳到新行。任何预取在行切换处必给错 `row`，现象是「每行第一个字符的 16 拍点阵错乱」——
**只在行首、不报错、仿真未必抓得到**。

打拍补偿的物理含义：拍 N 给地址 → 块 RAM 在拍 N+1 输出拍 N 地址的点阵 → `t_bit_q` 也是拍 N 的 `t_bit`，
配对完全正确，只是整体晚一拍。**跨字符窗口、跨行、跨带全部自动正确，零边界特判。**

## §6 位宽与参数（全部符合《裁定书》§7.2 / §7.4）

| 信号 | 改造前 | 改造后 | 理由 |
|---|---|---|---|
| `t_bit` | `[2:0]` | **`[3:0]`** | 字宽 8 → 16，列内偏移 0..15 需 4 位 |
| `glyph_px` / `cjk_px` | `[7:0]` | **`[15:0]`** | 16 位点阵行 |
| `scroll_px` | `[8:0]` | **`[9:0]`** | 0..1023，一轮 64 字 × 16 像素 |
| `ticker_src` | `[10:0]` | `[10:0]`（不变） | 639 + 1023 = 1662 < 2048 |
| `ticker_col` | `[5:0]` | **`[5:0]`（不变）** | 640 / 16 = 40 个中文字 < 64 |
| `t_col` | `[5:0]` | `[5:0]`（不变） | 同上，不扩到 7 位 |
| `t_row` / `t_line` | 4 位 | 4 位（不变） | — |

**四行必改**：

```verilog
scroll_px <= scroll_px + 10'd1;                              // 原 9'd1
wire [10:0] ticker_src = active_x + {1'b0, scroll_px};       // 原 {2'b00, scroll_px}
wire [5:0]  ticker_col = ticker_src[9:4];                    // 原 ticker_src[8:3]
t_bit = ticker_src[3:0];                                     // 原 ticker_src[2:0]（仅 ticker 分支）
```

**滚动参数**：`scroll_div` 阈值 `3'd7` → **`3'd3`**（每 4 帧 +1 像素）。
1,024 像素 × 4 帧 = 4,096 帧 @ 59.52 Hz ≈ **68.8 秒一轮**，约 67 ms/像素。
（`3'd7` 是 137.6 秒，慢到像卡住；`3'd0` 是 17.2 秒，太快看不清。）

**三条 ASCII 静态带零改动**：坐标常量一字未改（`TITLE_X0=32/X1=127`、`INDEX_X0=576/X1=623`、
`STATE_X0=32/X1=103`，四个 Y 常量不变）。
title / index / state 三个分支的 `t_bit` 由 `active_x[2:0]` 改为 **`{1'b0, active_x[2:0]}`**（4 位零扩展，值不变）；
只有 ticker 分支用 `ticker_src[3:0]`。**这三条带与 `caption_band` 一个寄存器都没加**——
8 像素网格上打一拍会看到文字偏 1 像素，明显错位；`caption_band` 打拍还会连带改
`video_overlay.v:287` 的 `img_final` 选通（动一处要动三处）。

## §7 六段切换与应急优先

```verilog
// 日常：index_val 0..5 → line 8..13；越界回落 line 8
always @(*) begin
    if (index_val >= 5'd6) seg_line = LINE_SEG0;              // 4'd8
    else                   seg_line = LINE_SEG0 + {1'b0, index_val[2:0]};
end

// 应急：state_line == 6 时锁定应急文案，每滚完一轮在 line 14 / 15 之间翻转
wire [3:0] ticker_line = ticker_emergency ? (LINE_EMG0 + {3'b000, emg_half}) : seg_line;
```

**接口决定 —— 不新增端口**：《裁定书》§7.5 说新增 `img_index[4:0]`，§10 第 3 条说「对外端口保持不变」，
两处冲突。裁定书 §11 **C-19 明确写「可复用 index_val」**，本实现采纳该口径：
**`osd_caption` 的对外端口与 v1 逐字相同（10 个）**，`seq_line` 直接用现有的 `index_val[4:0]` 计算。
好处有三个：`video_overlay.v:269-280` 的例化一个字符都不用改；悬空端口不会把 `seg_line` 污染成 `x`；
《裁定书》§10 第 3 条也满足。

**上游数据通路已通**：`dmz_eg4s20_hdmi_top.v:436` 已把 `player_ctrl` 的 `img_index[4:0]` 接进
`video_overlay` 的 `info_index`，而 `video_overlay.v:277` 又把 `info_index` 接到 `osd_caption` 的 `index_val`。
**所以无需改任何上层文件，六段切换即刻可用。**

**应急两行交替**：三段应急文案共 104 字，一行只够 64 字。为保证「任何一个字都不被截断」（安全内容），
拆成 line 14（0..63 字）与 line 15（64..103 字），每滚完一轮翻转一次 `emg_half`，两轮覆盖全文。

### §9.5 `0x67` 为什么一定没有字形（完整失效链）

答辩时若被追问「位宽错一点，为什么会整列空白」，按下面这条链一句话答完。

**第一段：位宽错，取值整体偏移 0x30**

`idx_ones` 为了做减法必须声明成 5 位（`[4:0]`），直接写 `{3'b011, idx_ones}` 会拼成 8 位，
前缀本是给 4 位数字留的，被 5 位数字一挤，数字段从 4 位变 5 位：

| 个位 idx | 拼接 8 位 | `ascii_rep[6:0]` | `rep_code[5:0]` | 落进 ROM |
|---|---|---|---|---|
| 0 | `0x60` | `0x60` | `0x20` | 空格（已收录，**看着正常**） |
| 1..9 | `0x61..0x69` | `0x61..0x69` | `0x21..0x29` | **全部无字形 → `default: 8'h00`** |

两处截位都「什么也没做」：`0x60..0x69` 最高位本来就是 0，取 `[6:0]` 不变；
取 `[5:0]` 时抹掉 bit6，才从 `0x6?` 落到 `0x2?`。**所以 `idx=0` 的帧上是隐形的**，只有 `idx=1..9` 才暴露。

**第二段：`0x21..0x29` 为什么一个字形都没有**

`osd_font8x16.v` 的字符码集合只有 **41 个**，且**不是**连续的 `0x20..0x5F`，而是三段：

| 段 | 内容 |
|---|---|
| `0x01..0x1A`（26 个） | 字母 A..Z，**走 1..26，不是 0x41..0x5A** |
| `0x20`（1 个） | 空格 |
| `0x2D..0x3A`（14 个） | `-` `.` `/` + `0`..`9` + `:` |

`0x21..0x29` 一个都没有 → 全部落到 `case` 的 `default: 8'h00` → 该列整列空白。

**第三段：字母为什么存 1..26**

因为 `osd_caption.v` 传给 `osd_font8x16` 的是 `rep_code[5:0]`（6 位）。
6 位地址空间装不下 `0x41..0x5A`，而 `0x41..0x5A` 截低 6 位**恰好**是 `0x01..0x1A`：

```
'A' 0x41 -> 0x01     'S' 0x53 -> 0x13     'Z' 0x5A -> 0x1A     26 个字母全部命中
```

所以 ROM 用小写段 1..26 存字母，是**配合这个截位做的设计，不是笔误**。
同理 `0x60 + idx` 截低 6 位就是 `0x20 + idx`——`idx=0` 落空格、`idx=1..9` 落空区。

**第四段：为什么仿真/综合都不报错**

`vlog` 对宽度不匹配默认**不报任何警告**。本次是靠 tb 的 54,248 项逐拍比对
定位到现场 `x=617 y=19`，才从「序号个位那一列空白」反推到 `idx_ones` 位宽。

### §9.6 断言要朝「失败时变红」的方向设计

`nz` 统计最初写的是 `if (mem[i] !== 16'h0000) nz = nz + 1;`——**这是朝「通过」方向设计的判据，方向错了**：

- `!==` 是四态严格不等，`x !== 0` 为**真**；
- 于是「字库根本没装载（整片 `x`）」会被统计成 **7440 个非零行**，`chk(nz > 6000)` 反而**通过**；
- 也就是说这个判据在最该报警的场景下最安静——恰好是它存在的唯一理由。

改成 `!=` 后语义反转：

| mem 实际值 | `mem !== 0` | `mem != 0`（if 里） | 判定 |
|---|---|---|---|
| `0000` | 假 | 假 | 不计数（对） |
| `xxxx` | **真** | `x` → 按假 | 不计数（对：未装载就该失败） |
| `3FF8` | 真 | 真 | 计数（对） |

**通用原则：断言的设计方向应当使「被测对象出问题时变红」，而不是使「正常时变绿」。**
凡是把 `x`/`z` 纳入比较的判据，都要先问一句「如果这块逻辑整个没生效，这条会红还是会绿」。
本次 `mem[13'd7440]` 那条判据（`$readmemh` 不覆盖的 752 个地址）同理改为 `!=`，
不再依赖 `cjk16_font.v` 的 `initial` 清零实现方式——判据对 RTL 实现细节不敏感，才不会因为
「有人为了省综合时间删掉清零循环」而误报。

### §9.7 `$readmemh` 的 cwd 陷阱（**跑 cjk 回归的人必读**）

这一条是仿真侧独有的坑，与 RTL 正确性无关，但**第一次跑 `tb_osd_caption_cjk` 的人几乎一定会踩**。

**现象**（干净库、没拷 `.hex` 时）：

```
# ** Warning: (vsim-7) Failed to open readmem file "cjk16_bitmap.hex" in read mode.
# （同一句重复 4 次——因为有 4 个例化都读这份字库：DUT、参考模型、探针…）
# [FAIL] C01 mem[13'd1... got=16'h0000 exp=16'h3ff8
#  *** FAILED: 5 check(s) ***
```

**判据（一句话）**：只要看到 `vsim-7 ... Failed to open readmem file`，
就**一定是路径问题，不是 RTL 问题**——先把 `rtl/osd/cjk16_bitmap.hex`（37,200 B）
`Copy-Item` 到 vsim 的工作目录，再谈别的。
症状是"5 条 FAIL、C01 报 `mem[1] got=0000 exp=3FF8`"，看起来非常像"字库没进块 RAM"，
于是很容易去改 RTL——而 RTL 本来就是对的。

**原理**：`cjk16_font.v` 里写的是裸相对路径 `$readmemh("cjk16_bitmap.hex", mem);`，
两套工具对相对路径的解析基准不同：

| 场景 | 相对路径基准 |
|---|---|
| 仿真（vsim） | **vsim 启动时的 cwd**，不是 `.v` 文件所在目录 |
| 综合（TD） | 源文件同目录 / `.al` 同目录 |

两边规则不一致，所以这是一个**纯粹的仿真侧陷阱**。本次实践做法是：
建一个专用工作目录 `sim/work_cjk/`，里面放一份 `.hex` 副本，`vlog`/`vsim` 都在该目录下跑。

**这条与 §5.4 的 V-11 断言正好配对**：
V-11 是"字库装进去了吗"的**运行期证据**（`mem[13'd1] == 16'h3FF8`）；
本节是"为什么没装进去"的**排查入口**（看有没有 `vsim-7`）。
一个负责报警，一个负责定位，两条都留着才不会在同一个坑里反复摔。

**背景**：`sim/scripts/` 里 23 个脚本目前**没有任何一个**跑 `tb_osd_caption_cjk`
（`run_frontend_regression.ps1:69` 只有旧的 `tb_osd_caption`）。
t9 补这条入口时若不知道本节，会把"没拷贝 `.hex`"误判成 RTL 退化。

本模块只有 9,216 bit，直接内联进 `initial` 块可**彻底消掉这个"忘了同步就静默全空白"的失败面**；
代价是文件 1,250 行，由脚本生成、不手改。

#### TD 6.2 实测证据（探针 `project/t13_narr_probe/`）

方法与 t2 的字库探针（`project/t2_cjk16_probe/`）同款：`elaborate → optimize_rtl →
optimize_gate → place → route → report_area`，两个变体只差"是否例化这张表"
（wrapper 完全相同的 LFSR 地址发生器 + 输出寄存器），**delta 即表的净代价**。

| 变体 | `#lut` | `#reg` | `#le` | **`#bram`** |
|---|---|---|---|---|
| `narr_wrap_a`（例化 `narr_subline`） | 436 | 23 | 436 | **1**（`#bram9k` 1） |
| `narr_wrap_ref`（纯 wrapper，不例化） | 37 | 15 | 37 | **0** |
| **delta** | **+399** | **+8** | **+399** | **+1** |

结论两条：

1. **`#bram` 增量恰好 1，与 §12.3 的算术推导一致**——`1024×9` 被综合成 1 块 `512×18` 的 BRAM9K，
   没有拆成 2 块也没有被推成分布式 RAM。`/* synthesis ram_style = bram */` 生效（t2 探针已证明
   TD 6.2 对这个模式默认就推断块 RAM，pragma 不是风险点）。
2. **LUT 代价 +399，比原估的"约 20 lut"高一个数量级**，如实记录：段选是 18 项 16 位比较 +
   4 级计数树 + 18 选 1 多路器，`seg_len`/`seg_base` 两个 function 又各是 18 项 case，
   全部是真实组合逻辑。**但仍在预算内**：LUT 余量约 4,237，本项吃掉约 9.4%。
   若后续 LUT 吃紧，第一顺位优化是把 `seg_len`/`seg_base` 也合并成单张 18×16 的小表
   （而不是两个独立 case），可省掉一层重复的多路器。

### §12.4 段选：为什么用「命中计数 − 1」而不是扫描

`start[]` 单调递增 → 命中项必然构成前缀 → **命中个数 − 1 = 最大命中下标**：

```verilog
wire [17:0] hit;   // assign hit[i] = (frame_idx >= start[i]);
wire [4:0]  cnt = hit[0] + ... + hit[17];
wire [4:0]  sel = cnt - 5'd1;
```

组合级数：16 位比较约 5 级 + 计数树 4 级 + 18 选 1 多路器约 5 级 ≈ **14 级 LUT**。
25 MHz（周期 40 ns）下远有余量。**没有用循环或运行加法器扫描 18 项**，避免把组合路径拖成串行链。

### §12.5 1 拍读延迟与「gate 必须与数据同拍」（**本次抓到的一个真 bug**）

块 RAM 的读延迟由输出寄存器承担，本模块**不再另加 `cjk_px_q` 式寄存器**。但这带来一个配对陷阱：

- 拍 N：给出 `addr(N)`
- 拍 N+1：`narr_q(N+1) = mem[addr(N)]`

第一版写的是 `assign narr_code = in_seg ? narr_q : BLANK;`——
`in_seg` 是**当拍**比较结果，而 `narr_q` 来自**上一拍**地址，两者差一拍。
后果：**段尾多出/少掉字符，只影响一两个像素列**，肉眼只看到字幕边缘"有点抖"，极难定位。

修法：`reg in_seg_q;` + `in_seg_q <= in_seg;`，改 `assign narr_code = in_seg_q ? narr_q : BLANK;`。
`in_seg_q(N+1) = in_seg(N)`，与 `narr_q` 严格同拍。

这条**反证抓到的**：把 `in_seg_q` 改回 `in_seg` 后断言变红一条
（`N03b col=15 应有字 got=9'h1ff exp=9'h077`）。注意**第一次写的时候根本没变红**——
说明当时的 N03 覆盖有缺口，于是补了 N03b（段尾门控同拍专项）才抓到。
**这是"反证驱动补测试"的一个实例：反证没变红，不一定是代码对，可能是测试漏。**

### §12.6 `osd_caption` 的三处 B-lite 改造 + Key5 门控修正

**（1）两条中文化路径拍数不同，各配一套配对寄存器**

| 路径 | 拍数 | 配对寄存器 |
|---|---|---|
| 非科普（滚动字幕吃 `cjk16_font`） | 1 拍（块 RAM 输出寄存器） | `t_bit_q / t_row_q / t_on_q / is_cjk_q` |
| 科普（再插一级 `narr_subline`） | **2 拍** | `t_bit_q2 / t_on_q2 / is_cjk_q2` |

`cjk_row = narr_active ? t_row_q : t_row` —— 科普路径的行号必须取**寄存后**的 `t_row_q`
（与 `narr_code` 同拍都对应"像素 N−1"），误用当拍 `t_row` 会整体错开一行、
屏幕上只是"有点糊"，比整条错位更难发现。

**（2）`narr_active = narr_en && !ticker_emergency` —— 应急优先于科普**

`state_line == 6` 时滚动带仍显示 `osd_strings` 的应急文案（line 14/15），不被视频字幕顶掉。
安全文案优先级高于体验。

**（3）`.col` 与 `t_bit` 必须同源（captain 抓到的接线错误，会毁掉功能）**

第一版把 `ticker_col`（随 `scroll_px` 递增）喂给 `narr_subline` 的 `.col`，后果链：

1. 地址 = `base[sel] + col`，`in_seg` 用 `col < cur_len` 门控 → **段 0（16 字）在 16×4=64 帧（12.8 s）内滚出屏幕，然后整段消失**；
2. 最长段 40 字需 40×4=160 帧 = 32 s，而**整支视频 126 s / 18 段、平均每段 7 s**——字幕来不及滚完就换段；
3. 最终现象：字幕从左往右滑出去、每段只露前几个字就消失，**比不显示还糟**。

修法（两处必须一起改）：
- `narr_subline u_narr` 的 `.col(active_x[9:4])` —— 静态列号，0..39 对应 x 0..639，一段 ≤40 字正好铺满一行；
- 槽位选择的 `t_bit = narr_active ? active_x[3:0] : ticker_src[3:0];` —— **格内位偏移必须与列号同源**。
  只改 `col` 不改 `t_bit` 会得到"字形索引取静态第 N 列、格内像素偏移取滚动第 M 位"，
  表现为**每个 16 px 字符块内点阵位置错乱，整行字像被横向切碎重新拼起来**——
  每个字还是那个字但笔画位置乱，极难定位。
- `t_col = ticker_col` **保持不变**：它喂 `osd_strings`，科普路径不走 osd_strings 的字形，改它反引入风险。

两处都有反证：把 `.col` 改回 `ticker_col` → 2 条断言变红；把 `t_bit` 改回无条件 `ticker_src[3:0]` → 1 条变红。

**（4）Key5 语义修正（D-06 消灭）**

用户原话「底部字幕开关按钮是 Key5」——只管底部那一条。改造前 `caption_en` 是整层总开关
（`if (caption_en)` 包住三条带 + `band_on = caption_en && (...)`），按 Key5 会连标题行/状态行一起关。

改为三带独立门控：

```verilog
if      (ticker_band && caption_en) begin ... end
else if (title_band  && !narr_en)   begin ... end
else if (state_band  && !narr_en)   begin ... end

assign band_on = (ticker_band && caption_en)
              || (title_band  && band_title_x  && !narr_en)
              || (state_band  && band_state_x  && !narr_en);
```

三个分支体内容与改造前**逐字相同**（`t_col`/`t_bit`/`t_row` 公式一个没动）。
新增端口：`input wire narr_en`、`input wire [15:0] frame_idx`（插在 `index_val` 之后）。

### §12.7 `narr_active` 是组合信号带来的瞬态（**结论：不改代码**）

`narr_active = narr_en && !ticker_emergency` 是纯组合（`ticker_emergency` 来自 `state_line`，
`state_line` 本身是顶层寄存器输出）。它在**同一拍内**同时选三样东西：`t_bit` 的源、`.col` 的源、
以及最终 `glyph_on_ticker` 二选一。所以 `narr_en` 或 `state_line` 跳变的那一拍，
上述三处会同时切到新源——而配对寄存器链（`t_bit_q2` 等）在这拍还停在旧路径上。

**量级**：最多错 2 个像素（2 拍），且只发生在模式切换的**那一拍**（一次切换只错一列），
滚动字幕本来每 4 帧移动 1 像素，与 §3.6「字幕右移 1 像素」同量级、肉眼不可见。

**不改成全寄存的理由**：把 `narr_active` 也打拍会让 `t_bit`、`.col`、选路三者各自需要一份
延迟版本，等于把整条 2 拍配对链重配一遍；收益（消掉一次切换的一列瞬态）远小于风险。

## §13 参数化改造的三个陷阱：坐标改了、算式没改

> 来源：2026-11-02 波形垂直位置改造（captain 授权的 t21 追加项）。
> 任务是把 `rtl/video/audio_waveform.v` 的波形从屏幕正中（`Y_CENTER=200`、`Y_SHIFT=9`）
> 挪到滚动字幕带上方（`Y_CENTER=408`、`Y_SHIFT=10`），落地用户需求
> 「滚动字幕的上方有做舒缓音乐的音频可视化」。改造本身只改两行参数值，
> **但测试台里有 21 处绝对坐标和 1 处硬编码移位量，全部要跟着参数化** —— 三个陷阱就出在这里。
>
> 为什么写进本文件：t11 答辩若被问「你们怎么保证改参数不会漏」，本节是现成答案；
> 且 t22（Key9 垂直跳行）同样要改移位/配额参数，与 `rle_decoder` 的 W14 陷阱同族，
> t9 会把它们一起收进「默认档恰好等于没测」的准则里。

### 陷阱 1：移位量本身被换掉，正负样本不再镜像

**现象**

`Y_SHIFT` 从 9 改到 10 后，原本用 ±512 造的两个样本，期望值从「`Y_CENTER` ±1 行」
变成「`Y_CENTER` +0 行 / `Y_CENTER` −1 行」：正向样本**彻底消失**（与无样本完全重合），
负向样本只偏移 1 行。表现是两条本应对称的断言一红一绿，看起来像「改对了一半」。

**根因**

Verilog 的 `>>>` 对负数**向下取整（floor）**，不是向零取整。实测（`%TEMP%\_trapmath.py`）：

| 表达式 | `Y_SHIFT=9` | `Y_SHIFT=10` |
|---|---|---|
| `+512 >>> Y_SHIFT` | `+1` | **`0`** ← 正向失效 |
| `-512 >>> Y_SHIFT` | `-1` | **`-1`** ← 负数向下取整，恰好还是 −1 |

所以「±N 的样本产生 ±k 行」这个对称假设，在 `N` 不是 `2**Y_SHIFT` 的整数倍时立刻失效。
更隐蔽的是两者的**表现不同**：正向失效是「该亮的地方不亮」（一眼能看出），
负向偏 1 行是「亮的行整体上移一格」（在小窗口里极易被当成「本来就是这样」）。

**正确做法**

造样本时用 `Y_STEP = 1 << Y_SHIFT` 的**整数倍**，不要写死 `512`。这样
`(k * Y_STEP) >>> Y_SHIFT == k` 精确成立，正负对称。
本工程实测：`+1024 >>> 10 = +1`、`-1024 >>> 10 = -1`（对称，恢复 `Y_CENTER ± 1`）；
而 `+512 >>> 10 = 0`、`-512 >>> 10 = -1`（不对称）。

**本工程实例**

- `sim/testbench/tb_audio_waveform.v:59` `localparam integer Y_STEP = 1 << Y_SHIFT;   // 一个像素行 = 样本高 16 位的倍数`
- 所有样本改成 `Y_STEP` 的倍数：正样本 `push_sample(Y_STEP * 256)`、负样本 `push_sample(-(Y_STEP * 256))`、
  斜坡 `push_sample(... * Y_STEP * 256)`、恢复段 `push_sample(2 * Y_STEP * 256)`。
- `tb_video_overlay.v` 的 V11 段同构：`WV_STEP` 与 `push_sample(16 * WV_STEP * 256)`。
- 断言随之改成符号：`ck_int(y_of(s16), Y_CENTER + 1, ...)`、`Y_CENTER - 1`、`Y_TOP`、`Y_BOT`。

### 陷阱 2：斜坡造法在参数变大后双向溢出，且**不报错**

**现象**

原斜坡是「每个样本比上一个多升 1 行」，`Y_SHIFT` 9→10 后每样本只升 **0.5 行**，不够一整行 →
64 段里大量段退化成单行，「逐列核对 y_min..y_max」的聚合断言直接报
`got 128, expected 0`（= 64 段 × 2 个「应亮」判据全部失效）。
若改成「步长 1024」硬顶，则整个斜坡被位宽截断，**仿真不报任何错**，只是数字全错。

**根因**

两个位宽同时被顶到上限（`63` = 64 个样本的末项下标）：

| 位宽 | 上限 | `Y_SHIFT=9` | `Y_SHIFT=10` |
|---|---|---|---|
| 16 位有符号历史 `hist[]`，`63 * Y_STEP` | 32,767 | `63×512 = 32,256` ✅ | **`63×1024 = 64,512` ❌ 溢出** |
| 24 位有符号 `push_sample` 入参，`63 * Y_STEP * 256` | 8,388,607 | `63×512×256 = 8,257,536` ✅ | **`63×1024×256 = 16,515,072` ❌ 溢出** |

只要「样本数(64) × 每样本行数 × 行内步长」超过位宽上限，斜坡就不成立；
Verilog 静默截位，不会报错。

**正确做法**

**先算位宽预算，再定斜坡**；超出就在满幅处**饱和** —— 用 `min(j, AMP_POS)` 而不是 `j`。
理由不是「妥协」，而是**物理上界**：波形能画出的最高行就是 `AMP_POS = 32767 >>> Y_SHIFT`，
再大的样本值也应该映射到同一行。饱和后最大值 `31 × 1024 = 31,744` / `31×1024×256 = 8,126,464`，两项都在界内。

**本工程实例**

- `sim/testbench/tb_audio_waveform.v:358` `push_sample(((j < AMP_POS) ? j : AMP_POS) * Y_STEP * 256);`
- `:384` `yc = Y_CENTER + ((q > AMP_POS) ? AMP_POS : q);`
- `:388` `yp = Y_CENTER + (((q - 1) > AMP_POS) ? AMP_POS : (q - 1));`
  （`q > AMP_POS` 时新旧两样本同值 → `ymin == ymax`，自然退化为单行，无需特判）
- 参数定义 `:60-61`：`AMP_POS = 32767 >>> Y_SHIFT`（正向满幅）、`AMP_NEG = -(32768 >>> Y_SHIFT)`（负向多 1，同为向下取整）。

**★ 关键副产品（这一步是整个两步法能成立的原因）**

`Y_SHIFT=9` 时 `AMP_POS = 32767 >>> 9 = 63`，而样本下标最大也正好是 63 ——
**饱和点恰好落在第 64 个样本之外**，所以「加了饱和的 tb」在**旧参数下行为与不饱和完全等价**。
这正是第①步「只改 tb、不动 RTL，`tb_audio_waveform` 76/0 与 `tb_video_overlay` 106/0 一字不变」
能够成立的原因。反过来说：如果当时随手写成 `j * 1024` 或不加饱和，
第①步就会从 76/0 变成一串红，而人会误判成「tb 改错了」——
**实际上是被测的斜坡造法本身在新参数下不成立，与 tb 无关。**

### 陷阱 3：坐标全参数化了，算式里的移位量还是字面量

**现象**

把 21 处 `10'd200` 全换成 `Y_CENTER`、`10'd263` 换成 `Y_TOP`、`10'd136` 换成 `Y_BOT`，
grep 已经搜不到任何旧坐标，看起来「彻底参数化」了。
但改 `Y_SHIFT` 之后断言仍然大面积变红 —— 因为**期望值的算法**没跟着变。

**根因**

参数化时被替换的是**数据**（坐标常量），而测试台里的参考模型（`y_of` 这个期望值函数）
是**代码**。数据换了符号、代码里的 `>>> 9` 没换，等于「用旧公式算新几何」。
这类漏网的典型特征：**改完之后 grep 不出任何旧数字，测试却还是红** ——
于是人开始在 tb 里乱找，而问题就在那行没被 grep 到的移位量上。

**正确做法**

参数化的验收标准**不是**「grep 不到旧数字」，而是**「改参数必须变红，改回来必须变绿」**。落到操作上就是两步法：

1. **第①步 —— 只改 tb，不动 RTL**：改完立刻用**旧 RTL 参数**跑一遍，
   断言数必须与改前**逐字相同**。这一步证明「改的是写法，不是语义」。
2. **第②步 —— 才改 RTL 参数**：必须变红，且红条数 `N > 0`。
   `N = 0` 说明 tb 根本没有绑死绝对坐标，第①步白做了。
3. **逐条修到全绿**，每条红都要能追到具体参数上（分不清归因就是没改对）。

三个数字缺一不可：`改参数前的通过数 / 改参数后立即跑的红条数 / 修完后的通过数`。

**本工程实例**

- 漏网的正是 `sim/testbench/tb_audio_waveform.v:122-125` 的
  `function integer y_of; ... y_of = Y_CENTER + (s >>> Y_SHIFT);`
  —— 改前这一行写的是 `>>> 9`，21 处坐标全参数化了、唯独它没参数化。
- 修好后的双计数实测：
  - `tb_audio_waveform`：**76/0** → 改 RTL 后 **76 checks / 27 errors** → 修 tb 后 **76/0**
  - `tb_video_overlay`：**106/0** → 改 RTL 后 **106 checks / 6 error(s)** → 修 tb 后 **106/0**
  - 第①步（旧参数）实跑：**76/0 与 106/0，数字一字不变** —— 68 + 19 处编辑全部只改写法。
- 27 条红**分三类穷尽归因**：20 条「旧中心线 y=200/201/202 落空」
  （`[reset]`3 / `[window]`2 / `[gate]`1 / `[ymap]`4 / `[degenerate]`2 / `[ramp]`6 / `[resume]`3）、
  6 条「旧极值 y=263/136/231 不再可达」（`Y_SHIFT` 9→10 后满幅从 ±63/64 行降到 +31/−32 行）、
  1 条聚合断言 `[ramp] all 64 columns match y_min..y_max exactly` 报 `got 128`。
- **独立反证**（不依赖上面的双计数）：把 RTL `Y_CENTER` 改回 `10'd200`、tb 保持 408 →
  `tb_audio_waveform` **27 errors**、`tb_video_overlay` **6 errors**，与第②步数字**逐字相同**；
  恢复后 `rtl/video/audio_waveform.v` 回到 5,257 B / sha16 `4489f8e6a48315c6`。

### §13.1 三条陷阱的共同点（收进准则时用这段）

1. **三条都「不报错」**：陷阱 1 的负向偏 1 行、陷阱 2 的静默截位、陷阱 3 的旧公式算新几何——
   编译器、lint、`check_port_names` 一个都不会报。能抓住它们的只有「改参数必须变红」这一条。
2. **三条都表现为「一部分对、一部分不对」**：这正是最危险的地方 ——
   人容易把它归因成「tb 写得糙」，而不是「参数化不彻底」。
3. **三条的正确做法都是同一个方向**：把**不变量**找出来（`k*Y_STEP >>> Y_SHIFT == k`、
   位宽预算、参考模型与 DUT 用同一套公式），再用测试把这个不变量钉住，
   而不是逐个去修被撞红的断言。
4. **由此得到一条通用验收准则**（建议 t9 收录）：
   > **参数化改造的完成标志不是「旧数字搜不到了」，而是「把参数改坏必须变红、改回来必须变绿」。
   > 只改 tb 的那一步必须证明数字一字不变，改 RTL 的那一步必须证明红条数 > 0。**

### §13.2 与其它任务的同族关系

  或斜坡/累加器在参数变大后超出位宽被静默截断。

## §14 t24：为什么不把 `osd_strings` 改成同步 BRAM（以及改了什么、实测降了多少）

> 本节回答一个容易被误读的问题：t24 的目标是「压掉 t7-B route 后那条 setup 违例路径」，但最终没有把 `osd_strings` 改成同步 BRAM。**不是没做，是算完账之后有意不做。**

### §14.1 为什么不改 BRAM：多 1 拍会让三条 ASCII 带整体右移 1 像素 + 下移 1 行

`osd_strings` 是组合 ROM（0 拍）。若改成同步 BRAM，`osd_caption` 的对齐链就要整体再延一级，三条路径拍数从 **0 / 1 / 2** 变成 **1 / 2 / 3**。而延一拍不只是「数据晚一拍」：

- `t_bit = ticker_src[3:0]`、`t_row = active_y[3:0]` 也都被寄存，所以整体是 **右移 1 像素 + 下移 1 行**，不是只右移。
- 三条 ASCII 带不打拍是本文件§五当时写下的硬规则：「8 像素网格，延后一拍 = 整条文字横向错 1 像素，一眼可见」。
- 下移 1 行还会碰到两处硬边界：状态带 48..63 → 49..64，`y=64` 落进 `osd_panel`（占 8..65，`px_box_on` 优先级高于 `px_caption`）；字幕带 448..463 → 449..464，`y=464` 落进信息条（`px_info = info_en && active_y >= 464`）。**两处末行会被盖掉。**
- 「加拍但不偏移」的唯一办法是预取（tick N 用 tick N+1 的坐标），已被裁定书 §3.5 与 `video_timing_gen.v:207-208`/`:78` 明令禁止；LUTRAM（`ram_style = distributed`）读延迟 0 拍，但**逻辑级数一级不减**，救不了 36 级。

结论：「砍 12 级 LUT 树」与「零像素偏移」二选一。t7-B 当时只差 **−0.183 ns**（= 36 级里的 0.46%），为此推翻一条已定的画面规则不划算 —— 改走「零代价」的 B 方案。

### §14.2 B 方案到底改了什么（四件，全部零拍数变化）

| # | 改动 | 文件 | 为什么 |
|---|---|---|---|
| B1 | `is_cjk` 由 `t_line[3]` 组合给出，不再从 ROM 读 | `osd_caption.v` | 373/373 条目逐条实测满足 `line<=7 => bit9=0`、`line>=8 => bit9=1` —— bit9 就是 `t_line[3]` 的冗余副本 |
| B2 | `src_code` / `rep_code` 两级 10 位三目拆成「9 位数据 + 1 位旁路」 | `osd_caption.v` | 原 `rep_code[0]` 网络 fo=60（t7-B 违例路径 L17），拆完直接消失 |
| B4 | `osd_strings` 输出位宽 **10 → 9 位** | `osd_strings.v` + `gen_osd_strings.py` | 每行 64 选 1 树每级少 1 个 LUT；16 行累计可观 |
| B3 | `osd_strings` 分层 case（16 行各 64 项 + 一级 16 选 1） | ——**未实施** | 静态分析证明无收益，见 §14.6 |

### §14.6 `col[0]` 扇出专项 + B3 为什么不做（B5 结论）

`col[0]` 的实际扇出由它被多少个 case 条目引用决定。对两版 `osd_strings` 逐条统计（脚本统计 373 条目的 `(line<<6)|col` 键值）：

| 位 | old 引用条目数 | new 引用条目数 |
|---|---|---|
| `col[0]` | **183** / 373（49.1%） | **183** |
| `col[1]` | 179 | 179 |
| `col[2]` | 168 | 168 |
| `col[3]` | 151 | 151 |
| `col[4]` | 144 | 144 |
| `col[5]` | 69 | 69 |

**两版完全相同** —— 因为 B1/B2/B4 改的是「字段宽度与中英标志的来源」，根本没碰 `col` 的译码结构。

**B3（分层 case）为什么被否决**：分成 16 个子 case 后，**每一个子 case 仍需要全部 6 个 `col` 位来译码**，所以 `col[0]` 的总负载没变（仍 183 份）；反而多一级 16 选 1 的 mux（约 15 个 LUT5）。按相关规则「**不要为了降扇出把结构改得更贵**」，结论是：**B3 不实施，理由是「无收益」（扇出不变）+ 「多一级 mux 会增 LUT」，不是「有害」。**

那么 `col` 的 144 上哪去了？答：**它在 route 阶段才被拆成 144 份复制网络**；gate 阶段 old 侧最差路径上的 `col[1]` 扇出已是 81，而 new 侧 `col` 系网络**完全不再出现在任何报告路径上**。说明 B1/B4 把它从「字段选择的关键路径」上摘下了——但译码本身（183 份 LUT）仍在，只是不再压在最差路径上。

#### ★ 工具的边界：为什么 B5 判据只能「间接佐证」而不能「直接量到」

B5 原本要求报「`col[0]` 的实际扇出值」。**这一条在 TD 上做不到，不是没做，是工具没有这个能力**：核过 `D:\TD_6_24_APP\doc\SWUG\SWUG105_TCL_Command_User_Guide.pdf`，**TD 不提供网络级扇出查询**（无 `report_fanout` 之类的命令；可用的只有 `report_area` / `report_cells` / `report_clock_utilization` / `report_param` / `report_qor` / `report_timing_exception` / `report_timing_status` / `report_timing_summary` 八个）。

而 `Max Fanout` **只在时序报告的最差路径头行出现**，测的是**当前最差那条路径上的**最大扇出，**不是指定网络的扇出**。所以 `Max Fanout 127 → 121` 这个数只说明「最差路径上遇到的最大扇出降了 6」，不能等同于「`col[0]` 从 144 降到了 121」。

**因此 B1/B4 是否真打中了 `col[0]` 这条 fo=144 的复制网络，只能通过下面三条间接证据佐证**，无法直接量到：

1. **`Max Fanout 127 → 121`** —— 最差路径上的最大扇出确实降了（−6）；
2. **`u_caption` 195 → 171（−24）、`u_axis` 2,352 → 2,285（−67）** —— 两处真实下降，且 `u_caption` 的 ripple / seq / bram 全不变（纯 LUT 减少）；
3. **`col[*]` 系网络在 new 侧的时序报告里彻底消失**（old 侧 `u_strings/col[1]_syn_992` 是 fo=81 / net 1.260 ns 的实体网络），同时 `rep_code[0]`（fo=73）改名为 `rep_data[0]`（fo=85）—— 说明字段选择链被重新划分，`col` 不再是关键路径的一部分。

> 把工具的边界写清楚，比留一个「未完成」的判据好：**「拿不到数」和「没去拿」是两件事**，报告里必须能分清。

#### §14.12.1 为什么是 bit3：二进制权值决定的恒等式，不是巧合

`t_line` 是 4 位、取值 0..15；`osd_strings` 的中文条目全在 **line 8..15**（324 条）、ASCII 全在 **line 0..7**（49 条）。于是「line >= 8」这个判定，在 4 位无符号二进制里**唯一等价的单比特判断就是最高位 bit3** —— 因为 bit3 的权值正好是 8。这不是挑了个凑巧对的位，是权值决定的。

写成 `bit2` 的代价，用 `osd_strings.v` 的 373 条条目逐条实测（脚本解析 `10'd<key> : char_code = 9'hXXX`，`line = key >> 6`）：

| 表达式 | 判错条目 | 占比 |
|---|---|---|
| `t_line[3]`（当前） | **0 / 373** | 0% |
| `t_line[2]` | **177 / 373** | **47.5%** |

**177 条是双向同时错**，四段分解（25 + 24 + 153 + 171 = 373）：

| 行段 | `bit2` 值 | 应为 | 条目数 | 判定 |
|---|---|---|---|---|
| line 0..3 | 0 | 0 | 25 | 判对 |
| line 4..7 | **1** | 0 | 24 | 判反 |
| line 8..11 | **0** | 1 | **153** | 判反 |
| line 12..15 | 1 | 1 | 171 | 判对 |

#### ★ 判反后的实际视觉后果（推算 + 反证双向验证，不是「满屏乱字」）

第一版我凭直觉写成「静态带冒随机汉字 / 校园介绍整段错字母」，**这是错的**。按 `osd_caption.v:566-575` 的真实输出结构重算：

```verilog
wire glyph_on_ascii  = t_on    && ascii_px[~t_bit[2:0]];        // 三条静态带走这条，不看 is_cjk
wire glyph_on_cjk    = t_on_q  && is_cjk_q && cjk_px[~t_bit_q[3:0]];
wire glyph_on_ticker = narr_active ? glyph_on_narr : glyph_on_cjk;
assign caption_pixel = ticker_band ? glyph_on_ticker : glyph_on_ascii;
```

- **line 4..7 判反（`is_cjk_eff=1`）：三带像素完全不变。** 因为 `rep_data = is_cjk_eff ? src_data : {2'b00, ascii_rep}`，而 `ascii_px` 只取 **低 6 位**：判反时 `rep_data[5:0] = raw_code[5:0]`，判对时 `ascii_rep[5:0] = (raw_code[6:0])[5:0] = raw_code[5:0]` —— **恒等**。实测 **0 / 49 条目会变**（占位符 `#`/`*` 只在 line 1 与 line 12 col13，line 1 的 bit2=0 不会被判反）。
- **line 8..11 判反（`is_cjk_eff=0`）：滚动字幕整条熄灭，不是错字母。** 因为 `is_cjk_q <= is_cjk_eff = 0` → `glyph_on_cjk = t_on_q && 0 && ... = 0` → `caption_pixel = ticker_band ? 0 : ... = 0`。暗底带还在、字没了。

**所以真实症状是：日常模式下滚动字幕带整条空白，而静态三带（标题/序号/状态）一切正常。** 这种「只坏一条带、其它全对」的形态最容易让人去查文案表或字库，**想不到是一条 1 位判定的位选问题** —— 比「满屏乱字」更隐蔽，也更值得写进文档。

> 这条修订本身是个教训：**注释里描述"改错了会怎样"时，也必须按 RTL 的真实数据通路算一遍，不能靠直觉。** 我第一版直觉写「乱字」，实测是「整条熄灭」；两个都是错，但根因、排查路径、责任归属完全不同。

> 顺便记一个我自己写错又改掉的地方：注释第一版我写「line 0..3 与 line 8..15 又是对的」，实测 **line 8..11 也判错**（其 bit2 = 0）。**注释里的数字必须来自脚本实测，不能凭位运算心算**——这条和 §13 那三条陷阱同族。

#### §14.12.2 参考模型的 `is_cjk` 必须独立于被测表达式

已加固（本轮改动）：

| 文件 | 原写法 | 现写法 | 理由 |

#### §14.12.3 反证实测：抓到了，但只抓到 42 条 —— 一个真实的覆盖缺口

把 RTL 的 `t_line[3]` 临时改成 `t_line[2]`（tb 一字不改），实跑：

| tb | 结果 | 说明 |
|---|---|---|
| `tb_osd_caption` | **46 / 0，全绿** | **抓不到** |
| `tb_osd_caption_cjk` | **54587 条里 42 条红**（`*** FAILED: 42 check(s) ***`） | 抓到了（全部落在滚动带；静态三带按设计就不该红） |

恢复后回到 46/0 与 54587/0。

**如实记录的缺口**：实际判反 **177 个条目**，测试只报 **42 条断言**（≈23.7%）。但更要紧的是**为什么 tb_osd_caption 一条都没报** —— 这个原因已经查清，而且结论比我第一版写的要硬：

- **`tb_osd_caption` 抓不到，不是覆盖率不够，而是「按设计它就该看不到」**：三带（标题 C03 / 序号 C04 / 状态 C05）走的是 `glyph_on_ascii = t_on && ascii_px[~t_bit[2:0]]`，**这条通路与 `is_cjk_eff` 完全无关**（只有 `rep_data[5:0]` 参与，而低 6 位在判对/判反下恒等，见 §14.12.1）。所以 line 4..7 判反后三带像素**真的没变**，`tb_osd_caption` 报 46/0 全绿是**正确行为**，不是漏测。
  - 我也验证了「若它变红反而说明我的机制分析错了」：注入 `[2]` 后 `tb_osd_caption` 实测 **46/0 全绿**，与机制推算一致。
- **42 条红全部来自 `tb_osd_caption_cjk`**，且集中在滚动带（C06 及后续）。它能抓到，靠的是两类**不依赖参考模型 `is_cjk`** 的交叉检查：`chk(dut.t_line === 4'd8 + i, ...)` 这类**直接断言 DUT 内部行号数值**；以及科普/应急段对 `dut.u_cjk.glyph` 端口的断言。
- **为什么 42 < 177**：`tb_osd_caption_cjk` 的滚动带按 16 个采样列 × 若干净字推进，**探针点只落在 153 条判反条目里的一小部分「列位置」上**；每命中一次就报一条。**断言数与错误条目数从来不是一一对应**，报告里两个数都要写，否则会给人「42 条就代表 42 个错误」的错觉。

> **这条教训的通用形式**：一个判定位写错造成的错误是「177 个条目」，而测试能报出来的只有「42 条断言」——**断言数与错误条目数从来不是一一对应**。报告里必须两个数都写，否则会给人「42 条就代表 42 个错误」的错觉。

#### §14.12.5 一条方法上的收获

> **「当前值恰好正确」与「测试能发现它错」是两件事。** 前者靠读代码，后者只能靠反证。
>
> 这次 `[3]` 之所以被发现，纯粹是因为 captain 恰好在一次写入中间态（反证注入的那 43 秒）抓到了 MD5 变化 —— 换个人、换个时间就发现不了。而它暴露的两个真问题（**判定位的理由没写进注释**、**参考模型的 `is_cjk` 与 RTL 用同一个位选表达式**）都不是「代码写错了」，是「代码没解释自己、测试没独立于实现」—— 这类问题任何 lint、任何门禁都不会报。

#### §14.12.6 反证注入的作业规矩（本次事故的整改，写进纪律）

本次反证注入直接改动了 `rtl/osd/osd_caption.v` 工作树，虽在 43 秒内恢复，但这**不只是「会被误读」的问题，而是一个真实的位流污染风险**：

- 当时 rtl-integ 正在并行跑 TD（`t7b_bit3.tcl`）。如果他的 `sync_src.ps1` 恰好落在那 43 秒窗口里，`project/hdmi/osd_caption.v` 就会带着 `t_line[2]` 进综合 —— **产出的是一个功能坏了、但时序好看的位流，而且没有任何断言会报错**（`t7b_bit3.tcl` 里那条 `#bram < 35` 断言防的是另一类问题，防不住这个）。
- 更麻烦的是它**不可观测**：位流能生成、时序能过、上板后只有「日常模式下滚动字幕带整条空白」这一处异常，而静态三带全对（见 §14.12.3），排查会一路查到文案表和字库去。

**规矩（自本次起执行）**：

> **反证注入一律在 `%TEMP%` 下的独立副本上做，不得改动 `rtl/` 或 `project/` 下的工作树。**
>
> 若必须在工作树做（例如 VHDL / Verilog 存在 include 路径依赖、`$readmemh` 依赖 cwd），则必须同时满足三条：
> 1. 注入前确认 `Get-Process td_commands_prompt` 计数为 **0**，且无人正在跑 `sync_src.ps1`；
> 2. 注入前后各贴一次 `Get-FileHash`（或 MD5 + 字节数），证明「改了哪几字节、恢复回哪几字节」；
> 3. 贴出恢复时刻的时间戳，并当场重跑受影响的门禁与 tb，用**同一时刻的绿**收尾。

**为什么这条值得单列**：这类注入是**有意为之的临时破坏**，而本工程的 TD 与 `sync_src.ps1` 是**并发的外部消费者**。三者叠在一起，风险不是「我忘了恢复」，而是「我恢复了、但有人在我恢复前读走了」。前一种靠纪律，后一种只能靠**隔离**。
