## 四、两个现象的代码级分析

### 4.1 先把"不可能"排掉

在往下猜之前，先确认这几条**不是**原因，避免下一手重复劳动：

| 假设 | 排除依据 |
|---|---|
| `vblank_rise` 一帧内多次触发，`fade_alpha` 在帧中间跳变 | 顶层 `dmz_eg4s20_hdmi_top.v:247` 把消隐期 `scan_y` **钳到 480**（`.scan_y(vblank ? 10'd480 : active_y)`），`ext_vblank` 在整个消隐期稳定为 1，`vblank_rise` 每帧只出一次 |
| `fade_mixer` 位宽溢出/通道串位 | 三通道独立缩放，`gain=level+1` 保证 level=255 逐位还原、level=0 全黑，乘积位宽按最大值取满 |
| 双缓冲地址重叠，装载写坏前台帧 | `back_sel = ~front_sel`，`back_off` 自带 `FRAME_SPAN`；读地址 `rd_base` 只在 `P_RESTART` 采样，翻转落在消隐内 |
| `image_ready` 掉了回落白彩条 | `image_ever_ready` 分支强制出黑（`video_content_mux.v:26-31`），10-30 已修 |
| 读 FIFO 被装载写请求饿死 → 下溢 | 写饥饿阈值 `WR_STARVE_LIMIT=256` 拍 @**40 MHz**（SDRAM 域，不是 150 MHz）= **6.4 µs** ≈ 160 像素（屏宽 1/4）；读 FIFO 深 1024 字（2048 像素 ≈ 3.2 行，≈ 82 µs 余量），**若水位维持在预填值以上**，6.4 µs 只消耗约 160 像素，仍有 12 倍余量。**但"水位能否维持"只是按设计推断，没有实测**；**该假设即 W5，已按"线段宽度 160 像素 vs 实测 3.2 像素"排除，见 §4.3** |
| 装载期间总带宽不足 | 总线 40 MHz、四字组 4 拍：写需求 ≈ 3.1 M 字/s ≈ 8%，读需求 ≈ 12.5 M 字/s ≈ 31%，合计 ≈ 39%。**平均值不算饱和，但读侧受 `RD_GROUP_CYCLES=13` 约束，单组效率只有 4/13 = 31%，正好卡在显示需求的临界点上**——这是 §4.4 的重要背景，不再是"远离饱和" |
| 缩放器越界写进另一帧（W1） | 640×480 源图走 `shrink=0` 的 1:1 分支：`out_w=640, out_h=480, out_off=(0,0)`，`col_eff∈[0,639]`、`ty_now∈[0,479]`，`word_addr∈[back_off, back_off+153599]`，**不越界**。此假设仅对需要缩放的非 640×480 图成立 |

> 第 6 条说明"带宽不够"这个最顺手的解释**在平均值上站不住**（但读侧处在临界点，见 §4.4）；
> 它派生的 W5（写饥饿抢占读通道造成补黑）已按线段宽度排除：
> W5 的签名是 160 像素宽、**黑色**，实测是 3.2 像素宽、**白色**，量级差 50 倍（§4.3）。
> 第 7 条说明**缩放器越界这条也排除了**（本次用 good\ 卡，全是 640×480，走 1:1 分支）。

### 4.2 现象 1：一条横向黑带

**"一条"把范围收窄，位置一项已于 §2.0 确认：上/中/下都可能出现 → 位置随机。**

三个候选，按可验证性排序（B1 已排除，留作备查）：

| # | 候选 | 机制 | 若成立应看到 |
|---|---|---|---|
| ~~B1~~ | ~~**letterbox 屏蔽边界差一行**~~ | **已复核源码，排除。** `rtl/video/image_window_mask.v:38-42` 用 `x_end = off_x + win_w`、`y_end = off_y + win_h`，判据是 `x >= off_x && x < x_end && y >= off_y && y < y_end`。本次 640×480 图 `off=(0,0)`、`w=640`、`h=480`，`x∈[0,639]`、`y∈[0,479]` 全部落在窗口内，**不会误屏蔽任何一行**。且上界用加法而非减法，`win_w=0` 的回绕已被处理 | — |
| ~~B2~~ | ~~**帧首预填不足**~~ | ~~`pix_reader` 每帧消隐走 `P_QUIET→P_DRAIN→P_RESTART→P_READY`，帧首前必须预填 `LEVEL_HI=768` 字（@40 MHz 约 19.2 µs）。若某帧 `P_RESTART` 完成握手迟到，帧首若干行 `pix_valid=0` → 补黑~~ | **已排除（§2.0）：带在上/中/下都可能。** 预填不足只可能在**画面顶部**。附带也被"静止时不出现"再排除一次——该路径每帧都走，与切图无关 |
| ~~B3~~ | ~~**某一行数据本身是错的/没写进去**~~ | ~~装载时那一行的写请求丢失或地址算错；读出来既是错数据，也可能整行偏黑~~ | **已排除（§2.0）：位置不固定。** 若是地址计算错，错的行号是**确定的**，每次切图都会落在同一行 |
| B4 | **该行被"局部破坏"** | 装载写后台帧时，某行的部分四字组写到了错误地址（跨行/跨帧），前台那行残留旧值或未初始化值 | 带的位置随图变，且带上可能有旧图的残影 |
| **B5** | **装载写入丢字/错字（当前首选）** | 写命令发出去了、`wr_ack` 也把 FIFO 队头消费了，但 SDRAM 实际没有落盘；该字保持上电随机值（读出来 `0xFFFF`=白，或 `0x0000`=黑）。丢一整段的连续字即形成**一条横向黑/白带** | 位置**随机**（取决于丢在哪个地址）、**换图后变**、**不报错**（装载完成判据只数命令，不校验落盘）、**静止时不出现**。四条全中 |

**位置这一项已于 §2.0 问清：上/中/下都可能出现 → 位置随机。**

- 顶部固定 → B2（已排除）
- 固定某一中间行、每次一样 → B3（已排除）
- 位置随图变 → B4 / **B5（当前首选）**

> B4 与 B5 的共同点是"写入侧出错"，区别是 B4 要求**写到错误地址**（会伴随旧图残影、且会破坏别处的数据），
> B5 只要求**没写进去**（该处保留上电值）。两者都指向 §4.4 的同一条机制，修复方向一致，
> 因此**不必先分开它们**再动手。

**一条重要的量级约束（本节此前算错了，2026-10-31 20:0x 更正）：**

「整行补黑」看起来也可以由"读通路中断"解释。此前本文用
`RD_TIMEOUT=1024` 拍 **@150 MHz = 6.8 µs** 去否定它，**那是错的**：
SDRAM 域实际是 **40 MHz**（`ip/config/sdram/global_def.v`：`SDR_CLK_PERIOD = 25 ns`，
`docs/eram_sdram_reference.md` §3 亦写明 `Sdr_clk` 为 40 MHz 0°）。按 40 MHz 重算：

| 量 | 值 | 与"一行"的关系 |
|---|---|---|
| 一行 640 像素 @25 MHz | **25.6 µs** | — |
| `RD_TIMEOUT=1024` 拍 @40 MHz | **25.6 µs** | **恰好等于一行** |
| 读 FIFO 深 1024 字 | 2048 像素 ≈ 3.2 行 ≈ 82 µs | 撑得比看门狗久 |

**所以"读通路卡住 25.6 µs → `rd_fault` → 补出约一行黑"在量级上是成立的，不能排除。**
`rd_fault` 之后仲裁器还会 `rd_restart` 重启读通路，现象上正好是"一条整宽黑带 + 之后恢复正常"。

**那为什么仍把黑带归到"写入丢字"？改用一个更强的证据——组数比例：**

| 通路 | 2 s 装载期间的组首机会 | 若"核吞命令"是随机的，应看到 |
|---|---|---|
| 读组（4 字/组，12.5 M 字/s） | ≈ 6.2 M 次 | 成百上千条黑带 |
| 写组（4 字/组，≈3.1 M 字/s） | ≈ 38 K 次 | 几十条白线 |

读组机会是写组的 **160 倍**，而实测是 **1 条黑带 + 几十条白线**。
**说明"吞命令"几乎只发生在写侧**——读侧有 `RD_GROUP_CYCLES=13` 保护，写侧一条保护都没有
（`framebuf_arbiter.v:124-128` 只有 `rd_group_wait`，没有 `wr_group_wait`）。
这条比例论证同时解释了"黑带极少、白线较多"，也把修复方向锁定在**写侧组首间隔**（§6.1）。

> 仍要如实标注：这是**概率推断**，不是实测。它能解释比例，不能证明机制。
> 若上板后按 §6.1 改完仍有黑带，则黑带另有一条独立成因（`rd_fault` 补黑这条就重新成为候选）。

### 4.3 现象 2：细碎线条 + 每次都 2 s

> **颜色已于 §2.0 确认为白色，宽度约 1/200 屏宽（≈3.2 像素），散布在约 3/5 的画面区域。**

#### (a) 颜色与宽度两个数一给出来，假设空间就塌缩了

先做一个正面排除：正常显示通路**产不出亮像素**——
欠载时 `pix_valid=0` 会被下游补**黑**，`image_ready` 掉了也补**黑**，
装载写的是后台帧、读的是前台帧。所以"补出来的异常像素"只可能是**黑**。
**用户看到的确实是白线 → 它不是补出来的，而是读到了错数据。**

| # | 颜色 | 来源 | 机制 | 判据结果 |
|---|---|---|---|---|
| ~~W5~~ | ~~黑~~ | ~~读 FIFO 短暂欠载 → 补黑；`WR_STARVE_LIMIT=256` 拍 @40 MHz ≈ 6.4 µs ≈ 160 像素（屏宽 1/4）~~ | — | **已排除：量级差 50 倍。** 用户量到的是 3.2 像素，W5 的签名宽度是 160 像素；而且 W5 只会是**黑** |
| ~~W3~~ | ~~白/彩~~ | ~~TMDS/像素时钟亚稳，整片随机噪点~~ | — | **已排除：静止时不出现（§2.0）**，且形态是"细碎线条"不是整片雪花 |
| W2 | 白 | **SDRAM 读出未初始化区** | `back/front` 某块从未被完整写过；读到上电随机值（RGB565 `0xFFFF`=纯白） | **部分成立**：若是"首帧没写过"，应只在**第一次**切图出现；用户是**每次都出现** → 不是"整块没写"，而是"**每次都有少量字没写进去**"，与 B5 合流 |
| W4 | 白 | **数据位被置 1（结构性错位）** | 某条 SDRAM 数据线在特定突发拍不稳，形成方向性短线 | **降权**：数据线问题通常**位置固定**（同一位线总在同相位出错），而用户看到的是**散布 3/5 区域** |

**宽度 3.2 像素这个数非常有用**：一个 32 位字 = 2 个 RGB565 像素，一条四字组 = 8 像素。
用户量到的 3.2 像素落在**单个字（2 像素）**的量级上，而不是整组（8 像素）或补黑段（160 像素）。
**所以丢的是"字"，不是"组"，也不是"通道整段停摆"。**

> 这排除了"整段读通道被抢占"这一类（W5），也排除了"整组写命令丢失"（那会是 8 像素）。
> 剩下最自然的解释：**个别写命令没有真正落盘，那一个字保持上电值（白），或者个别字被写成了 0（黑）。**
> 一条横向黑带 = 一段连续的这类坏字（数百到数千个字连续丢失）；散布的白线 = 零星的单字丢失。
> **两者可以是同一个缺陷的不同规模表现。**

#### (b) "每次都 2 s" 是本轮最有价值的线索

**理论基线：**

| 阶段 | 理论耗时 | 依据 |
|---|---|---|
| CMD17 + 512 B 数据 @12.5 MHz SPI | 约 334 µs/扇区 | `sd_spi_ctrl.v` SCK_FAST_DIV=1 |
| 1801 扇区（921,654 B） | **约 601 ms** | IMG001 文件尺寸 |
| FAT 簇链遍历（226 簇） | 约 5~20 ms | 每簇一次 FAT 扇区读 |
| 淡出 8~9 帧 + 淡入 8 帧 | **约 283 ms** | `FADE_FRAMES=8`，每帧 16.7 ms |
| **合计** | **约 0.9 s** | |

实测 **2 s**，多出约 **1.1 s**。**关键是"每次都一样"**——这排除了偶发，只剩两类确定性解释：

**解释 1：SPI 实际吞吐只有理论值的一半左右（最可能）**

若卡的 CMD17 响应慢、或 `sd_spi_ctrl` 在字节之间有空隙，实际单扇区耗时可能到 700~900 µs，
1801 扇区就是 1.3~1.6 s，加转场正好 1.6~1.9 s。**这正是"每次都一样"该有的样子**——
卡和时钟都是固定的，慢也是固定地慢。

**判据**：逻辑分析仪量一次 **CMD17 命令末尾 → 该扇区最后一个数据字节** 的时长。
- 若 ≈334 µs → 传输没问题，2 s 来自别处
- 若 ≈700~900 µs → **不是缺陷，是卡慢**，2 s 属正常，只需在文档里写明"切图约 2 s"

**解释 2：装载被执行了两次（本次加固新引入的路径）**

`image_player.v:241-245` 在 `C_RESET/C_MEM/C_START/C_LOAD` 里复查 `sd_ready`，
一旦为 0 就退回 `C_WAIT` **从头重装**。重装一次，耗时正好翻倍。

**但这条的前提是 `sd_ready` 真的会掉。** 而：

```
sd_ready = sd_owner_player = sd_ok && (gallery_done || gallery_fail)
```

`sd_ok`（`sd_probe` 的 P_OK）和 `gallery_done`（`gallery_probe` 的终态）**都是粘滞的，只有复位才清**。
所以**静态看 `sd_ready` 不该掉**，这条假设的置信度**不高**。

> **但它必须被验证掉**，理由有三：
> ① 它是本次改动**新引入**的唯一能解释"翻倍"的路径；
> ② 若成立，它是**真缺陷**（白白多读一遍卡），必须修；
> ③ 验证成本很低——抓一根线看整个装载期有没有下跳。

**判据**：逻辑分析仪抓 `sd_ready` 或 `sd_owner_player`，跨整个 2 s 窗口。
- 全程为高 → **解释 2 排除**，2 s 就是卡慢（解释 1），文档记为"已知性能特性"而非缺陷
- 有下跳 → **解释 2 成立**，按 §6 的 P1 修

### 4.4 把两个现象合成一条机制（~~当前首选假设~~ **已被上板证伪，见 §4.5**）

§4.2 的 B5 与 §4.3 的 W2 变体是同一条链的两端。合起来是这样：

```
装载期间，写后台帧的命令发出去了（wr_ack=1，FIFO 队头被消费）
   ↓  但 SDRAM 控制器核没有真正执行这条写命令
那一个字保持上电随机值（通常是 0xFFFF → 白）或 0x0000（→ 黑）
   ↓
装载"完成"的判据只数命令数（writes_complete），从不回读校验
   ↓
双缓冲翻转，新帧上台 → 坏字被当成正常画面显示出来
```

**四个现象特征全部对上：**

| 特征 | 为什么 |
|---|---|
| 位置随机（上/中/下都可能） | 丢哪条命令取决于装载期间与刷新/换向的相位关系，与画面内容无关 |
| 只在切图时出现、静止时不出现 | 静止时没有写通路，也就没有写命令可丢 |
| 不报错 | `writes_complete` 是"命令发完了"，不是"数据落盘了"；没有任何回读校验 |
| 黑带与白线并存 | 同一机制：丢在连续地址上 = 一条带；丢在零星位置 = 散布短线。带是黑是白取决于那段的初始化值 |

#### 为什么怀疑"命令被核静默丢弃"——三条代码级证据

**证据 1（最强）：这个核对命令间隔不足会静默吞命令，是**已在真核上复现过**的事实。**

`rtl/storage/framebuf_arbiter.v:9` 原文：

```
// APUG011 的间歇读组首至少相隔 13 拍；12 拍间隔已在真核复现漏 ACT。
```

同一文件 `:122-123` 还有一段：

```
// 只限制下一组首拍，已开启的四拍组保持连续。不能靠 rd_valid 判断核已可
// 再接受组首：真实 APUG011 在特定 12 拍间隔会返回 valid 却漏掉 bank ACT。
```

**注意"返回 valid 却漏掉 ACT"——核会给出成功的样子，实际没干活。** 这正是"不报错但数据错"的范式。

**证据 2：读侧有 13 拍保护，写侧一条都没有。**

- 读：`RD_GROUP_CYCLES = 13`，`rd_group_wait` 计数器保证相邻读组首间隔 ≥13 拍（`:124-128`）。
- 写：**没有对应的 `WR_GROUP_CYCLES`，没有 `wr_group_wait`**。`wr_fire` 只看 `wr_grp_active || wr_new_allowed`（`:97`），
  即"这一组还没写完"或"现在允许开新组"，**对组首之间的间隔不做任何约束**。

**证据 3：装载期间的写组恰恰是"间歇"的，不是连续的。**

写要拿到总线，只有两种可能（`:94`）：

```verilog
assign wr_new_allowed = wr_req && (!rd_req || wr_starved || rd_fault);
```

- 要么 `rd_req=0`（读 FIFO 已够满，暂时不要数据）；
- 要么 `wr_starved=1`（写等满 `WR_STARVE_LIMIT=256` 拍，强行抢占）。

**问题在于这里用的是 `rd_req`（"想读"），而不是"这个周期读是否真能开组"。**
读侧真能开组的条件是 `rd_new_allowed`（`:95-96`），其中含 `rd_group_wait == 0`；
而 `rd_group_wait` 在读组**结束后还要再等 12 拍**（`RD_GROUP_CYCLES=13`，`:124-128`）。

于是装载期间的实际时序是：

```
读组 4 拍（t=0..3）→ rd_group_wait 从 12 递减到 0（t=4..12）
                              ↑ 这 9 拍里 rd_req 仍为 1，于是 wr_new_allowed=0
                                 写被挡在门外，总线空转 9 拍
t=13 → 下一读组
```

**这 9 拍本可以放两个写组（8 拍），却一个也放不进去。**
读带宽效率只有 `4/13 = 31%`，而显示需求正好是 31%（12.5 M 字/s ÷ 40 MHz 字/s）。
**读侧没有余量，写侧只能靠"饿 256 拍后强行抢占"来插入——每次抢占都会在读通路上开一个 6.4 µs 的洞。**

而读侧之所以要那 13 拍，注释写得很清楚是"间歇读组首"。**写侧面对同一颗核、同一类场景，却裸奔。**

**证据 4（本节 2026-10-31 补充）：写组首间隔因此既"不规则"又"可能极短"。**

- 靠 `wr_starved` 抢占时，写组跟在读组后面，间隔由饥饿计数决定（几百拍）；
- 靠 `rd_req=0` 放行时（读 FIFO 满了、显示暂时不要数据），写组可以**背靠背连续开组，组首间隔只有 4 拍**。

**这两种情况落在完全不同量级的间隔上，说明写组首间隔在整个帧装载期间扫过很大范围**——
恰好覆盖注释里说的那类"会漏 ACT"的窗口。**读侧有 13 拍闸门挡住了它，写侧没有。**

#### 另外两处需要一并注意的薄弱点（同一段代码）

| 位置 | 问题 | 影响 |
|---|---|---|
| `framebuf_arbiter.v:8` | 注释原文：`ref_vld 中不接受命令，模型保留组相位；**真核跨刷新相位尚待硬件核实**` | 刷新窗口的**边界**（刚结束的那几拍，tRFC 未满）是否也吞命令，**从未在硬件上核实过**。而刷新是周期性自动的，落点随机——与"位置随机"高度吻合 |
| `framebuf_arbiter.v:15` | `BUS_TURN_GAP = 2`（读↔写换向空拍），**注释里没有任何"已在真核确认"的字样** | 换向前后各只有 2 拍静默；同族的 `RD_GROUP_CYCLES` 要 13 拍才安全，2 拍显得过小 |

**这两条与"证据 1"是同一类风险：核的时序余量只在读侧被认真对待过，写侧和刷新边界都没有。**

> **诚实标注**：以上是**代码与注释层面的推断，不是已证实的根因**。
> 没有任何一条能仅凭 RTL 阅读证明"就是它"。要证实必须上板做**单变量实验**（见 §6.1）。

因为只有这一个变量，且综合结果确认没有引入时序问题，所以这条结论是硬的：

> **"写组首间隔太短 → 核漏 ACT → 丢写命令"这条链条不成立。**
> 不成立的可能有两种：要么写命令根本没被吞，要么被吞的触发条件不是组首间隔。**两者都要求换方向。**

#### 4.5.2 一条此前被忽略的痕迹推理：**写侧丢字产生不出纯黑带和纯白线**

这是本轮最重要的推理，它把方向从"写侧"翻到"读侧"。

**前提**：双缓冲下，装载期间写的是**后台帧**，而后台帧在本次装载开始前，装的是**上一张图**（上一次装载写进去的）。

**推论**：

| 如果发生 | 该位置最终显示 | 用户应该看到 |
|---|---|---|
| 写侧丢一个字的写命令 | 该字保持**上一张图**的内容 | **彩色残片**（上一张图的局部） |
| 写侧写入了错误地址 | 目标地址被覆盖成新图内容 | **新图的碎片出现在错误位置**（彩色） |
| 读侧读到了**从未写过的地址** | 该地址保持 SDRAM 上电值 | **纯黑（全 0）或纯白（全 1）** |
| 读侧根本没读（下溢） | `pix_reader` 主动补 0 | **纯黑** |

用户看到的是**纯黑的一条带**和**纯白的细线**，**不是彩色残片**。

> **所以：这不是"写丢了"，而是"读到了没有内容的地方"。**
> 之前 §4.4 把两个现象都归到写侧，方向错了——P6 上板无效正好印证了这一点。

#### 4.5.3 重新排序后的候选（下一手从这里开始）

| 编号 | 候选 | 能解释什么 | 代码位置 / 依据 | 优先级 |
|---|---|---|---|---|
| **R1** | **读通路超时 → `pix_reader` 下溢 → 主动补黑一行** | 黑带：`RD_TIMEOUT = 1024` 拍 @40 MHz = **25.6 µs，恰好等于一行 640 像素 @25 MHz 的 25.6 µs**；超时落点随机 → **位置随机** | `framebuf_arbiter.v:17` `RD_TIMEOUT`；`pix_reader` 下溢补 0 | **最高** |
| **R2** | **写侧零星漏写（不是组首间隔，而是握手/队头管理）** | 白线：单条 1~2 个字、读到上电值全 1 | `image_player.v:366-382` 的 `fifo_pop`/`write_head_valid`/`wr_ack` 三者时序 | 高 |
| **R3** | **读地址相位错位**（`rd_restart` 与 `pix_reader` 行相位不同步） | 整行错位后读到帧外区域 → 纯黑/纯白 | `framebuf_arbiter.v:207-240`、`pix_reader.v:147-149` 的 P_DRAIN/P_RESTART | 中 |
| R4 | `BUS_TURN_GAP=2` 换向余量不足 | 原 P7 | `framebuf_arbiter.v:15` | 中（保留） |
| R5 | 刷新窗口边界（tRFC 未满）吞命令 | 原 P8 | `framebuf_arbiter.v:8` 注释自述"尚待硬件核实" | 中（保留） |

**R1 为什么排第一**：`RD_TIMEOUT` 的数值与一行像素时间**精确相等**，这是本次唯一一处"代码常数与现象尺度严格对上"的巧合。一次超时 = 恰好黑一行，且落点由刷新/写抢占的相位决定 → 随机。这与"一条横向黑带、上中下都可能"完全一致。

#### 4.5.4 零成本的下一步判据：**盯 LED2**

顶层的 LED 已经引出了这个信号（`dmz_eg4s20_hdmi_top.v:598-600`）：

```verilog
assign led = {err_active, image_loading, sdram_lock_pix[1], ..., mode==2,
              |reader_status[1:0],   // ← LED2 = overflow_sync | underflow_lat
              auto_play, image_ready};
```

`reader_status[2:0] = {armed, overflow_sync, underflow_lat}`（`pix_reader.v:126`），
其中 **`underflow_lat` 是粘滞位——只要发生过一次下溢就会一直亮到下次复位**。

> **判据：按 KEY1 切图，黑带/白线出现时看 LED2（README §5 里标为「读 FIFO 异常」）。**
> - **LED2 亮** → R1 成立，方向就是"读不过来 / 读被挡住"，直接去查 `rd_fault` 与 `wr_starved` 的竞争。
> - **LED2 不亮** → 数据是真的被读出来了、只是读错了地方 → 转向 R2/R3（写侧零星漏写或地址相位）。
>
> 这一步**不需要改任何代码、不需要重新综合**，只需要再上板按一次 KEY1 并观察一个 LED。

## 五、本次最值得注意的结构性缺口

**连续切图（第二次及以后的装载）在仿真里从未被真实数据覆盖过。**

| 仿真 | 装载次数 | 数据 | 覆盖 KEY1 场景 |
|---|---|---|---|
| `tb_display_content` | 1 次 | 真实 IMG001.BMP + 真实 `img_loader`+`img_scaler` | ❌ 只装一次 |
| `tb_image_player` CASE 8a/8b | 多次 | 模型化扇区数据，**不含 scaler** | ❌ 数据不真实 |
| `tb_image_player` CASE 13/14 | 1 次 | 模型化 | ❌ 只验新增路径 |

**"真实 BMP + scaler + 连续两次装载" 这个组合，一条仿真都没有。** 而这次两个现象都在这个组合里。

**但要说清一点**：本次用的是 640×480 的图，走 `shrink=0` 的 1:1 分支，
**scaler 在这条路径上基本是直通**（`r_step=r_thr=1`、`c_step=c_thr=1`、`off=0`、`dst=src`）。
所以"scaler 有 bug"的可能性也被压低——**问题更可能出在装载期间读写争用、或装载的重复性上，而不是几何变换**。

**还要说清第二点**：装载期间"写后台帧"与"读前台帧"共用同一个 SDRAM 仲裁器
（`framebuf_arbiter`，读优先 + 写饥饿 256 拍抢占）。这个争用**只在装载时存在**，
**而所有仿真里的读通路都是模型化空转或没有写竞争**——所以任何"装载期间读写并发"导致的缺陷，
现有仿真都**抓不到**（W5 是这一类的一个已排除实例，B5 是仍成立的另一个）。这是比"连续装载没覆盖"更本质的缺口：
**读写并发从未被真实压测过**。

这让 §6 的优先级更清楚：**先做零成本的 LED2 判决（§4.5.4），再按 §4.5.3 的 R1/R2/R3 分支**；
仿真只能作为回归护栏，**不能用来证明这条缺陷不存在**（P6 上板证伪就是活例子）。

> 原因：`wr_fire` 要求 `st == A_WR`，而状态机只有 `A_IDLE` 能切 `A_WR`（`framebuf_arbiter.v:136-151`），

**依据见 §4.4 证据 1~4。**

**补丁 A：给写组首补上组首间隔保护（照抄读侧现成机制）**

```verilog
// framebuf_arbiter.v
parameter WR_GROUP_CYCLES = 13,      // 新增，与 RD_GROUP_CYCLES 同值起步
reg [7:0] wr_group_wait;
wire wr_grp_start = wr_fire && !wr_grp_active;   // 本组首拍

always @(posedge clk or negedge rst_n) begin
    if (!rst_n) wr_group_wait <= 8'd0;
    else if (wr_grp_start) wr_group_wait <= WR_GROUP_CYCLES - 1;
    else if (wr_group_wait != 8'd0) wr_group_wait <= wr_group_wait - 8'd1;
end

// wr_new_allowed 追加条件
assign wr_new_allowed = wr_req && (wr_group_wait == 8'd0) &&
                        (!rd_req || wr_starved || rd_fault);
```

> 注意计的是**组首**（`wr_grp_start`），不是 `wr_ack`——`wr_ack` 每拍都给，
> 若用它装载，计数器会被本组自己的 4 拍不断重置，等于没有保护。

**补丁 B：让写能填进读组后的 9 拍空档（否则补丁 A 会让写更慢）**

```verilog
// 读"这个周期真能开组"的条件（与 rd_new_allowed 同源，但不含 wr_starved）
wire rd_would_start = rd_req && !rd_rst_pend && !rd_restart &&
                      (rd_outstanding <= 27) && (rd_group_wait == 0);

// 原：(!rd_req || wr_starved || rd_fault)
// 新：(!rd_would_start || wr_starved || rd_fault)
assign wr_new_allowed = wr_req && (wr_group_wait == 8'd0) &&
                        (!rd_would_start || wr_starved || rd_fault);
```

**为什么两个必须一起做：**

| 只做 A | 只做 B | A + B（推荐） |
|---|---|---|
| 写组首被拉到 ≥13 拍，但仍被 `rd_req` 挡在 9 拍空档外 → 写只能继续靠饿 256 拍抢占，**装载显著变慢** | 写能背靠背塞满 9 拍空档（组首间隔只剩 4 拍）→ **可能正好踩中核的组首要求**，等于换一种方式踩坑 | 读组 4 拍 + 写组 4 拍 + 空 5 拍 = 13 拍稳态；读组首间隔仍 ≥13 拍、写组首间隔 ≥13 拍，**两个约束同时满足** |

**稳态时序（40 MHz，13 拍一轮）：**

```
t=0..3   读组 4 拍
t=4..12  rd_group_wait 递减，其中 t=6..9 插入一个写组（组首距上一个写组 ≥13 拍）
t=13     下一读组 —— 读组首间隔正好 13 拍，与 RD_GROUP_CYCLES 一致
```

**代价评估（按 40 MHz 重算，此前误用了 150 MHz）：**

| 量 | 计算 | 值 |
|---|---|---|
| 一帧组数 | 153600 字 ÷ 4 | 38400 组 |
| 若组首间隔从"随机"变 ≥13 拍 | 38400 × 13 / 40 MHz | **12.5 ms** |
| 相对装载总时长 | 12.5 ms / (0.6~2 s) | **< 2%** |
| 读写稳态占用 | (4+4)/13 | 61%（读 31% + 写 31%） |

**结论：不影响切图速度，且读带宽一点不降**（读组首间隔本来就必须 13 拍，插入写组不占读的份额）。

**反向验证实测（2026-10-31 20:00，这是本次最硬的一条证据）**
