## 1. 一句话结论

**屏幕确实在显示 IMG001，但「深色内容」没有正确显示出来。**

具体地说：白边、中央白框的位置都对，但

- 图片的深蓝底（`RGB888(24,24,48)`）没有呈现为深蓝，而是呈现为「暗底 + 窄亮条」的周期性条纹；
- 中央白框内部的黑色数字笔画看不到，白框是一片纯白。

换句话说，**亮的内容在、暗的内容丢**。这不是「没出图」，也不是「整屏乱码」，
而是「画面结构正确、暗部信息缺失」这一类缺陷。

## 4. 显示通路的 RTL 事实（已逐行核实）

### 4.1 最终画面的三选一（`rtl/top/dmz_eg4s20_hdmi_top.v`）

```verilog
234: wire [23:0] image888 = {image565[15:11],image565[15:13],image565[10:5],
236:                         image565[10:9], image565[4:0],image565[4:2]};
237: wire [23:0] video_base = !de ? 24'd0 : ((mode==2) ? 24'hFF0000 :
238:     ((image_ready && image_pixel_valid) ? image888 : {pr,pg,pb}));
```

**这是全案最关键的一行**：只要 `image_pixel_valid` 为 0，
该像素就**不是**图片，而是测试图案的颜色 `{pr,pg,pb}`。
所以「图片与测试图交替」在结构上是**天然可能**的，不需要任何新 bug。

### 4.2 `image_pixel_valid` 由谁产生（`rtl/storage/pix_reader.v`）

```verilog
116: assign take_even = display_enable && de && !pix_count[0];   // 两像素只出队一次
117: assign fifo_rd_en = !fifo_rd_empty && ((state == P_DRAIN) || take_even);
122: assign pix_valid = de && display_enable &&
123:     (pix_count[0] ? word_valid : !fifo_rd_empty);            // 缺字时不谎报有效
124: assign pix_rgb565 = !pix_valid ? 16'd0 :
125:     (pix_count[0] ? word_hold[31:16] : fifo_rd_data[15:0]);
```

- 偶像素（`pix_count` 偶）取 `fifo_rd_data[15:0]`，**要求 FIFO 非空**；
- 奇像素取 `word_hold[31:16]`，**要求 `word_valid`**；
- 任一侧不满足 → `pix_valid=0` → 顶层回退到测试图案；
- **一次 FIFO 欠载至少让 even + odd 两个像素同时失效**（`word_valid` 要到下一个 `take_even` 才更新）。

### 4.3 像素域与 SDRAM 域的水位（同文件）

- `LEVEL_HI=384`、`LEVEL_LIMIT = 384-8 = 376`、`FIFO_AW=9`（512 深）
- 读带宽：SDRAM 40 MHz × 4 B = 160 MB/s = 40 M 字/s
- 消费带宽：像素 25 MHz ÷ 2 像素/字 = 12.5 M 字/s
- **理论上 3.2 倍余量，稳态不该欠载**——除非仲裁器把读组长时间挤掉。

### 4.4 每帧都重新对齐（同文件）

```verilog
141: always @(*) begin
144:   P_WAIT:   if (blank) next_state = P_QUIET;
145:   P_QUIET:  if ((arm_count >= ARM_QUIET_C) && idle_sync) next_state = P_DRAIN;
147:   P_DRAIN:  if ((arm_count >= ARM_SETTLE_C) && fifo_rd_empty && idle_sync) next_state = P_RESTART;
149:   P_RESTART:if (done_sync != restart_seen) next_state = P_READY;
150:   P_READY:  if (blank_prev && !blank) next_state = P_RUN;
151:   P_RUN:    if (blank) next_state = P_QUIET;     // ← 每帧消隐期都回到 P_QUIET
```

→ 相位错位**不会**跨帧累积，每帧都会重新对齐。所以「条纹固定在同一批列上」**不能**用「相位漂移」解释。

### 4.5 测试图案定义（`rtl/video/test_pattern_gen.v:171-227`）

| `pattern_sel` | 图案 | 关键色 |
|---|---|---|
| 0 | 8 色彩条（每带 80 px） | 白/黄/青/绿/品红/红/蓝/黑 |
| 1 | **64×64 网格** | 黑底 + 纯白线（`active_x[5:0]==0 \|\| active_y[5:0]==0`） |
| 2/3/4 | 横向渐变 | `rgb_r = {active_x[10:3]}`（只到 0~79） |
| 5 | 纯色 | `user_color`，顶层接 `24'd0` → 纯黑 |
| 6 | 移动方块 | 绿 `(00,FF,00)` / 深蓝 `(00,00,20)` |
| 7 | 16×16 棋盘 | `active_x[4] ^ active_y[4]` → 白 |

### 4.6 数码管显示什么（`rtl/top/dmz_eg4s20_hdmi_top.v:515-523`）

```verilog
seg_decoder u_dec0 (.bin_data({1'b0,pattern_sel}), ...)   // dig0 = pattern_sel
seg_decoder u_dec1 (... loader_index[3:0] ...)            // dig1 = 图片序号
seg_decoder u_dec2 (... error_value ...)                  // dig2 = 错误码
seg_decoder u_dec3 (... state_value ...)                  // dig3 = 播放状态
```

→ **最左边一位就是当前测试图案编号**。这是零成本的现场观测点。

## 5. 假设清单（按可能性排序，每条都给出判别方法）

### H1 · 相机摩尔纹（可能性最高，且意味着「可能没有 bug」）

显示器把 640×480 拉伸到物理分辨率后，像素栅格与相机传感器栅格拍频，
在**中等亮度的均匀区域**产生周期性亮暗条纹；纯白区因为饱和而不显，
纯黑区因为对比度不足也不显。**这正好解释「只在深蓝底上看到条纹」**。

- 支持：条纹周期随水平位置单调变化（透视），占空比约 19%，亮条永远达不到纯白；
- 支持：直方图里没有任何像素 < 47，说明照片已经整体压缩，拍频可见是合理的；
- **判别**：让屏幕显示一块**纯色**（`pattern_sel=5`，顶层 `user_color=0` → 纯黑），
  若条纹**仍然存在** → 摩尔纹；若**消失** → 是数据问题。

### H2 · `image_pixel_valid` 周期性为 0，图片与测试图案交替

机制见 4.1 / 4.2。若 FIFO 每 20 个字欠载一次（= 40 像素周期），
就会得到「每 40 像素里有一小段显示测试图案」的效果。

- 支持：周期 40 px 与实测的「约 40 RTL 像素」量级一致；
- 反证：4.3 的带宽核算有 3.2 倍余量，稳态不该欠载；
- 反证：4.4 说明每帧重新对齐，无法解释「固定列位置」；
- **判别**：按 KEY4/KEY5 把 `pattern_sel` 切到 0（彩条）。
  若深蓝底上的条纹**变成彩色** → 确实是回退到测试图案（H2 成立）；
  若条纹**不变** → H2 排除。

### H3 · 帧缓冲写入地址错位（`pixel_x/pixel_y` 与实际像素序不符）

`rtl/storage/image_player.v:232` 的写地址是
`word_addr = pixel_y * WORDS_LINE + (pixel_x >> 1) + back_off`，
其中 `pixel_x/pixel_y` 由 `bmp_parser` 输出（`bmp_parser.v:380,389`）。
若行填充（BMP 每行补齐到 4 字节）没有正确跳过，或 `top_down` 翻转方向判断错，
就会把像素写到错误地址 → **部分区域正确、部分区域保留上一帧或上电随机值**。

- 支持：能解释「白框位置对但框内数字丢失」——数字笔画那几列可能被写到了别处；
- 反证：若地址整体错位，白框位置也应该错；
- **判别**：换一张**全屏纯色**（例如整幅 `RGB(200,40,40)`）的 BMP 显示。
  若整屏均匀 → 地址无误，H3 排除；若出现分块/条纹 → H3 成立。

### H4 · SDRAM 读数据在 40 MHz 下偶发错误

读路径 slack 只有 **+1.935 ns**（全设计最小，见 `reports/timing_40mhz_20261027/run.ts`），
板级温度/电压漂移可能导致偶发采样错误。

- 反证：时序已收敛，且错误若随机就不会形成稳定周期条纹；
- **判别**：同一张图连续观察 10 分钟，条纹是否**位置稳定**。
  稳定 → 排除 H4；缓慢漂移/闪动 → H4 可疑。

### H5 · RGB565 深色量化误差被误读为缺陷

`RGB888(24,24,48)` → RGB565 `0x0B06` → 经 `image888` 位复制扩展回
**`(24,24,49)`**。数值上是对的，但深色的 5/6/5 量化只有 32/64/32 级，
在低亮度区间色阶极粗，配合显示器 gamma 会把深蓝显示得偏灰。

- 说明：**这只能解释「颜色不准」，解释不了「周期性条纹」**；
- 但它提醒：**不要拿「深蓝看起来不对」当缺陷证据**。

## 6. 最短判别路径（建议按顺序做，总计约 3 分钟）

| 步 | 动作 | 观察 | 结论 |
|---|---|---|---|
| 1 | 读数码管**最左一位** | 是 `1` 还是 `0` | `1` = 当前测试图案是 64px 网格；`0` = 彩条 |
| 2 | 按 **KEY4 或 KEY5** 把图案切到 `0`（彩条） | 深蓝底区域变成彩色条纹？ | **变彩色 → H2 成立**（回退到测试图案）<br>**不变 → H2 排除** |
| 3 | 再按到 `5`（纯黑） | 条纹是否还在 | **还在 → H1 摩尔纹**（无 bug）<br>**没了 → 是数据问题** |
| 4 | 换成一张全屏纯色 BMP | 是否整屏均匀 | 不均匀 → H3（地址错位） |

第 3 步是**性价比最高的一步**：纯色图案下若仍有条纹，那就不可能是 FPGA 数据问题。

## 7. 本次排查踩过的坑（下一位接手者请务必先读）

1. **透视裁剪用错了坐标，导致「白边全丢」的假结论。**
   曾用 `topY=378 / botY=1487 / leftX=205 / rightX=2155` 做校正，
   但 `screen_now.png` 的高度只有 **1215**，`1487` 必然越界；
   脚本 `measure_now.ps1:33` 因此抛了几百次
   `Parameter must be positive and < Height. Parameter name: y`。
   这组边界来自**另一张更大的照片**，与当前图无关。
   → **教训：任何写死坐标的测量脚本，第一步必须先打印图片尺寸并断言边界合法。**

2. **显示器是斜拍的，任何「线性映射」都不可靠。**
   曾假设屏幕上下边界是水平线，实测上边界从 `y=394`（左）变到 `y=369`（右）、
   下边界从 `1553` 变到 `1398`——**倾斜 150 像素**。
   用矩形裁剪必然错位，用四点单应性又因为四角取到了屏幕外的黑边而失败。
   → **教训：要定量比较，先拍正视图；斜拍照片只适合看「有没有」「大致在哪」。**

3. **块平均能压掉摩尔纹，但也会把窄条纹平均成中灰。**
   `r = 0.2791`（块平均）与 `r = 0.2588`（逐像素）都低得没有判别力，
   原因不是「画面不对」，而是**几何没对齐 + 条纹被平均**。
   → **教训：相关系数在这种场景下没有诊断价值，不要用它下结论。**

4. **`New-Object 'double[,]'` 二维数组不能作为 PowerShell 函数参数。**
   会报 `Unable to cast object of type 'System.Double[,]' to type 'System.Double[]'`，
   随后刷屏 200 KB 错误并超时。
   → **教训：统计计算全部内联在同一脚本块，不要定义带数组参数的函数。**

5. **`"x=$minX..$maxX"` 在 PowerShell 双引号里会被当成属性访问 `$minX.`**，
   输出变成 `x=..1980`（minX 打印为空）。
   → **教训：字符串里拼数值用 `-f` 格式串。**

6. **本会话模型无视觉能力**，`read_image` 会被系统过滤。
   → **教训：任何「我看图觉得……」的表述都是幻觉，必须换成像素统计。**

## 10. 若确认为 H2/H3，修复方向（按改动量从小到大）

1. **加观测点**：把 `reader_status`（`{armed, overflow_sync, underflow_lat}`）挪到 LED 上，
   或临时把 `underflow_lat` 接到某个空闲 LED——一次上板就能确认有没有欠载。
   `underflow_lat` 目前**置位后只有复位能清**（`pix_reader.v:190,204`），
   非常适合当「曾经欠载过」的指示。
2. **抬高水位**：`image_player.v:318` 现在是
   `.FIFO_AW(9), .LEVEL_HI(384)`；SDRAM 侧 512 深只用了 384。
   可试 `.FIFO_AW(10), .LEVEL_HI(768)`（与 `pix_reader` 默认值一致），
   把抗突发能力翻倍。
3. **降低读侧竞争**：`framebuf_arbiter` 的 `WR_STARVE_LIMIT = 256`、
   `BUS_TURN_GAP = 2`；图片装载完成后写侧本应空闲，
   若仍在抢占，说明 `writes_complete`/`write_settle` 逻辑有问题，需单独查。
4. **核对写地址**：在 `image_player.v:232` 附近加断言或仿真检查，
   确认 `pixel_x` 覆盖 0..639 且 `pixel_y` 覆盖 0..479、每个值恰好出现一次。

## 11. 给下一位接手者的三条建议

1. **先做第 6 节的 4 步判别，再改代码。** 目前所有假设都还没有被证伪，
   直接改 RTL 很可能白改一轮（本会话已经因为测量错误自我推翻过三次）。
2. **优先补「可观测性」而不是「猜逻辑」。** 板上有 8 个 LED、4 位数码管，
   `reader_status` / `underflow_lat` / `arb_error` 都是现成的信号，
   接出来一个就能把 5 个假设砍到 2 个。
3. **要定量结论就拍正视图。** 斜拍 + 无视觉能力 = 只能得到「有没有」，
   得不到「偏了多少」。
