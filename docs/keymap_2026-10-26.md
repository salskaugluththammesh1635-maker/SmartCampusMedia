## 三、八个新键的设计

### 3.1 KEY7 亮度（`bright_sel[2:0]`，5 档循环）

**为什么是"右移减法"而不是乘法**：FPGA 里 `x*7/8` 会推一个乘法器，而 `x - (x>>3)` 只要一个移位加一个减法，
且结果**逐位可预测**，便于在 testbench 里写死期望值做断言。

| 档位 | 表达式 | 等效比例 | 255 → | 128 → | 64 → |
|---|---|---|---|---|---|
| 0 | `x` | 100% | 255 | 128 | 64 |
| 1 | `x - (x>>3)` | 87.5% | 224 | 112 | 56 |
| 2 | `x - (x>>2)` | 75% | 192 | 96 | 48 |
| 3 | `x - (x>>2) - (x>>3)` | 62.5% | 161 | 80 | 40 |
| 4 | `x >> 1` | 50% | 127 | 64 | 32 |

> 档 1、3 的除法余数直接截断（255→224 而不是 223.125 四舍五入到 223），
> 因此**低亮度会略微偏亮**，这是刻意选择：截断只会让画面更亮一点，不会更暗。

### 3.2 KEY8 反色（`invert_en`）

`{r,g,b}` 三通道各自按位取反（`~x`，等价 `255-x`）。作用点在亮度之后，所以"最暗 + 反色"= 先把亮度降到 50% 再取反，
得到的是**中灰**而不是暗色。这是有意为之：夜间使用场景要的是"暗色文字在亮底上"，不是"整屏更暗"。

### 3.3 KEY9 轮播倍率（`auto_sw_sel[1:0]`）

**改动难点**：`player_ctrl` 原来的轮播间隔是编译期常量

```verilog
localparam AUTO_TICKS = CLK_FREQ_HZ * AUTO_SW_S;   // 5 秒 = 125,000,000 拍
wire do_switch_frame = auto_play_en && (auto_cnt == AUTO_TICKS - 32'd1);
```

`AUTO_TICKS` 是 `localparam`，改不了。本次新增输入端口 `auto_sw_sel` 和一个组合出的目标值：

```verilog
wire [31:0] auto_target = (auto_sw_sel == 2'd1) ? (AUTO_TICKS << 1) :
                          (auto_sw_sel == 2'd2) ? (AUTO_TICKS + (AUTO_TICKS << 1)) :   // ×3 = T + 2T，避免乘法器
                          (auto_sw_sel == 2'd3) ? (AUTO_TICKS << 2) : AUTO_TICKS;
wire do_switch_frame = auto_play_en && (auto_cnt == auto_target - 32'd1);
```

**默认档 0 下 `auto_target == AUTO_TICKS`，行为与改造前逐拍等价**，这是本次改动的兼容性底线。

**为什么还要一个 `auto_sw_sel_d`（档位上一拍值）**：

```verilog
auto_sw_sel_d <= auto_sw_sel;
if (auto_sw_sel != auto_sw_sel_d) auto_rst_req <= 1'b1;
```

只改阈值不改计数器会出问题：假设当前档位 ×4、计数器已经计到 3 秒，用户按到 ×1（阈值 5 秒）——没毛病；
但反向操作，从 ×1 的 3 秒按到 ×4（阈值 20 秒）也没毛病；**真正的问题是从 ×4 的 15 秒按到 ×1（阈值 5 秒）**，
此时 `auto_cnt (15s) >= 5s` 立刻成立，会当场跳一张，用户感觉"按一下跳了两张"。加 `auto_rst_req` 让改档当拍清零计时器，
从新阈值重新起算，避免这种"按一下连跳"。

**×3 为什么写成 `T + (T<<1)`**：`AUTO_TICKS × 3` 会被综合器识别为乘法，占一个乘法器或大块逻辑；
`T + (T<<1)` 是一个移位加一个加法，资源可忽略。上限 `5s × 4 = 500,000,000 < 2^29`，32 位远够。

### 3.4 KEY10 图库重扫（`rescan_req`，单拍）

**为什么需要它**：`gallery_probe` 的张数扫描是**一次性**的——进 `G_DONE`/`G_FAIL` 后状态自锁，
要重新扫描只能整板复位（`README.md` 原本就写着"插好卡后按复位键重新初始化"）。现场换一张卡按复位键，
会把 HDMI 重新握手、SDRAM 重新初始化、图库重新扫描全做一遍，代价大且屏幕会闪。加一个重扫入口把代价降到最小。

**改动**：`gallery_probe` 新增输入端口 `rescan`，在**唯一的时序 always 块内**加一条前置分支：

```verilog
if (rescan && sd_ok && ((st == G_DONE) || (st == G_FAIL))) begin
    st <= G_ARST;  probe_idx <= 5'd1;  hit_cnt <= 5'd0;  rst_cnt <= 3'd0;
    done <= 1'b0;  fail <= 1'b0;  err_code <= 4'd0;
end else begin
    case (st)  ...  endcase
end
```

三个条件缺一不可：

1. `rescan` —— 收到按键；
2. `sd_ok` —— **SD 链路必须健康**。没插卡时按此键不能有任何反应，否则会从"卡坏了"跳到"扫描中"再到"卡坏了"，
   屏幕和数码管错误码乱闪，比不响应更糟；
3. `st` 必须是终态 `G_DONE`/`G_FAIL` —— **扫描进行中按此键必须被忽略**。若允许中途重扫，就会出现两个扫描序列
   交叠，`probe_idx`、`hit_cnt` 被前一个序列写脏，张数变成随机值。这一条在 `tb_gallery_probe` 的 W09 用例里被显式断言。

重扫完成后会**再发一次 `first_img_req`**（与首次扫描完成后一样），让新卡的图立刻显示出来，不必再按 KEY1。

### 3.5 KEY11 九宫格（`grid_en`）

四条线：`x = 213 / 426`、`y = 160 / 320`，绿色 `24'h00FF00`，**单像素宽**。

**为什么是 213/426 而不是 640/3 ≈ 213.33**：整数运算取 `640/3 = 213`，第二条线取 `2*640/3 = 426`，
两条线分别是 213 和 426，间距 213 与 213，右边到 639 剩 213，**三段等宽**。若用 320（中点）会变成二分不是三分。

**用途**：现场目检画面是否偏移、缩放比例是否对。合成参考线比拿尺子量屏幕可靠，且不依赖任何外部设备。

### 3.6 KEY12 信息条（`info_en`）

底部 `y >= 464` 铺深灰底（`24'h101820`），在 `y ∈ [468, 475]` 这一行画 12 个"格位"，
**每个格子 8 像素宽，其中前 6 像素实心、后 2 像素间隔**（`bd_x[2:0] ∈ {6,7}` 不点亮），颜色青绿 `24'h40E0D0`。

12 个格位的位序（按格序号从左到右）：

| 格 0～4 | 格 5～6 | 格 7～9 | 格 10～11 |
|---|---|---|---|
| 图片索引 `info_index[4:0]` | 模式 `info_mode[1:0]` | 亮度 `bright_sel[2:0]` | 倍率 `info_auto[1:0]` |

**为什么用"格位"而不是字符**：真正的字符 OSD 需要字模 ROM（一张 8×16 的 ASCII 表约 4 KB BRAM）和一行行的
扫描逻辑，而本项目 `rtl/osd/` 至今为空、B1 任务是零起点。用 12 个格子把 12 个二进制位直接显示出来，
**代价只有几十个 LUT、零 BRAM、零时序风险**，而且对调试更直接——看格子的亮灭就知道每个参数当前是什么值，
不用去数数码管的十六进制。

**这条要如实说**：它**不是字幕**，显示不了文字。B1 的"图层叠加与字幕"只完成了"图层叠加"这一半。

### 3.7 KEY13 音频图层循环（`level_en` / `wave_en`）

KEY13 是 4 态循环：关 → 电平条 → 波形 → 电平+波形 → 关。`key_action`
同时输出 `level_en` 与 `wave_en`，`video_overlay` 用这两个电平分别控制右侧
电平条与中部波形。

**电平条**：右侧 `x ∈ [616, 631]`（16 像素宽），从 `y = 380` 向上长，绿色 `24'h20FF20`。

幅度映射：

```verilog
mag_abs  = audio_sample[23] ? (~audio_sample + 24'd1) : audio_sample;  // 取绝对值（补码）
level_h  = mag_abs[20:14];                                             // 7 位 → 0..127
level_top = 10'd380 - {3'b000, level_h};
```

**为什么取 bit[20:14]**：`audio_tone_gen` 输出的三角波经 `>>> 2` 之后幅度约 ±2.1×10⁶（≈2²¹）。
取 bit[20:14] 正好把 0～2²¹⁻¹ 映射到 0～127，满幅时条子占满 128 像素高度，**刚好用满动态范围而不溢出**。

**为什么要取绝对值**：音频是交流信号，正负半周各占一半时间。若不取绝对值，条的左半周会消失（负数被当成 0），
看起来就是"闪一下断一下"。

**波形**：`audio_waveform` 保存 64 点历史，窗口 `x ∈ [64, 575]`，每 8 像素一个样本，
中心线 `y = 200`，黄色 `24'hFFFF40`。当前样本与相邻旧样本之间整段点亮，形成连续线；
左边是较旧样本，右边是最新样本。波形与电平条共用同一份 `audio_sample`，
因此看到的跳动与听到的声音严格同步。

### 3.8 KEY14 蜂鸣器静音（`beep_muted`）

**只掐蜂鸣器，不碰音频**。HDMI 内嵌音频与 3.5 mm 输出归 KEY6 的 `audio_muted` 管，两者互不影响。
这个分工看起来多余，但场景上确实不同：演示时想静音哔哔声但保留背景音乐（按 KEY14），
或者反过来（按 KEY6）。

**实现方式**：`buzzer_tone` 的 `tone_sel` 本来就有 0 = 静音档（`sq_en` 恒 0），
所以顶层只改接法，**没有改动 `buzzer_tone` 一行代码**：

```verilog
.tone_sel(beep_muted ? 3'd0 : (alarm_req ? 3'd3 : (mode == 2 ? 3'd2 : 3'd1)))
```

> 只为加一个开关就去改一个已通过 40+ 条断言的模块端口表，收益为零、回归风险非零。

## 四、为什么单独新建两个模块

### 4.1 `rtl/control/key_action.v`（88 行）

八个新键全部是"开/关某个开关"或"档位加一"这类小事。如果继续堆在顶层：

- 顶层会出现 8 个 `always` 块，每个新键都要改一次顶层；
- 而顶层是 **三个版本共用** 的装配图（`hdmi_top` / `bringup_top` / `min_top`），改它等于同时改三份工程；
- 最要命的是**键号会散落在多个 `always` 块里**——这正是本项目历史上 KEY0/KEY1 双占用事故的成因
  （见 `docs/progress.md`：一次按键同时触发"切图片"和"切图案"）。

收拢到 `key_action` 后，**键位表只存在于一处**（模块内的 8 个 `localparam`），顶层只按功能连线，
键号本身不再出现在顶层代码里。`player_ctrl` 也因此**不认识 KEY9**，它只接收一个叫 `auto_sw_sel` 的档位参数，
从结构上杜绝了"同一个键被两个模块消费"。

### 4.2 `rtl/video/video_overlay.v`（185 行，**纯组合、零寄存器**）

像素后处理天然是组合逻辑：给一个 `(x, y, 输入颜色)`，算出 `(输出颜色)`。
写成纯组合的三个好处：

1. **不引入新时钟域**——不需要跨域同步，不需要考虑复位相位；
2. **不改变像素时序**——没有寄存器就没有延迟，`de`/`active_x`/`active_y` 与输出严格同拍。
   `test_pattern_gen` 的文件头就明确写着"下游不可再寄存，否则图案会向右偏移 1 像素"，这里遵守同一约定；
3. **可被 testbench 用 `#1` 直接打桩**——`tb_video_overlay.v` 没有时钟驱动的激励序列，
   全部是"设坐标 → `#1` → 采样"，64 条断言 268 ns 跑完。

**处理顺序是刻意的：亮度 → 反色 → OSD。** OSD 在最后叠加，因此**不受亮度与反色影响**。
这一条是做人机界面的关键：如果反色开着时信息条也变成反色，现场读数就全靠猜了。
`tb_video_overlay` 的 V10 用例专门用一个"最暗 + 反色"的极端配置断言 OSD 四个元素的颜色一字不变，
同时断言同一时刻的图像层**确实**被调暗又反色（证明前两级没有被跳过）。

## 六、接口与时序假设

1. **`key_event` 是单拍脉冲，`key_code` 在同拍有效**（来自 `key_matrix_4x4`）。`key_action` 与
   `player_ctrl`、顶层 `pattern_sel` 块都按同一时钟域直接采样，**不做跨域同步**——三者都跑 `clk_pixel`（25 MHz）。
2. **`rescan_req` 是单拍脉冲**。`key_action` 在块首无条件清 0、需要时再置 1，因此上层永远看不到持续为高的请求。
   `gallery_probe` 把它当**电平**用（`if (rescan && sd_ok && ...)`），因为前置的 `st` 条件本身已经限定了只有终态才采纳，
   即使脉冲略宽也不会重复触发。
3. **`auto_sw_sel` 是电平**（不是事件）。`player_ctrl` 内部用"档位与上一拍是否相同"检测改档，改档当拍清计时器。
4. **`video_overlay` 零延迟**：`rgb_out` 与 `rgb_in` 同拍，`de=0` 时 `rgb_out` 恒为 `24'd0`（与改造前的顶层写法一致）。
5. **OSD 关闭时输出与输入逐像素相同**：全部控制位为 0 时 `rgb_out === rgb_in`，这条由 `tb_video_overlay` 的 V02 断言。
   **新增功能不能改变"什么都不按"时的默认观感**，这是本次改动的兼容性底线。
6. **`beep_muted` 只影响 `buzzer_tone`**，与 `audio_muted`（KEY6）互不影响，两者静音的对象不同。

## 八、上板时先做这件事：确认键盘行序

`docs/pending_confirmations.md` 记录的两处来源冲突里，键盘行序这一条**直接影响本次全部八个新键**：

- 「走近FPGA」资料给出的行序是 `E10, C10, F9, D9`；
- 底板例程是**反序**。

如果行序反了，`key_code` 的映射会整体错位——按 KEY7 得到 KEY11、按 KEY9 得到 KEY13，八个新键会成对互换。
**上板第一件事不是试新功能，而是先确认哪一行对应 KEY0。**

最省事的确认方法：`dmz_eg4s20_hdmi_top` 的数码管 `dig0` 显示 `pattern_sel`、`dig1` 显示 `loader_index` 低 4 位。
按 KEY4（应为上一测试图），看 `pattern_sel` 是否 −1；按 KEY0（应为上一张），看 `loader_index` 是否 −1。
两者都对，行序即正确。

若确认反序，**唯一需要改的地方是 `key_matrix_4x4` 内的行序映射**——
`key_action` 里 8 个 `localparam` 是按"功能 ↔ 键号"写的，键号语义不变，因此不受影响
（这正是把键号写成 `localparam` 而不是硬编码的原因）。

## 九、遗留问题与下一步

### 遗留问题（按优先级）

1. **八个新键无上板证据**，且键盘行序未确认 → A5 仍是 🔶。
2. **B1 只完成"图层叠加"，没有"字幕"**：信息条是 12 个二进制格位，不是字符。真正的文字字幕需要字模 ROM
   （8×16 ASCII 表约 4 KB）与逐行扫描逻辑，`rtl/osd/` 至今为空。
3. **参数不保存**：亮度/反色/倍率掉电即恢复默认，无 NVM 写入。
4. **`video_overlay` 未综合**，LUT 占用与关键路径未知。
5. **无菜单式 OSD 调节入口**：B3 的"实时参数调节"目前只有键盘直调，没有可导航的菜单。

### 下一步任务（建议顺序）

1. 先解决 P0 的两项：SDRAM 接口时序（补 SDC 的 `set_input_delay`/`set_output_delay`）+ 正式顶层首次上板点亮。
   **在这两项完成之前，继续堆功能只会让首次上板要排查的变量更多。**
2. 上板确认键盘行序（方法见第八节），确认后把 A5 的验证档位从"仿真"提升到"上板"。
3. 若 LUT 超预算，`video_overlay` 的九宫格与电平条可以按"关掉即不综合"的方式加参数裁剪。
4. B1 补齐字符字幕：新增 `rtl/osd/` 下的字模 ROM 与文字扫描器，把信息条的 12 格位图升级为真正的文字。
5. B2 淡入淡出转场（需要双缓冲，当前单缓冲）。

   `project/hdmi_td.al`（否则 TD 判 black box）→ 跑 `sim/scripts/run_frontend_regression.ps1`。
