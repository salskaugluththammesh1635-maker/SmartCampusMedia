| 项 | 值 |

交接文档给的三条假设：A) `img_loader` 卡在 `T_FATLOC`；B) `loader_start` 从未到达；
C) 顶层仲裁第三分支 `sd_owner_gallery ? gallery_start : (sd_owner_player ? player_start : probe_start)`
在 `sd_ok` 瞬时为 0 时把播放器请求静默丢弃。

## 2. 关键推理：`d8` 本身就是证据

`d8` 不是"某个子模块报错"，而是 `image_player` 在 `C_LOAD` 里等不到 `blk_done`
且 loader 既没 done 也没 fail 时的兜底（`image_player.v` 超时段，`error_code = 9`）。
这一点很关键，因为它**排除**了"请求在 `T_FATLOC` 被吞"这一类直觉解释：

- `fat32_reader` 自己带 `BLK_TIMEOUT = 2_097_152` 拍（`fat32_reader.v:90`）的握手超时，
  请求被吞时约 84 ms 就会报 `fat_fail` → `img_loader` 报 `E_FATLOC(1)` → 提示 `F4`；
- `img_loader` 的 `T_FATRD`/`T_DATRD` 也各有 `E_BLKTMO(10)` 看门狗。

**所以 `d8` 只能由"loader 根本没有在跑"产生**：`img_loader` 停在 `T_IDLE`
（start 丢了），或者 `fat32_reader` 压根没被启动。仿真侧的证据也一致：
10-30 的 `tb_display_content` 用真实 `IMG001.BMP`（640×480、921654 字节、226 簇）
跑通了完整帧比对，说明数据通路本身没坏——坏的是**启动握手**。

## 3. 四处修复

### 3.1 复位毛刺：`loader_enable`/`store_enable` 改为寄存器输出

`image_player.v` 原来把 `state` 的组合译码直接当**异步复位**用：

```verilog
wire loader_enable = (state != C_WAIT) && (state != C_RESET);
wire loader_async_pix = rst_n_pix && rst_n_sdr && loader_enable;   // 送进 negedge 复位端
```

`C_START(4'b0011) → C_LOAD(4'b0100)` 要同时翻转 3 位。硅上这三位不同时到，
中间态可能被译码成 `C_WAIT(0000)`/`C_RESET(0001)`，于是 `loader_enable` 出现一个
**低电平毛刺**，把 `img_loader`/`fat32_reader`/`bmp_parser`/`img_scaler`/写 FIFO
一起异步复位——**恰好发生在它们刚锁存完那一拍 start 之后**。结果：loader 回到
`T_IDLE`，之后不再有任何 `blk_start`，`image_player` 只能等 4 s 报 9。

这也解释了三个现象：仿真永远不复现（仿真没有门延迟毛刺）、`d8` 而不是 `dA/F4`
（毛刺把子模块自己的看门狗一起清了）、以及结果与布局相关。

修法（`image_player.v:78-87`）：把使能寄存一拍再做复位源，毛刺不再能穿过触发器。

```verilog
wire loader_enable_d = (state != C_WAIT) && (state != C_RESET);
always @(posedge pix_clk or negedge rst_n_pix)
    if (!rst_n_pix) begin loader_enable <= 1'b0; store_enable <= 1'b0; end
    else begin loader_enable <= loader_enable_d;
               store_enable  <= loader_enable_d || store_keep; end
```

### 3.2 start 未被接收 → 立刻报 `dd`（新增错误码 13）

光修毛刺不够：必须让"start 没被接收"变成**可观测、可区分**的故障，而不是混进
4 s 的 `d8`。`img_loader` 在 `T_IDLE` 收到 start 的那一拍就置 `busy`，之后只会以
`done`/`fail` 收场，所以"进 `C_LOAD` 后连续 16 拍既不 busy 也没 done/fail"
必然是 start 丢了或 loader 被意外复位。

- `image_player.v:107-108`：接出 `loader_busy`、新增 `idle_cnt`；
- `image_player.v:259-260`：命中即 `error_code <= 4'd13` → 提示 **`dd`**；
- `image_player.v:299-301`：只在 `C_LOAD` 内计数，饱和于 15；
- `image_player.v:331`：`img_loader` 例化补上 `.busy(loader_busy)`（原来悬空）。

### 3.3 装载中途 SD 归属被收回 → 退回 `C_WAIT` 保留请求

`C_WAIT` 只在进入时检查 `sd_ready`，进入 `C_RESET..C_LOAD` 后不再复查。若所有权
在这期间被收回（顶层仲裁换了 owner），后续 `blk_start` 会被路由到别的模块，
`image_player` 只能等到超时。现在（`image_player.v:241-245`）四个状态统一复查：

```verilog
C_RESET, C_MEM, C_START, C_LOAD: if (!sd_ready) begin
    pending <= 1'b1;                              // 请求不丢
    if (!load_req) pending_index <= selected_index; // 记住是哪张图
    timer <= 0;
    state <= C_WAIT;                              // 等总线回来从头重装
end else case (state)
```

### 3.4 顶层仲裁：显式 one-hot，取消三元回退

原写法（`dmz_eg4s20_hdmi_top.v:155-158`）用嵌套三元表达式，**第三个分支是隐式
兜底**：`sd_ok` 为 0 时请求会被路由给 `probe_start`，播放器/图库的 `blk_start`
被静默吃掉。改为显式 one-hot 与门或（`dmz_eg4s20_hdmi_top.v:159-167`）：

```verilog
wire sd_owner_probe   = !sd_ok;
wire sd_owner_gallery = sd_ok && !gallery_done && !gallery_fail;
wire sd_owner_player  = sd_ok && (gallery_done || gallery_fail);
wire sd_arb_start = (sd_owner_probe & probe_start)
                  | (sd_owner_gallery & gallery_start)
                  | (sd_owner_player & player_start);
```

现在任何一个 owner 未命中都表现为"没人接收"，由 §3.2/§3.5 的看门狗负责报错，
不再有"看起来发出去了其实没发"的路径。

### 3.5 FAT 定位段补独立看门狗，并把"握手超时"与"定位失败"分开

- `img_loader.v:123-132`：新增 `E_FATLMO = 4'd14`、`FAT_E_BLKTMO = 4'd7`、
  `FATLOC_TIMEOUT = 2×BLK_TIMEOUT`；`T_FATLOC` 从"只等 found/fail"变成带进度看门狗
  （`img_loader.v:311-333`，每收到一个 `blk_done` 就清零）。
- `fat32_reader.v:272-277`：握手超时从 `4'd5`（与"控制器报 blk_err"混用）拆成
  `4'd7`，语义变成"请求没被接收、也没有错误返回"。
- `img_loader.v:323`：`fat_err == FAT_E_BLKTMO ? E_BLKTMO : E_FATLOC`——握手超时报
  **`dA`**，其余定位失败仍是 **`F4`**。

## 4. 新增仿真用例（把"请求被吞"钉成回归）

| 用例 | 场景 | 断言 | 实测 |
| --- | --- | --- | --- |
| `tb_img_loader` T16 | 定位阶段 `blk_start` 被吞（不回 done 也不回 err） | 必须失败且报 10，耗时 ≤ `BLK_TIMEOUT+200` | err=10，20012 拍 |
| `tb_img_loader` T17 | 数据阶段 `blk_start` 被吞 | 同上 | err=10，21034 拍 |
| `tb_img_loader` T18 | 吞请求 **且** `fat32_reader` 卡死（`force` 其计数器） | 必须报 14，耗时 ≤ `2×BLK_TIMEOUT+200` | err=14，40008 拍 |
| `tb_image_player` CASE 13 | 装载中途 `sd_ready=0` | 退回 `C_WAIT`、保留 `pending`、不置 `failed`；恢复后重装成功 | 通过 |
| `tb_image_player` CASE 14 | `force loader_start=0`（start 丢失） | 2 万拍内失败且 `error_code==13`；重试成功 | 通过 |
| `tb_err_prompt` C3/C4 | 新码映射 | `7→dA`、`13→dd`、`14→dE`、`10→dA` | 通过 |

`tb_img_loader` 通过 `TB_BLK_TIMEOUT = 20000`（`tb_img_loader.v:38,107-109`）
把 DUT 的块超时缩短，T16/T17 才能在可接受的仿真时间内跑完；`drop_start`
（`tb_img_loader.v:175,205`）模拟"仲裁吞掉 `blk_start`"。

**关键判据满足交接要求**：被吞的请求现在在 `BLK_TIMEOUT` 量级报错
（20012 / 21034 拍），而不是拖到 4 s 的 `LOAD_TIMEOUT` 报 9；且"块超时（10）"
与"请求未被接收（14）"、"start 丢失（13）"三者码值互不相同。
