# KEY1 切图黑边与延迟：理论分析交接（2026-11-01）

## 交接范围

本文只记录理论分析，不修改 RTL、不重新综合、不生成位流，也不把理论判断写成板上结论。

当前讨论对象是正式顶层 `dmz_eg4s20_hdmi_top`，以及 2026-11-01 生成的 FIFO 背压修复版。该版本已经完成综合、布局布线和 bitgen，但本文写作时没有新的板端波形或目视复测，因此必须把“代码能解释什么”和“现场已经证实什么”分开。

## 先区分“黑边”的四种含义

用户说的“黑边”可能对应三种不同机制。它们的修复方向完全不同，不能只凭颜色判断。

### 1. 固定的四周黑框：可能是有意的 letterbox

`img_scaler` 对非 640×480 图片采用 contain 式缩放并计算居中窗口；顶层 `image_window_mask` 只允许窗口 `{off_x, off_y, out_w, out_h}` 内的像素通过，窗口外的 `pixel_valid` 被拉低，`video_content_mux` 再把无效像素输出为黑色。

因此，如果素材本身不是 640×480，四周出现稳定黑边是设计结果，不是 SDRAM 丢数据。它应满足三个特征：

- 黑边固定在四周，位置不随机；
- 不按键、静止显示时也一直存在；
- 黑边宽度随图片宽高比和缩放比例变化。

对交接记录中使用的 `good\\` 卡（640×480）而言，输出窗口应覆盖整个 640×480 活动区，理论上不应出现固定几何黑边。若现场使用的不是 640×480 素材，需要先按这个条件重新分类。

还有一个只在**跨分辨率切图**时成立的暂态风险：顶层 `image_window_mask` 直接使用
`image_player` 当前 `img_scaler` 的 `out_w/out_h/out_off_*`，而双缓冲的 `front_sel` 要等后台帧完整写入后才在消隐期翻转。新图片的 BMP 头一到，窗口参数可能已经更新，但此时屏幕仍在读旧前台帧；于是旧图会先被新图的窗口裁掉。比如从 640×480 切到 320×240 时，旧图在新图的居中窗口外会暂时被强制成黑色，看起来像黑边或黑框。这个窗口配置与前台帧不是同一提交点的问题，对同分辨率的 `good\\` 素材不触发，但应在混用不同尺寸素材时单独记录。

### 2. 切图期间随机出现的横向黑带：优先怀疑读侧欠载

若现象是“按 KEY1 才出现、位置上中下都可能、随后恢复”，它与固定 letterbox 无关，更符合显示读通路暂时没有稳定像素的机制。

当前读通路的关键关系是：

1. `pix_reader` 从 SDRAM 返回 FIFO 取像素；
2. 偶数像素拍从 FIFO 出队，奇数像素拍使用 `word_hold` 的高半字；
3. FIFO 空或当前字无效时，`pix_valid=0`，`pix_rgb565=0`；
4. `video_content_mux` 在已经有有效图片的情况下，对 `image_pixel_valid=0` 输出黑色。

所以，只要切图时读 FIFO 暂时空、读返回超时、读端重新对齐尚未完成，屏幕就会显示黑色，而不是白色测试图案。这能形成横向黑带或短黑段。

这里有一个必须纠正的容量口径：当前生产实例是

```text
pix_reader #(.FIFO_AW(9), .LEVEL_HI(384))
```

即 FIFO 深度为 2^9 = 512 个 32 位字，约 1024 个像素；预取水位为 384 字，约 768 个像素，约 1.2 行，而不是旧交接文档中写的 1024 字、约 3.2 行。旧文档的容量论证不能继续作为“读侧余量足够”的证据；当前读侧在装载写入并发期间更容易受到 SDRAM 仲裁、刷新和换向影响。

此外，`framebuf_arbiter` 的 `RD_TIMEOUT=1024` 是 SDRAM 时钟域计数。按工程当前 40 MHz SDRAM 时钟计算，1024 拍约为 25.6 µs，正好接近 640 像素一行在 25 MHz 像素时钟下的时间。因此，读侧一次无回包超时在尺度上足以解释“一条横向黑带”。

但要保留一个重要限制：`rd_fault` 在仲裁器内是粘滞故障，`restart_apply` 又要求 `!rd_fault`。因此不能简单说“超时后一定自动重启，黑带只出现一行然后恢复”。一次真实的 `rd_fault` 可能导致后续读重启被抑制，最终表现为持续黑、错误状态或下一次复位才恢复。这个分支必须靠波形或板上状态确认，不能仅凭代码注释下结论。

### 3. 整屏均匀变黑：可能只是转场淡出

当前 `image_player` 默认 `FADE_EN=1`、`FADE_FRAMES=8`。新图写入完成后，状态机不是立刻翻转前台帧，而是：

```text
旧图逐帧淡出到黑
→ 全黑消隐点翻转 front_sel
→ 新图逐帧淡入
```

亮度系数只在垂直消隐上更新，因此正确的淡出应是整幅画面均匀变暗，不应是某一条固定边或某一条随机横带。若现场看到的是整屏同步变暗，属于转场观感；若只有一条带或局部线段，则不能用淡出来解释。

## 为什么 2026-11-01 修复后仍可能有黑带

本次修复主要作用在**图片写入端**：

- `async_fifo` 增加 `wr_almost_full`；
- `img_loader` 在扇区边界预留 FIFO 空间；
- `image_player` 用真实 `wr_ack` 计数；
- SDRAM 读写换向默认改为 `BUS_TURN_GAP=3`。

它解决的是“写 FIFO 在一个 512B 扇区中途溢出、像素字静默丢失、后台帧无法完整提交”这一条链路。真实核回归已证明这条链路的 `produced/consumed/written` 可以完整闭合。

它没有直接证明以下事项：

1. SDRAM 读侧不会在切图并发期间欠载；
2. `RD_TIMEOUT` 不会触发；
3. `rd_fault` 不会阻止后续读重启；
4. 每个 `pix_valid=1` 的周期都对应正确稳定的 FIFO 数据；
5. 物理 SDRAM 在所有刷新/换向边界都实际落盘；
6. 现场使用的素材一定是 640×480、不会触发有意的 letterbox。

因此，新的写侧修复通过仿真和真实核回归，并不等价于“所有黑带已经被理论上排除”。如果板上黑带仍然出现，优先级最高的剩余方向是读侧欠载/读重启/真实 SDRAM 边界行为，而不是再次调 `WR_GROUP_CYCLES`。

## 为什么按下 KEY1 后不是立刻换图

这里要区分“按键事件被接受”和“屏幕内容完成切换”。前者很快，后者故意较慢。

### 按键识别本身只有几十毫秒

正式顶层以 25 MHz 实例化 `key_matrix_4x4`，参数为 `DEBOUNCE_MS=20`：

- 每 1 ms 扫描一行；
- 4 行轮询一次，所以同一按键每约 4 ms 采样一次；
- `DB_MAX=(20+3)/4=5`，但代码在计数达到 5 的那一拍只把计数器加到 5，下一次不一致采样才翻转稳定状态，因此实际需要连续 6 次不一致采样；
- 按下沿确认后产生一个时钟周期的 `key_event`。

因此，从第一次有效采样到 `KEY1` 事件约为 20 ms；考虑按下时刻到该按键所在行下一次被扫描的等待，物理按下到事件的理论范围约为 20~24 ms，另有两个同步触发器以及 `key_event`、`img_switch_req` 的几个 25 MHz 周期。它不会解释约 2 s 的屏幕延迟。

`player_ctrl` 收到 `key_event && key_code==1` 后，在一个像素时钟沿更新 `img_index` 并发出单拍 `img_switch_req`。也就是说，逻辑上的“请求下一张”是即时登记的。

如果当前已经在装载上一张图，新的按键不会打断当前 SD→SDRAM 事务；`image_player` 只保存待处理索引（连续按键时保留最后一次请求），等当前后台帧完成或失败后再处理。因此快速连按时，用户看到的响应可能比单次按键更晚，也不保证每一个中间图号都短暂显示。

### 屏幕延迟来自双缓冲和完整装载

`image_player` 的设计是双缓冲：

```text
KEY1 事件
→ 记录新的 image_index
→ 等 SD 总线归播放器所有
→ 从 SD 读取 BMP/FAT 数据
→ 解析像素、可选缩放
→ 写满后台 SDRAM 帧
→ 等 writes_complete
→ 等垂直消隐
→ 翻转 front_sel
→ 淡出/淡入完成
```

在后台帧完成前，前台旧图必须继续显示，否则会把“半张新图”送到屏幕上。`C_COMMIT` 只有在真实写计数达到期望字数后才允许进入提交；提交又通过 `commit_pending` 等待垂直消隐。因此屏幕不在 KEY1 的那一拍切换，是双缓冲一致性要求，不是按键失灵。

### 转场还会额外增加约 0.28~0.29 秒

`FADE_FRAMES=8`，显示刷新约 59.5 Hz：

- 淡出约 8 帧；
- 全黑消隐点翻帧；
- 淡入约 8 帧。

合计约 17 帧，理论上约 286 ms。这个时间是确定的设计开销，但只占观测到的约 2 s 的一小部分。不能把全部 2 s 都归咎于淡入淡出，也不建议只调小 `FADE_FRAMES` 来掩盖装载路径问题。

## 约 2 s 的剩余差额如何理解

以 921,654 B、约 1801 个 512B 扇区的 IMG001 为例，12.5 MHz SPI 的 512B 数据体理论上约 328 µs/扇区；加命令、令牌、CRC、FAT 簇链和握手，理想装载量级约 0.6~0.8 s，再加约 0.286 s 转场，通常应低于 1 s。

现场旧位流记录的是“每次约 2 s”。现有代码和报告没有记录以下实际量，所以多出的约 1.1 s 仍不能定论：

- SD 卡每个 CMD17 的真实响应与字节间空隙；
- FAT 定位和簇链遍历的实际次数；
- `img_loader` 因 FIFO 预留而等待的总时间；
- `sd_ready` 是否曾下跳并让 `image_player` 回到 `C_WAIT` 重装；
- SDRAM 写完成等待和读写换向停顿；
- 现场是否把“按键确认到新图完全稳定”的时间包含了整段淡入。

所以当前最稳妥的理论结论是：

> 约 20~24 ms 来自按键扫描/消抖；约 0.6~0.8 s 来自 SD/FAT/BMP/后台帧装载的理想量级；约 0.286 s 来自转场；剩余约 1.1 s 尚无测量证据，不能直接归咎于按键、淡出或某一个状态。

## 当前假设排序

| 优先级 | 假设 | 能解释的现场特征 | 当前证据状态 |
|---|---|---|---|
| 1 | 读 FIFO 欠载、读超时或读重启未完成 | 切图期间随机横向黑带；静止时不出现 | 代码尺度吻合，但未有板上波形闭环 |
| 2 | 跨分辨率切图时窗口配置先于前台帧提交 | 切图期间暂态黑框/黑边，随后新图稳定 | 由当前连线可推出；仅对不同尺寸素材成立，未做板上复测 |
| 3 | 实际素材触发 letterbox | 固定四周黑框、静止时也存在 | 对非 640×480 成立；对 640×480 不成立 |
| 4 | 转场淡出到黑 | 整屏均匀变暗约 0.286 s | 设计上确定；不能解释局部黑边 |
| 5 | 写入仍有个别错误/物理落盘边界问题 | 白线、局部坏字，可能伴随黑段 | 新写 FIFO 修复已降低概率，但未做实板回读 |
| 6 | SD 卡吞吐或 `sd_ready` 重入造成长延迟 | 每次切图耗时稳定偏长 | 只有时间目测，没有总线测量 |

## 交接给下一位执行者

本轮不改代码。下一次现场或波形采集应先记录：

1. 黑色区域是四周固定边、整屏变暗，还是随机横向黑带；
2. 黑色区域是否只在切图时出现，静止显示是否消失；
3. 黑带出现时 LED2 是否亮。当前 LED2 汇总 `reader_status[1:0]`，可指示读侧溢出/欠载粘滞状态；
4. 黑带出现后 `rd_fault` 是否置位，以及是否一直保持；
5. `front_sel`、`commit_pending`、`pix_reader.state`、`pix_reader.pix_valid` 和 FIFO 空标志的时序；
6. 一次 CMD17 从发命令到扇区结束的真实时间，以及整个装载期间 `sd_ready` 是否下跳；
7. 明确当前板上烧录的位流文件和素材分辨率；
8. 若使用不同尺寸素材，专门做 640×480→320×240→640×480 切换，记录黑边是否只在后台装载期间出现，以验证窗口配置与前台帧不同步候选。

在这些信息补齐前，不能把“黑边”统一归因于写 FIFO，也不能把“约 2 s”统一归因于按键消抖或淡入淡出。
